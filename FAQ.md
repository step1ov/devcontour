# FAQ: DevContour для первого проекта

Здесь «целевой проект» — ваш будущий сервис, сайт, приложение или библиотека. DevContour — инструмент, который помогает агентам разрабатывать этот проект. Ответы описывают возможности текущей реализации; проект продолжает развиваться.

## Зачем нужен DevContour?

Чтобы поручать AI-агентам разработку продукта и сохранять понятный порядок работы: что нужно сделать, почему выбрана такая архитектура, какие задачи зависят друг от друга и чем подтверждён результат.

Обычно при работе через чат человек сам напоминает требования, переносит контекст между агентами, просит запустить тесты и проверяет, не потерялась ли часть задачи. DevContour хранит состояние этой работы и проверяет условия перехода к следующему шагу. В панели видно, что выполняется, что завершено и почему работа остановилась.

## Как DevContour работает в двух словах?

**Идея → согласованный план → задачи агентам → проверки → проверенный общий результат.**

Ведущий агент помогает сформулировать продукт и организовать разработку. DevContour запускает подготовленные задачи, учитывает зависимости, собирает результаты и допускает их принятие только после нужных проверок. Claude Code и Codex выполняют интеллектуальную часть: предлагают решения, пишут код и проводят ревью.

## Чем он поможет при вайбкодинге сервиса?

Допустим, вы хотите сервис записи на консультации. Агент поможет уточнить сценарии клиента и консультанта, правила расписания, отмены и оплаты. Затем превратит это в согласованную структуру продукта и небольшие проверяемые задачи.

При разработке календаря, API и уведомлений DevContour будет учитывать связи между задачами и общие договорённости. Изменение не считается готовым только потому, что агент так написал: нужны проверки кода, независимое ревью и проверка после объединения изменений.

Это уменьшает объём ручного сопровождения. Однако качество постановки и тестов по-прежнему важно: инструмент не может сам определить, что удобный для пользователя продукт получился, если это нигде не описано и не проверено.

## Нужно ли заранее писать подробное ТЗ?

Можно начать с идеи или черновика. Полезно объяснить, для кого продукт, какую проблему он решает, какие сценарии обязательны и какие есть ограничения. Ведущий агент должен помочь превратить это в понятную постановку, а не требовать от вас готовой технической архитектуры.

До разработки постановку нужно уточнить и утвердить. Для важных сценариев нужны проверяемые признаки готовности: например, «занятое время нельзя забронировать повторно», а не просто «удобный календарь».

## Что остаётся за человеком?

Вы определяете смысл продукта, приоритеты и ограничения. В текущем процессе вы также утверждаете в панели последовательные версии:

1. Продуктовую постановку: пользователи, сценарии, границы и критерии результата.
2. Архитектуру и стек. Агент готовит объяснение и схемы C1/C2: связи продукта с внешним миром и его основные части.
3. Референсы, а для продукта с интерфейсом — затем концепт и дизайн-систему. Если интерфейс не затрагивается, отдельно утверждается неприменимость дизайна.

Только после этой цепочки начинается настройка проекта и разработка. Готовить технические варианты, настраивать инструменты, формировать задачи и проверки должен агент.

По умолчанию технические планы и контракты проходят агентское согласование с независимым ревью. Режим `approvalMode: operator` добавляет ручные технические согласования. Режим `agent` не отменяет обязательные продуктовые решения пользователя. Внешняя публикация результата также остаётся отдельным действием человека.

## Что нужно для первого запуска?

Нужны установленный DevContour, Git и Node.js 24.3 или новее. Для настоящей разработки нужны установленные и авторизованные Claude Code и Codex CLI: текущая схема независимого ревью использует разные программы для исполнения и проверки. Также понадобятся инструменты выбранного стека — их состав и настройку готовит агент.

Ведущий агент должен получить инструкции DevContour: через подключённый skill либо через `START.md` установленного инструмента. Ему нужно передать идею или ТЗ, режим размещения и абсолютный путь рабочего пространства.

Например:

> Хочу создать сервис записи на консультации. Используй DevContour. Размещение — embedded, workspace — /absolute/booking-service. Сначала открой панель, помоги уточнить продукт и проведи обязательные согласования. Затем самостоятельно подготовь проект, задачи и проверки.

Путь в примере нужно заменить своим. Само появление ТЗ в папке ничего не запускает. Для знакомства с панелью есть demo: он работает без вызовов моделей и не показывает качество реальной AI-разработки.

## Что такое workspace и какой режим выбрать?

Workspace — место, где DevContour координирует работу над вашим продуктом.

| Режим      | Где находится workspace                | Для чего подходит                                                                       |
| ---------- | -------------------------------------- | --------------------------------------------------------------------------------------- |
| `embedded` | В корне Git-репозитория самого проекта | Один репозиторий, в том числе монорепозиторий с несколькими компонентами                |
| `separate` | В отдельной папке координации          | Несколько самостоятельных репозиториев: например, сервис, приложение и общая библиотека |

При первом запуске режим и абсолютный путь выбираете вы. Сохранённый выбор используется дальше без повторных вопросов. Каталог установки DevContour не должен становиться хранилищем задач вашего продукта.

Одна установка инструмента может обслуживать несколько независимых workspace. У каждого будут свои данные и сервер; одновременно работающим серверам нужны разные порты.

## Какие агенты DevContour добавляет в проект?

DevContour добавляет **инструкции ролей** и настраивает, каким исполнителям поручать задачи. Наличие файла роли не означает, что в проекте постоянно работают отдельный бот или отдельная модель.

В стандартном шаблоне есть инструкции для следующих ролей:

| Роль        | За что отвечает                                              |
| ----------- | ------------------------------------------------------------ |
| `architect` | Архитектурные решения и договорённости между частями системы |
| `backend`   | Серверная часть и API                                        |
| `frontend`  | Веб-интерфейс                                                |
| `qa`        | Тесты и проверка поведения                                   |
| `mobile`    | Мобильное приложение                                         |
| `qa-mobile` | Проверка мобильного приложения                               |

При обычной настройке без специального набора ролей используются первые четыре. Профиль проекта может задать другой набор: например, мобильный профиль объявляет `mobile` и `qa-mobile`. Не все скопированные инструкции обязательно будут задействованы.

Есть ещё **ведущий агент** — ваш основной собеседник, который организует работу, — и **независимый ревьюер**, который проверяет результат. Ревьюер назначается настройкой и не обязан быть отдельной ролью в списке задач.

## Можно ли расширить список агентов?

Да. Можно добавить, например, роль инженера инфраструктуры или специалиста по данным. Ведущий агент должен описать её обязанности, подключить инструкции и объявить роль в конфигурации или профиле проекта.

Для роли задаются программа-исполнитель, при необходимости модель, доступные инструменты, область изменения файлов и ревьюер. Затем роль можно назначать задачам. Одного нового Markdown-файла недостаточно: конфигурация должна действительно использовать его.

Добавление роли не требует нового AI-провайдера. Подключение другой программы-исполнителя, кроме поддерживаемых Claude Code и Codex, уже требует разработки соответствующего адаптера DevContour.

## Какие модели используются и где это фиксируется?

У DevContour нет одной обязательной модели для всей разработки. Нужно различать **роль**, **программу** и **модель**. Например: роль — бэкенд-разработчик, программа — Claude Code, модель — выбранная в её настройках модель.

По умолчанию стандартная настройка назначает исполнителям Claude Code, а ревьюеру — Codex. Профили и настройки компонентов могут менять эти назначения. В реальном режиме независимое ревью требует другую программу: Claude Code проверяет Codex или наоборот. Две разные модели внутри одной программы это условие не заменяют.

| Что настраивается                         | Где смотреть                                                                    |
| ----------------------------------------- | ------------------------------------------------------------------------------- |
| Общие исполнители и ревьюер workspace     | Рабочая конфигурация `.devcontour-local/config.json`, поля `roles` и `reviewer` |
| Переопределения для отдельного компонента | `roles` и `reviewer` в `devcontour.component.json`                              |
| Конкретная модель                         | Поле `model` в настройках исполнителя или ревьюера                              |
| Чем выполнялась конкретная попытка        | Запись запуска и доступная статистика вызовов в локальном состоянии DevContour  |
| Модель вашего ведущего агента в чате      | Настройки AI-клиента, в котором вы с ним общаетесь                              |

Если `model` не задано, DevContour не передаёт явный выбор модели в CLI: используется выбор самой программы. Для воспроизводимой работы лучше закрепить модель явно. DevContour сохраняет настройки попытки и, когда исполнитель сообщает эти сведения, фактическую модель и данные вызова. Неизвестные сведения нельзя считать подтверждёнными.

Модель ведущего агента не становится автоматически моделью всех исполнителей. И установка DevContour сама по себе не предоставляет доступ к платным моделям.

## Для чего нужен CLI DevContour?

CLI — это программа `devcontour`, которой управляют из терминала. Через неё запускают панель и исполнение, настраивают workspace, управляют задачами, проверяют состояние, синхронизируют память и получают диагностику.

Большинство рабочих команд может выполнять ведущий агент. Вам не обязательно запоминать их все: полезнее понимать, что происходит, и уметь прочитать состояние в панели.

В установленном пакете команда выглядит как `devcontour ...`. В руководствах для работы из исходников встречается эквивалентная форма `npm run devcontour -- ...`. Команды работы с продуктом должны явно указывать его `--workspace` либо существующий каталог данных через `--data`.

## Для чего нужен skill DevContour?

Skill — инструкция для ведущего агента о том, **как пользоваться DevContour**: в каком порядке готовить продукт, какие операции вызывать, как оформлять задачи и как разбирать остановки.

Сам skill не запускает сервер, не хранит состояние задач и не заменяет CLI. Агент читает инструкцию и использует доступные инструменты, а DevContour проверяет допустимость операций.

Skill поставляется вместе с инструментом. Команда `devcontour skill-path` показывает его расположение. Подключение к конкретному AI-клиенту выполняется отдельно по правилам этого клиента: DevContour не изменяет его глобальные настройки автоматически.

## Какие скиллы и инструкции передаются в целевой проект?

При настройке копируются общие правила `AGENTS.md` и `CLAUDE.md`, файлы ролей в `.agents/roles/` и инженерные инструкции в `.agents/context/`.

Базовые темы инструкций — порядок работы, ревью, контракты, дизайн и тестирование. Профиль стека может добавить материалы по дизайн-системе, технике тестирования или мобильным проверкам. Конфигурация определяет, какие из этих материалов получит конкретный исполнитель.

Это не означает автоматическую установку набора именованных skills в меню вашего AI-клиента. В частности, `setup` не подключает skill DevContour в клиентские каталоги `.claude/skills` или `.agents/skills`. Инструкции проекта и skill для управления инструментом решают разные задачи.

## Что ещё DevContour создаёт в целевом проекте?

Он готовит основу для организованной работы, а затем агенты наполняют её содержанием конкретного продукта.

| Файлы и каталоги                     | Для чего нужны                                                                      |
| ------------------------------------ | ----------------------------------------------------------------------------------- |
| `AGENTS.md`, `CLAUDE.md`, `.agents/` | Правила работы и инструкции исполнителей                                            |
| `contracts/`                         | Договорённости об API, данных и взаимодействии компонентов                          |
| `design/`                            | Материалы и правила интерфейса                                                      |
| `memory/`                            | Долговременные знания, решения и передача контекста                                 |
| `docs/devcontour-*.md`               | Копии выбранных руководств по работе с инструментом                                 |
| `devcontour.component.json`          | Настройки компонента: проверки, роли, окружение и другие правила                    |
| `.devcontour/`                       | Переносимые записи задач и командной памяти, когда они создаются и синхронизируются |
| `.devcontour-local/`                 | Локальные настройки, базы, запуски, рабочие копии и артефакты                       |

Для workspace также сохраняется выбранный режим размещения. Конкретное расположение общих и компонентных записей зависит от режима.

Настройка не создаёт готовый сервис одним копированием шаблона. Установку зависимостей, прикладной код, реальные тесты и наполнение документации должен подготовить агент.

## Можно ли подключить уже существующий проект?

Да, но ведущий агент сначала должен изучить его структуру, команды и принятые соглашения. Уже работающие правила проекта нужно согласовать с процессом DevContour.

При копировании стартовых файлов `setup` сохраняет существующие файлы. Например, готовый `AGENTS.md` не будет автоматически заменён новой версией. Поэтому успешное копирование ещё не означает, что все инструкции, проверки и исключения Git согласованы: агент должен проверить их содержимое.

Это относится и к обновлению DevContour. Новая версия инструмента не означает, что её шаблоны немедленно появились во всех подключённых проектах. Изменения правил переносит ведущий агент с учётом особенностей продукта.

## Что такое профиль проекта и можно ли выбрать свой стек?

Профиль — стартовый набор настроек для определённого стека: команды сборки и тестов, инженерные инструкции, а иногда и специальные роли.

Есть готовые профили для React/Vite, Next.js, Go, Python, NestJS и React Native/Expo. Можно описать собственный профиль внутри проекта или расширить существующий. Название профиля не гарантирует, что все зависимости уже установлены и проверки подходят вашему приложению: агент должен довести окружение до рабочего состояния.

Выбирать и объяснять стек, а затем настраивать профиль должен ведущий агент. Пользователь утверждает архитектурное решение, а не собирает вручную техническую конфигурацию.

## Как устроена оркестрация?

Оркестрация — это управление порядком и условиями работы нескольких исполнителей. У неё две части: ведущий агент готовит содержательный план, а контроллер DevContour исполняет подготовленный процесс по правилам.

В плане у задач есть зависимости. Например, интерфейс, использующий новый API, должен учитывать готовность API и согласованный контракт. Независимые задачи можно выполнять параллельно в пределах настроенного лимита.

Для попыток создаются отдельные Git worktree — рабочие папки с изолированными изменениями. Затем DevContour проверяет результат, организует независимое ревью, объединяет код и снова проверяет его уже вместе с принятой версией проекта. Права и инструменты исполнителей также ограничиваются конфигурацией исполнения.

В текущей версии один контроллер исполняет работу на одном компьютере. Командная синхронизация через Git не превращает несколько компьютеров в единый распределённый планировщик.

## Зачем независимое ревью, если тесты уже зелёные?

Тест может успешно проходить и при этом не проверять нужное поведение. Ревьюер должен сопоставить постановку, изменение кода и проверки: выполнена ли задача, соблюдены ли договорённости, нет ли очевидных пробелов.

DevContour требует проверки отдельного результата и результата после интеграции. Подтверждения привязаны к конкретному коммиту — версии кода с идентификатором SHA. Проверка старой версии не подтверждает произвольные последующие изменения.

Это создаёт несколько уровней контроля, но не гарантирует отсутствие ошибок. Содержательные требования, подходящие тесты и качественное ревью остаются необходимыми.

## Как понять, что проверена конкретная функция, а не просто запущены тесты?

В задаче можно связать критерий приёмки с разделом требований, командой проверки и конкретным тестовым сценарием. Для точной связи используется `testId` — идентификатор теста в отчёте JUnit.

Тогда одного зелёного запуска всей команды недостаточно: нужный тест должен действительно присутствовать в отчёте и успешно выполниться на проверяемой версии кода. Пропущенный или отсутствующий тест не подтверждает критерий.

Такую связь готовит агент. Старые задачи без неё не становятся автоматически столь же подробными после обновления инструмента. И даже правильно найденный тест нужно оценить по смыслу: действительно ли он проверяет пользовательский сценарий.

## Как организована память проекта?

Память состоит из нескольких частей, которые служат разным целям.

| Часть                            | Что хранит                                                                                    | Как передаётся коллегам                            |
| -------------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `docs/`, `contracts/`, `memory/` | Требования, договорённости, решения с объяснениями, выводы и заметки для продолжения работы   | Обычными Git-коммитами                             |
| `.devcontour/`                   | Переносимые задачи, доски, подтверждения результатов и другие структурированные записи памяти | Через Git; для состояния задач используется `sync` |
| `.devcontour-local/`             | Локальные базы, попытки исполнения, подробные логи, рабочие копии и настройки                 | Не передаётся обычной Git-синхронизацией           |

Кроме обычных документов есть механизм сохранения отдельных знаний со ссылкой на источник: фактов, решений, опыта, гипотез и сводок. Ведущий агент должен сформулировать и сохранить полезное знание. Весь разговор автоматически в такую память не превращается.

Перед выполнением задачи подбираются относящиеся к ней актуальные знания. Исполнитель и ревьюеры получают закреплённый для попытки набор. Устаревшие, спорные записи и гипотезы по умолчанию не выдаются как обычная рабочая память.

Критически важные требования нужно оформлять в постановке, контрактах и обязательных правилах. Нельзя рассчитывать, что вспомогательный поиск по памяти обязательно найдёт нужную фразу из старого обсуждения.

## Что произойдёт, если закрыть чат или сменить ведущего агента?

Закрытие чата само по себе не останавливает работающий сервер. Уже зарегистрированный и подготовленный процесс может продолжаться, пока работают компьютер, DevContour и необходимые инструменты.

Новый ведущий агент может прочитать состояние, правила, решения и записи о том, где остановилась работа. Для передачи контекста полезны handoff — заметка для следующего исполнителя — и checkpoint, то есть краткая сохранённая точка продолжения.

Это не перенос полного разговора и не обещание автоматически решить любую новую проблему. Для нового планирования, изменения продукта и разбора не предусмотренных процессом сбоев нужен ведущий агент. Копирование репозитория на другой компьютер также не переносит работающие процессы.

## Как ведётся журнал работ?

DevContour сохраняет события и состояние запусков в локальной базе SQLite. По ним можно проследить задачи, попытки, ошибки, проверки и принятые результаты. Для вызовов моделей собирается доступная статистика; отдельные логи и артефакты остаются в локальном хранилище.

Есть и автоматически формируемые Markdown-журналы:

| Журнал                                                                 | Где находится                                                                |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Работа над компонентом: задачи, попытки, модели, проверки и SHA        | `.devcontour-local/journal/activity.md` компонента при компонентном хранении |
| Общее изменение нескольких задач или компонентов, называемое ChangeSet | В режиме `embedded` — `.devcontour-local/journal/CHG-*.md` workspace         |
| Такой же журнал ChangeSet при отдельном workspace                      | В режиме `separate` — `docs/journal/CHG-*.md` workspace                      |

Эти файлы — представление состояния базы. Ручное редактирование не меняет историю в DevContour и будет заменено при следующем формировании журнала. После устранения файловой ошибки журналы можно пересоздать командой `journal`.

Объяснения «почему выбрали это решение», важные выводы и заметки для коллег следует сохранять отдельно в документации и `memory/`. Автоматический журнал не заменяет такую содержательную историю проекта.

## Как работать командой?

У каждого участника — собственная копия Git-репозитория и локальное состояние DevContour. Команда использует одинаковые идентификаторы компонентов, но локальные пути могут различаться. Каждому участнику задаётся свой идентификатор, например `alice` или `bob`.

Задачи назначаются участникам. Claude Code и Codex одного разработчика работают в рамках его назначения: идентификатор участника обозначает человека или его рабочую среду, а не название модели.

Обмен выглядит так:

1. Завершить активную работу и остановить сервер и другие процессы, меняющие состояние.
2. Выполнить `sync`, чтобы согласовать локальную базу и переносимые записи задач.
3. Передать изменения обычным процессом команды: Git-коммиты, получение изменений, ревью и объединение веток.
4. После получения изменений снова выполнить `sync`, разобрать возможные конфликты и только затем продолжить исполнение.

Сама команда `sync` не делает commit, push, pull или merge. Она отвечает за согласование данных DevContour с файлами, которые команда передаёт через Git. Подробная последовательность приведена в [руководстве по командной работе](docs/team-sync.md).

## Будет ли у команды единый журнал всех действий?

Команда может видеть общую историю кода, задач, договорённостей и подтверждений результатов, переданную через Git. Однако полного общего журнала всех локальных процессов и диалогов в реальном времени в текущей версии нет.

Подробные логи попыток, локальная база и рабочие папки остаются на компьютере того, кто выполнял работу. Даже доступный для коммита журнал ChangeSet в отдельном workspace не заменяет эти данные. Поэтому полезный итог этапа агент должен оформить в переносимой памяти: что сделано, какое решение принято и что нужно следующему участнику.

Импортированное подтверждение результата означает, что DevContour принял сведения о проверке из доверенной Git-истории. Это не означает, что ваш компьютер заново выполнил чужие тесты. Совместную версию компонентов на новом контроллере нужно проверять отдельно.

## Как избежать конфликтов и двойной работы в команде?

Согласовывать ответственных за задачи, регулярно обмениваться изменениями и не начинать работу по заведомо устаревшему состоянию. В командном режиме локальная очередь учитывает назначение задач.

DevContour проверяет согласованность импортируемых записей и зависимостей, но не имеет общей мгновенной блокировки на все компьютеры. Если две машины долго работают без обмена изменениями, организационный конфликт всё ещё возможен.

Не нужно класть SQLite в Git или запускать два независимых контроллера над одной локальной базой. Для передачи работы используйте переносимые записи и обычный процесс командного ревью.

## Можно ли продолжать разработку без исходников самого DevContour? Всё ли копируется в продукт?

**Без исходного репозитория DevContour — да. Но сам исполняемый инструмент целиком в продукт не копируется.**

DevContour можно установить из собранного npm-архива `.tgz`. В пакет входят CLI, сервер, готовый интерфейс, шаблоны, профили, skill и документация. Для его запуска не нужен checkout исходников DevContour и инструменты его разработки. Сейчас установка описана через подготовленный архив, а не через опубликованный пакет в публичном npm registry.

В целевом проекте остаются собственный код, правила и память. Для продолжения оркестрации нужна установленная рабочая версия DevContour, программы-исполнители и локальная конфигурация проекта.

Если вы пока запускаете инструмент прямо из его исходного каталога, перед удалением этого каталога нужно установить собранный пакет и обновить пути запуска и подключения skill. Одна папка `.agents/` исполняемый инструмент не заменяет.

## Можно ли продолжить разработку вообще без DevContour?

Да. Продукт остаётся обычным проектом со своим стеком и Git-историей. Его можно развивать вручную или с AI-агентом, используя сохранённые требования, решения и правила. DevContour не становится обязательной библиотекой, без которой не может работать ваш сервис.

Однако изменения, сделанные вне его процесса, не получают автоматически историю проверок и приёмку DevContour. Если позднее вернуться к оркестрации, ведущему агенту нужно сверить фактический код с состоянием задач и заново подтвердить затронутые результаты.

## Достаточно ли клонировать Git-репозиторий на новый компьютер?

Этого достаточно для получения закоммиченного кода и переносимой памяти. Для продолжения работы через DevContour нужно также установить инструмент и AI-программы, настроить окружение, локальные пути и синхронизацию.

В клоне не будет прежних подробных логов, локальной базы исполнения, действующих процессов и секретов. Если нужна именно резервная копия операционной истории, её делают отдельно при остановленном сервере. Восстановление такой копии отличается от обычного Git-clone и требует проверки конфигурации и путей.

Для командной работы полезно согласовать версию DevContour. Участники не должны одновременно обслуживать одну базу разными версиями инструмента.

## Что делать, если агент застрял или проверка не проходит?

Сначала посмотреть причину в панели и журнале: не прошёл тест, отсутствует инструмент, нет доступа к провайдеру, требуется решение пользователя или исчерпан лимит попыток.

В подготовленном процессе предусмотрены ограниченные попытки исправления. Они не должны превращаться в бесконечное повторение одной ошибки. Когда автоматическое восстановление невозможно, ведущий агент разбирает причину, исправляет окружение или постановку и готовит продолжение.

Недоступный обязательный тест нельзя просто пропустить и объявить результат готовым. Если нужна полная остановка для обновления, синхронизации или резервной копии, одной паузы очереди недостаточно: нужно завершить активные операции и остановить сервер и остальные записывающие процессы.

## Можно ли менять требования по ходу разработки?

Да. Изменения оформляются новой версией постановки или корректировкой, чтобы было видно, что именно поменялось и какие результаты нужно перепроверить.

Принятый результат относится к определённым требованиям и версии кода. Он не становится подтверждением новых требований автоматически. Существенные продуктовые изменения возвращаются на соответствующее согласование, а ведущий агент обновляет задачи и зависимости.

## Когда сервис можно считать готовым? DevContour сам его публикует?

Завершение одной задачи означает, что пройдены условия её приёмки. Готовность всего сервиса требует выполнения продуктовых критериев и совместной проверки нужной комбинации компонентов.

Публикация в удалённый Git, объединение PR/MR и развёртывание сервиса — отдельные действия. В текущем процессе внешнюю публикацию выполняет человек; DevContour может подготовить передачу результата и проверить предусмотренные условия доставки, включая удалённые проверки.

Проверенный результат можно попробовать локально: DevContour собирает его в Docker и запускает по постоянному адресу, подтверждая, что по адресу работает именно проверенная версия. Это preview на вашем компьютере, а не публикация для пользователей. [Как устроен preview](docs/preview.md).

Поэтому статус готовности локальной разработки не следует понимать как «сервис уже развёрнут и доступен пользователям».

## DevContour контролирует расходы на модели?

Он собирает доступные сведения о вызовах, времени, токенах и стоимости, когда их сообщает исполнитель или позволяет оценить явно настроенная таблица тарифов. Неполные данные не означают нулевой расход, а расчётная стоимость может отличаться от реального счёта по подписке.

Можно ограничивать параллельность, время попытки и количество повторов. Но общего жёсткого денежного лимита для всех используемых провайдеров сейчас нет. Такие ограничения нужно учитывать и в настройках самих провайдеров.

## Для чего нужен MCP и обязателен ли он?

MCP — дополнительный способ дать ведущему агенту доступ к операциям DevContour как к структурированным инструментам. Вместо сборки терминальной команды агент вызывает операцию с именованными параметрами.

MCP необязателен: есть CLI и HTTP API. Основные правила задач и приёмки у этих способов доступа общие. Само подключение MCP не запускает сервер исполнения и не означает, что очередь уже работает.

## Какие данные следует хранить в Git, а какие — отдельно?

В Git полезно хранить код, согласованные требования, правила, контракты и предназначенную для команды переносимую память. Каталог `.devcontour/` служит именно для переносимых записей; `.devcontour-local/` должен оставаться локальным и игнорироваться Git.

Секреты, учётные данные и локальные исполняемые настройки нельзя переносить вместе с обычной командной памятью. Чувствительные исследования, аудиты и сведения о других проектах следует хранить в предназначенном для них игнорируемом каталоге, например `.private/`, согласно правилам проекта.

Ссылки из публичной документации на такие материалы тоже могут раскрывать сведения о них. Для публичных примеров используйте вымышленные названия и пути. Добавление файла в `.gitignore` не удаляет его из уже опубликованной Git-истории.
