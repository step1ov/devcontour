# AI-native запуск продукта

В установленном npm-пакете вызывай `devcontour ...`: готовые CLI, сервер и UI уже собраны. Примеры `npm run devcontour -- ...` ниже предназначены для исходного checkout; при работе с архивом замени этот префикс на `devcontour`, а `npm ci/build` самого инструмента не выполняй. `devcontour capabilities` показывает текущие схемы agent API; `devcontour skill-path` — переносимый skill.

Это инструкция ведущему агенту, которому поручено реализовать ТЗ с помощью DevContour. Здесь описаны его действия; доменные проверки исполняет сам инструмент. Оператор кладёт ТЗ в `docs/spec.md` продукта и даёт одно стартовое поручение. Дальше ведущий агент готовит окружение и ведёт разработку до проверенного результата.

## 0. Обязательно выбрать workspace с пользователем

В новой продуктовой сессии сначала проверь, указан ли пользователем абсолютный путь workspace. Если пути нет, задай один явный вопрос и дождись ответа:

> В какой папке вести workspace этого проекта? Укажите абсолютный путь, например `/absolute/product-workspace`.

Не начинай setup, не создавай задачи и не запускай сервер, пока путь не определён. Не используй cwd, последнюю demo-базу или путь другого проекта как догадку. Если пользователь уже передал путь в текущем поручении или ты продолжаешь ту же сессию с установленным workspace, повторять вопрос не нужно. Выбор workspace обязателен и при `approvalMode: "agent"`; это выбор проекта, а не согласование инженерного этапа.

Workspace должен быть отдельным каталогом вне devcontour и репозиториев компонентов. После ответа проверь существующее содержимое: при продолжении используй прежнюю конфигурацию и БД; новую папку создай по указанному пути. Сохраняй требования, прогресс, proposals и служебные файлы ведущего агента в этом workspace. Продуктовое ТЗ и необходимые исполнителям контракты также должны быть доступны в репозиториях/карточках задач.

Каждая команда принимает `--workspace /absolute/workspace` и использует `<workspace>/.harness/local`. Для старых или нестандартных папок данных можно явно передать `--data`; эти два флага нельзя смешивать. CLI не задаёт интерактивный вопрос сам: он останавливает команду без выбранного контекста. Вопрос задаёшь ты в диалоге. Demo запускается только явной командой `demo`.

Одна сессия ведущего агента отвечает за один workspace. В общем каталоге инструмента нет глобального active-workspace: несколько агентов могут параллельно работать с разными workspace. Перед запуском выбери свободный порт админки, проверь `/api/state` (dataRoot и config.workspaceRoot), сохрани URL, путь данных и ID сессии сервера в `<workspace>/docs/harness-progress.md`. Занятый чужим workspace порт не освобождай принудительно — выбери другой. Зависимости и сборку общего инструмента подготовь один раз; не выполняй конкурентные npm ci/build и не обновляй общий runtime во время работ других проектов.

Если продукты используют одну изменяемую библиотеку, объедини их под одним workspace и ведущим агентом; параллельность обеспечивают его workers. Не подключай библиотеку к двум независимым БД. Отдельные workspace не делят лимиты: учитывай общую нагрузку и лимиты провайдеров при выборе concurrency.

## Существующий проект: обязательная подготовка агентом

Прочитай [интеграционный процесс](docs/project-integration.md). Изучи существующие правила, API, scripts, package manager, исходные проверки и приватные зависимости. Старый оркестратор используй как донор знаний; его очередь не запускай. Library-specific правила, роли, задачи и журнал оставь в библиотеке; общие контракты и координацию веди в workspace. Для прежней общей БД используй storage-migrate после остановки сервера.

Настрой harness.component.json, toolProfiles, environment, dependency snapshots и lifecycle по реальному стеку. Выполни doctor, затем doctor --probe с настроенными read-only/installation probes. Недоступные проверки обозначай явно. Не выдумывай готовый доступ к MCP по факту его наличия у ведущего агента. Проведи небольшой сквозной пилот прежде, чем запускать большой backlog.

Forge-neutral публикация ручная: DevContour готовит handoff, человек делает push/PR/MR/merge. GitLab/GitHub адаптеры читают состояние; MCP GitLab сохраняет read-only права. При completionMode=remote после публикации выполни remote-check; до подтверждения merge/CI не принимай ChangeSet. Не запрашивай write-токен и не расширяй права MCP ради завершения задачи.

## Режим согласования

`approvalMode: "agent"` — значение по умолчанию. Ведущий агент принимает обычные технические решения, готовит проект, проводит архитектуру/контракты и план через независимое ревью, запускает работу, разбирает сбои и принимает проверенные доски. Не останавливайся на каждом этапе ради подтверждения оператора.

`approvalMode: "operator"` — оператор хочет подтверждать архитектуру, контракты, план и итоговую приёмку. Готовь конкретные результаты для согласования. Не изменяй этот режим на `agent` без поручения оператора. Команды `review-contract`, `review-plan` и `accept` вернут `awaiting-operator` вместо автоматического утверждения. В интерфейсе доступны ручные действия.

Переключение режима не отменяет тесты, независимое ревью кода, ограничения защищённых файлов и проверку Git-интеграции. Прямое редактирование SQLite и подделка отчётов запрещены. Продолжительность попыток, число повторов и параллелизм ограничены конфигурацией; общего денежного лимита провайдеров пока нет.

## Если продукт зависит от ваших библиотек

Используй [workspace-процесс](docs/workspaces.md). Прочитай его до bootstrap: единая папка управления вне репозиториев, реестр компонентов, локальные базы задач в самих компонентах, одна БД координации, один сервер и общий DAG. Профили и правила выбирай для каждого компонента. Не запускай отдельную очередь DevContour в общей библиотеке.

После подготовки Git и настоящих локальных тестов создай `workspace.json` и выполни `workspace-init --file <absolute/workspace.json>`. Используй возвращённый `data` во всех командах. Для каждой задачи укажи `repositoryId`; при необходимости добавь зависимость от задачи другого компонента. Документы требований и progress ведущего агента веди в workspace, контракт и память конкретной библиотеки — в её репозитории. Reviewer должен получить релевантные выдержки требований и контрактов: одного пути к внешнему документу может быть недостаточно при ограниченных правах CLI.

Настрой `workspaceGates`, использующие компоненты из `HARNESS_COMPONENTS_JSON`. Подготовь и проверь скрипт реальной сборки/подключения библиотеки и сценариев продукта, защити его в `protectedPaths`. Для каждого зарегистрированного продукта обязателен собственный интеграционный test gate с JUnit. Не ослабляй проверки, чтобы скрыть несовместимость. Подробности о manifests, артефактах и среде команд — в workspace-документе.

Создай ChangeSet (`changeset-create`) из досок одного результата. После локальных задач и приёмки досок запусти `workspace-verify`, затем `changeset-accept --author-runtime codex|claude`. При `agent` пройди приёмку сам, при `operator` дождись подтверждения. Не объявляй продукт готовым только потому, что локальные задачи done. Проверь автоматический `docs/journal/CHG-*.md`; ошибки проекции устраняй командой `journal`. Для принятого результата создавай новый ChangeSet с `supersedes`; историю не переписывай.

Сервер по-прежнему запускаешь ты. Одна активная сессия ведущего агента отвечает за следующий этап, исправления, обновление конфигурации и общий результат.

## 1. Прочитать ТЗ и зафиксировать исходную точку

Определи каталог инструмента и отдельный каталог продукта. Не создавай продукт поверх исходников harness. Если ТЗ положили в `docs` самого инструмента, перенеси его копию в `docs/spec.md` отдельного продукта в согласованной рабочей области. Сохрани исходник.

Прочитай все относящиеся к задаче документы, существующие AGENTS.md и код. Не меняй пользовательские незакоммиченные изменения. Для существующего проекта выбери безопасную исходную Git-точку; если её нельзя определить без риска потери работы, это основание для вопроса.

Создай `<workspace>/docs/requirements.md`: требования с устойчивыми IDs, этапы, границы результата, соответствующие задачи и проверки. Сохрани `<workspace>/docs/harness-progress.md` с текущим этапом, состоянием, следующими действиями, путём данных DevContour и IDs досок. Это контекст для возобновления, а не источник статусов done.

Выбирай разумные обратимые решения самостоятельно и записывай предположения. Обращайся к оператору, только если неоднозначность меняет продуктовую цель, доступы недоступны, нужен выход за заданные ограничения или действие выходит за порученный scope. В режиме `operator` дополнительно соблюдай этапные подтверждения.

## 2. Выбрать стек и подготовить проект

Обоснуй стек требованиями, существующим кодом и целями продукта. Выбери основной профиль из `react-vite-admin`, `next-product`, `go-api`, `mobile-maestro`; для нескольких компонентов настрой общие команды проверок из корня репозитория. Профиль не является генератором приложения.

Если оператор включил согласования, сначала представь ему архитектурное решение и дождись ответа. В обычном режиме продолжай самостоятельно.

Установи зависимости DevContour (`npm ci`, `npm run build`), если они ещё не подготовлены. Выполни из каталога инструмента, подставив выбранный профиль:

```sh
npm run devcontour -- setup \
  --repository /absolute/path/to/product \
  --profile react-vite-admin \
  --workspace /absolute/path/to/product-workspace
```

Для режима подтверждений добавь `--approval-mode operator`. ТЗ по умолчанию — `docs/spec.md`; другое имя внутри `docs` передаётся через `--brief`. Координация — `<workspace>/.harness/local`; локальные задачи и попытки — `<repository>/.harness/local`. Используй --workspace с выбранным путём или абсолютный data из результата во всех следующих командах. Не выполняй затем повторный `init`.

`setup` переносит правила, роли, память, инструкции по дизайну/контрактам, конфигурацию, lock и снимок профиля. Существующие файлы не перезаписывает. Изучи `preserved`, согласуй старые правила с новыми, дополни `.gitignore` для `.harness/`, `.reports/`, зависимостей и секретов. Повторный setup сохраняет прежнюю конфигурацию и режим; он не сбрасывает проект.

Продолжай после `needs-agent-bootstrap`: это промежуточное состояние, не завершение задачи. Создай минимальный каркас приложения, зависимости, команды gates, JUnit reporter и начальные настоящие тесты. Подготовь дизайн через референсы, макет состояний, guidelines и семантические токены. Не заставляй оператора копировать файлы и редактировать config.json.

Проверь CLI исполнителей командой `doctor`; отдельно проверь, что они действительно могут работать в своём окружении. Авторизацию и недоступные учётные данные не выдумывай. Рабочая подписка или лимит должны быть доступны установленному CLI.

Выполни каждый gate с теми же командами и настройками, которые будут использоваться в worktree. Тесты обязаны создавать настоящий JUnit по `HARNESS_REPORT_PATH`; ошибки, пустой отчёт и skips не являются успехом. Сохрани результаты и ограничения в локальном `.private/` выбранного workspace; прежде проверь, что каталог исключён из Git и распространяемых пакетов. Исправляй проблемы, не ослабляя проверки ради зелёного результата.

Для нового продукта инициализируй Git, проверь список файлов и создай исходный локальный commit. Не добавляй секреты, данные DevContour и чужие незакоммиченные файлы. Не делай push или deployment без отдельного поручения. Все нужные агентам ТЗ и правила должны быть закоммичены до появления worktree.

## Инженерный контекст перед запуском очереди

После bootstrap прочитай [инженерные расширения](docs/engineering-context.md). Адаптируй `.agents/roles` и `.agents/context` к проекту; сохрани утверждённые соглашения отдельно от легаси и долгов. Setup создаёт определения context packs. Для workspace нескольких репозиториев добавь определения в workspace.json/config.json с правильными repositoryId; перенеси инструкции выборочно, учитывая существующие правила компонентов.

После исходного коммита выполни `context-lock --workspace <WORKSPACE>`, затем перезапусти сервер. По умолчанию закрепляется HEAD каждого источника; проверь, что это нужная версия. Не запускай очередь с незакреплёнными packs. Библиотечные пакеты контекста добавь нужным задачам через contextPacks; проверяй их командами context-show перед утверждением плана. Мобильным задачам явно подключай mobile-maestro.

Укажи writePaths задач/ролей по фактической структуре проекта, generatedPaths репозиториев и защищённые файлы проверки. Изменения другой области оформляй зависимыми задачами. Задай repository.dependsOn для продуктов/библиотек и gate.dependsOn для codegen → build → consumer tests. verificationMode=all оставь по умолчанию; affected используй только при полном графе потребителей.

Если проверки делят устройство, порт или аккаунт, зарегистрируй resources и укажи их IDs в задачах/gates. Одинаковые kind/value во всех workspace используют один host pool. Запусти окружение, проверь readiness, автоматизируй test-only авторизацию и очистку данных. Не перекладывай это на оператора. При аварии аренды прочитай resources, очисти осиротевшие процессы и только затем выполняй resource-release с cleanup-confirmed.

Разбирай доску «Находки агентов»: воспроизводи, приоритизируй, привязывай контракты/зависимости до утверждения. Находка модели — предложенная задача; она не становится validated-знанием без проверки. Правки инструкций и конфигурации выполняй как ведущий агент при остановленной очереди и отсутствии активных попыток, затем закрепляй новый контекст и перезапускай сервер.

## 3. Провести архитектуру и контракты через независимое ревью

Подготовь JSON-файлы вида `{"title":"API каталога v1","content":"Полное согласуемое содержимое..."}`. Для архитектуры включи выбор стека, ограничения, выполненную bootstrap-проверку и ссылки на артефакты. Для API включи схему, ошибки, auth и совместимость; для UI — референсы, версию макета, состояния и токены.

```sh
npm run devcontour -- review-contract \
  --file /absolute/path/to/product-workspace/docs/proposals/api-v1.json \
  --author-runtime codex \
  --data /absolute/path/to/product-workspace/.harness/local
```

Укажи реальный runtime автора: `codex` или `claude`. Проверяет противоположный runtime. Команда расходует его лимит, сохраняет предложение и ревью в `decisions/`. При отклонении исправь предложение и повтори в пределах рабочего бюджета; не подменяй автора и reviewer.

В режиме `agent` успешно проверенный контракт регистрируется автоматически. Сохрани полученный ID. В режиме `operator` предложи оператору зарегистрировать проверенное содержимое через вкладку «Контракты» и дождись подтверждения. Повтор уже утверждённого идентичного контракта возвращает прежний ID.

## 4. Декомпозировать и утвердить первый этап

Для требований выдели устойчивые `REQ-*` разделы и используй привязки из `requirements-snapshot`: [прослеживаемость](docs/requirements.md). После подготовки графа в agent mode регистрируй `workflow_start` для доски и, при необходимости, ChangeSet, чтобы работающий сервер продолжал этапы без активного чата. [Договор восстановления](docs/lead-workflow.md) описывает ожидания, ошибки и бюджеты. Не регистрируй workflow до завершения настройки окружения и контрактов.

Сформируй `<workspace>/docs/first-slice.md` с первым сквозным пользовательским сценарием и ссылками на полное ТЗ. Не заставляй оператора писать этот файл. Для первого этапа ориентируйся на 5–15 задач; полный объём требований остаётся в дорожной карте.

```sh
npm run devcontour -- plan \
  --brief /absolute/path/to/product-workspace/docs/first-slice.md \
  --runtime codex \
  --data /absolute/path/to/product-workspace/.harness/local
```

Или самостоятельно создай JSON по `packs/example-plan.json` и выполни `import-plan`. Перед повтором проверь `export`: эти команды создают новую доску, а не обновляют существующую. В задачах должны быть IDs требований, наблюдаемые критерии, необходимые тесты, зависимости и ID утверждённых контрактов. Исправляй черновики через `edit-task` или UI. Backend/frontend не утверждаются без контрактов.

```sh
npm run devcontour -- review-plan \
  --board B1 \
  --author-runtime codex \
  --data /absolute/path/to/product-workspace/.harness/local
```

Подставляй IDs из ответа, не считай B1 константой. Независимое ревью проверяет текущую спецификацию; если она изменилась во время проверки, повтори ревью. В режиме `agent` черновики утверждаются автоматически. В режиме `operator` передай оператору план с результатом ревью и дождись ручного утверждения. Утверждение плана не доказывает реализацию требований.

Перед первым запуском сервера закоммить дополнительные документы подготовки, включая first-slice.md и все файлы, на которые ссылаются задачи. После создания интеграционной ветки новые изменения требований и документации проводи через задачи harness: новый commit в основном checkout сам по себе не попадает в harness/accepted. Существенные условия задачи должны быть в её описании и закреплённых контрактах, а не только в незакоммиченном файле.

## 5. Вести выполнение без оператора

Запусти один сервер для очереди и наблюдения:

```sh
npm run devcontour -- serve --data /absolute/path/to/product-workspace/.harness/local --port 4317
```

Сервер — долгоживущий процесс; запускай его в отдельной управляемой сессии. Не запускай второй scheduler через `run` одновременно с сервером. Управляй действующей очередью из другого терминала:

```sh
npm run devcontour -- queue --start --data /absolute/path/to/product-workspace/.harness/local
npm run devcontour -- export --data /absolute/path/to/product-workspace/.harness/local
```

Интерфейс служит оператору для наблюдения; в режиме `agent` клики не требуются. Ведущий агент следит за результатами и продолжает работу. Он не должен завершать свою сессию сразу после постановки задач, если пользователь поручил весь продукт.

Исполнители реализуют задачи в отдельных worktree. DevContour делает коммиты, обязательные gates, независимое ревью, последовательную интеграцию и повторные проверки merge SHA. При сбое прочитай причину и артефакты, устрани проблему и выполни `retry --task <ID> --data <DATA>`. Повтор ограничен `maxAttempts`; увеличение лимита не заменяет разбор причины.

Для паузы выдачи задач используй `queue --pause`. Уже работающие попытки продолжаются. Если нужна смена конфигурации, дождись их окончания и перезапусти сервер. Не ослабляй gates, protectedPaths или критерии для обхода отказа. Не меняй `harness/accepted` вручную во время работы scheduler.

## 6. Принять результат и перейти к следующему этапу

Когда задачи завершены, проверь соответствие требований результату и сохранённым доказательствам. Проверяй приложение на версии из `harness/accepted`, используя detached worktree; основной checkout сам не обновляется.

```sh
npm run devcontour -- accept \
  --board B1 \
  --author-runtime codex \
  --data /absolute/path/to/product-workspace/.harness/local
```

Команда требует `done` и присутствия всех результатов в интеграционной ветке. В режиме `agent` она сохраняет принятую ревизию с автором действия. В режиме `operator` возвращает `awaiting-operator`: человек проверяет продукт и нажимает «Принять доску». Тесты и ревью исполнения обязательны в обоих режимах.

Обнови таблицу требований и progress-документ. Следующий самостоятельный этап — новая доска. Корректировка принятого результата — `correct --board <ID> --roots <ID,ID> --reason <причина> --data <DATA>`, затем редактирование новых черновиков, повторное ревью плана, выполнение и приёмка. Не стирай историю r1.

Продолжай этапы, пока выполнен порученный scope. Если пользователь поручил только MVP, не расширяй задачу до всех будущих возможностей ТЗ. Если поручено всё ТЗ, не выдавай один принятый срез за готовый продукт. Итоговый отчёт должен перечислить реализованные требования, проверки, ограничения и оставшиеся блокеры.

## Возобновление и границы автоматизации

Для командного проекта прочитай [синхронизацию через Git](docs/team-sync.md). Подготовь отдельный Git workspace, исключи `.harness/`, включи `.devcontour/` в версионирование. До планирования выполни `sync --member <ID-разработчика> --workspace <WORKSPACE>`; новые задачи получат локального ответственного. Существующие неназначенные задачи распредели через `assign-task`. Назначение согласуется в общем Git до параллельного исполнения на разных компьютерах.

Перед передачей работы и после получения изменений коллег останови выдачу, дождись активных попыток, выполни `sync-status` и `sync`. Агент разрешает однозначные расхождения и готовит проверенный diff, человек публикует его. Не меняй ветку и не выполняй pull во время активных workers. Не выдавай receipt другого участника за локальный запуск тестов; общий ChangeSet на новой машине проверяется заново. Не копируй SQLite, токены и аренды через Git.

При перезапуске прочитай `<workspace>/docs/harness-progress.md`, конфигурацию и `export`. Состояние SQLite и Git важнее текстовых заметок. Не дублируй доски и контракты. Подготовительные изменения выполняет ведущий агент через свой обычный набор инструментов; `setup` самостоятельно не вызывает модель и не строит приложение.

Этот сценарий требует активной сессии ведущего агента. Файл в `docs` сам по себе не запускает фоновый сервис, а web-сервер выполняет уже утверждённую очередь. Если сессия ведущего агента остановлена, для продолжения планирования и разбора сбоев её нужно возобновить. Это не повод перекладывать ручную настройку на оператора.
