# AI-native запуск продукта

В установленном npm-пакете вызывай `devcontour ...`: готовые CLI, сервер и UI уже собраны. Примеры `npm run devcontour -- ...` ниже предназначены для исходного checkout; при работе с архивом замени этот префикс на `devcontour`, а `npm ci/build` самого инструмента не выполняй. `devcontour capabilities` показывает текущие схемы agent API; `devcontour skill-path` — переносимый skill.

Это инструкция ведущему агенту, которому поручено реализовать ТЗ с помощью DevContour. Здесь описаны его действия; доменные проверки исполняет сам инструмент. Оператор кладёт ТЗ в `docs/spec.md` продукта и даёт одно стартовое поручение. Дальше агент сразу открывает панель, прорабатывает продукт и архитектуру, получает два решения пользователя и ведёт разработку до проверенного результата.

## 0. Выбрать режим размещения и workspace с пользователем

Проверь, указаны ли режим и абсолютный путь. Для продолжения прочитай `devcontour.workspace.json` выбранного workspace и существующую конфигурацию. Если пользователь ещё не выбрал размещение, задай один вопрос и дождись ответа:

> Где хранить оркестрацию: внутри репозитория проекта или в отдельном workspace? Укажите режим и абсолютный путь — корень проекта для первого варианта или отдельную папку для второго.

Предложи два понятных варианта: **внутри репозитория (`embedded`)** для одного проекта/монорепозитория и **отдельный workspace (`separate`)** для самостоятельных репозиториев. Можешь рекомендовать подходящий, но не выбирай его молча. Попроси только недостающие сведения, если часть уже передана. Сохранённый выбор повторно не согласовывай. Подробности: [режимы размещения](docs/workspace-modes.md).

Не начинай setup, задачи или сервер до определения режима и пути. Не используй cwd, последнюю demo-базу или чужую сессию как догадку. Выбор обязателен и при `approvalMode: agent`.

В embedded workspace совпадает с корнем единственного репозитория; приложения и внутренние пакеты остаются каталогами этого Git. В separate workspace находится вне репозиториев компонентов. Оба режима находятся вне установки DevContour. Общая память координации и подробные локальные задачи сохраняют своих логических владельцев; в embedded физически используется одна SQLite внутри проекта. `requirements.source` всегда относится к репозиторию задачи.

Каждая команда принимает `--workspace /absolute/workspace` и использует `<workspace>/.devcontour-local`. Для старых или нестандартных папок данных можно явно передать `--data`; эти два флага нельзя смешивать. CLI не задаёт интерактивный вопрос сам: он останавливает команду без выбранного контекста. Вопрос задаёшь ты в диалоге. Demo запускается только явной командой `demo`.

Одна сессия ведущего агента отвечает за один workspace. В общем каталоге инструмента нет глобального active-workspace: несколько агентов могут параллельно работать с разными workspace. Перед запуском выбери свободный порт админки, проверь `/api/preparation`, а после подключения разработки — `/api/state` (dataRoot и config.workspaceRoot), сохрани URL, путь данных и ID сессии сервера в `<workspace>/docs/devcontour-progress.md`. Занятый чужим workspace порт не освобождай принудительно — выбери другой. Зависимости и сборку общего инструмента подготовь один раз; не выполняй конкурентные npm ci/build и не обновляй общий runtime во время работ других проектов.

Если продукты используют одну изменяемую библиотеку, объедини их под одним workspace и ведущим агентом; параллельность обеспечивают его workers. Не подключай библиотеку к двум независимым БД. Отдельные workspace не делят лимиты: учитывай общую нагрузку и лимиты провайдеров при выборе concurrency.

## 0.1. Сразу запустить панель и пройти продуктовые согласования

До выбора стека, setup и создания технических задач запусти один сервер:

```sh
# Выбран один проект или монорепозиторий:
npm run devcontour -- start --workspace-mode embedded --workspace /absolute/product --port 0
# Либо выбран отдельный workspace:
npm run devcontour -- start --workspace-mode separate --workspace /absolute/workspace --port 0
```

Выполни только команду выбранного режима; при повторном запуске флаг режима можно опустить. Передай пользователю URL и проверь показанные режим и путь. Панель должна оставаться доступной во время обсуждения. Прочитай [продуктовый процесс](docs/staged-workflow.md). Через preparation_create и preparation_product сохраняй промежуточные версии постановки; пользователь видит сценарии, границы, критерии, материалы и вопросы. Когда постановка полна, используй preparation_submit и дождись решения пользователя в панели. Не утверждай её от его имени.

Только после утверждения продукта подготовь architecture/stack, обоснование, альтернативы, C1 и C2 через preparation_architecture. Отправь эту версию на согласование и дождись второго решения пользователя. До него запрещены setup, каркас приложения, код и задачи исполнения. Чтение существующего проекта и изучение ограничений допустимы. Обе паузы обязательны и при approvalMode=agent.

Затем выполняй шаги подготовки ниже. Уже запущенный сервер подхватит конфигурацию на том же URL; второй serve не запускай. При изменении продукта или архитектуры сначала создай новую версию и получи соответствующие согласования. Память подготовки синхронизируется через Git даже до настройки стека; порядок указан в staged-workflow.

## Существующий проект: обязательная подготовка агентом

Прочитай [интеграционный процесс](docs/project-integration.md). Изучи существующие правила, API, scripts, package manager, исходные проверки и приватные зависимости. Старый оркестратор используй как донор знаний; его очередь не запускай. Library-specific правила, роли, задачи и журнал оставь в библиотеке; общие контракты и координацию веди в workspace. Для прежней общей БД в отдельном workspace используй storage-migrate после остановки сервера. Встроенный workspace сохраняет единую БД и не использует эту миграцию.

После двух согласований настрой devcontour.component.json, toolProfiles, environment, dependency snapshots и lifecycle по реальному стеку. Выполни doctor, затем doctor --probe с настроенными read-only/installation probes. Недоступные проверки обозначай явно. Не выдумывай готовый доступ к MCP по факту его наличия у ведущего агента. Проведи небольшой сквозной пилот прежде, чем запускать большой backlog.

Forge-neutral публикация ручная: DevContour готовит handoff, человек делает push/PR/MR/merge. GitLab/GitHub адаптеры читают состояние; MCP GitLab сохраняет read-only права. При completionMode=remote после публикации выполни remote-check; до подтверждения merge/CI не принимай ChangeSet. Не запрашивай write-токен и не расширяй права MCP ради завершения задачи.

## Режим согласования

`approvalMode: "agent"` — значение по умолчанию для технических контрактов, планов и приёмки. Продуктовую постановку и архитектуру со стеком обязательно утверждает пользователь в панели. После этих двух решений агент готовит проект, проводит контракты и план через независимое ревью, запускает работу и принимает проверенные доски.

`approvalMode: "operator"` — оператор дополнительно подтверждает технические контракты, план и итоговую приёмку. Готовь конкретные результаты для согласования. Не изменяй этот режим на `agent` без поручения оператора. Команды `review-contract`, `review-plan` и `accept` вернут `awaiting-operator` вместо автоматического утверждения. В интерфейсе доступны ручные действия.

Переключение режима не отменяет тесты, независимое ревью кода, ограничения защищённых файлов и проверку Git-интеграции. Прямое редактирование SQLite и подделка отчётов запрещены. Продолжительность попыток, число повторов и параллелизм ограничены конфигурацией; общего денежного лимита провайдеров пока нет.

## Если продукт зависит от ваших библиотек

Используй [workspace-процесс](docs/workspaces.md). Прочитай его до bootstrap: единая папка управления вне репозиториев, реестр компонентов, локальные базы задач в самих компонентах, одна БД координации, один сервер и общий DAG. Профили и правила выбирай для каждого компонента. Не запускай отдельную очередь DevContour в общей библиотеке.

После подготовки Git и настоящих локальных тестов создай `workspace.json` и выполни `workspace-init --file <absolute/workspace.json>`. Используй возвращённый `data` во всех командах. Для каждой задачи укажи `repositoryId`; при необходимости добавь зависимость от задачи другого компонента. В workspace веди общую карту требований и progress, а требования библиотеки — в её Git, с источником и связью с общим контрактом. Reviewer получает закреплённые тексты через задачу; одного пути к внешнему документу недостаточно.

Настрой `workspaceGates`, использующие компоненты из `DEVCONTOUR_COMPONENTS_JSON`. Подготовь и проверь скрипт реальной сборки/подключения библиотеки и сценариев продукта, защити его в `protectedPaths`. Для каждого зарегистрированного продукта обязателен собственный интеграционный test gate с JUnit. Не ослабляй проверки, чтобы скрыть несовместимость. Подробности о manifests, артефактах и среде команд — в workspace-документе.

Создай ChangeSet (`changeset-create`) из досок одного результата. В режиме `agent` зарегистрируй `workflow_start` с `kind: changeset`: сервер дождётся принятых досок, выполнит совместную проверку и применит условия приёмки. Remote mode ждёт Delivery, полученной отдельным `remote-check` после публикации человеком. Ручная альтернатива — `workspace-verify`, затем `changeset-accept --author-runtime codex|claude`; при `operator` дождись подтверждения. Не запускай оба маршрута одновременно. Не объявляй продукт готовым только потому, что локальные задачи done. Проверь автоматический `docs/journal/CHG-*.md`; ошибки проекции устраняй командой `journal`. Для принятого результата создавай новый ChangeSet с `supersedes`; историю не переписывай.

Сервер по-прежнему запускаешь ты. Одна активная сессия ведущего агента отвечает за следующий этап, исправления, обновление конфигурации и общий результат.

## 1. Прочитать ТЗ и зафиксировать исходную точку

Определи каталог инструмента и отдельный каталог продукта. Не создавай продукт поверх исходников devcontour. Если ТЗ положили в `docs` самого инструмента, перенеси его копию в `docs/spec.md` отдельного продукта в согласованной рабочей области. Сохрани исходник.

Прочитай все относящиеся к задаче документы, существующие AGENTS.md и код. Не меняй пользовательские незакоммиченные изменения. Для существующего проекта выбери безопасную исходную Git-точку; если её нельзя определить без риска потери работы, это основание для вопроса.

В ТЗ каждого компонента выдели разделы `## REQ-id: Название`. В `<workspace>/docs/requirements.md` веди карту общих сценариев, этапов и ссылок на компоненты/доски; не копируй туда внутренний backlog библиотек. Сохрани `<workspace>/docs/devcontour-progress.md` с текущим этапом, следующими действиями, путём данных, IDs досок и ключами workflow. Это контекст для возобновления, а не второй источник статусов. Реальные связи с проверками хранятся в `Task.requirements`, актуальность читается через `requirements-report`.

Выбирай разумные обратимые решения самостоятельно и записывай предположения. Обращайся к оператору, только если неоднозначность меняет продуктовую цель, доступы недоступны, нужен выход за заданные ограничения или действие выходит за порученный scope. В режиме `operator` дополнительно соблюдай этапные подтверждения.

## 2. Подготовить проект на утверждённом стеке

Обоснуй стек требованиями, существующим кодом и целями продукта. Выбери основной профиль из `react-vite-admin`, `next-product`, `go-api`, `mobile-maestro`; для нескольких компонентов настрой общие команды проверок из корня репозитория. Профиль не является генератором приложения.

Если оператор включил согласования, сначала представь ему архитектурное решение и дождись ответа. В обычном режиме продолжай самостоятельно.

Установи зависимости DevContour (`npm ci`, `npm run build`), если они ещё не подготовлены. Выполни из каталога инструмента, подставив выбранный профиль:

```sh
npm run devcontour -- setup \
  --repository /absolute/path/to/product \
  --profile react-vite-admin \
  --workspace /absolute/path/to/product-workspace
```

Выбор стека не ограничен встроенными примерами. Если они не подходят, создай локальный профиль `profiles/service.json`, разделив стек, gates и окружение через extends. Проверь `profile-show --repository <PRODUCT> --profile ./profiles/service.json`; затем передай этот путь в setup. Профили библиотеки хранятся в ней. Формат и обновление lock описаны в [профилях](docs/mcp-and-profiles.md). Не подбирай чужой стек только ради прохождения setup.

Для режима подтверждений добавь `--approval-mode operator`. ТЗ по умолчанию — `docs/spec.md`; другое имя внутри `docs` передаётся через `--brief`. Координация — `<workspace>/.devcontour-local`; локальные задачи и попытки — `<repository>/.devcontour-local`. Используй --workspace с выбранным путём или абсолютный data из результата во всех следующих командах. Не выполняй затем повторный `init`.

`setup` переносит правила, роли, память, инструкции по дизайну/контрактам, конфигурацию, lock и снимок профиля. Существующие файлы не перезаписывает. Изучи `preserved`, согласуй старые правила с новыми, дополни `.gitignore` для `.devcontour-local/`, `.reports/`, зависимостей и секретов. Повторный setup сохраняет прежнюю конфигурацию и режим; он не сбрасывает проект.

Продолжай после `needs-agent-bootstrap`: это промежуточное состояние, не завершение задачи. Создай минимальный каркас приложения, зависимости, команды gates, JUnit reporter и начальные настоящие тесты. Подготовь дизайн через референсы, макет состояний, guidelines и семантические токены. Не заставляй оператора копировать файлы и редактировать config.json.

Проверь CLI исполнителей командой `doctor`; отдельно проверь, что они действительно могут работать в своём окружении. Авторизацию и недоступные учётные данные не выдумывай. Рабочая подписка или лимит должны быть доступны установленному CLI.

Выполни каждый gate с теми же командами и настройками, которые будут использоваться в worktree. Тесты обязаны создавать настоящий JUnit по `DEVCONTOUR_REPORT_PATH`; ошибки, пустой отчёт и skips не являются успехом. Сохрани результаты и ограничения в локальном `.private/` выбранного workspace; прежде проверь, что каталог исключён из Git и распространяемых пакетов. Исправляй проблемы, не ослабляя проверки ради зелёного результата.

Для нового продукта инициализируй Git, проверь список файлов и создай исходный локальный commit. Не добавляй секреты, данные DevContour и чужие незакоммиченные файлы. Не делай push или deployment без отдельного поручения. Все нужные агентам ТЗ и правила должны быть закоммичены до появления worktree.

## Карта продукта и порученный релиз

В embedded локальный intent хранится в `docs/implementation-intent.md`, общий — в корневом `INTENT.md`. При render/snapshot используй возвращённый `source`.

До декомпозиции подготовь [INTENT.md](docs/intent.md) в каждом затронутом компоненте. Используй committed REQ-источники, сформулируй цель, пользователей, ограничения, nonGoals, истории по релизам и наблюдаемые критерии со стабильными IDs. Все REQ объявленных источников должны иметь историю либо обоснованное исключение. Генератор intent-render/intent_render возвращает Markdown без записи: проверь diff, сохрани в выбранном владельце и закоммить. Существующий INTENT.md сначала прочитай; значимые неоднозначности продуктовой цели разрешай по обычным правилам.

Для задачи получи intent_snapshot по истории и requirements_snapshot по подробным REQ. Привяжи обе группы к Task.requirements с реальными gate/scenario. Продуктовый контекст попадёт автору и reviewers через закреплённую постановку. Общий workspace хранит цель, карту приложений/технических компонентов/фич и закреплённые ссылки на локальные истории и релизы; подробности остаются локальными. Подготовь product и releases[].features по [карте продукта](docs/product-map.md). Для каждой фичи явно укажи included/deferred/not-applicable во всех приложениях релиза и настоящие сквозные gates. Приложение не обязано иметь отдельный Git; path технического компонента не заменяет writePaths или граф repository.dependsOn. Будущие релизы не включай в текущий scope. После изменения ТЗ обнови карту и используй обычную корректировку.

## Проектная память

В начале этапа вызови `memory_recall` в каждом затронутом компоненте по теме задачи. Не копируй локальные знания библиотеки в workspace. Проверь источники важных решений; hypothesis и устаревшие записи не заменяют контракт. После этапа сохрани обоснования в Markdown, закоммить источник и вызови `memory_retain` для коротких полезных знаний. Для исправления прежнего знания используй `supersedes`, для сводки — `supports`. Подробности — [проектная память](docs/project-memory.md).

Не увеличивай бюджет контекста без причины. Исполнитель и reviewers получают общий закреплённый снимок дополнительных знаний. Расходы и полноту их измерения проверяй через `workflow_metrics`/`usage_report`; смену runtime/model проверяй отдельным экспериментом, сохраняя gates.

## Инженерный контекст перед запуском очереди

После bootstrap прочитай [инженерные расширения](docs/engineering-context.md). Адаптируй `.agents/roles` и `.agents/context` к проекту; сохрани утверждённые соглашения отдельно от легаси и долгов. Setup создаёт определения context packs. Для workspace нескольких репозиториев добавь определения в workspace.json/config.json с правильными repositoryId; перенеси инструкции выборочно, учитывая существующие правила компонентов.

После исходного коммита выполни `context-lock --workspace <WORKSPACE>` до запуска сервера. Если сервер уже работает, останови его для изменения политики и затем запусти заново. По умолчанию закрепляется HEAD каждого источника; проверь, что это нужная версия. Не запускай очередь с незакреплёнными packs. Библиотечные пакеты контекста добавь нужным задачам через contextPacks; проверяй их командами context-show перед утверждением плана. Мобильным задачам явно подключай mobile-maestro.

Укажи writePaths задач/ролей по фактической структуре проекта, generatedPaths репозиториев и защищённые файлы проверки. Изменения другой области оформляй зависимыми задачами. Задай repository.dependsOn для продуктов/библиотек и gate.dependsOn для codegen → build → consumer tests. verificationMode=all оставь по умолчанию; affected используй только при полном графе потребителей.

Если проверки делят устройство, порт или аккаунт, зарегистрируй resources и укажи их IDs в задачах/gates. Одинаковые kind/value во всех workspace используют один host pool. Запусти окружение, проверь readiness, автоматизируй test-only авторизацию и очистку данных. Не перекладывай это на оператора. При аварии аренды прочитай resources, очисти осиротевшие процессы и только затем выполняй resource-release с cleanup-confirmed.

Разбирай доску «Находки агентов»: воспроизводи, приоритизируй, привязывай контракты/зависимости до утверждения. Находка модели — предложенная задача; она не становится validated-знанием без проверки. Правки инструкций и конфигурации выполняй как ведущий агент при остановленном сервере и отсутствии активных операций/других записывающих клиентов, затем закрепляй новый контекст и запускай сервер.

## 3. Провести архитектуру и контракты через независимое ревью

Подготовь JSON-файлы вида `{"title":"API каталога v1","content":"Полное согласуемое содержимое..."}`. Для архитектуры включи выбор стека, ограничения, выполненную bootstrap-проверку и ссылки на артефакты. Для API включи схему, ошибки, auth и совместимость; для UI — референсы, версию макета, состояния и токены.

```sh
npm run devcontour -- review-contract \
  --file /absolute/path/to/product-workspace/docs/proposals/api-v1.json \
  --author-runtime codex \
  --data /absolute/path/to/product-workspace/.devcontour-local
```

Укажи реальный runtime автора: `codex` или `claude`. Проверяет противоположный runtime. Команда расходует его лимит, сохраняет предложение и ревью в `decisions/`. При отклонении исправь предложение и повтори в пределах рабочего бюджета; не подменяй автора и reviewer.

В режиме `agent` успешно проверенный контракт регистрируется автоматически. Сохрани полученный ID. В режиме `operator` предложи оператору зарегистрировать проверенное содержимое через вкладку «Контракты» и дождись подтверждения. Повтор уже утверждённого идентичного контракта возвращает прежний ID.

## 4. Подготовить граф и привязки требований

После коммита ТЗ получи `requirements-snapshot --repository-id <ID> --file docs/spec.md --workspace <WORKSPACE>`. Перенеси `id`, `text`, `digest` нужного раздела в `requirements` задачи, добавь `source`, существующий test `gate` и наблюдаемый `scenario`. Не пересказывай закреплённый `text` и не вычисляй digest вручную. [Прослеживаемость](docs/requirements.md) объясняет исходный HEAD, проверяемые SHA и корректировки. Одного ID в описании задачи для машинной проверки недостаточно.

Сформируй `<workspace>/docs/first-slice.md` с первым сквозным пользовательским сценарием и ссылками на полное ТЗ. Не заставляй оператора писать этот файл. Для первого этапа ориентируйся на 5–15 задач; полный объём требований остаётся в дорожной карте.

```sh
npm run devcontour -- plan \
  --brief /absolute/path/to/product-workspace/docs/first-slice.md \
  --runtime codex \
  --data /absolute/path/to/product-workspace/.devcontour-local
```

Или самостоятельно создай JSON по `packs/example-plan.json` и выполни `import-plan`. Перед повтором проверь `export`: эти команды создают новую доску, а не обновляют существующую. В задачах должны быть IDs требований, наблюдаемые критерии, необходимые тесты, зависимости и ID утверждённых контрактов. Исправляй черновики через `edit-task` или UI. Backend/frontend не утверждаются без контрактов.

Подставляй IDs из ответа, не считай B1 константой. В режиме `agent` независимое review плана выполняет workflow следующего шага. Если выбран ручной маршрут или `operator`, выполни `review-plan --board <ID> --author-runtime codex|claude --workspace <WORKSPACE>`; при operator передай человеку план и результат ревью для ручного утверждения. Утверждение плана не доказывает реализацию требований.

Перед первым запуском сервера закоммить нужные worktree документы и тесты в соответствующих компонентах. Общий first-slice.md может оставаться в Git workspace: существенные условия из него должны попасть в постановки и контракты. После создания интеграционной ветки новый commit ТЗ в основном checkout сам по себе не попадает в devcontour/accepted; задача обязана перенести закреплённый раздел в проверяемый результат в пределах своего write scope. Не сдвигай ref вручную ради обхода проверки.

## 5. Вести выполнение без оператора

После готовности среды и контрактов проверь, что ранее запущенный start подключил техническую конфигурацию: `/api/preparation` возвращает engineConnected=true. Если процесс был остановлен, возобнови `start --workspace <WORKSPACE> --port 0`.

Сервер — долгоживущий процесс; запускай его в отдельной управляемой сессии и сохрани фактический URL. Не запускай второй scheduler через `run` одновременно с сервером. В режиме `agent` вызови MCP `workflow_start` либо создай в workspace JSON-запрос:

```json
{
  "operation": "workflow_start",
  "input": { "kind": "board", "id": "BOARD_ID", "authorRuntime": "codex", "maxAttempts": 3 }
}
```

Подставь ID подготовленной доски и настоящий runtime автора. Через CLI:

```sh
npm run devcontour -- agent --file /absolute/path/to/product-workspace/docs/workflow-start.json --workspace /absolute/path/to/product-workspace
```

Сервер проведёт review плана, включит общую очередь и примет доску после проверок. `workflow_status` читает jobs выбранного владельца: для локальной доски передай `repositoryId`, для общей доски или ChangeSet не передавай его. Повтор `workflow_start` с тем же входом вернёт прежний job. [Договор восстановления](docs/lead-workflow.md) содержит стадии, статусы и ограничения. MCP сам по себе этот цикл не запускает.

Для operator mode либо выбранного ручного маршрута после review/утверждения используй `queue --start --workspace <WORKSPACE>`, затем отдельную приёмку. Не запускай ручной и сохраняемый маршрут одной доски параллельно. Регистрация workflow включает очередь всего workspace, а не только выбранной доски.

После двух обязательных согласований интерфейс разработки служит наблюдению; в техническом режиме `agent` дополнительные клики не требуются. Подготовленный workflow продолжится без активного чата, пока работает сервер. Ведущий агент отвечает за весь порученный объём, следующие этапы и диагностику; регистрация одного job не означает завершение продукта.

Исполнители реализуют задачи в отдельных worktree. DevContour делает коммиты, обязательные gates, независимое ревью, последовательную интеграцию и повторные проверки merge SHA. При сбое прочитай причину и артефакты, устрани проблему и выполни `retry --task <ID> --data <DATA>`. Повтор ограничен `maxAttempts`; увеличение лимита не заменяет разбор причины.

Для паузы выдачи задач используй `queue --pause`. Уже работающие попытки продолжаются. Это не пауза всех стадий workflow: стадия запуска нового job может включить очередь. Перед Git sync, сменой конфигурации или общей остановкой дождись/останови активные операции, штатно заверши сервер и исключи другие записывающие клиенты. После исправления упавшей Task выполни её retry, затем при необходимости `workflow_retry`; один retry не заменяет другой. Не ослабляй gates, protectedPaths или критерии для обхода отказа.

## 6. Принять результат и перейти к следующему этапу

Когда задачи завершены, проверь соответствие требований результату и сохранённым доказательствам. Проверяй приложение на версии из `devcontour/accepted`, используя detached worktree; основной checkout сам не обновляется. При работающем workflow приёмку выполняет сервер; сначала прочитай его статус. Для ручного маршрута:

```sh
npm run devcontour -- accept \
  --board B1 \
  --author-runtime codex \
  --data /absolute/path/to/product-workspace/.devcontour-local
```

Команда требует `done` и присутствия всех результатов в интеграционной ветке. В режиме `agent` она сохраняет принятую ревизию с автором действия. В режиме `operator` возвращает `awaiting-operator`: человек проверяет продукт и нажимает «Принять доску». Тесты и ревью исполнения обязательны в обоих режимах.

Прочитай `requirements-report --repository-id <ID> --workspace <WORKSPACE>` для затронутых компонентов и обнови общую карту требований и progress-документ. Следующий самостоятельный этап — новая доска. Изменённые связанные разделы принятой доски обрабатывает `requirements-correct`; обычное изменение результата — `correct --board <ID> --roots <ID,ID> --reason <причина> --workspace <WORKSPACE>`. Проверь влияние, обнови AC/scenario/контракты новых черновиков и зарегистрируй новый workflow. Корректировка сама не пишет реализацию и не запускает работу. Не стирай историю r1.

Продолжай этапы, пока выполнен порученный scope. Перед завершением прочитай intent_report для выбранного релиза каждого компонента и общей карты; CLI intent-report --require-complete возвращает ненулевой exit при пропусках. Устрани забытые истории, нераспределённые REQ и устаревшее покрытие. Для завершения продуктового релиза создай общий ChangeSet с releaseId и всеми досками, содержащими актуальные задачи релиза, затем зарегистрируй его workflow. Система потребует принятые доски, актуальное покрытие, закреплённую карту и полные совместные проверки. Перед итоговым отчётом требуй product-view --release <ID> --require-accepted. Технический ChangeSet без releaseId и один coverageComplete не завершают продукт. После изменения принятого результата создай следующий ChangeSet с supersedes; историю не переписывай. Если пользователь поручил только MVP, не расширяй задачу до всех будущих возможностей ТЗ. Если поручено всё ТЗ, не выдавай один принятый срез за готовый продукт. Итоговый отчёт должен перечислить реализованные требования, проверки, ограничения и оставшиеся блокеры.

## Возобновление и границы автоматизации

Для командного проекта прочитай [синхронизацию через Git](docs/team-sync.md). Подготовь отдельный Git workspace, исключи `.devcontour-local/`, включи `.devcontour/` в версионирование. До планирования выполни `sync --member <ID-разработчика> --workspace <WORKSPACE>`; новые задачи получат локального ответственного. Существующие неназначенные задачи распредели через `assign-task`. Назначение согласуется в общем Git до параллельного исполнения на разных компьютерах.

Перед передачей работы и после получения изменений коллег останови выдачу, дождись активных попыток и штатно останови сервер, затем выполни `sync-status` и `sync`. Агент разрешает однозначные расхождения и готовит проверенный diff, человек публикует его. Не меняй ветку и не выполняй pull во время активных workers/workflow. Не выдавай receipt другого участника за локальный запуск тестов; общий ChangeSet на новой машине проверяется заново. Git переносит задачи и привязки требований, но не jobs workflow, signal receipts, токены или аренды.

При перезапуске прочитай `<workspace>/docs/devcontour-progress.md`, конфигурацию, checkpoint и изменения после него, затем `project_overview`, нужные `task_briefing` и `workflow_status`. Используй `export` для полной диагностики задач и событий; jobs/signals читаются отдельными операциями. Состояние SQLite и Git важнее текстовых заметок. На той же машине сервер продолжает сохранённые jobs; после Git clone ведущий агент проверяет перенесённый граф и регистрирует их заново. `setup` самостоятельно не вызывает модель и не строит приложение.

Файл в `docs` сам по себе не запускает фоновый сервис. Ведущий агент нужен для bootstrap, новых этапов и разбора ошибок; сервер продолжает уже зарегистрированные workflow. Checkpoint помогает восстановить замысел, но не запускает работу и не заменяет evidence. Перед передачей сессии сохрани краткий проверенный next step у владельца данных. Внешние сигналы создают только предложенную работу; перед запуском её нужно воспроизвести и подготовить как обычный этап.
