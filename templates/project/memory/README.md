# Память команды

Храним знания, не дублируем SQLite-статусы.

- decisions/ADR-NNN.md: решение, контекст, альтернативы, последствия, owner, source, verifiedAt, status.
- services/<service>.md: ответственность, зависимости, API/events, инварианты, расположение тестов.
- handoffs/<task>-<attempt>.md: цель, SHA, сделанное, непринятое, команды и результаты проверок, блокеры, следующий шаг.
- lessons.md: симптом → причина → проверенное исправление → условия применимости. Гипотеза сначала proposed.

Проверку свежести выполняет ответственный при изменении контракта/архитектуры. Отчёт агента не получает validated автоматически.

Эта папка версионируется обычным Git вместе с правилами `.agents/` и документацией. Пишите отдельные записи по решению/задаче, чтобы независимые изменения не сталкивались в одном большом файле. Указывайте Git SHA и источник проверки; не сохраняйте credentials и полный диалог модели. Локальные выводы библиотеки остаются здесь, межпроектные — в workspace.

Статусы задач не ведутся вторым списком в Markdown. Для командного обмена служит `.devcontour/`, а ведущий агент выполняет `sync` перед передачей работы и после получения изменений. SQLite и активные процессы остаются локальными. В handoff указывайте ID задачи и следующий шаг, ссылаясь на её запись, а не копируя статус как альтернативный источник истины.

Checkpoint ведущего агента в `.devcontour/checkpoints/` — переносимая заметка о контексте; workflow job в SQLite — оперативная стадия исполнения. После clone заметка помогает восстановить замысел, но job регистрируется заново. Привязки REQ переносятся с задачей; источники требований библиотеки и знания о ней остаются в этом Git. Подробные signal receipts и измерения попыток не копируются в общую память workspace.

Скилл/инструкция описывает утверждённое соглашение, не инвентарь произвольных реализаций. Расхождения и долги возвращаются в discoveries и становятся draft-задачами SQLite. Они не подтверждены автоматически и не переписывают существующее соглашение. Не создавайте общий TODO как второй task tracker.

Инструкции собственной библиотеки версионируются вместе с API и минимальным примером использования. При изменении контракта ведущий агент проверяет примеры, свежесть знаний и потребителей, затем закрепляет новый context pack. Сведения о конкретной попытке не включаются в общий пакет знаний.
