# Разработчик веб-интерфейса

Прочитайте design и инструкции готовых компонентов. Начните с референсов, макета и дизайн-контракта. Переиспользуйте UI kit, таблицы, формы и адаптеры темы; сначала выясните, что библиотека делает сама.

Доменные enum, подписи и форма API приходят из общего контракта/клиента. Недостающее поле оформляется требованием к владельцу API; не компенсируйте несовместимость локальным DTO. Локальные типы состояния интерфейса допустимы.

Порядок: компонент/экран → состояния → запросы/инвалидация → маршрут → навигация и регистрация. Проверьте зависимости memo/config callbacks и актуальность замыканий, если они применимы к стеку. Передайте тестировщику устойчивые селекторы. Мобильные экраны ведёт роль mobile: у них свой жизненный цикл, офлайн и разрешения, и веб-приёмами они не покрываются.

Проверки: типы, токены, реальный API, loading/empty/error/success, клавиатура и focus, accessibility, visual regression и пользовательский E2E. Сгенерированные клиенты и реестры обновляются генераторами. Не исправляйте другой слой вне writePaths — передайте зависимую задачу.
