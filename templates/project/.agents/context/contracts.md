# Контракты и собственные библиотеки

Назначьте владельца общего API: роль architect с пакетом контрактов либо профильный backend. Владение — область работы и writePaths, а не обязательный дополнительный процесс для каждой задачи.

Для изменения публичной формы данных подготовьте контракт, совместимость и миграцию потребителей до параллельной реализации. Имена экспортов, DTO, операций, событий и перечислений могут быть публичным API. Не переименовывайте их как косметическую правку без анализа потребителей.

Порядок: исходная схема → экспорты/barrel → сборка примитивов и библиотеки → генератор API/клиента → проверка типов потребителей → контрактные и интеграционные тесты → пользовательский сценарий продукта. Для Go/Protobuf/OpenAPI выберите соответствующие инструменты; Zod/Nest не обязательны.

Зафиксируйте для каждого генератора входы, команду, cwd, выходы и зависимости gates. Проверьте свежий checkout: dist или generated могут отсутствовать. Генераторы запускаются из определённого cwd; выходы не должны уходить за worktree. Исходник генерации редактируется, производный артефакт вручную не исправляется. Защитите команды проверки и generatedPaths; отслеживаемые generated-файлы обновляет ведущий агент отдельным подготовительным изменением, поскольку gates не вправе менять проверяемый SHA.

Каждая библиотека поставляет versioned контекст: назначение, API, ограничения, минимальный пример, типичные ошибки и команды тестов потребителей. Подключайте его задаче через contextPacks. После изменения API обновляйте инструкцию и её версию; context-lock закрепляет Git revision и digest.

repository.dependsOn описывает компоненты, Task.dependsOn — работу, Gate.dependsOn — порядок проверок. Эти графы не заменяют друг друга. Изменение manifests/lockfiles/configs также меняет SHA компонента и проверяет потребителей. В одном монорепозитории MVP проверяет весь репозиторий; внутренний package graph не угадывается по путям.

## Контракт — это код, а не документ о коде

Контракт, написанный прозой, разваливается на ревью: каждая формулировка
оставляет неоднозначность, которую приходится закрывать следующей формулировкой.
Пишите контракт исполняемым и присылайте на ревью ссылку на файлы:

| Что                   | Чем                                                          |
| --------------------- | ------------------------------------------------------------ |
| Формы входа и выхода  | Схема в коде: zod, JSON Schema, Protobuf, OpenAPI — по стеку |
| Границы схемы         | Тесты схемы, проходящие уже сейчас                           |
| Публичная поверхность | Объявленные сигнатуры операций в компоненте-владельце        |
| Приёмка               | Сценарии из ТЗ как тесты, с фикстурами из ТЗ                 |

Сценарии, для которых реализации ещё нет, помечайте `todo`/`skip`: они
зафиксированы и проверяемы, но не выдают себя за пройденные. Задача считается
выполненной, когда снимает свои `todo`, — это её доказательство, а не отчёт.

Документ контракта остаётся коротким и содержит только то, чего схема выразить
не может: детерминизм и порядок сравнения, чистота, приоритет причин отказа,
инварианты между операциями, принятые пользователем решения и их обоснование.
Всё, что выражается схемой, в документе не дублируется: два источника разойдутся.

Схему пишите так, чтобы недопустимое состояние нельзя было выразить. Пустой
обязательный список, дубликат идентификатора, структура, невозможная физически,
— это ошибки схемы, а не соглашение в тексте. Ошибки входа возвращайте значением
в типе результата, а не исключением: иначе их не видно в контракте.

## Область доказательства задачи

У задачи есть `writePaths` — что ей позволено менять, и `gates` — чем она
доказывает себя. Это подмножество проверок профиля; прогон задачи требует
именно его, а полный набор остаётся обязательным для приёмки доски и релиза.

Без этого параллельные задачи делят один общий набор проверок, и зелёный gate
не различает, чьи ожидания закрыты: задача может не закрыть ни одного и всё
равно пройти. Поэтому давайте каждой задаче свой файл приёмки и свой test gate
над ним. Тогда тесты настоящие, а не пропущенные: красный gate блокирует
только свою задачу и честно показывает, что она не сделана.

Область обязана включать хотя бы один gate с `kind: test` — проверки типов и
стиля проходят и на нереализованном коде. Требование задачи может ссылаться
только на gate внутри её области.
