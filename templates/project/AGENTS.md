# Правила проекта под управлением DevContour

Если workspace не указан в текущем поручении/контексте, ведущий агент сначала спрашивает пользователя об абсолютном пути и ждёт ответа. У исполнителя отдельной задачи контекст уже задан оркестратором; повторно выбирать workspace ему не нужно.

Режим размещения (`embedded` внутри этого репозитория или `separate` отдельно) выбирает пользователь до первого запуска; существующий `devcontour.workspace.json` сохраняет выбор. Рабочий worktree исполнителя не запускает controller. В embedded локальный intent — `docs/implementation-intent.md`, общий — `INTENT.md`; используйте source из API.

Ведущий агент начинает с `docs/devcontour-start.md`, если файл установлен, и ведёт проект до порученного результата. Продуктовую постановку, затем архитектуру и стек с C1/C2, затем дизайн-трек — референсы, а при применимом интерфейсе концепт и дизайн-систему — обязательно утверждает пользователь в панели до настройки и разработки. Панель запускается первой через `start --workspace`. После всей цепочки технические согласования по умолчанию выполняют агенты после независимого ревью; `approvalMode: "operator"` добавляет подтверждения технических этапов человеком. Порядок описан в `docs/devcontour-staged-workflow.md`. Исполнитель отдельной задачи работает только в её scope и не запускает общий bootstrap или другие задачи.

1. Прочитайте карточку задачи, acceptance criteria, связанные REQ-разделы и закреплённые контракты. `requirements.source` относится к этому репозиторию; реализуйте закреплённое поведение и проверьте указанные gate/scenario. Изменившийся источник требует решения ведущего агента, а не переписывания утверждённого digest исполнителем. Если контракт не определён, зафиксируйте блокер.
2. Работайте только в выданном worktree и в пределах задачи. Git commit, merge и принятие результата выполняет devcontour. Не запускайте собственных исполнителей без выданного scope и бюджета.
3. Не меняйте утверждённые gates, CI, baseline и определения done для получения зелёного результата. Предлагайте отдельную корректировку политики.
4. Для UI: референсы → направление → макет/состояния → guidelines/tokens → реализация. В компонентах только семантические токены, не произвольные цветовые литералы. Проверяйте keyboard, loading, empty, error, mobile.
5. Тесты проверяют наблюдаемое поведение. Не вычисляйте ожидаемый результат тем же кодом, который проверяете. Не заменяйте реальную интеграцию только моками.
6. Выводите действия, результаты и доказательства. Не объявляйте done и не подменяйте машинные отчёты текстом «всё проверено».
7. Память: устойчивые решения — в memory/decisions, сервисные контракты — в memory/services, незавершённое — в handoff. Каждая запись имеет source, owner, verifiedAt и статус proposed/validated/superseded.
8. В командном режиме задачи синхронизирует ведущий агент через `sync`; `.devcontour/` версионируется, `.devcontour-local/` игнорируется. Worker не редактирует `.devcontour/` и не меняет назначения. До выполнения согласуйте ответственного в общем Git; инструкции ведущему агенту — в `docs/devcontour-team-sync.md`. Pull и согласование Git-файлов с SQLite выполняются при остановленном сервере без активных операций. Receipt коллеги не выдаётся за локальный запуск тестов.
9. Ошибки и неопределённость явно фиксируются. Модель другого провайдера делает независимое ревью; согласие моделей само по себе не критерий корректности.

В workspace нескольких репозиториев ведущий агент использует единый `data` и `docs/devcontour-workspaces.md`. Для общей библиотеки не запускается независимый scheduler. Исполнитель меняет только свой компонент; межрепозиторная работа оформляется отдельными задачами. Общий результат требует совместной проверки ChangeSet на закреплённых версиях. Автоматический дневник в workspace не редактируется вручную; API/changelog и память библиотеки обновляются в её репозитории.

Подготовленные доски ведущий агент передаёт в сохраняемый workflow по `docs/devcontour-lead-workflow.md`; привязки ТЗ описаны в `docs/devcontour-requirements.md`. Эти операции принадлежат ведущему агенту, worker не запускает новый цикл. Пауза очереди не останавливает все стадии workflow: перед Git sync и сменой политики ведущий агент штатно останавливает сервер. Jobs и receipts внешних сигналов остаются в локальной SQLite, задачи и требования переносятся через Git. Сигнал или находка создают предложенную работу, не тестовое доказательство.

## Рабочие инструкции

Ведущий агент готовит INTENT.md по docs/devcontour-intent.md и проверяет полноту порученного релиза через intent_report. Истории, подробные требования и задачи принадлежат компоненту; workspace хранит общие ссылки. Worker получает и REQ-intent истории, и её подробные REQ в Task.requirements. Не меняйте цель или критерии под реализацию; находка становится предложением корректировки. Статус истории вычисляется из evidence, вручную отмечать её done в Markdown не нужно.

Роль и выбранные context packs поступают в промпт с Git revision и digest. Общие инструкции: `.agents/context/workflow.md`; ревью: `.agents/context/review.md`. Профильные правила — `.agents/roles/<role>.md`, contracts/design/testing; `mobile-maestro` подключается только нужным задачам. Учитывайте локальные соглашения проекта и версии библиотек.

Не ведите второй TODO со статусами. Находки вне задачи возвращайте в structured discoveries: DevContour создаст непроверенные черновики. Ведущий агент разбирает их и добавляет зависимости после воспроизведения. Утверждённые знания остаются в memory с source/owner/verifiedAt/status.

Локальные задачи, роли и журнал этого компонента принадлежат ему: devcontour.component.json, .agents/, .devcontour-local/state.sqlite и .devcontour-local/journal/activity.md. Внешний workspace хранит общие контракты, связи и межпроектную приёмку. Используйте команды через общий coordinator, не запускайте отдельный scheduler поверх локальной базы.

Публикует человек. Не выполняйте push, создание PR/MR, merge на forge или публикацию пакетов. DevContour готовит handoff и подтверждает удалённый результат через read-only GitLab/GitHub/другой адаптер. Отсутствующий write-доступ не является причиной запрашивать расширение прав MCP.

Для продуктового релиза ведущий агент готовит общую карту приложений и фич по docs/devcontour-product-map.md. Подробные истории и задачи остаются локальными. Смысл общей фичи отразите в локальных критериях и контрактах. Итоговый ChangeSet получает releaseId; перед завершением требуется product-view --release <ID> --require-accepted. Обычная приёмка технической доски или ChangeSet без releaseId не подтверждает готовность продукта.
