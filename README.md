# DevContour

**Claude Code пишет код. Codex проверяет. DevContour решает, можно ли принять результат.**

Когда над продуктом работают несколько AI-агентов, кто-то должен держать общий план, дождаться зависимостей, запустить тесты и убедиться, что изменения работают вместе. DevContour берёт эту координацию на себя. Вы передаёте ведущему агенту ТЗ и путь к workspace; он готовит проект и ведёт работу по графу задач.

Это локальный инструмент для разработчиков, которые хотят поручать агентам целые изменения и видеть, чем подтверждён результат. Проект пока развивается: автоматические проверки используют реальные Git-репозитории, а качество работы живых моделей проверяется отдельно. Текущий статус и ограничения — в [отчёте проверки](docs/verification-review.md).

## Как выглядит работа

Допустим, нужно добавить управление чатами в админку и доработать общую библиотеку API.

1. Вы кладёте ТЗ в `docs/spec.md` и указываете агенту workspace.
2. Агент изучает существующий код, выбирает стек и проверки, фиксирует API-контракт и разбивает работу на связанные задачи.
3. Библиотека и интерфейс получают своих исполнителей. Независимые задачи идут параллельно, зависимые ждут нужного результата.
4. Каждый исполнитель работает в отдельном Git worktree. Другой runtime проверяет его изменения, а DevContour запускает настоящие тесты.
5. Перед принятием система повторяет тесты и ревью на результате интеграции с текущей веткой. Если проверка не прошла, задача остаётся незавершённой.

Прогресс, причины блокировки и результаты проверок видны в веб-консоли. Ведущий агент разбирает сбои и готовит следующие этапы. Подтверждения оператором опциональны; тесты и независимое ревью обязательны. Публикацию в GitHub/GitLab выполняет человек.

## Что здесь полезного

- **У завершения есть доказательства.** Слова агента «готово» недостаточно: нужны результаты проверок на конкретном коммите и проверенная интеграция.
- **Модели можно сочетать.** Назначайте Claude Code и Codex по ролям и репозиториям. Например, Claude реализует бэкенд, Codex проверяет; для фронтенда — наоборот.
- **Библиотеки сохраняют собственную память.** Их задачи, правила и дневник остаются рядом с кодом. Workspace связывает общие контракты и изменения нескольких компонентов.
- **Команда обменивается задачами через Git.** Переносимая память хранится в читаемых JSON-файлах; SQLite обслуживает локальные запуски и не коммитится.
- **Исправления не стирают историю.** После приёмки можно создать новую ревизию и перепроверить затронутые зависимости.
- **Стек выбирается под продукт.** Есть готовые профили React/Vite, Next.js, Go, Python, NestJS, React Native/Expo. Собственный профиль с командами сборки и тестирования хранится в проекте.

## Посмотреть без подключения моделей

Нужны Git и Node.js 24.3+. В каталоге клонированного репозитория:

```sh
npm ci
npm run build
npm run demo
```

Откройте адрес, который напечатает сервер, обычно [localhost:4317](http://127.0.0.1:4317). Запустите очередь и проследите задачу от реализации до приёмки. Demo использует тестовых исполнителей и не расходует лимиты моделей.

## Начать свой проект

Подготовьте ТЗ и передайте ведущему агенту:

> Прочитай START.md в DevContour. Реализуй ТЗ /absolute/product/docs/spec.md. Workspace: /absolute/product-workspace. Сам подготовь конфигурацию, контракты, задачи и проверки. Запусти веб-консоль и веди работу до проверенного результата. Согласования этапов отключены; внешнюю публикацию выполняет человек.

Для реальной работы нужны установленные и авторизованные Claude Code и Codex CLI. Если путь workspace не указан, агент спросит его. Остальную настройку он выполняет по [START.md](START.md). Само появление файла в `docs` ничего не запускает.

Установку DevContour можно использовать для нескольких независимых workspace. Подготовленный этап продолжает выполняться сервером и после закрытия чата; для нового планирования и разбора сбоев нужен ведущий агент. [Подробный порядок работы](docs/workflow.md).

## Где находятся данные

```text
devcontour/                  установка инструмента
product-workspace/           общая координация и контракты
product/                    код, правила и задачи продукта
shared-library/             код, правила и задачи библиотеки
```

В каждом владельце `.devcontour/` содержит переносимую память для Git, а `.devcontour-local/` — локальную SQLite, запуски и артефакты. Настройки компонента — в `devcontour.component.json`. Установка инструмента не хранит прогресс ваших продуктов. [Память и синхронизация](docs/team-sync.md).

## Границы текущей версии

Один controller работает на одном хосте: до 10 компонентов и 1–4 параллельных исполнителей. Git worktree изолирует изменения, но не заменяет контейнер или системную песочницу. Нет общего денежного лимита двух провайдеров и автоматического выбора модели по сложности задачи. Большой проект сначала стоит проверить на небольшом сквозном сценарии.

Старое служебное имя и алиасы удалены: прежние экспериментальные workspace автоматически не мигрируют. Используйте новый setup, сохранив старые данные отдельно. [Правила приёмки и ограничения](docs/mvp.md).

## Развивать DevContour

Начните с [руководства разработчика](docs/development.md), затем прочитайте [архитектуру](docs/architecture.md) и [обоснования решений](docs/decisions.md). Для проверки изменений: `npm run check` и `npm run format:check`.

[GitHub Actions](https://github.com/step1ov/devcontour/actions) показывает статус опубликованного кода; локальные результаты и состояние живого пилота приведены в [отчёте](docs/verification-review.md). Наличие workflow само по себе не означает успешного прохождения проверок.
