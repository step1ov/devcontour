# DevContour

**Claude Code пишет код. Codex проверяет. DevContour решает, можно ли принять результат.**

Когда над продуктом работают несколько AI-агентов, кто-то должен держать общий план, дождаться зависимостей, запустить тесты и убедиться, что изменения работают вместе. DevContour берёт эту координацию на себя. Вы передаёте ведущему агенту ТЗ, выбранное размещение и путь к workspace; панель открывается сразу. Сначала вы утверждаете продуктовую постановку, затем архитектуру и стек с C1/C2, затем дизайн: референсы, а если изменение касается интерфейса — ещё концепт и дизайн-систему. После этого агент готовит проект и ведёт работу по графу задач.

Это локальный инструмент для разработчиков, которые хотят поручать агентам целые изменения и видеть, чем подтверждён результат. Проект пока развивается: автоматические проверки используют реальные Git-репозитории, а качество работы живых моделей проверяется отдельно.

## Как выглядит работа

Допустим, нужно добавить управление чатами в админку и доработать общую библиотеку API.

1. Вы передаёте ТЗ и workspace. Агент сразу запускает веб-панель.
2. Агент прорабатывает продукт: пользователи, сценарии, границы и критерии. Промежуточные версии видны в панели; вы утверждаете постановку.
3. Агент готовит архитектуру, стек с обоснованием и диаграммы C1/C2. Вы утверждаете эту версию.
4. Агент ведёт дизайн-трек: референсы, затем концепт и дизайн-систему. Вы утверждаете каждый шаг; для изменения без интерфейса достаточно утвердить, что дизайн неприменим.
5. Агент настраивает проект и граф задач. Библиотека и интерфейс получают исполнителей в отдельных Git worktree.
6. Тесты, независимое ревью и повторная проверка после интеграции подтверждают технический результат.

[Четыре этапа и порядок согласований](docs/staged-workflow.md).

В разделе разработки, на вкладке карты продукта, видны возможности для пользователя и их участие в приложениях. Приёмка продуктового релиза требует актуального покрытия требований и совместных проверок компонентов. [Как устроена карта продукта](docs/product-map.md).

Прогресс, причины блокировки и результаты проверок видны в веб-консоли. Ведущий агент разбирает сбои и готовит следующие этапы. Продуктовые согласования обязательны; дополнительные технические подтверждения опциональны. Тесты и независимое ревью обязательны. Публикацию в GitHub/GitLab выполняет человек.

## Что здесь полезного

- **У завершения есть доказательства.** Слова агента «готово» недостаточно: нужны результаты проверок на конкретном коммите и проверенная интеграция.
- **Модели можно сочетать.** Назначайте Claude Code и Codex по ролям и репозиториям. Например, Claude реализует бэкенд, Codex проверяет; для фронтенда — наоборот.
- **Библиотеки сохраняют собственную память.** Их задачи, правила и дневник остаются рядом с кодом. Workspace связывает общие контракты и изменения нескольких компонентов.
- **Команда обменивается задачами через Git.** Переносимая память хранится в читаемых JSON-файлах; SQLite обслуживает локальные запуски и не коммитится.
- **Исправления не стирают историю.** После приёмки можно создать новую ревизию и перепроверить затронутые зависимости.
- **Стек выбирается под продукт.** Есть готовые профили React/Vite, Next.js, Go, Python, NestJS, React Native/Expo. Собственный профиль с командами сборки и тестирования хранится в проекте.

## Посмотреть без подключения моделей

Нужны Git и Node.js 24.3+. В каталоге клонированного репозитория:

```sh
npm ci
npm run build
npm run demo
```

Откройте адрес, который напечатает сервер, обычно [localhost:4317](http://127.0.0.1:4317). Запустите очередь и проследите задачу от реализации до приёмки. Demo использует тестовых исполнителей и не расходует лимиты моделей.

## Начать свой проект

Готовые команды с опциями и поручения агенту: [запуск через CLI и skill](docs/start-examples.md).

Подготовьте ТЗ и передайте ведущему агенту:

> Прочитай START.md в DevContour. Реализуй ТЗ /absolute/product/docs/spec.md. Размещение: separate. Workspace: /absolute/product-workspace. Сразу запусти веб-консоль. Проработай продукт и получи моё утверждение, затем подготовь архитектуру, стек и C1/C2, затем дизайн-трек — каждую версию утверждаю я. После этого самостоятельно готовь конфигурацию, контракты, задачи и проверки. Дополнительные технические согласования отключены; внешнюю публикацию выполняет человек.

Для реальной работы нужны установленные и авторизованные Claude Code и Codex CLI. Перед первым запуском агент уточняет размещение: внутри одного репозитория/монорепозитория (`embedded`) или в отдельном workspace (`separate`), и абсолютный путь. Сохранённый выбор повторно не спрашивается. Остальную настройку он выполняет по [START.md](START.md). Само появление файла в `docs` ничего не запускает.

Установку DevContour можно использовать для нескольких независимых workspace. Подготовленный этап продолжает выполняться сервером и после закрытия чата; для нового планирования и разбора сбоев нужен ведущий агент. [Подробный порядок работы](docs/workflow.md).

## Где находятся данные

Для одного репозитория или монорепозитория можно выбрать `embedded`: сам корень проекта становится workspace, вся память находится внутри его `.devcontour/` и `.devcontour-local/`. Продуктовые данные не требуют отдельного Git. Для нескольких самостоятельных репозиториев используется `separate`:

```text
devcontour/                  установка инструмента
product-workspace/           общая координация и контракты
product/                    код, правила и задачи продукта
shared-library/             код, правила и задачи библиотеки
```

В каждом владельце `.devcontour/` содержит переносимую память для Git, а `.devcontour-local/` — локальную SQLite, запуски и артефакты. Настройки компонента — в `devcontour.component.json`. Установка инструмента не хранит прогресс ваших продуктов. [Память и синхронизация](docs/team-sync.md).

## Границы текущей версии

Один controller работает на одном хосте: до 10 компонентов и 1–4 параллельных исполнителей. Git worktree изолирует изменения, но не заменяет контейнер или системную песочницу. Нет общего денежного лимита двух провайдеров и автоматического выбора модели по сложности задачи. Большой проект сначала стоит проверить на небольшом сквозном сценарии.

Старое служебное имя и алиасы удалены: прежние экспериментальные workspace автоматически не мигрируют. Используйте новый setup, сохранив старые данные отдельно. [Правила приёмки и ограничения](docs/mvp.md).

## Развивать DevContour

Начните с [руководства разработчика](docs/development.md), затем прочитайте [архитектуру](docs/architecture.md) и [обоснования решений](docs/decisions.md). Для проверки изменений: `npm run check` и `npm run format:check`.

[GitHub Actions](https://github.com/step1ov/devcontour/actions) показывает статус опубликованного кода. Наличие workflow само по себе не означает успешного прохождения проверок.
