# Roadmap: секреты не сохраняются нигде

Дата: 2 октября 2026 года.

Статус: план развития. Задачи и критерии ниже не являются заявлением о реализованной возможности. Идентификаторы S01–S06 новые и не пересекаются с A01–A13 [основного roadmap](2026-09-24-ai-native-development.md) и F01–F08 [roadmap петли обратной связи](2026-09-29-feedback-loop.md).

## 1. Проблема

Контур передаёт проверкам, исполнителям и ревьюерам секреты окружения и маскирует их в выводе. Маскирование сделано в местах сборки отдельных записей: вывод команды, итог gate, отдельные поля evidence. Независимая проверка находила утечки по одному пути за раунд, и каждое точечное исправление открывало соседний путь того же класса:

- текст ошибки, пути и аргументы, выбранные проверкой, попадали в итог, лог и отказ попытки мимо маски;
- секрет в экранированной форме — JSON (`\"`, `"`), JSON внутри JSON, XML-сущность (`&quot;`, `&#34;`) — не совпадал с исходной строкой и сохранялся; после разбора отчёта он снова декодировался;
- декодированные ответы ревьюера и автора попадали в discoveries, реестр воспроизведений, попытки ревью контракта, локальные записи операций, журналы и последующие подсказки;
- ключи объектов пользовательских отчётов не маскировались;
- сырой файл результата CLI оставался, если CLI завершался с ошибкой;
- служебная квитанция окружения сохраняла значение секрета с разрешённым именем;
- маскирование всей записи целиком портило служебные поля (SHA, фаза, id, digest, путь к логу) при коротком секрете или совпадающем наследуемом значении.

Общей границы маскирования на уровне хранилища нет: каждый новый путь записи — новая потенциальная утечка.

## 2. Уже сделано

Отправная точка, а не приёмка класса:

- redactor знает исходную, URL-, JSON-экранированную (один и два уровня) и XML-экранированную (`&quot;`) форму секрета;
- evidence gate задачи и совместной проверки, `review.json` и evidence ревью маскируются по диагностическим полям; служебные поля маска не трогает;
- общий обработчик ошибок gate задачи и совместной проверки маскирует текст ошибки; маска строится по заданным секретам и тогда, когда окружение целиком собрать нельзя;
- аргументы команд маскируются при сохранении, исполняются исходные;
- «воспроизведение наблюдено» ставится по id запуска проверки ревьюера, на который сослался ревьюер, в журнале контура; команда в реестре берётся из записи о запуске, а id сравнивается в той же маске, что применена к ответу.

## 3. Работы

Общие правила для всех работ:

- **Чьи секреты.** Маскируются значения секретов окружения выбранного workspace, компонента и прогона — тех, что передаются проверке, исполнителю или ревьюеру. Незаданный секрет — причина отказа запуска, но маска строится по заданным, и её отсутствие у одного не снимает маску с остальных.
- **Служебные и диагностические поля.** Служебные: SHA, id сущностей, digest, enum (фаза, вид, статус), числа, пути к артефактам контура и ссылки на них. Диагностические: текст вывода, итоги, сообщения, команды для показа, отчёты проверок, ответы агентов, id тестов и пути, выбранные проверкой. Маскируется только диагностика; digest соответствует сохранённому содержимому после маски.
- **Где хранится.** Критерии проверяются по каждому физическому хранилищу: центральная база, базы компонентов (`storage: component`), база координации workspace и локальные записи каждого владельца — с независимыми владельцами и без переноса записей между ними.
- **Граница исключений.** Не маскируются точные метаданные, которые не несут текста проверки: manifest, зависимости, impact, Git SHA и tree, схемы и конфигурация пользователя. Внешние входы (сигналы, forge handoff) маскируются по тем же правилам, если сохраняются.
- **Уже сохранённая история.** Записи, сделанные до S01, не переписываются молча: `doctor` находит в них известные секреты и называет записи; очистка — явная операция с журналом, сохраняющая digest утверждений через пометку «замаскировано после утверждения».

### S01. Граница маскирования в хранилище

**P0 · M.** Все записи state, событий и локальных записей (`local_workflow`) проходят маскирование при записи. Схема записи различает служебные поля и диагностическую нагрузку; маскируется только нагрузка, включая ключи пользовательских объектов. Ключи, совпавшие после маски, не теряют данных: значения сохраняются под различимыми ключами с пометкой коллизии. **Приёмка:** секрет, переданный любым агентским ответом или выводом проверки, не находится ни в SQLite, ни в журнале событий, ни в локальных записях; служебные поля и digest не меняются ни при каком значении секрета; коллизия ключей сохраняет все значения.

### S02. Нормализация структурированных форматов

**P0 · S–M.** Сохраняемые JSON, JSONL и XML маскируются после декодирования, а не только как текст: строки, ключи и атрибуты; поддерживаются Unicode-экранирование JSON и числовые XML-сущности. Потоковая маска вывода учитывает эти формы. **Приёмка:** корпус форм секрета (кавычка, обратная косая черта, перевод строки, Unicode-экранирование, числовая XML-сущность, двойное экранирование) не обнаруживается ни в одной сохранённой записи и ни в одном файле контура, кроме сырых артефактов, явно объявленных по S06.

### S03. Артефакты исполнения и производные файлы

**P1 · S–M.** Обрабатываются при успехе, ненулевом коде, таймауте, отмене и ошибке разбора: файл результата CLI, журналы runtime (включая имена и аргументы процессов в диагностике дерева процессов), usage-диагностика, журнал проверок ревьюера, копии отчётов, логи setup, ready и teardown окружения, включая ветки отказа уборки. Производные файлы контура — Markdown-журналы, `task.json`, `context.json`, `prompt.txt`, черновики продолжения — собираются из уже замаскированных записей. Сырые временные файлы не остаются среди долговременных артефактов. **Приёмка:** каждое завершение CLI и каждая ветка lifecycle оставляют только замаскированные артефакты, кроме сырых артефактов, явно объявленных по S06; секрет из ответа агента или вывода проверки не попадает ни в одну последующую подсказку и ни в один журнал.

### S04. Квитанции и экспорт

**P1 · S.** Квитанции окружения хранят имена переменных и ссылки на секреты, а не значения; значения берутся из окружения при восстановлении. Completion receipt, peer receipt и team sync экспортируют только замаскированные поля. **Приёмка:** секрет с любым разрешённым именем не попадает в квитанцию, receipt и файлы sync.

### S05. Политика маски

**P1 · S.** Наследуемые значения (`PATH`, `HOME`, имена пользователей) маскируются только по явному признаку секрета, а не по наследованию. Минимальная длина маскируемого значения задана явно; секрет короче неё — ошибка конфигурации: `doctor` её называет, и запуск с ним блокируется, пока секрет не заменён или явно не принят как маскируемый вопреки длине. **Приёмка:** типичное наследуемое значение не портит служебных полей и не делает диагностику нечитаемой; короткий настоящий секрет не запускается молча; настоящий секрет маскируется.

### S06. Сырые артефакты и рабочие копии

**P2 · S.** Договор хранения байтов, которые проверка оставила: объявленные артефакты (отчёты, снимки), необъявленные файлы отчётов в рабочем дереве, сохранённые worktree и патчи продолжения. Каждый вид либо маскируется, либо хранится как есть с явной пометкой, только локально и без экспорта; evidence ссылается на hash. **Приёмка:** решение задокументировано для каждого вида и проверено тестом; артефакт с секретом либо замаскирован, либо помечен, не экспортируется и не попадает в подсказки агентам.

## 4. Порядок

1. S05 и S01 — политика маски и граница хранилища.
2. S02 — формы секрета в структурированных форматах.
3. S03 и S04 — артефакты исполнения, квитанции, экспорт.
4. S06 — договор для сырых артефактов.

Каждая работа проверяется корпусом форм секрета по всем местам сохранения, а не воспроизведением одного пути.
