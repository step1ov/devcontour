# Roadmap: срок фазы попытки после вывода `runTimeoutMs`

Дата: 9 ноября 2026 года.

Статус: setup одного репозитория выводит `runTimeoutMs` из оценки фазы
интеграции, `config-apply` применяет `gateTimeoutFloorMs` без перезапуска,
doctor предупреждает (`gates:timeout`), когда сумма сроков проверок больше
срока фазы. Ниже — два оставшихся пункта, каждый со своей приёмкой.

## 1. Движок: отдельный срок фаз проверок и вызовов моделей

`runTimeoutMs` сейчас ограничивает и фазы проверок попытки, и вызовы моделей
(исполнитель, ревьюер, планировщик), и срок ревью. Длинные проверки требуют
большого значения, и тогда зависший вызов модели прерывается так же поздно,
а учёт бюджета дольше считает вызов без владельца живым.

Приёмка:

- политика движка различает срок фазы проверок (prepare, gates, повтор,
  проверки потребителей) и срок вызова модели и ревью; прежний
  `runTimeoutMs` остаётся умолчанием обоих, прежние политики читаются без
  изменений;
- setup выводит срок фазы проверок из оценки, не трогая срок вызова модели;
- тест движка: долгий gate укладывается в свой срок, зависший вызов модели
  прерывается по своему, более короткому сроку.

## 2. Setup workspace из нескольких репозиториев выводит `runTimeoutMs`

Setup workspace из нескольких репозиториев берёт только наибольший
`runTimeoutMs` профилей и иначе пишет умолчание 15 минут. Совместные проверки
workspace и проверки базы идут под тем же сроком.

Приёмка:

- для каждого компонента — та же оценка, что у setup одного репозитория
  (шаги подготовки, сумма сроков gates с нижним пределом, повтор самого
  долгого gate), и отдельно для совместных проверок workspace; пишется
  наибольшее значение с запасом в тех же пределах;
- уже заданное значение конфигурации или профиля сохраняется, план называет
  значение и причину;
- unit-тест: компонент с долгими проверками и совместные проверки, каждый из
  которых определяет итог.
