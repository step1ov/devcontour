# Roadmap: остатки живого прогона быстрого изменения

Дата: 8 ноября 2026 года.

Статус: прогон небольшого изменения с вопросом исполнителя, обсуждением и
центром внимания прошёл до приёмки. Найденные дефекты исправлены; ниже —
пункты, оставленные тогда на потом, каждый со своей приёмкой. Все выполнены.

## 1. Попытка с вопросом не расходует лимит попыток — выполнено

Движок 0.1.0-alpha.38: остановка `needs-input` возвращает попытку в
`maxAttempts`, не трогая счётчик нейтральных сбоев; ответ на вопрос последней
попытки применяется `input_apply` без `reset` (описано в `START.md`,
`docs/agent-interface.md` и `docs/upgrade.md`). Тесты — тест движка «вопрос на
последней попытке» и `tests/input-flow.test.ts`.

## 2. Решения исполнителя видны оператору — выполнено

Блок «Решения исполнителя» (вопрос — выбор — обоснование — серьёзность, с
минимумами, которые её подняли) — у попытки в «Ходе попыток» карточки задачи и
в результате быстрого изменения. Данные — `assumptions` попытки в деталях
задачи, попытке и результате быстрого изменения (`src/application/assumptions.ts`,
описано в `docs/agent-interface.md` и `docs/ui-tour.md`). Учебный исполнитель
записывает развилки для задачи с маркером `[demo:assume]`. Тесты —
`tests/assumptions.test.ts` и `e2e/writer-decisions.spec.ts` (принятая попытка
показывает решения в карточке задачи, попытка без решений — без блока).

## 3. Следующий этап после принятой доски — выполнено

Отказ `task_create` на принятой доске называет следующий этап (`plan_import`
с `boardId`, CLI `import-plan --board`) и оставляет корректировку для
изменения принятого результата; описания операций в каталоге говорят то же.
Задачи `plan_import` привязываются к активному изменению так же, как задачи
`task_create` (закреплено тестом и описано). Вид быстрого изменения
показывает сводку всех задач изменения со статусом и этапом, шаги называют их
число. Тесты: unit (отказ, привязка, проекция и шаги), e2e сводки в
`quick-route.spec.ts`.

## 4. Мелочи эксплуатации — выполнено

- START: шаг `merge --ff-only devcontour/accepted` перед коммитом правок
  контекста, `context-lock` и `base-update`; тест
  `tests/start-context-commit.test.ts`.
- `stop --workspace` останавливает сервер workspace по записи
  `.devcontour-local/server.json`; сигнал — только серверу, который
  подтвердил pid и экземпляр через `GET /api/server`; описано в
  `docs/cli.md`, тест `tests/server-stop.test.ts`.
- `doctor` больше не сообщает ложное `budgets:applied` после одного
  `context-lock`: сервер запоминает digest ключей применённой конфигурации,
  `budgets:applied` — только при отличии `budgets`/`prices`, иначе
  `config:applied` с ключами; тест `tests/budget-doctor.test.ts`.
- `usage_report` без `repositoryId` — общий контур, в embedded вместе с
  единственным компонентом (итог одним запросом); ответ называет
  `scope.owners`, запись — `owner`; описано в `docs/metrics.md`, тест
  `tests/usage.test.ts`.
- `session-handoff --board` для черновой доски отказывает 409 с числом
  черновиков и шагом (пакет без `--board`, затем `review-plan`); описано в
  `docs/cli.md`, тест `tests/handoff.test.ts`.
- Очередь панели показывает задачу с открытым вопросом ожиданием, а не
  сбоем: `GET /api/queue` отдаёт блокер `input:<requestId>` и состояние
  вопроса, очередь «Хода работ» — значок ожидания, «Ждёт ответа» и следующий
  шаг; тесты `tests/input-progress.test.ts`, `e2e/input.spec.ts`.
