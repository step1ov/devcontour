# Обновление и откат DevContour

Документ описывает, какие версии состояния и общих записей читает DevContour,
как обновить установку или закреплённый движок исполнения и как откатиться.
Общие правила движка (версии, строгие схемы, сверка Git) — в
`node_modules/devcontour-harness/docs/upgrade.md`; здесь — продуктовая часть:
центральная база и базы компонентов, общие записи `.devcontour`, команды
DevContour.

## Что версионируется

| Что                                      | Где видно                                                                                                                                                          |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| DevContour                               | `devcontour --version` (версии DevContour и вложенного движка), `package.json`                                                                                     |
| Движок исполнения (`devcontour-harness`) | `vendor/harness/README.md`, `package-lock.json` (версия и integrity), `devcontour doctor`                                                                          |
| Состояние                                | центральная база `<workspace>/.devcontour-local/state.sqlite`; при `storage: component` — ещё база каждого компонента `<компонент>/.devcontour-local/state.sqlite` |
| Общие записи Git sync                    | каталог `.devcontour` в репозиториях workspace и компонентов (receipts принятых задач)                                                                             |

Каждая новая попытка хранит версию движка (`engineVersion`) и DevContour
(`consumerVersion`). Старые записи сохраняют то, что в них было; недостающие
сведения не дописываются.

0.4.0-alpha.2 поставляет движок `devcontour-harness` 0.1.0-alpha.3: роль
controller хранит версию движка, а `devcontour doctor` (проверка `engine`)
называет версии, записавшие состояние. 0.4.0-alpha.1 поставлял 0.1.0-alpha.1,
который этого поля не знает.

0.4.0-alpha.4…0.4.0-alpha.7 поставляют движок
0.1.0-alpha.4 (номер 0.4.0-alpha.3 не выпускался). Формат состояния
DevContour тот же, что у 0.4.0-alpha.2 (столбец «0.4.0-alpha.2…9»), с двумя
отличиями:

- активную попытку и совместную проверку ChangeSet продолжает только движок
  той версии, что их начал; попытка прежней версии (или без версии) с верным
  token до истечения срока получает отказ, продолжение — только истечением и
  recovery с новым владением;
- совместная проверка записывает версию движка. 0.4.0-alpha.2 и раньше это
  поле не читают и не проверяют, поэтому откат с идущей проверкой — только
  после остановки writers, как в разделе «Откат».

0.4.0-alpha.8 поставляет движок 0.1.0-alpha.13. С 0.1.0-alpha.6 в нём
протокол находок ревью кода: находка получает ID controller, повторное ревью называет состояние
каждой открытой (`closed`, `withdrawn`, `open`) с основанием, а ответ
reviewer вне протокола останавливает попытку классом `review-protocol`
(`REVIEW_PROTOCOL_INVALID`) без повтора writer. Протокол ведут живые codex и
claude и demo runtime; `AgentAdapter` без `reviewProtocol: 1` сохраняет
прежнюю приёмку (раунд `legacy`). Evidence ревью получает необязательные
`reviewRound` и `findings[].id/status`. Строгая схема 0.1.0-alpha.4 этих
полей не знает: после первого раунда ревью новой версией откат на
0.4.0-alpha.7 — только через копию, как в разделе «Откат».

С 0.1.0-alpha.7 итог `inspection` ревью кода учитывает команды, которые
reviewer действительно выполнил: новые значения `source`, `exitCode: null` и
необязательные поля. Прежние записи не пересчитываются; откат после ревью
новой версией — также только через копию. 0.1.0-alpha.8 формат состояния не
меняет. Сетевые отказы TLS/DNS (`EPROTO`, `ENOTFOUND`, `EAI_AGAIN` и другие)
движок относит к классу `environment` с одним автоматическим повтором и
`RUNTIME_UNAVAILABLE`; сохранённые прежние записи не переклассифицируются.
Файловая часть `setup` и проекции диагностики панели и агентского API
(корни цепочки, причины невыдачи, следующий шаг, причина остановки очереди)
вычисляются общими операциями движка; продуктовые причины и тексты остаются
у DevContour.

0.1.0-alpha.9 формат состояния не меняет. Общий запрос планирования, схема
draft плана и структурная проверка импорта (повтор ключа, неизвестная
зависимость, цикл) — операции движка. Продуктовые инструкции planner идут
отдельным блоком перед постановкой; JSON Schema плана и каталог агентского API
байтово прежние, порядок и коды отказов импорта прежние. Пустая постановка
теперь отклоняется до вызова модели.

0.1.0-alpha.10 формат состояния не меняет. Усечение строк ответов, байтовые
пределы транспорта, постраничная выдача контекста и отчётов, построитель
каталога агентского API и разрешение профилей стеков — операции движка.
Каталог (`/api/capabilities`, `devcontour capabilities`, digest каталога в
отчётах оценок), digest закреплённых профилей в `packs.lock.json` и тексты и
статусы отказов cursor прежние. Тексты отказов профилей — тексты движка;
профиль с `toolchain` по-прежнему отклоняется.

0.1.0-alpha.11 формат состояния не меняет. Профиль стека разбирается схемой
профиля DevContour: локальные профили прежней формы (роли с runtime `demo` и
`reviewVendor`, пакеты контекста с `revision`/`digest`, нестрогие вложенные
объекты) принимаются как раньше; путь отчёта JUnit по-прежнему обязан быть
относительным. Путь отчёта JUnit с символом конца строки (`\n`, `\r`, U+2028,
U+2029) больше не разрешается: повтор `setup` с таким профилем отказывает до
записи («Путь JUnit gate <id>: …»). Исправьте путь в профиле и повторите
setup.

0.1.0-alpha.12 и 0.1.0-alpha.13 формат состояния не меняют. alpha.12
добавляет skill установки движка, alpha.13 — локальные пакеты контекста
для задач коннектора; DevContour этих возможностей не использует. Корень
источника контекста через symlink движок теперь отклоняет как
`INVALID_INPUT` («Контекст не читается через symlink») вместо `NOT_READY`.

**Изменение прежних контрактов.** С 0.4.0-alpha.8 ревью контракта
применяет правило `verifiability`: контракт с вычислительными обещаниями
(точность, оптимальность, полнота, производительность) без структурного
`checks` отклоняется. Правило действует и для новой редакции контракта,
утверждённого раньше без `checks`: уже утверждённая редакция и привязанные к
ней задачи продолжают работать, но любое её изменение через `contract-change`
потребует полного договора проверки (gate `properties`, корпус, обязательства
по [check-contracts](check-contracts.md)). В 0.4.0-alpha.8 `--revise` не
перечитывает файл предложения: добавить `checks` к отклонённой операции можно
только отменой и новым стартом.

`harness doctor --state` открывает состояние только для чтения и не
становится его писателем. В 0.4.0-alpha.8 и раньше полный `devcontour doctor`
(без `--scope data`) открывал центральную базу как writer: переводил её в
режим WAL, создавал недостающие таблицы и строки (в базе 0.3.x — таблицу
`revision` с одной строкой), документ состояния и события не менял. Поэтому
предпроверка идёт на копии. Изменения 0.4.0-alpha.9 — в одноимённом
разделе ниже.

Попытки ранних версий, которые 0.3.x хранит как есть, записывают источник
продолжения (`continuedFrom.kind`) прежними формами: без поля или
`timeout` — продолжение черновика попытки, исчерпавшей время, `review` —
продолжение кандидата, отклонённого ревью. 0.4.0-alpha.8 читает их как
`unfinished` с классом отказа `timeout` и `candidate` с классом `review`
(записанный `reason` не заменяется), не переписывая записи в базе: запись
попытки без изменений сохраняет прежнюю форму. Прежде `doctor --scope data`
отклонял такое состояние как несовместимое.

С 0.4.0-alpha.8 `doctor --scope data` открывает базу в режиме WAL без файлов журнала (`-wal`,
`-shm`, `-journal`) как неизменяемую и не создаёт рядом с ней файлов; прежде
соединение только для чтения с такой базой создавало `-wal` и `-shm`. Есть
файлы журнала — база читается с ними, они не трогаются. База в режиме DELETE
(хранение компонентов) читается обычным соединением с блокировками: файлов
оно не создаёт. Появились файлы журнала или изменился файл базы за время
проверки — базу менял writer, итог несовместим (`storage-quiet`): остановите
writers и повторите проверку.

### 0.4.0-alpha.9

0.4.0-alpha.9 поставляет движок `devcontour-harness` 0.1.0-alpha.16 —
локально собранный архив `vendor/harness/devcontour-harness-0.1.0-alpha.16.tgz`
(SHA-256 `f4c394d621588665f3ff15cf0f919edfe310df5defd5c0a24bd5d3e63ad120d8`),
в npm ещё не опубликован. 0.1.0-alpha.14 и 0.1.0-alpha.15 не выпускались.
Формат состояния прежний.

- **Эталонные наборы в договоре проверки.** Договор
  проверки (`checks`) принимает необязательные поля обязательства `gates`,
  `verification` и `reference` — сверку с закреплёнными эталонными наборами
  ([договор проверки](check-contracts.md#эталонные-наборы-verification-reference)) —
  и `crossChecks[].artifacts`. Контракты без них разбираются, проверяются и
  дают тот же digest контракта, манифест gate и основание корпуса. Контракт с
  новыми полями 0.4.0-alpha.8 и раньше не читают (строгая схема движка
  0.1.0-alpha.13): после ревью такого контракта откат — только через копию,
  как в разделе «Откат». `checks_view` добавляет к свойству задачи `gates` и
  `verification`. Изменение отказа: обязательство без `reference` на gate
  без `property` теперь отклоняется при любом обещании (прежде — только
  вычислительное), а кандидат, чей изменённый код называет строковым литералом файл эталонного
  набора, — до gates (`scope-violation`). ID testcase node:test —
  `test.<имя>`: отказ «testcase X отсутствует в JUnit» называет найденный ID.
  Ревью контракта считает перекрёстную проверку без закреплённых
  `artifacts` непроверенным утверждением автора.
- **Закрепление контракта.** Предложение контракта (`review-contract`, `contract-change`)
  с закреплённым JS/TS-артефактом, который импортирует незакреплённый и
  незащищённый локальный файл, отклоняется до ревью с перечнем путей; приёмка,
  импортирующая реализацию, перечисляет её файлы (не каталоги) в новом поле `underTest`. Предложения,
  которые проходили прежде, могут потребовать `underTest` или дополнительных
  `artifacts`/`protectedPaths`. Утверждённые контракты не отзываются: `doctor`
  называет неполное закрепление проверкой `contract-closure:<id>:<компонент>`
  (`not-checked`, готовность не снимает). Контракт с
  `underTest` хранит это поле, и его запись Git sync (`kind: contract`) не
  принимают 0.4.0-alpha.8 и раньше — откат после такого утверждения только
  через копию.
- **`devcontour --version`** (и `devcontour version`) печатает версию
  DevContour и версию вложенного `devcontour-harness`. В установке из архива
  `npm ls devcontour` для этого не годится: вложенная `file:`-зависимость
  движка помечается `invalid`, и команда завершается с `ELSPROBLEMS`. Справка
  установленного пакета называет его бинарник (`devcontour`, в каталоге
  установки — `npx devcontour`), а не `npm run devcontour` checkout.
- **Полный `devcontour doctor`** открывает базы только для чтения, как
  `doctor --scope data`: без режима журнала, DDL, начальных строк и владельца
  баз компонентов. Таблицы и строки, которых нет в базе прежней версии,
  создаёт первый writer (`serve`, `run`). Записывает doctor только свой отчёт
  `doctor.json` в каталоге данных. `doctor --probe` пишет больше: временный
  worktree и журналы preflight в `<данные>/doctor/<id>`, квитанции окружения
  и lease ресурсов в базе ресурсов (`resourceDatabase`, по умолчанию
  `~/.devcontour-local/resources.sqlite`). Состояние workflow он не меняет.
  Базы компонента ещё нет — doctor её не создаёт: проверка `state` получает
  `not-checked`, а роль controller, попытки и контракты без владельца-компонента
  читаются из центральной базы: проверка `engine` выполняется (роль другой
  версии движка — `blocked`), закрепление этих контрактов проверяется, а
  непрочитанные контракты названы проверкой `contract-closure:unread`
  (`not-checked`). Если
  writer пишет во время неизменяемого чтения, doctor перечитывает состояние.
- **`scripts/copy-precheck.mjs`**:
  - сравнивает только входы `doctor --scope data` (поле `compared` отчёта):
    каталог данных workspace, `.devcontour-local` каждого репозитория
    конфигурации, файлы конфигурации компонентов (`configFile`), профили из
    репозиториев (`packs[].source`), `devcontour.workspace.json` и HEAD (ветку
    и коммит) workspace и каждого репозитория. Сверяются оригинал с копией до
    проверки и оригинал и копия до и после неё. Копируется по-прежнему весь
    `R`. Прочая работа Git (worktrees, index, рабочие файлы) проверку не валит.
    Неподвижны должны быть writers базы, конфигурация компонентов и HEAD;
  - при расхождении называет пути, не больше 20, и число остальных;
  - до копирования сверяет свободное место во временном каталоге (`TMPDIR`)
    с размером `R` и отказывает, если его не хватает;
  - при любом отказе и при SIGINT/SIGTERM удаляет свою временную копию, даже
    с `--keep` (копирование и контейнер идут асинхронно, сигнал обрабатывается
    сразу; код выхода 130/143). Контейнер запускается с `--init` и именем
    `dc-copy-precheck-<токен>`; при сигнале скрипт сначала удаляет его
    (`docker rm -f`, не дольше 30 с), затем копию. Копию оставляет только завершённая проверка с
    `--keep`. Удаляется лишь каталог `$TMPDIR/dc-copy-precheck-*`, в котором
    лежит метка с токеном этого запуска;
  - запускает контейнер от пользователя хоста (`--user uid:gid`): файлы,
    созданные в копии, удаляются без root. Если удалить копию всё же не
    удалось (`EACCES`), скрипт называет каталог и причину;
  - передаёт пути в контейнер аргументами, а не подстановкой в текст
    скрипта; `R`, каталог архива или `TMPDIR` с «:» отклоняются до
    копирования (`docker run -v` делит значение по двоеточию);
  - содержимое баз читает с отдельной временной копии. Копия, которую
    получает контейнер, побайтно совпадает с оригиналом: файлов `-wal` и
    `-shm` рядом с базой WAL нет. Так проверка действительно идёт путём
    неизменяемого чтения, а `copyChanged` у совместимых данных пуст.
- **Правила ревью в `workspace.json`.** `workspace.json` принимает поле `review` (правила ревью кода, плана и
  контракта), и `workspace-init --file` переносит его в `config.json`, до
  записи проверив его загрузчиком сервера. Реестр без `review` выбор в
  `config.json` не меняет. Виды ревью переносятся по отдельности: объявленный
  `code` не стирает `plan` и `contract` из `config.json`. Ручная правка
  `config.json` для смены ревьюеров больше не нужна. Объявление `review`
  применяет только тот же `workspace-init`, а при единственном компоненте он
  заодно обновляет устаревшие копии ролей (ниже, «Действующие gates
  компонента»). Поэтому первый такой запуск после обновления может сделать
  утверждённые графы устаревшими (`APPROVAL_STALE`, «Повторное
  согласование»), даже если правила ревью совпадают с `config.json`.
  Применить одно `review`, не обновив копии ролей, нельзя: выполняйте этот
  `workspace-init` до операции, которая держит утверждённые задачи, или
  вместе с её пересмотром, чтобы ревью плана согласовало граф уже по новому
  digest.
- **Действующие gates компонента.** При списке репозиториев верхнеуровневые `gates` и `protectedPaths` берутся
  из первого компонента, а не из копии в `config.json`. Панель и `doctor`
  показывают действующий список. Если копия устарела, digest загруженной
  конфигурации меняется, и штатный перезапуск после обновления его применяет.
  Первый `workspace-init` после обновления может ответить
  `declaration-updated`: он обновит устаревшие копии gates, `protectedPaths`
  и, при единственном компоненте, ролей.
- **Повторное согласование.** Верхнеуровневые роли и `review` входят в digest политики исполнения
  (`executionDigest`). Если при единственном компоненте `workspace-init`
  переписал копии ролей (или изменились правила ревью), каждый утверждённый
  граф получает `APPROVAL_STALE` («согласуйте заново»): утверждённые планы
  нужно согласовать повторно. Действующие привязки ролей при этом прежние.
- **`degraded` в `doctor`.** `doctor` отмечает claude-ревьюера без профиля инструментов статусом
  `degraded` и называет исправление (профиль `claude-review` с `Bash`).
  `ready` этот статус не снимает.
- **Пересмотр по исправленному предложению.** `contract-change --id ID
--revise --expected-version N --file FILE` (агентский API —
  `contract_change_revise` с `proposal`) берёт исправленное предложение того
  же контракта (`checks`, `artifacts`, `underTest`, текст) с предпроверками
  старта до вызова модели и сохраняет операцию, удержания и историю;
  `revisions[].proposal` — digest прежнего предложения. Файл, `title`,
  `repositoryId` в записанном виде и компонент должны совпадать с операцией.
  Каталог агентского API меняется только этим полем.
- **Предупреждение о договоре проверки.** Предложение без `checks` получает
  до вызова модели предупреждение `checks-missing` (`warnings` в
  `contract-impact` и при старте операции, строка `Предупреждение:` в
  stderr); `contract-impact` показывает его рядом с `closure.refusal`, а
  такой отказ по-прежнему останавливает старт и пересмотр до ревью.
- **Код выхода `contract-change`** — 1 при `failed` и `stale`.
- **Удержание в прогрессе.** Удержание операции видно в `progress.reasons`
  (`held_by_operation`, поле `progress.hold`).
- **История операции.** `history[].detail` и `error` сокращаются по границе
  фразы или слова; запись ревью ссылается на свою попытку полем `review`,
  а ревью связываются с операцией по каталогу решения (`reviews`), а не по
  названию. Записи истории прежних операций не пересчитываются.

### 0.4.0-alpha.10

0.4.0-alpha.10 поставляет тот же движок `devcontour-harness` 0.1.0-alpha.16 —
архив `vendor/harness/devcontour-harness-0.1.0-alpha.16.tgz` с прежним
SHA-256 `f4c394d621588665f3ff15cf0f919edfe310df5defd5c0a24bd5d3e63ad120d8`.
Исходники движка опубликованы на GitHub с тегом `v0.1.0-alpha.16`; в npm он
пока не опубликован. Формат состояния меняется: 0.4.0-alpha.10 — первая
версия, которая хранит роль controller отдельной строкой и пишет в документ
метку `heldInRow` (строки «состояние 0.4.0-alpha.10» в разделе
«Совместимость»).

- **Роль controller — отдельной строкой.** Роль хранится в таблице
  `controller` центральной базы (coordinator), а не в документе состояния:
  её продление на каждом такте очереди больше не переписывает документ.
  Таблицу создаёт первая запись роли; роль, записанная прежней версией в
  документ, читается как прежде и при первой смене переносится в строку.
  Прежние версии строку не читают, поэтому, пока роль держит процесс этой
  версии, в документе лежит её метка — запись роли с полем `heldInRow`.
  Строгая схема прежних версий это поле отклоняет: прежняя версия не
  перенимает роль и не выдаёт работу (`run` завершается с кодом 1 на
  неизвестном поле, `serve` пишет `scheduler.error`). Но управление паузой
  и события ошибок проходят: прежний `queue --pause|--start` меняет документ
  и журнал, прежний `run` до отказа записывает снятие паузы (возобновит
  очередь работающего controller новой версии), прежний `serve` меняет
  флаг паузы и пишет событие ошибки. Не запускайте прежние CLI против
  состояния, роль в котором держит эта версия. Метку пишут только получение
  и снятие роли: после штатной остановки её нет, и прежняя версия работает с
  базой как обычно. После аварийной остановки метка остаётся, и прежние
  версии отказывают в роли, пока эта версия не будет запущена и остановлена
  штатно (или пока не восстановлена копия, раздел «Откат»).
- **Такт без изменений.** Работающий `serve` на паузе разбирает документ один
  раз на версию данных и не пишет ничего, кроме продления роли.
- **Попытки без версии движка в `doctor`.** Проверка `engine` больше не
  сообщает об отсутствии попыток, когда их записали версии, не хранившие
  версию движка: она называет число попыток, записавшие их версии и сколько
  попыток без версии.
- **`--version` и `help` без предупреждения.** `devcontour --version` и
  `devcontour help` больше не открывают `node:sqlite` и не печатают в stderr
  его `ExperimentalWarning`.

Неизвестная версия документа состояния или поле, которого строгая схема
движка не знает, отклоняются до любой записи. Проверка — тесты
`tests/harness-versions.test.ts` и `tests/harness-legacy.test.ts`; сценарии
обновления и отката — `npm run check:upgrade` (ниже).

### 0.4.0-alpha.11

0.4.0-alpha.11 поставляет движок `devcontour-harness` 0.1.0-alpha.17 —
архив `vendor/harness/devcontour-harness-0.1.0-alpha.17.tgz` с SHA-256
`09ebf5ba72ff0c988e550d5fc47e3d45f32d17c3596677c05dd25472b8f854ae`.
Исходники движка опубликованы на GitHub с тегом `v0.1.0-alpha.17`; в npm он
пока не опубликован. Формат состояния меняется: движок добавляет
необязательные поля и классы отказа, DevContour — закрепление политики
утверждения (`approvedPolicy`) и локальную запись проверки доски
(`board-coverage`). Что с ними делают прежние версии — строка «состояние
0.4.0-alpha.11» в разделе «Совместимость»; после первой записи откат — только
через копию, как в разделе «Откат».

- **Движок 0.1.0-alpha.17.** Попытка, прерванная штатной остановкой,
  получает `interrupted: shutdown`, а её задача возвращается в очередь без
  траты попытки; отказы окружения, провайдера и истёкшее владение попытку не
  засчитывают, у них свой предел (`neutralFailures`, три на задачу).
  Отклонённая ревью попытка несёт `inputClasses` и пары `classified`,
  воспроизведение — `inputClass`; два отказа ревью подряд по одному свойству
  и классу останавливают задачу как пробел приёмки. `completed: false`
  исполнителя — класс `unfinished` с повтором от черновика. Пустой результат
  принимается только с подтверждением ревью и механическим основанием
  (`alreadySatisfied` в evidence), иначе — класс `needs-lead`. Тесты и
  сценарии, ждавшие засчитанной попытки после обрыва окружения или `failed`
  после штатной остановки, ведут себя иначе.
- **Автоматическая перемотка базы.** Отставшая база прогонов, когда это
  fast-forward продуктовых коммитов, перематывается диспетчером сам и встаёт
  на ожидание `base-check`; коммиты, задевающие приёмку и настройку контура,
  по-прежнему требуют `base-update` (D42, [операции](operations.md)).
- **Перемотка и защищённые пути.** Каталог контура (`.devcontour/` и другие
  защищённые префиксы), закоммиченный ссылкой (symlink или gitlink), в diff
  виден без завершающей `/` и тоже останавливает автоматическую перемотку.
- **Проверка доски вне областей задач.** Приёмка доски выполняет gates, не
  вошедшие в область ни одной задачи, один раз на её итоговом SHA в каждом
  компоненте (D44). `review-plan` и `workflow_start` заранее возвращают
  `coverageGaps` с предупреждением, регистрацию это не останавливает.
  Evidence пишется в локальную запись `board-coverage`, привязанную к SHA,
  digest политики компонента и ревизии доски; приёмка учитывает запись,
  только если совпадают все три. Провал gate — отказ приёмки с его именем;
  прошедшие gates повтор после частичного провала не перезапускает.
- **Расход по всему потоку.** Продуктовые вызовы моделей (планирование,
  оценки, recovery) считают расход и модель по всему stdout, а не по его
  последним 2 МБ: стоимость длинного вызова больше не выпадает из итогов.
  `runtime.json` хранит разобранный расход; строка длиннее 8 МБ отмечает
  расход неполным.
- **Класс ввода ревьюера.** Собственная схема ответа ревью DevContour
  требует `reproduction.inputClass` (допускается `null`); ответы без поля
  по-прежнему разбираются.
- **Такт без выдачи.** Такт без работы на большой доске не перечитывает
  документ состояния по каждой задаче: digest контракта берётся из уже
  прочитанного состояния, попытки разбираются один раз на версию данных.
- **Пределы предложения контракта.** Пределы прежние (`artifacts` — до 50,
  `purpose` — до 200 знаков, `underTest` — до 50 путей), но теперь они
  описаны в [cli](cli.md) («Пределы предложения»). `contract-impact`
  показывает превышения в `limits` рядом с `closure`, а не падает с массивом
  zod. `review-contract` и `contract-change` отказывают сообщением, где
  названы предел, элементы, величина превышения и способы исправления.
- **Верхнеуровневый `reviewer` при единственном компоненте.** Если
  компонент объявляет своего `reviewer`, `workspace-init` обновляет и
  верхнеуровневую копию в `config.json`, как копии ролей. Первый запуск после
  обновления может ответить `declaration-updated`. Копия входит в политику
  исполнения, поэтому её обновление делает вход задания доски устаревшим
  (ниже).
- **Утверждение плана закрепляет политику исполнения.** Утверждение задачи
  записывает `approvedPolicy` — digest утверждаемой части политики
  исполнения (gates, роли и области записи, ревьюеры и правила вендора,
  защищённые пути, окружение, изоляция). Граф с устаревшим закреплением
  проецируется с ним. Эксплуатационные пределы (параллельность, сроки,
  попытки, бюджеты) повторного утверждения не требуют. Раньше граф всегда
  получал текущий digest, и смена gate, правила вендора ревью или области
  записи применялась к утверждённому плану без повторного ревью. Теперь
  задача, утверждённая при другой политике, не выдаётся: `eligible` ложно,
  `progress.reasons` называет `approval_stale`, а `progress.approvalStale`
  подсказывает `review-plan --board ID`. `review-plan` такую доску не
  считает `already-approved`: план проходит ревью и закрепляет новую
  политику. Утверждения прежних версий без поля закрепляются за действующей
  политикой на первом такте controller после обновления, массового
  повторного утверждения нет. Поле локальное и при синхронизации не
  переносится. Решение — D43 в [decisions](decisions.md).
  Сначала обновите DevContour и запустите controller, а политику исполнения
  меняйте после первого такта. Обновление и смену политики одновременно не
  делайте: правка, применённая до первого такта, закрепится за прежними
  утверждениями без повторного ревью. Утверждение, полученное от другого
  клона, закрепляется за локальной политикой так же (известный пробел, D43).
- **Устаревшее задание доски видно на паузе.** Задание доски с изменившимся
  входом очередь заданий отмечает `stale` только при следующем взятии
  стадии. Теперь оно видно сразу: `workflows[].inputStale` и
  `progress.workflowStale` у задач доски. Выдачу это сведение не держит, а
  новое задание доски (`workflow_start`) снимает его и на паузе.
- **Команды без предупреждения SQLite.** CLI отсекает только
  `ExperimentalWarning` о SQLite: `doctor --scope data`, `contract-*` и
  другие команды больше не печатают его в stderr. Остальные предупреждения
  node выводит как прежде.

- **Шире область gates задачи.** Задача может назвать до 100 gates (предел
  профиля, `GATE_SCOPE_LIMIT` движка) вместо 20; неверный план отклоняется с
  понятной причиной.
- **Проверка перенесённой базы в режиме агента.** В `approvalMode: "agent"`
  ожидание `base-check` снимает цикл board workflow: весь профиль gates
  каждого компонента на новой базе. Перенос, задевший чувствительные пути,
  автоматически не снимается (D42).
- **Покрытие выпуска без отменённых задач.** Отменённые и заменённые задачи
  не входят в покрытие выпуска.
- **Поле состояния `baseMoves`.** Пока очередь ждёт `base-check`, рядом с
  ожиданием хранится непроверенный диапазон переноса каждого компонента
  (`{at, bases: [{repositoryId, from, to}]}`, `at` — время постановки
  ожидания). Снятие ожидания удаляет поле. Прежняя версия после отката поле
  не трогает; ожидание, поставленное ею, новая версия по чужому диапазону не
  снимает и оставляет решению человека (`queue --start`).
- **Поле `tries` локальной записи `base-check`.** Число прогонов базы под
  этим договором; запись без поля читается как один прогон.
- **События `base.check.held` и `retry`.** `base.check.held` называет
  чувствительные пути переноса, который автоматическая проверка базы не
  снимает. `base.check.started` повторного прогона получает поле `retry`
  (номер повтора).
- **Установка зависимостей в песочнице.** Каталоги IDE (`.idea`, `.vscode`)
  внутри `node_modules` открыты для записи, прочие обязательные запреты
  песочницы действуют на весь checkout (D45). `doctor --probe` проверяет
  установку в песочнице (`isolation:install`).
- **Git хоста над checkout.** Снимки зависимостей и checkout ревью DevContour
  сверяет теми же правилами, что и движок (`hostGitArgs` движка, своя копия
  удалена): изменённый файл `.git`, перенаправление `commondir`/`gitdir` и
  вложенный репозиторий — отказ «Git на хосте не запущен»; поверх —
  `core.fsmonitor=false`, `core.hooksPath=/dev/null`,
  `protocol.ext.allow=never` и `GIT_CONFIG_NOSYSTEM=1`.
- **Потомок проверки не переживает её при любой локали.** Отсоединившегося
  потомка с очищенным окружением DevContour и движок находят по текущему
  каталогу внутри каталогов проверки и отсекают процессы старше команды по
  времени старта из `ps`. В `ru_RU.UTF-8` `ps` печатал дату по-русски,
  `Date.parse` её не читал, и потомок оставался жить. Теперь `ps`, `lsof` и
  `sysctl` запускаются с `LC_TIME`, `LC_NUMERIC` и `LC_MESSAGES` в локали C;

  `LC_CTYPE`), а экранирование путей `lsof` в локали C снимается — каталог с
  кириллицей в пути узнаётся. Процесс в каталогах проверки с нечитаемым
  временем старта останавливается; не останавливается только процесс, точно
  старше команды, и процесс, которого нет в снимке таблицы процессов (сам
  `lsof`).
- **Сверка защищённых путей и класс отказа.** Новое или изменённое
  защищённое имя после gate или работы исполнителя — `scope-violation`.
  Отказ песочницы — класс `environment` только по журналу ядра macOS; текст
  EPERM в выводе и любой отказ на Linux остаются `gate`.
- **Известные пробелы.** Регрессионные тесты в настоящей песочнице для
  запретов `.git`, для сверки защищённых путей после переноса каталога и для
  отказа по пределу перечисления не написаны (решение владельца проекта).
  Запреты на Linux и запуск/остановка наблюдения за журналом ядра тестами не
  покрыты; поэтому два мутанта этих путей (D1, D2) выживают.

  деревья остаются в каталоге состояния, а `doctor` помечает `checkouts`
  как `degraded` с причиной (EPERM для инструментов, ищущих конфигурацию
  вверх по дереву, тогда остаётся) — задайте `checkoutRoot` на томе
  репозитория.

  `.devcontour-local`, остаются там и убираются как раньше: по пути,
  записанному в попытке, при очистке окружения и через
  `git worktree remove`/`prune`. Новые попытки создают деревья под новым
  корнем.
- **Миграция.** Не меняйте корень (`checkoutRoot`, перенос каталога
  данных workspace, смену тома кэша) между падением процесса и очисткой
  прерванной попытки: окружение под прежним корнем очистка не трогает и

- **Движок 0.1.0-alpha.22: защищённые пути строже.** Имена защищённых путей

- **Доказательство продуктового релиза закрепляет только свои задачи.**
  `stateDigest` в `productRelease` проверки ChangeSet считается по задачам
  выбранных досок и задачам историй релиза из расчёта покрытия (связанные,
  привязанные `task_story` и исключённые), только по полям, которые читают
  покрытие и приёмка (статус, digest постановки и утверждения, `resultSha`,

  проверка». Новая задача истории или выбранной доски, её результат, связи и

  релиза без связи со своей историей: она входит в историю как неназначенный
  вклад и после отмены остаётся в отчёте исключённой — проверку нужно
  повторить и тогда. Задача, назначенная истории другого релиза, проверку не
  снимает. Подробности — «Обязательная приёмка продуктового релиза» в
  `docs/product-map.md`.
- **Совместимость.** Доказательства, записанные прежней версией, хранят digest
  прежнего вида: после обновления их проверка один раз завершится тем же
  отказом «нужна новая проверка». Повторите проверку ChangeSet релиза
  (`workspace_verify` или задание `changeset`); формат состояния не меняется.

## Перед обновлением

1. **Остановить записывающих.** `devcontour queue --pause --workspace W`,
   дождаться завершения активных попыток и проверок ChangeSet, затем
   остановить сервер (`devcontour serve`), workflow, MCP-клиентов и всех, кто
   пишет в базу. Одной паузы очереди недостаточно: workflow и сервер
   продолжают писать.
2. **Зафиксировать.** Версию установки (`devcontour --version`; до 0.4.0-alpha.8
   включительно команды нет — версия в `node_modules/devcontour/package.json`),
   `devcontour doctor --workspace W`
   (проверка `engine` называет версию движка, роль controller и версии,
   записавшие попытки), вершины target ref каждого репозитория
   (`git rev-parse main`), незакоммиченные изменения компонентов, состояние
   Git sync.
3. **Сделать копию.**
   - `storage: central` — `devcontour backup --out FILE --workspace W`
     (согласованная копия SQLite);
   - `storage: component` — копия **всех** баз: центральной и каждого
     компонента, вместе с файлами `-wal`/`-shm`, при остановленных writers.
     Команда `backup` копирует одну базу и этого не обеспечивает.
   - Git-объекты должны оставаться доступными: копия базы без коммитов, на
     которые она ссылается, историю не восстанавливает.
4. **Проверить совместимость данных на копии.** Конфигурация и базы хранят
   абсолютные пути (workspace, репозитории, владелец базы компонента),
   поэтому копия в другом каталоге — уже другой workspace:
   `doctor --workspace <копия>` отказывает («Конфигурация не принадлежит
   выбранному workspace»), а перенос путей, повторный `setup` или правка
   владельца базы проверку не заменяют. Копию проверяют в изолированном
   контейнере, где она смонтирована по тем же абсолютным путям, что оригинал,
   а сам оригинал не смонтирован. Скрипт поставляется не в архиве, а в
   исходниках: запускайте его из checkout той версии DevContour, архив
   которой проверяете:

   ```sh
   git clone <репозиторий DevContour> dc && cd dc && git checkout <тег или SHA версии>
   node scripts/copy-precheck.mjs --root R --workspace W --archive devcontour-<версия>.tgz
   ```

   `R` — общий каталог, внутри которого лежат workspace и все репозитории
   его конфигурации (иначе скрипт отказывает и называет пути вне `R`). Скрипт
   проверяет, что во временном каталоге (`TMPDIR`) хватит места на копию `R`,
   копирует `R` целиком (Git-объекты, базы всех компонентов вместе с
   `-wal`/`-shm`), ставит архив новой версии в контейнер Docker (нужны Docker
   и доступ к образу `node:24.3.0-bookworm`) и выполняет в нём
   `devcontour doctor --scope data` над копией. Сравниваются только входы
   проверки данных (каталоги данных, конфигурация компонентов, профили из
   репозиториев, `devcontour.workspace.json`, HEAD репозиториев): во время
   проверки должны стоять writers базы, а прочая работа Git в `R` (worktrees,
   index) итог не меняет. При отказе скрипт называет расходящиеся пути и
   удаляет свою копию.

   Это **проверка совместимости данных**, а не готовности среды: проверяются
   конфигурация штатного загрузчика и её принадлежность workspace, владение
   баз компонентов, версия каждого исходного документа (центральной базы или
   coordinator и каждой базы компонента), версия движка и роль controller,
   документ исполнения строгими схемами движка. Начиная с 0.4.0-alpha.6
   каждая база открывается только для чтения: проверка не запускает проекции
   и журнал, не создаёт баз и таблиц и не присваивает владельца; отсутствующая
   база или база компонента без владельца — отказ. С 0.4.0-alpha.7 версия
   каждого документа базы компонента проверяется и у пустого workspace, где
   coordinator ещё не записал реестр компонентов, — при любом чтении и до
   любой записи. Модели, CLI агентов, песочница и live-проверки в
   контейнере не проверяются — их нет в образе, и их отсутствие не делает
   данные несовместимыми. Итог — JSON: `scope: "data-compatibility"`, код
   выхода проверки данных (`dataCheckExit`, 0 — данные совместимы),
   `compared` (сравниваемые каталоги данных), `originalUnchanged` (их
   отпечаток в оригинале до и после), `copyChanged` (какие файлы этих
   каталогов в копии изменились, например перевод базы с журналом DELETE в
   WAL) и
   `copyDataChanged` (базы, у которых изменилось содержимое таблиц; ожидается
   пусто). Проверка несовместимой версии не меняет данные.

## Обновление

- **Установка DevContour** — новый архив: `npm install --omit=dev
--ignore-scripts ./devcontour-<version>.tgz` (движок вложен в архив).
- **Смена закреплённого движка в checkout DevContour** —
  `node scripts/vendor-harness.mjs ./devcontour-harness-<version>.tgz --commit <SHA исходников>`,
  затем `npm ci` и `npm run check`. Меняются только `package.json`,
  `package-lock.json` и `vendor/harness`; пакет сам не обновляется.

После обновления — **обязательно полный** `devcontour doctor --workspace W`
на хосте, до возобновления writers: это проверка среды (CLI агентов,
песочница, роли, профили), которую проверка данных на копии не заменяет.
Только при `ready: true` — запуск **одного** controller (`devcontour serve` или `devcontour run`). Попытки, активные во
время остановки, со старыми токенами не продолжаются: живую роль controller
процесса другой версии новая версия не перенимает; после истечения роли
попытка завершается явно, и задача ждёт явного повтора
(`devcontour retry --task T`) — новая попытка получает новое владение и новые
проверки. Установка не меняет профиль, закрепления контекста, инструкции
агентам и принятые результаты.

## Откат

| Ситуация                                                                                             | Действие                                                                                                                                  |
| ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Только движок, формат совместим (новая версия остановлена штатно, роль снята)                        | Остановить writers → вернуть прежние `package.json`, `package-lock.json`, `vendor/harness` → `npm ci` → `devcontour doctor` → возобновить |
| Новая версия изменила формат (например, роль controller с `engineVersion` после аварийной остановки) | Прежняя версия отказывает до записи. Остановить writers → восстановить копию всех баз вместе с совместимой версией → сверить Git (ниже)   |
| DevContour откатывается к версии без `gateIdentity` после Git sync новой версии                      | Ниже, «Откат после Git sync»                                                                                                              |

### Сверка Git после восстановления копии

База и Git не образуют одну транзакцию. Если после копии новая версия
приняла задачу, target ref продвинут, а восстановленная база об этом не
знает.

1. Для каждого репозитория найдите коммиты работы, не покрытые принятыми
   задачами восстановленной базы:
   `git rev-list main ^<result SHA каждой принятой задачи> -- . ':(exclude).devcontour'`.
2. Каждый такой коммит — принятие, выполненное вне восстановленного
   состояния. Его нельзя молча «забыть»: повторите задачу новой попыткой
   (`devcontour retry`/обычная очередь — её интеграция продолжит текущий
   target ref) либо явно задокументируйте это принятие.
3. Не выполняйте `git reset --hard` и не переписывайте target ref ради
   совпадения с базой — это не откат, а потеря принятой работы.

Откат успешен, только когда каждый коммит работы на target ref учтён
принятой задачей восстановленного состояния.

### Откат после Git sync новой версии

Начиная с 0.4.0-alpha.1 receipt принятой задачи содержит необязательное поле
`gateIdentity` (тождество проверок, по которым задача принята). Версии до
этого поля отклоняют такой receipt: Git sync прежней версии останавливается,
ничего не записав.

Варианты:

- **оставить всю команду на новой версии** — receipts прежних версий она
  читает;
- **откатиться**: остановить writers → восстановить копию баз, сделанную до
  обновления → в каждом репозитории сделать `git revert` коммитов
  `.devcontour`, выпущенных новой версией (историю не переписывать) → Git
  sync прежней версией → сверка Git (выше): задачи, принятые новой версией
  после копии, повторяются прежней версией.

## Проверка процедур

На копии этого checkout во временном каталоге, без моделей и реальных
workspace:

```bash
# обновление закреплённого движка (T40/T41)
npm run check:upgrade -- ./devcontour-harness-<from>.tgz ./devcontour-harness-<to>.tgz --to-commit <SHA to>
# если checkout закреплён не на <from> — добавьте --from-commit <SHA from>
# прерванное обновление, откат пакета, восстановление копии, откат DevContour (T42)
npm run check:upgrade -- ./devcontour-harness-<from>.tgz ./devcontour-harness-<to>.tgz --to-commit <SHA to> \
  --rollback --baseline-commit <SHA прежней версии DevContour>
```

T42 выполняется в обеих топологиях хранения на настоящих Git-репозиториях:
прерванная установка не трогает базы и refs, первое открытие новой версией
ничего не переписывает; откат только движка продолжает работу; после
аварийной остановки новой версии прежняя отказывает до записи, копия
восстанавливается, сверка Git называет принятие, о котором копия не знает,
и успех объявляется только после повторной попытки; откат DevContour после
Git sync новой версии проходит через копию баз и `git revert` общих записей.

### Обновление DevContour вместе с движком

Режим выше закрепляет оба движка под одними исходниками DevContour и годится
только для смены одной зависимости. Когда меняются и исходники DevContour
(новые imports движка), каждая сторона проверяется своим source snapshot:

```bash
npm run check:upgrade -- ./devcontour-harness-<from>.tgz ./devcontour-harness-<to>.tgz \
  --from-commit <SHA исходников from> --to-commit <SHA исходников to> \
  --from-devcontour-commit <полный SHA DevContour «до»> \
  --to-devcontour-commit <полный SHA DevContour «после»> \
  [--to-worktree] [--out <manifest.json>]
```

Оба snapshot — клоны этого репозитория во временном каталоге на указанных
SHA; ветка, HEAD и index checkout не меняются. Каждый snapshot обязан сам
поставлять свой архив (зависимость, lock, integrity, байты в
`vendor/harness` и строка `vendor/harness/README.md` с SHA-256 архива и
commit исходников движка) и ставит только свой lock: прежний движок под
новые исходники не ставится. `--to-worktree` (когда
`--to-devcontour-commit` — HEAD checkout) переносит в snapshot «после»
незакоммиченные изменения и сверяет их байты. Fixture создаёт DevContour
«до» своим движком: живая роль и активная попытка, принятые задачи с
настоящими коммитами и receipts Git sync в топологиях central и component.
DevContour «после» не перенимает живую роль, после истечения продолжает с
новым владением, открывает состояние без перезаписи баз, сохраняет историю,
SHA и прежние receipts и продолжает цепочку задач; прежний DevContour над
живой ролью новой версии не пишет и не выдаёт работу. Fingerprints обеих
сторон (commit, tree, digest `git ls-tree -r`, архив и его commit) — в
`upgrade-check.json` и `--out`.
