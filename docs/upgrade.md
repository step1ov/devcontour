# Обновление и откат DevContour

Документ описывает, какие версии состояния и общих записей читает DevContour,
как обновить установку или закреплённый движок исполнения и как откатиться.
Общие правила движка (версии, строгие схемы, сверка Git) — в
`node_modules/devcontour-harness/docs/upgrade.md`; здесь — продуктовая часть:
центральная база и базы компонентов, общие записи `.devcontour`, команды
DevContour.

## Что версионируется

| Что                                      | Где видно                                                                                                                                                          |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| DevContour                               | `devcontour --version` (версии DevContour и закреплённого движка), `package.json`                                                                                  |
| Движок исполнения (`devcontour-harness`) | `vendor/harness/README.md`, `package-lock.json` (версия и integrity), `devcontour doctor`                                                                          |
| Состояние                                | центральная база `<workspace>/.devcontour-local/state.sqlite`; при `storage: component` — ещё база каждого компонента `<компонент>/.devcontour-local/state.sqlite` |
| Общие записи Git sync                    | каталог `.devcontour` в репозиториях workspace и компонентов (receipts принятых задач)                                                                             |

Каждая новая попытка хранит версию движка (`engineVersion`) и DevContour
(`consumerVersion`). Старые записи сохраняют то, что в них было; недостающие
сведения не дописываются.

**Изменение прежних контрактов.** С 0.4.0-alpha.8 ревью контракта
применяет правило `verifiability`: контракт с вычислительными обещаниями
(точность, оптимальность, полнота, производительность) без структурного
`checks` отклоняется. Правило действует и для новой редакции контракта,
утверждённого раньше без `checks`: уже утверждённая редакция и привязанные к
ней задачи продолжают работать, но любое её изменение через `contract-change`
потребует полного договора проверки (gate `properties`, корпус, обязательства
по [check-contracts](check-contracts.md)). В 0.4.0-alpha.8 `--revise` не
перечитывает файл предложения: добавить `checks` к отклонённой операции можно
только отменой и новым стартом.

соединение только для чтения с такой базой создавало `-wal` и `-shm`. Есть

(хранение компонентов) читается обычным соединением с блокировками: файлов
оно не создаёт. Появились файлы журнала или изменился файл базы за время
проверки — базу менял writer, итог несовместим (`storage-quiet`): остановите
writers и повторите проверку.

### 0.4.0-alpha.9

0.4.0-alpha.9 поставляет движок `devcontour-harness` 0.1.0-alpha.16 —
локально собранный архив `vendor/harness/devcontour-harness-0.1.0-alpha.16.tgz`
(SHA-256 `f4c394d621588665f3ff15cf0f919edfe310df5defd5c0a24bd5d3e63ad120d8`),

- **Эталонные наборы в договоре проверки.** Договор
  проверки (`checks`) принимает необязательные поля обязательства `gates`,
  `verification` и `reference` — сверку с закреплёнными эталонными наборами

  новыми полями 0.4.0-alpha.8 и раньше не читают (строгая схема движка
  0.1.0-alpha.13): после ревью такого контракта откат — только через копию,
  как в разделе «Откат». `checks_view` добавляет к свойству задачи `gates` и
  `verification`. Изменение отказа: обязательство без `reference` на gate
  без `property` теперь отклоняется при любом обещании (прежде — только
  вычислительное), а кандидат, чей изменённый код называет строковым литералом файл эталонного
  набора, — до gates (`scope-violation`). ID testcase node:test —
  `test.<имя>`: отказ «testcase X отсутствует в JUnit» называет найденный ID.
  Ревью контракта считает перекрёстную проверку без закреплённых
  `artifacts` непроверенным утверждением автора.
- **Закрепление контракта.** Предложение контракта (`review-contract`, `contract-change`)
  с закреплённым JS/TS-артефактом, который импортирует незакреплённый и
  незащищённый локальный файл, отклоняется до ревью с перечнем путей; приёмка,
  импортирующая реализацию, перечисляет её файлы (не каталоги) в новом поле `underTest`. Предложения,
  которые проходили прежде, могут потребовать `underTest` или дополнительных
  `artifacts`/`protectedPaths`. Утверждённые контракты не отзываются: `doctor`
  называет неполное закрепление проверкой `contract-closure:<id>:<компонент>`
  (`not-checked`, готовность не снимает). Контракт с
  `underTest` хранит это поле, и его запись Git sync (`kind: contract`) не
  принимают 0.4.0-alpha.8 и раньше — откат после такого утверждения только
  через копию.
- **`devcontour --version`** (и `devcontour version`) печатает версию
  DevContour и версию вложенного `devcontour-harness`. В установке из архива
  `npm ls devcontour` для этого не годится: вложенная `file:`-зависимость
  движка помечается `invalid`, и команда завершается с `ELSPROBLEMS`. Справка
  установленного пакета называет его бинарник (`devcontour`, в каталоге
  установки — `npx devcontour`), а не `npm run devcontour` checkout.
- **Полный `devcontour doctor`** открывает базы только для чтения, как
  `doctor --scope data`: без режима журнала, DDL, начальных строк и владельца
  баз компонентов. Таблицы и строки, которых нет в базе прежней версии,
  создаёт первый writer (`serve`, `run`). Записывает doctor только свой отчёт
  `doctor.json` в каталоге данных. `doctor --probe` пишет больше: временный
  worktree и журналы preflight в `<данные>/doctor/<id>`, квитанции окружения
  и lease ресурсов в базе ресурсов (`resourceDatabase`, по умолчанию
  `~/.devcontour-local/resources.sqlite`). Состояние workflow он не меняет.
  Базы компонента ещё нет — doctor её не создаёт: проверка `state` получает
  `not-checked`, а роль controller, попытки и контракты без владельца-компонента
  читаются из центральной базы: проверка `engine` выполняется (роль другой
  версии движка — `blocked`), закрепление этих контрактов проверяется, а
  непрочитанные контракты названы проверкой `contract-closure:unread`
  (`not-checked`). Если
  writer пишет во время неизменяемого чтения, doctor перечитывает состояние.
- **`scripts/copy-precheck.mjs`**:
  - сравнивает только входы `doctor --scope data` (поле `compared` отчёта):
    каталог данных workspace, `.devcontour-local` каждого репозитория
    конфигурации, файлы конфигурации компонентов (`configFile`), профили из
    репозиториев (`packs[].source`), `devcontour.workspace.json` и HEAD (ветку
    и коммит) workspace и каждого репозитория. Сверяются оригинал с копией до
    проверки и оригинал и копия до и после неё. Копируется по-прежнему весь
    `R`. Прочая работа Git (worktrees, index, рабочие файлы) проверку не валит.
    Неподвижны должны быть writers базы, конфигурация компонентов и HEAD;
  - при расхождении называет пути, не больше 20, и число остальных;
  - до копирования сверяет свободное место во временном каталоге (`TMPDIR`)
    с размером `R` и отказывает, если его не хватает;
  - при любом отказе и при SIGINT/SIGTERM удаляет свою временную копию, даже
    с `--keep` (копирование и контейнер идут асинхронно, сигнал обрабатывается
    сразу; код выхода 130/143). Контейнер запускается с `--init` и именем
    `dc-copy-precheck-<токен>`; при сигнале скрипт сначала удаляет его
    (`docker rm -f`, не дольше 30 с), затем копию. Копию оставляет только завершённая проверка с
    `--keep`. Удаляется лишь каталог `$TMPDIR/dc-copy-precheck-*`, в котором
    лежит метка с токеном этого запуска;
  - запускает контейнер от пользователя хоста (`--user uid:gid`): файлы,
    созданные в копии, удаляются без root. Если удалить копию всё же не
    удалось (`EACCES`), скрипт называет каталог и причину;
  - передаёт пути в контейнер аргументами, а не подстановкой в текст
    скрипта; `R`, каталог архива или `TMPDIR` с «:» отклоняются до
    копирования (`docker run -v` делит значение по двоеточию);
  - содержимое баз читает с отдельной временной копии. Копия, которую
    получает контейнер, побайтно совпадает с оригиналом: файлов `-wal` и
    `-shm` рядом с базой WAL нет. Так проверка действительно идёт путём
    неизменяемого чтения, а `copyChanged` у совместимых данных пуст.
- **Правила ревью в `workspace.json`.** `workspace.json` принимает поле `review` (правила ревью кода, плана и
  контракта), и `workspace-init --file` переносит его в `config.json`, до
  записи проверив его загрузчиком сервера. Реестр без `review` выбор в
  `config.json` не меняет. Виды ревью переносятся по отдельности: объявленный
  `code` не стирает `plan` и `contract` из `config.json`. Ручная правка
  `config.json` для смены ревьюеров больше не нужна. Объявление `review`
  применяет только тот же `workspace-init`, а при единственном компоненте он
  заодно обновляет устаревшие копии ролей (ниже, «Действующие gates
  компонента»). Поэтому первый такой запуск после обновления может сделать
  утверждённые графы устаревшими (`APPROVAL_STALE`, «Повторное
  согласование»), даже если правила ревью совпадают с `config.json`.
  Применить одно `review`, не обновив копии ролей, нельзя: выполняйте этот
  `workspace-init` до операции, которая держит утверждённые задачи, или
  вместе с её пересмотром, чтобы ревью плана согласовало граф уже по новому
  digest.
- **Действующие gates компонента.** При списке репозиториев верхнеуровневые `gates` и `protectedPaths` берутся
  из первого компонента, а не из копии в `config.json`. Панель и `doctor`
  показывают действующий список. Если копия устарела, digest загруженной
  конфигурации меняется, и штатный перезапуск после обновления его применяет.
  Первый `workspace-init` после обновления может ответить
  `declaration-updated`: он обновит устаревшие копии gates, `protectedPaths`
  и, при единственном компоненте, ролей.
- **Повторное согласование.** Верхнеуровневые роли и `review` входят в digest политики исполнения
  (`executionDigest`). Если при единственном компоненте `workspace-init`
  переписал копии ролей (или изменились правила ревью), каждый утверждённый
  граф получает `APPROVAL_STALE` («согласуйте заново»): утверждённые планы
  нужно согласовать повторно. Действующие привязки ролей при этом прежние.
- **`degraded` в `doctor`.** `doctor` отмечает claude-ревьюера без профиля инструментов статусом
  `degraded` и называет исправление (профиль `claude-review` с `Bash`).
  `ready` этот статус не снимает.
- **Пересмотр по исправленному предложению.** `contract-change --id ID
--revise --expected-version N --file FILE` (агентский API —
  `contract_change_revise` с `proposal`) берёт исправленное предложение того
  же контракта (`checks`, `artifacts`, `underTest`, текст) с предпроверками
  старта до вызова модели и сохраняет операцию, удержания и историю;
  `revisions[].proposal` — digest прежнего предложения. Файл, `title`,
  `repositoryId` в записанном виде и компонент должны совпадать с операцией.
  Каталог агентского API меняется только этим полем.
- **Предупреждение о договоре проверки.** Предложение без `checks` получает
  до вызова модели предупреждение `checks-missing` (`warnings` в
  `contract-impact` и при старте операции, строка `Предупреждение:` в
  stderr); `contract-impact` показывает его рядом с `closure.refusal`, а
  такой отказ по-прежнему останавливает старт и пересмотр до ревью.
- **Код выхода `contract-change`** — 1 при `failed` и `stale`.
- **Удержание в прогрессе.** Удержание операции видно в `progress.reasons`
  (`held_by_operation`, поле `progress.hold`).
- **История операции.** `history[].detail` и `error` сокращаются по границе
  фразы или слова; запись ревью ссылается на свою попытку полем `review`,
  а ревью связываются с операцией по каталогу решения (`reviews`), а не по
  названию. Записи истории прежних операций не пересчитываются.

### 0.4.0-alpha.10

0.4.0-alpha.10 поставляет тот же движок `devcontour-harness` 0.1.0-alpha.16 —
архив `vendor/harness/devcontour-harness-0.1.0-alpha.16.tgz` с прежним
SHA-256 `f4c394d621588665f3ff15cf0f919edfe310df5defd5c0a24bd5d3e63ad120d8`.
Исходники движка опубликованы на GitHub с тегом `v0.1.0-alpha.16`; в npm он
пока не опубликован. Формат состояния меняется: 0.4.0-alpha.10 — первая
версия, которая хранит роль controller отдельной строкой и пишет в документ
метку `heldInRow` (строки «состояние 0.4.0-alpha.10» в разделе
«Совместимость»).

- **Роль controller — отдельной строкой.** Роль хранится в таблице
  `controller` центральной базы (coordinator), а не в документе состояния:
  её продление на каждом такте очереди больше не переписывает документ.
  Таблицу создаёт первая запись роли; роль, записанная прежней версией в
  документ, читается как прежде и при первой смене переносится в строку.
  Прежние версии строку не читают, поэтому, пока роль держит процесс этой
  версии, в документе лежит её метка — запись роли с полем `heldInRow`.
  Строгая схема прежних версий это поле отклоняет: прежняя версия не
  перенимает роль и не выдаёт работу (`run` завершается с кодом 1 на
  неизвестном поле, `serve` пишет `scheduler.error`). Но управление паузой
  и события ошибок проходят: прежний `queue --pause|--start` меняет документ
  и журнал, прежний `run` до отказа записывает снятие паузы (возобновит
  очередь работающего controller новой версии), прежний `serve` меняет
  флаг паузы и пишет событие ошибки. Не запускайте прежние CLI против
  состояния, роль в котором держит эта версия. Метку пишут только получение
  и снятие роли: после штатной остановки её нет, и прежняя версия работает с
  базой как обычно. После аварийной остановки метка остаётся, и прежние
  версии отказывают в роли, пока эта версия не будет запущена и остановлена
  штатно (или пока не восстановлена копия, раздел «Откат»).
- **Такт без изменений.** Работающий `serve` на паузе разбирает документ один
  раз на версию данных и не пишет ничего, кроме продления роли.
- **Попытки без версии движка в `doctor`.** Проверка `engine` больше не
  сообщает об отсутствии попыток, когда их записали версии, не хранившие
  версию движка: она называет число попыток, записавшие их версии и сколько
  попыток без версии.
- **`--version` и `help` без предупреждения.** `devcontour --version` и
  `devcontour help` больше не открывают `node:sqlite` и не печатают в stderr
  его `ExperimentalWarning`.

Неизвестная версия документа состояния или поле, которого строгая схема
движка не знает, отклоняются до любой записи. Проверка — тесты
`tests/harness-versions.test.ts` и `tests/harness-legacy.test.ts`; база с
обсуждениями задач, записанная до вопросов исполнителя (черновик и
продолжение попытки, закреплённая политика, учёт вызовов, заметки и
обращения), — `tests/legacy-discussion.test.ts`; сценарии обновления и
отката — `npm run check:upgrade` (ниже).

утверждения (`approvedPolicy`) и локальную запись проверки доски

через копию, как в разделе «Откат».

- **Движок 0.1.0-alpha.17.** Попытка, прерванная штатной остановкой,
  получает `interrupted: shutdown`, а её задача возвращается в очередь без
  траты попытки; отказы окружения, провайдера и истёкшее владение попытку не
  засчитывают, у них свой предел (`neutralFailures`, три на задачу).
  Отклонённая ревью попытка несёт `inputClasses` и пары `classified`,
  воспроизведение — `inputClass`; два отказа ревью подряд по одному свойству
  и классу останавливают задачу как пробел приёмки. `completed: false`
  исполнителя — класс `unfinished` с повтором от черновика. Пустой результат
  принимается только с подтверждением ревью и механическим основанием
  (`alreadySatisfied` в evidence), иначе — класс `needs-lead`. Тесты и
  сценарии, ждавшие засчитанной попытки после обрыва окружения или `failed`
  после штатной остановки, ведут себя иначе.
- **Автоматическая перемотка базы.** Отставшая база прогонов, когда это
  fast-forward продуктовых коммитов, перематывается диспетчером сам и встаёт
  на ожидание `base-check`; коммиты, задевающие приёмку и настройку контура,
  по-прежнему требуют `base-update` (D42, [операции](operations.md)).
- **Перемотка и защищённые пути.** Каталог контура (`.devcontour/` и другие
  защищённые префиксы), закоммиченный ссылкой (symlink или gitlink), в diff
  виден без завершающей `/` и тоже останавливает автоматическую перемотку.
- **Проверка доски вне областей задач.** Приёмка доски выполняет gates, не
  вошедшие в область ни одной задачи, один раз на её итоговом SHA в каждом
  компоненте (D44). `review-plan` и `workflow_start` заранее возвращают
  `coverageGaps` с предупреждением, регистрацию это не останавливает.
  Evidence пишется в локальную запись `board-coverage`, привязанную к SHA,
  digest политики компонента и ревизии доски; приёмка учитывает запись,
  только если совпадают все три. Провал gate — отказ приёмки с его именем;
  прошедшие gates повтор после частичного провала не перезапускает.
- **Расход по всему потоку.** Продуктовые вызовы моделей (планирование,
  оценки, recovery) считают расход и модель по всему stdout, а не по его
  последним 2 МБ: стоимость длинного вызова больше не выпадает из итогов.
  `runtime.json` хранит разобранный расход; строка длиннее 8 МБ отмечает
  расход неполным.
- **Класс ввода ревьюера.** Собственная схема ответа ревью DevContour
  требует `reproduction.inputClass` (допускается `null`); ответы без поля
  по-прежнему разбираются.
- **Такт без выдачи.** Такт без работы на большой доске не перечитывает
  документ состояния по каждой задаче: digest контракта берётся из уже
  прочитанного состояния, попытки разбираются один раз на версию данных.
- **Пределы предложения контракта.** Пределы прежние (`artifacts` — до 50,
  `purpose` — до 200 знаков, `underTest` — до 50 путей), но теперь они
  описаны в [cli](cli.md) («Пределы предложения»). `contract-impact`
  показывает превышения в `limits` рядом с `closure`, а не падает с массивом
  zod. `review-contract` и `contract-change` отказывают сообщением, где
  названы предел, элементы, величина превышения и способы исправления.
- **Верхнеуровневый `reviewer` при единственном компоненте.** Если
  компонент объявляет своего `reviewer`, `workspace-init` обновляет и
  верхнеуровневую копию в `config.json`, как копии ролей. Первый запуск после
  обновления может ответить `declaration-updated`. Копия входит в политику
  исполнения, поэтому её обновление делает вход задания доски устаревшим
  (ниже).
- **Утверждение плана закрепляет политику исполнения.** Утверждение задачи
  записывает `approvedPolicy` — digest утверждаемой части политики
  исполнения (gates, роли и области записи, ревьюеры и правила вендора,
  защищённые пути, окружение, изоляция). Граф с устаревшим закреплением
  проецируется с ним. Эксплуатационные пределы (параллельность, сроки,
  попытки, бюджеты) повторного утверждения не требуют. Раньше граф всегда
  получал текущий digest, и смена gate, правила вендора ревью или области
  записи применялась к утверждённому плану без повторного ревью. Теперь
  задача, утверждённая при другой политике, не выдаётся: `eligible` ложно,
  `progress.reasons` называет `approval_stale`, а `progress.approvalStale`
  подсказывает `review-plan --board ID`. `review-plan` такую доску не
  считает `already-approved`: план проходит ревью и закрепляет новую
  политику. Утверждения прежних версий без поля закрепляются за действующей
  политикой на первом такте controller после обновления, массового
  повторного утверждения нет. Поле локальное и при синхронизации не
  переносится. Решение — D43 в [decisions](decisions.md).
  Сначала обновите DevContour и запустите controller, а политику исполнения
  меняйте после первого такта. Обновление и смену политики одновременно не
  делайте: правка, применённая до первого такта, закрепится за прежними
  утверждениями без повторного ревью. Утверждение, полученное от другого
  клона, закрепляется за локальной политикой так же (известный пробел, D43).
- **Устаревшее задание доски видно на паузе.** Задание доски с изменившимся
  входом очередь заданий отмечает `stale` только при следующем взятии
  стадии. Теперь оно видно сразу: `workflows[].inputStale` и
  `progress.workflowStale` у задач доски. Выдачу это сведение не держит, а
  новое задание доски (`workflow_start`) снимает его и на паузе.
- **Команды без предупреждения SQLite.** CLI отсекает только
  `ExperimentalWarning` о SQLite: `doctor --scope data`, `contract-*` и
  другие команды больше не печатают его в stderr. Остальные предупреждения

  повторить и тогда. Задача, назначенная истории другого релиза, проверку не
  снимает. Подробности — «Обязательная приёмка продуктового релиза» в
  `docs/product-map.md`.
- **Совместимость.** Доказательства, записанные прежней версией, хранят digest
  прежнего вида: после обновления их проверка один раз завершится тем же

### 0.4.0-alpha.18

0.4.0-alpha.18 поставляет движок `devcontour-harness` 0.1.0-alpha.37: быстрый

- **Центр внимания.** Новый список актуальных действий (`GET /api/attention`, `attention_list`) — проекция существующих записей: миграции нет. Отметки оператора «прочитано» и «увидел» хранятся в локальных записях базы workspace (пространство `attention`), в Git sync не переносятся, входят в `backup`. Прежняя версия DevContour эти записи не читает: после отката они остаются лишними строками без влияния на работу. Первое открытие после обновления показывает все карточки непрочитанными. Строка отметок хранит последние пять появлений предмета (поле `earlier` рядом с отметкой текущего появления); строки, записанные сборкой с одним появлением на строку, читаются без миграции, число строк не меняется. Откат к выпущенной 0.4.0-alpha.17 эти строки не затрагивает: в ней центра внимания нет. Откат к промежуточной сборке из исходников с одним появлением на строку ломает отметки: её запись строгая и поле `earlier` отклоняет, поэтому отметка текущего появления предмета, строка которого уже содержит `earlier`, завершается ошибкой, и весь пакет отметок `POST /api/attention/marks` откатывается. Перед таким откатом восстановите базу из копии, снятой до обновления (`backup`), или примите, что отметки этих предметов не пишутся до их нового появления.

Заголовок сводки (`headline`) больше не учитывает решения; панель дополняет его по карточкам центра. Формат состояния не меняется.
- **Поля компонента — только из его файла.** Запись репозитория с
  `configFile` в `config.json` прежде могла хранить полную копию полей
  компонента (её записывал повторный `workspace-init` или обновление профиля).
  Загрузчик складывал файл поверх копии, и поле, удалённое из файла
  (например `prepare` или `environment.inherit`), продолжало действовать из
  копии. Теперь из общей записи берутся только `id`, `path`, `dependsOn`,
  `configFile` и роли (складываются с ролями файла), остальное — только из
  файла компонента. Поведение workspace с такой копией меняется: значение,
  которое было только в копии, больше не применяется. Перед запуском
  выполните `devcontour doctor`: расхождение копии с файлом названо
  проверкой `component-copy:<id>` (`degraded`) со списком полей. Нужные
  значения перенесите в файл компонента, затем повторный `workspace-init`
  с реестром `workspace.json` уберёт копию (`declaration-updated`).
- **Последствия расхождения копии.** Где `doctor` называет
  `component-copy:<id>`, действующий компонент после обновления другой
  (поля из копии больше не применяются). Поэтому меняется digest политики
  исполнения: утверждённые, но не завершённые задачи получают
  `APPROVAL_STALE` и требуют повторного согласования, а закреплённые
  квитанции (receipts), записанные по прежнему digest, с действующей
  политикой больше не совпадают. Перенесите нужные значения в файл компонента
  до перезапуска сервера, если хотите сохранить прежнее поведение.
- **`workspace-init` дописывает файл компонента.** Поля компонента
  действуют только из файла, поэтому `workspace-init` дописывает в него
  значения, которых в файле нет: объявленные для репозитория в
  `workspace.json` (при установке и на каждом запуске) и значения профиля

  `APPROVAL_STALE` и требуют повторного согласования. Файл компонента —
  чувствительный путь: после коммита база прогонов отстаёт от рабочей ветки

### 0.4.0-alpha.20

Закреплённый движок сменился с 0.1.0-alpha.37 на 0.1.0-alpha.38 — локально
собранный архив `vendor/harness/devcontour-harness-0.1.0-alpha.38.tgz` с
SHA-256 `24be97501f6af776e67dbfa4778f6f2dbada696a6fe4066f9492c97c031ea9ed`
(commit `7ed3c151c235e35817b6986cfaa1e952f70e56dc`). Формат состояния
прежний.

- **Вопрос не тратит попытку.** Остановка вопросом исполнителя
  (`needs-input`) не засчитывается в `maxAttempts` и не тратит предел
  незасчитанных отказов: ответ на вопрос последней попытки применяется
  `input_apply` без `reset`. Задачи, остановленные вопросом до обновления,
  хранят прежний счётчик попыток: если он исчерпан, применение по-прежнему
  требует `reset` с причиной. Отчёт и `attempt.diagnosed` считают такую
  остановку незасчитанной.
- **Предел остановок вопросом.** Попытку возвращают не больше `maxAttempts`
  остановок вопросом за всю жизнь задачи (счёт по записям попыток, сброс
  его не обнуляет, прежние остановки входят в счёт); следующая засчитывается
  как обычная попытка. Поэтому цикл «вопрос → ответ модели → применение» в
  `approvalMode: agent` и отмена с повтором вместо ответа кончаются
  исчерпанием попыток, а не только бюджетом. Новой настройки нет.
- **Запись работающего сервера.** `start` и `serve` пишут
  `.devcontour-local/server.json` (pid, адрес, экземпляр) и удаляют его при
  остановке; `devcontour stop` останавливает сервер только по этой записи.
  Сервер, запущенный 0.4.0-alpha.19 или раньше, записи не пишет: пока он
  держит роль controller, `stop` отвечает `running-unrecorded` с кодом 1 и
  сигнала не посылает — остановите такой сервер вручную один раз: Ctrl+C в
  его терминале, а запущенный в фоне — `kill -TERM <pid>` по шагам из

### 0.4.0-alpha.22

Закреплённый движок сменился с 0.1.0-alpha.38 на 0.1.0-alpha.39 — локально
собранный архив `vendor/harness/devcontour-harness-0.1.0-alpha.39.tgz` с
SHA-256 `3bd95bc721e81a85a12582a8cc2a32850843600081959e57d5e40e6c77234478`
(commit `c79b94a1c2edcf8138e07c3a1e82e9ab3695971e`). Формат состояния
прежний.

- **Ревью интеграции видит только изменения своей задачи.** Дифф ревью
  интеграции и строка «Base commit» запроса reviewer считаются от рабочей
  ветки, на которую слита задача (первый родитель коммита интеграции), а не
  от базы начала попытки. Раньше, когда задача другой доски из той же
  очереди интегрировалась раньше, её уже принятые файлы попадали в дифф, и
  reviewer отклонял задачу за чужие изменения вне её области. Ревью
  кандидата по-прежнему — от базы попытки. Если слияние не дало коммита с
  родителями «целевая ветка, кандидат» (кандидат уже входит в целевую
  ветку), интеграция завершается отказом `merge` до проверок и ревью. По тому же правилу дифф
  результата задачи на странице быстрого изменения считается от первого
  родителя коммита интеграции, а не от базы попытки: работа другой доски,
  принятая раньше, больше не показывается под этим изменением.
- **Нижний предел срока проверок `gateTimeoutFloorMs`.** Новый необязательный
  ключ `config.json` (целое, 1000–600000 мс): каждая проверка — на кандидате,
  интеграции, при приёмке доски, проверке на SHA и проверке ревьюера —
  исполняется со сроком не меньше предела, даже если её `timeoutMs` короче
  (объявленный срок в конфигурации не меняется). Короткий срок быстрой
  проверки (например, 10 с) под нагрузкой хоста срывался, тратил попытку и
  ронял приёмку доски. Setup пишет в новую конфигурацию `60000`; в
  существующую конфигурацию допишите ключ сами и перезапустите `serve`
  (`config-apply` его не применяет). Ключ эксплуатационный: утверждения
  планов не устаревают; digest исполнения движка меняется, как при правке
  `runTimeoutMs`, поэтому меняйте его без активных попыток. Текст отказа по
  времени называет предел: «Проверка прервана или превысила timeout: предел
  N с» и, если предел поднят, «(объявлен M с, поднят gateTimeoutFloorMs)».
  Предел больше `runTimeoutMs` конфигурация не проходит (отказ политики).
  Срок `timeoutMs` проверки — защита от зависания, а не предел
  производительности: бюджет времени, который проверка должна соблюдать,
  проверяйте внутри самой проверки. Откат: 0.4.0-alpha.21 и раньше ключ молча
  отбрасывает (предел исчезает), а движок 0.1.0-alpha.38 политику с этим
  полем отклоняет — уберите ключ из `config.json` до отката; как и при
  правке ключа, откатывайте без активных попыток.
- **Номер изменения продукта продолжает папки `docs/changes`.** Новое
  изменение получает номер после всех папок `docs/changes/r-NNN.*` на диске,
  а не только после изменений базы: свежий `.devcontour-local` над
  репозиторием с закоммиченными изменениями больше не повторяет занятый
  ключ. Индекс `docs/changes/README.md` сохраняет строки закоммиченных
  изменений, которых нет в базе, по их `change.json`; сами их папки проекция
  не переписывает. Хранимые данные не меняются.
- **Изменения продукта независимы в работе.** Новое изменение (быстрое
  поручение или `preparation_create`), ставшее активным, больше не делает
  `stale` задание доски уже утверждённого изменения: вход задания зависит от
  изменений его задач, а не от активного. Запуск очереди и утверждение плана
  тоже требуют готовности хоть одного изменения, а не активного; привязку
  каждой задачи по-прежнему проверяет её изменение.
- **Перезапуск сервера не отключает технику из-за изменения в проработке.**
  `start` подключает техническую конфигурацию, когда она применена
  (`config.json` есть) и готово хоть одно изменение, а не только активное.
  Раньше перезапуск, пока активное изменение ждало согласований, оставлял
  весь workspace в режиме проработки, и задачи уже утверждённых изменений
  нельзя было повторить или запустить.
- **Привязка задач к изменению продукта — по доске, а не по активному
  изменению.** `plan_import` с `boardId` и `task_create` без `preparation`
  привязывают задачу к изменению задач доски; новая доска — к активному
  изменению или к необязательному `changeId` (CLI `import-plan --change`).
  `task_edit` с `preparation.changeId` перепривязывает задачу (меняется
  `specDigest`), без него задача остаётся в своём изменении. Ответы
  `task_create`/`task_edit` называют `preparation` (`changeId`, `key`),
  `plan_import` — `changeId`. Для явной привязки достаточно
  `preparation: {changeId}`; переданные digests сверяются с утверждёнными, и
  устаревшие отклоняются. Отклоняются и `changeId` вне продуктового
  процесса, и изменение, отличное от изменения живых задач доски (доска ведёт
  одно изменение). Корректировка, когда постановку изменения оригинала
  открыли заново, создаёт замену без привязки — её привязывает правка
  черновика. Импорт следующего этапа без `changeId`, пока активно другое
  изменение, возвращает `warning` с обоими ключами и путём новой доски.
  Хранимые данные не меняются.
- **Панель называет утверждённые изменения, пока активное ждёт
  согласований.** Раздел «Разработка» такого изменения говорит, что работа
  утверждённых изменений продолжается, и перечисляет их; доски, повтор задач
  и запуск очереди доступны. `preparation_status` и `/api/preparation`
  возвращают `readyChanges`.
- **Команды подготовки при работающем сервере.** Хранилище подготовки
  больше не переключает базу из WAL в DELETE: CLI `agent --file` с операциями
  `preparation_*` и `setup --change … --plan` работают, пока сервер с
  подключённым движком держит базу, вместо отказа «database is locked».
  Новая база подготовки по-прежнему создаётся в DELETE; база с компонентами
  остаётся в DELETE. Формат данных прежний, откат на 0.4.0-alpha.21 читает
  базу в любом из режимов.
- **Сохранённый файл компонента в setup быстрого изменения.** Если в
  репозитории уже лежит `devcontour.component.json`, `setup --change … --plan`
  называет его в `files` (`preserve`) и в поле `component`
  (`precedence: true`, пояснение `note`), а поле `gates` перечисляет
  проверки, которые будут действовать, — проверки файла, а не предложения. Панель показывает
  их и предупреждение. Нечитаемый файл компонента или файл, с которым
  конфигурация не пройдёт схему, проверки gates и согласование ролей с
  профилями, — отказ плана и применения с причиной. Для нового файла `component.action` — `create`.
- **Профили инструментов для ролей файла компонента.** Setup создаёт в новом
  `config.json` профили `toolProfiles`, на которые ссылаются роли
  сохранённого файла компонента (`{ "runtime": … }` привязки — те же
  инструменты, что без профиля). Раньше `config.json` начинался с пустых
  `toolProfiles`, и такая конфигурация не загружалась («Неизвестный или
  несовместимый toolProfile»). Уже созданные конфигурации не меняются.
- **Реестр пакетов в песочнице npm и pnpm.** Setup с профилем, где есть npm
  или pnpm, пишет `isolation.domains` с `registry.npmjs.org` (или реестром
  `registry=` из `.npmrc`) и реестрами областей `@scope:registry=`. Локальные
  адреса (`localhost`, `*.localhost`, `*.local`, IP-литералы) автоматически
  не открываются: план называет их в `isolation.skipped` — добавьте вручную,
  если это намеренно. План и ответ setup показывают `isolation.domains` и
  создаваемые `toolProfiles`; панель — тоже. Doctor выводит предупреждение
  `isolation:network` (degraded), если шаг установки зависимостей
  (`npm ci`, `pnpm --filter x install`, `corepack pnpm install`,
  `yarn install`…) идёт в песочнице, а домена реестра из `.npmrc`
  компонента (или публичного) нет в `isolation.domains`. Существующие
  конфигурации setup не меняет: допишите домен сами.
- **`stop --pid` для сервера без записи.** Сервер, запущенный до
  0.4.0-alpha.20 в фоне (`nohup`), записи `server.json` не пишет, и
  терминала для Ctrl+C у него нет. `devcontour stop --pid <pid> --workspace W`
  останавливает его SIGTERM, только если pid держит открытой базу этого
  workspace и слушает TCP-порт (по `lsof`, без него — отказ), его argv —
  `node <программа devcontour> serve|start` с `--workspace W` (без обёрток
  вроде `bash -c`, `ssh`, `tmux`, `sudo`), роль controller живая и pid не
  сменил процесс за время проверок. Иначе — отказ без сигнала. Данные не
  меняются.
- **Обращения ведущего агента держат его «на связи».** Присутствие ведущего
  в «Внимании» и на главной считается не только по записям активного
  изменения, но и по его обращениям: любая операция агентского API (CLI
  `agent --file`, HTTP `/api/agent`, MCP), в том числе только для чтения, и
  CLI `session-handoff`. Отметка последнего обращения — файл
  `lead-activity.json` рядом с базой в каталоге данных (`.devcontour-local`);
  база, её ревизия и журнал от неё не меняются, `session-handoff` по-прежнему
  только читает базу. Без активного изменения присутствие — по одной
  отметке. Порог тишины прежний — 15 минут; отметка, датированная будущим
  дальше минуты, не учитывается. `scripts/copy-precheck.mjs` отметку и её
  временный файл не сравнивает: обращения ведущего во время проверки копии
  её не валят. Удалить файл безопасно.
- **Вопросы исполнителя и его находки — на русском.** Запрос writer теперь
  называет язык текста для оператора: вопрос (`input request` — вопрос,
  варианты, последствия, рекомендация) и попутные находки исполнитель пишет
  по-русски, команды, пути и идентификаторы — дословно. Код и файлы
  репозитория по-прежнему следуют соглашениям репозитория; запрос reviewer
  не меняется. Подсказки `host.next` из пакета harness пока по-английски.

Закреплённый движок сменился с 0.1.0-alpha.39 на 0.1.0-alpha.40 — локально
собранный архив `vendor/harness/devcontour-harness-0.1.0-alpha.40.tgz` с
SHA-256 `cfeadab1eea9dbe5c01eb6e44ac489537e99a333c6556b0a3bc182f7433a38d2`
(commit `315eaf84a67268f78aedf639936c293262d7183a`). Формат состояния
прежний.

- **Пробы ревью интеграции доверяют целевой ветке.** Пробные проверки
  reviewer на этапе интеграции считают доверенной базой ту же ветку, от
  которой строится дифф ревью (первый родитель коммита интеграции), а не базу
  начала попытки. Сбой registry в такой пробе при неизменённых входах
  установки теперь распознаётся как сбой сети зависимостей, а не как вина
  кандидата. Ревью кандидата, проверки и шаги `prepare` интеграции
  по-прежнему считают доверенной базой базу попытки.
- **`config-apply` применяет `gateTimeoutFloorMs`.** Нижний предел срока
  проверок работающий `serve` теперь применяет без перезапуска:
  `devcontour config-apply --keys gateTimeoutFloorMs --workspace ...`. Как и
  прочие эксплуатационные ключи, применение ждёт окончания идущих попыток и
  проверок (новые не выдаются, пока запрос не применён), затем движок
  пересобирается с новым пределом; утверждения планов, договор задачи и
  workspace не меняются, повторного утверждения не нужно. Без `--keys`
  команда по-прежнему применяет только `budgets,prices`. Предел больше
  `runTimeoutMs` команда отклоняет до запроса. Сервер 0.4.0-alpha.22 и
  раньше ключа в запросе не знает: команда снимет отклонённый запрос и
  ответит `refused` — примените ключ перезапуском `serve`. `doctor` при
  расхождении ключа теперь называет `config-apply --keys gateTimeoutFloorMs`
  вместо перезапуска.
- **Setup выбирает `runTimeoutMs` по проверкам.** Раньше setup (в том
  числе быстрого изменения) писал умолчание 15 минут независимо от
  проекта, и долгие реальные проверки (установка зависимостей, typecheck и
  тесты монорепозитория) не укладывались в фазу попытки. Теперь значение
  берётся из существующей `config.json` workspace (setup её не
  перезаписывает) или из `runTimeoutMs` профиля, а иначе — из оценки самой
  долгой фазы, интеграции, по проверкам и шагам, которые будут действовать
  после setup: известные сроки шагов подготовки (`prepare`, `setup`/`ready`
  окружения), сумма сроков gates по очереди (каждый не короче
  `gateTimeoutFloorMs`) и один повтор самого долгого gate (повтор проверки,
  упавшей на интеграции и прошедшей на кандидате). Проверки потребителей
  setup не знает, поэтому это оценка, а не гарантия. К оценке — запас 25%,
  не меньше 2 минут, до минуты; итог не меньше 15 и не больше 120 минут.
  План setup и страница быстрого изменения показывают выбранное значение и
  причину («Срок фазы попытки», поле `runTimeout` ответа setup); если
  сохранённое значение меньше оценки, причина это называет.
  `runTimeoutMs` ограничивает не только фазы попытки, но и вызовы моделей
  (исполнитель, ревьюер, планировщик) и срок ревью: с большим выведенным
  значением зависший вызов модели прерывается позже — причина плана
  называет этот срок. Существующие конфигурации не меняются: при долгих
  проверках поднимите `runTimeoutMs` в `config.json` сами и перезапустите
  `serve`.
- **Doctor предупреждает о проверках длиннее фазы.** Проверка
  `gates:timeout` (`degraded`) называет компонент или совместные проверки
  workspace, у которых сумма сроков gates (каждый не короче
  `gateTimeoutFloorMs`) больше `runTimeoutMs`: такая очередь проверок
  обрывается сроком фазы, а не своим. Это видно и после подъёма
  `gateTimeoutFloorMs` через `config-apply`. Сумма — нижняя граница, а не
  оценка setup: повтор проверки на интеграции, шаги подготовки и окружения
  и проверки потребителей в неё не входят, а задача с частью проверок может
  уложиться и при предупреждении.
- **Подсказки `host.next` — на языке `hintLocale`.** Новый необязательный
  ключ конфигурации `hintLocale` (`en` | `ru`) задаёт язык текста шага
  DevContour в `session_handoff` (`host.next.detail`, строка «Следующий шаг»
  приложения Markdown) и указания ведущему агенту в карточке доски центра
  внимания. Новая конфигурация setup (один репозиторий, быстрое изменение,
  workspace из нескольких репозиториев) пишет `"hintLocale": "ru"`:
  панель и вопросы исполнителя и так на русском. Существующий `config.json`
  не меняется: без ключа — английский, тексты байтово прежние; для русского
  добавьте `"hintLocale": "ru"` в `config.json` и перезапустите `serve`.
  Команды, JSON, id и пути в тексте — дословно на любом языке. Шаг теперь
  несёт стабильные `code` и `params` (параметры — только то, чего нет в
  полях шага); прежние поля не менялись. Появление карточки «вход задания не
  построить» по-прежнему считается по полному английскому тексту шага: id
  прежние при любой длине причины, и смена языка не возвращает признанные
  карточки. Шаг `host.next` в ответе `session_handoff` теперь проходит ту же
  маску секретов, что пакет; после маски причина и ошибка задания в нём
  ограничены 1000 символами (длиннее — усечены с «…»). Ключ не
  входит в политику исполнения: план не переутверждается, digest политики
  прежний; `config-apply` его не применяет — нужен перезапуск `serve`.
  Описания команд harness (`commands`) остаются по-английски.

  черновика до закрепления контрактов, поэтому это работает и для задач с
  контрактом), сохраняет снимок; правка постановки после переноса
  по-прежнему делает применение устаревшим. Ревью
  ответа в черновике привязано к редакции постановки: раунд, проведённый до
  правки черновика, к новой редакции не применяется (`APPROVAL_REQUIRED`), а
  ревью черновика, проведённое до обновления, нужно повторить. Подсказки
  `nextStep` (`input_answer`, `input_supersede`) и `next` заменённого
  вопроса называют этот порядок. Если на доске нет ни одной утверждённой
  задачи (например, единственная задача доски вернулась в черновик),
  основания для переноса в черновике нет: `input_target` называет это вместо
  внутренней ошибки, `input_apply` отказывает `NOT_READY`, а подсказки
  называют порядок «пауза очереди → утверждение → перенос → снятие паузы».
- **Область записи роли в ответах и правках.** `task_create` и `task_edit`
  отвергают добавленный путь области записи, целиком лежащий вне области
  роли задачи (400), и называют роль, которой он принадлежит: нужна
  отдельная задача этой роли. Прежде такой путь принимался (проверялось
  только, что пересечение не пусто), и задача тратила попытки на отказ по
  области записи. Уже записанные пути правка не отвергает; перенос ответа в
  постановку с такими путями отказывает `ROLE_SCOPE` до вызова модели, а
  `input_target` называет причину. Ревью ответа получает область записи роли.
- **Счёт попыток после новой постановки.** Утверждение черновика, основание
  которого (постановка и закреплённые контракты) отличается от основания
  последней попытки, начинает счёт попыток заново — автоматически не больше
  одного раза за жизнь задачи. Событие утверждения несёт `attemptsRestarted`
  (задача и число снятых попыток) или `attemptsKept` с причиной, когда
  счётчик сохранён: `restart-limit` (перезапуск уже был), `human-cancel`
  (задачу вернули из отмены человеком; отметка ставится при `reopen`),
  `exhausted`. Дальше попытки даёт только человек (`retry --reset --reason`
  после исчерпания). Утверждение той же постановки счётчик не трогает;
  бюджеты и предел остановок вопросом считаются по истории. Ревью плана
  видит прежние попытки черновика и выданных, затем отменённых задач той же
  ревизии (`attemptHistory`; тексты отказов помечены как данные, размер
  ограничен). Номера попыток после
  перезапуска начинаются с 1; `firstAttemptAcceptanceRate` перезапущенную
  задачу не считает принятой с первой попытки. Новые локальные поля задачи:
  `attemptRestarts`, `restartBlocked`. Обоснование — D47 в docs/decisions.md.
- **Область роли в плане.** `import-plan` отвергает задачу плана с путём
  области записи вне области роли так же, как `task_create`.

### 0.4.0-alpha.28

Закреплённый движок сменился с 0.1.0-alpha.43 на 0.1.0-alpha.44 — локально
собранный архив `vendor/harness/devcontour-harness-0.1.0-alpha.44.tgz` с
SHA-256 `b6c2773cd0828aa235952d38b736c33eb31949e9d409474a7bf060d1ceff4b94`
(commit `0aa2775b8f094f66bf78c2116202a5585c512d16`).

- **Прерванная совместная проверка не тратит предел набора; сброс — решение
  оператора.** С движком 0.1.0-alpha.44 проверка, прерванная до результата
  gates остановкой сервера (DevContour передаёт движку сигнал своей
  остановки) или потерей владения, получает отметку `interrupted` и в предел
  совместных проверок набора не засчитывается; у таких проверок свой предел
  (3 подряд). Отказ gate и прерывание после результата gates тратят предел,
  как прежде. Свой предел ChangeSet («Исчерпан лимит попыток ChangeSet»)
  считает так же. Проверки, прерванные прежними версиями, отметки не имеют и
  предел тратят: исчерпанный ими набор освобождает новая команда
  `devcontour changeset-budget-reset --changeset ID --reason … --workspace …`
  — решение оператора с обязательной причиной. Она снимает только
  завершённые проверки набора без результата gates; сброс, которому нечего
  снимать или после которого набор всё равно исчерпан, отклоняется. Отказ
  начала проверки и карточка остановленного задания ChangeSet просят
  ведущего обратиться к пользователю (без готовой строки команды) и
  предлагают сброс, только когда движок его примет; иначе называют выход —
  принятие успешной проверки или новый набор задач. Сам DevContour сброс не
  вызывает, у ведущего агента его нет, `--by host` отклоняется, а START.md и
  навык ведущего запрещают ему выполнять эту команду. Состояние с отметкой `interrupted` или записями сброса
  прежние версии DevContour не читают: откат — через резервную копию.
- **Совместная проверка ChangeSet живёт дольше такта задания.** Стадия
  проверки задания ChangeSet (`workflow_start`, kind `changeset`) теперь
  начинает совместную проверку и ждёт её итога следующими тактами, а не под
  своим сроком владения. Прежде на большом наборе задач стадия синхронно
  читала Git для каждой задачи и каждого источника требований, процесс стоял
  дольше срока владения заданием (`leaseMs`), продление не успевало, и
  задание обрывало свою же проверку до первого gate («This operation was
  aborted»); три такие проверки исчерпывали попытки стадии. Требования
  теперь читаются один раз на источник, снимок продуктового релиза
  снимается до начала проверки движком, а потеря владения заданием — не
  провал стадии, а возврат в очередь. Останавливает идущую проверку только
  остановка сервера. Пока проверка идёт, такты задания ждут и попыток стадии
  не расходуют; итог проверки (успех или отказ gate) — итог стадии, как
  прежде. Отказ начала проверки по ожиданию (`NOT_READY`: идёт попытка или
  другая проверка; остановка сервера) — снова ожидание стадии, а не её
  провал. Ожидание ограничено: после отказа `NOT_READY` новое начало — через
  паузу (15 с, затем вдвое дольше), а пятый такой отказ подряд проваливает
  стадию с причиной «Совместная проверка не начинается: … (отказ начала 5
  раз подряд)» — постоянная причина больше не держит задание в ожидании без
  карточки. Во время паузы стадия только ждёт: требования (Git) не
  перечитываются. Счёт отказов подряд начинается заново, когда стадия
  падает по любой другой причине, задание заканчивается или ChangeSet
  принят: повтор задания снова ждёт с паузами. Если попытки стадии исчерпаны прерываниями (потеря владения),
  ошибка задания называет и последнюю причину: «Исчерпаны попытки стадии;
  последняя причина: …». Итог проверки забирает такт, который её дождался, даже если сам
  он упадёт по другой причине (например, изменились требования): повтор
  задания начинает новую проверку, а не повторяет прежний итог. Потеря
  владения узнаётся по коду отказа `LEASE_STALE`. Незавершённые задачи ChangeSet теперь называются отказом
  «Сначала завершите все задачи ChangeSet: …» до проверки покрытия релиза.
- **Отказ по пределу совместных проверок называет путь.** Предел движка
  считает каждую начатую проверку набора задач — и прерванную до первого
  gate — до принятия ChangeSet этого набора; сбросить его нельзя, и новый
  ChangeSet над теми же задачами получает тот же отказ. Тексты «Исчерпан
  лимит попыток ChangeSet» и «Исчерпан предел совместных проверок этого

  запас есть, отказ называет остаток и предлагает новый ChangeSet по тем же

- **Карточка остановленного задания ChangeSet.** Карточка центра внимания
  («Задание ChangeSet остановлено», прежде «Автоматическое восстановление
  ChangeSet остановлено») называет причину задания, итог последней
  совместной проверки (и что она прервана до первого gate) и пути:

  раньше ChangeSet того же релиза карточку следующего не закрывает.

  задача одной из историй этой фичи несёт связь `requirements`, чей
  `scenario` совпадает с текстом сценария слово в слово (различия только в
  пробелах), и `testId` testcase, который его проверяет и прошёл на принятом
  SHA. Задача другой фичи с тем же текстом не засчитывается. Один gate может
  проверять несколько сценариев фичи; текст сценария внутри фичи уникален,
  потому что доказательство сопоставляется по тексту, а не по gate.
- **Отложить сценарий решает пользователь.** Поле `deferred` с причиной у
  проверки в INTENT убирает сценарий из релиза; ведущий агент предлагает это
  и спрашивает, а не откладывает сам. `product-view`, `intent-report` и
  результат приёмки ChangeSet называют отложенные сценарии отдельно
  (`deferredScenarios`), карта продукта показывает их предупреждением.
  Отдельного подтверждения оператора для `deferred` пока нет.
- **Пока сценарий не доказан и не отложен**, `coverageComplete` ложно,
  совместная проверка релиза не начинается, приёмка ChangeSet с `releaseId`
  и `product-view --require-accepted` отказывают и называют сценарий.
  Релиз, принятый прежней версией без доказанных сценариев, остаётся в
  истории, но `releaseAccepted` для него ложно, и карта называет это
  отдельной строкой. Что сделать после обновления: для каждого сценария
  добавить связь с testcase обычной корректировкой задачи или согласовать с
  пользователем, какие сценарии отложить, затем проверить релиз заново.
  Релизы без карты фич не меняются; отчёт пишет, что сценарии не
  отслеживаются.

- **Этап, меняющий несколько контрактов, проходит `contract-change` без
  обходов** ([D49](decisions.md)). Документы соседних контрактов коммитятся
  вместе, и прежде шаг `base` каждой операции отказывал («изменения вне
  контракта»), а правка одного документа после отказа ревью делала остальные
  одобренные операции устаревшими. Теперь шаг `base` переносит вместе со своим
  контрактом одобренные редакции соседей — документ по blob одобренного
  текста, закреплённый артефакт по закреплённому blob, оба в том же режиме
  файла — только у живых операций, прошедших ревью (запись истории
  `siblings`), и сверяет это ещё раз в транзакции сдвига ref. Пути соседей,
  ещё не одобренных, переводят операцию в ожидание `waiting` с их id в
  `waitingFor`; когда сосед переносит базу, ждавшие операции продолжаются в том
  же вызове (`continued` в ответе `contract-change`, запись `carried`).
  Ожидание, чьи соседи больше не идут к базе, и операция, чей процесс
  оборвался посреди шага (`running` с истёкшим lease), показываются в
  «Внимании». Продолженные операции, остановившиеся `failed` или `stale`, CLI
  называет строкой в stderr; код выхода — по самой операции.
  Сдвиг HEAD до переноса базы только в файлах соседних живых операций больше
  не делает операцию `stale`, если её собственные пути не менялись (запись
  `rebased`). Посторонние пути и неодобренное содержимое по-прежнему
  останавливают операцию; отказ называет группы путей и выход
  `base-update --by host` и `contract-change --id ID`. Входы агентского API
  не менялись; действий с данными после обновления не требуется.

- **Условные gates.** Закреплённый движок — `devcontour-harness`
  0.1.0-alpha.45. Gate компонента может объявить `when: { "paths": [...] }`
  ([справочник](configuration.md#условный-gate-when)): он исполняется, только
  когда настоящий diff фазы задевает его пути или неявный вход, а иначе
  пишет evidence `not-applicable` — не PASS и не провал. Панель, доска,
  попытка и быстрый маршрут показывают его как «не применим (пути)» с
  шаблонами и сводкой diff; доказательства сценариев, требований и testcases
  его не читают. Приёмка доски исполняет пропущенный условный gate один раз
  на итоговом SHA, если его задевает объединённый diff задач. Receipt Git
  sync переносит такую запись (вид `not-applicable` с полем
  `notApplicable`). Клон прежней версии такую запись не читает, и его
  синхронизация прерывается целиком, а не только на этой задаче: обновите
  все клоны команды до того, как добавите `when`. Держите `when` одинаковым
  во всех клонах: получатель сверяет неприменимость со своей политикой, и
  результат участника, пропустившего gate под другим определением, требует
  перепроверки задачи. Принятые задачи, область которых состояла из gate,
  ставшего условным, по-прежнему импортируются: правило области
  («test gate без `when`») действует только при постановке, правке,
  утверждении и выдаче.
- **Повторное утверждение.** Добавление или изменение `when` меняет digest
  политики: задачи, утверждённые раньше, не выдаются до повторного
  утверждения плана. Конфигурация без `when` сохраняет прежние digest, и
  действий не требует.
- **Каждый условный gate исполняется один раз после обновления.** Основание
  решения включает версию harness: первая попытка после обновления движка
  исполняет каждый условный gate, и только следующие пропускают его по
  путям.
- **Откат.** Состояние с evidence `not-applicable` или полями `gateBasis` и
  `notApplicable` прежние версии не читают: откат — через резервную копию.
  Без условных gates откат возможен без изменений состояния.

  `guides:<компонент>`, `degraded`, готовность не снимает) и называет

  `guides-refresh --workspace W` (для прежней конфигурации — `--data`) пишет
  в рабочее дерево только копии, которые записал инструмент и с тех пор не
  правили, и недостающие в уже установленном наборе — через временный файл
  и rename, никогда через ссылки. Изменённые, снятые копии и не обычные
  файлы остаются как есть и называются в `kept` с причиной. Чтобы взять
  новую версию изменённой копии, перенесите правку в собственный документ,
  удалите копию и повторите команду. Копии, поставленные до этой версии,
  метки не имеют: если их текст совпадает с текстом копии любого прежнего
  релиза (таблица digest, `scripts/guide-history.ts`) или с текущим, они
  считаются устаревшими и обновляются без флага; иначе заменяются только с
  `--replace-unmarked` и только закоммиченные без локальных изменений —
  прежний текст остаётся в истории Git, а `next` называет заменённые пути,
  чтобы проверить их в `git diff`. Команда ничего не коммитит и не меняет

  выполните `context-lock`. Повторный setup по-прежнему не перезаписывает
  существующие файлы. Миграции нет: после обновления выполните `doctor`,
  затем `guides-refresh`.

   продолжают писать.
   - Сервер 0.4.0-alpha.20 и новее: `devcontour stop --workspace W`
     (`stopped` или `not-running`).
   - Сервер, запущенный версией до 0.4.0-alpha.20, записи
     `.devcontour-local/server.json` не пишет, и `stop` отвечает
     `running-unrecorded` (код 1) без сигнала. В терминале остановите его
     Ctrl+C. Запущенный в фоне (`nohup`, `&`, менеджер процессов) терминала
     не имеет: найдите pid по командной строке
     (`ps -ax -o pid,command | grep -F -- W`) или по порту панели
     (`lsof -nP -iTCP:<порт> -sTCP:LISTEN`, по умолчанию 4317), убедитесь,
     что это `devcontour serve`/`start` именно этого workspace, и остановите
     сами: `kill -TERM <pid>` — штатная остановка, как Ctrl+C (сервер
     дожидается идущих операций и снимает роль controller). Новая установка
     может сделать это сама: `devcontour stop --pid <pid> --workspace W`
     посылает SIGTERM, только если pid держит открытой базу этого workspace
     и слушает порт (`lsof`), его argv — программа devcontour с подкомандой
     `serve` или `start` и `--workspace W` без обёрток, роль controller живая;
     иначе отказ без сигнала. Сервер под
     менеджером процессов останавливайте его средствами, иначе он
     перезапустится. Затем проверьте: `devcontour stop --workspace W`
     должен ответить `not-running`.
2. **Зафиксировать.** Версию установки (`devcontour --version`; до 0.4.0-alpha.8
   включительно команды нет — версия в `node_modules/devcontour/package.json`),
   `devcontour doctor --workspace W`
   (проверка `engine` называет версию движка, роль controller и версии,
   записавшие попытки), вершины target ref каждого репозитория
   (`git rev-parse main`), незакоммиченные изменения компонентов, состояние
   Git sync.
3. **Сделать копию.**
   - `storage: central` — `devcontour backup --out FILE --workspace W`
     (согласованная копия SQLite);
   - `storage: component` — копия **всех** баз: центральной и каждого
     компонента, вместе с файлами `-wal`/`-shm`, при остановленных writers.
     Команда `backup` копирует одну базу и этого не обеспечивает.
   - Git-объекты должны оставаться доступными: копия базы без коммитов, на
     которые она ссылается, историю не восстанавливает.
   - Файл `.devcontour-local/quick-setup.json` (отметки `setup --change`)
     лежит вне базы и в `backup` не входит: копируйте его вместе с базой.
4. **Проверить совместимость данных на копии.** Конфигурация и базы хранят
   абсолютные пути (workspace, репозитории, владелец базы компонента),
   поэтому копия в другом каталоге — уже другой workspace:
   `doctor --workspace <копия>` отказывает («Конфигурация не принадлежит
   выбранному workspace»), а перенос путей, повторный `setup` или правка
   владельца базы проверку не заменяют. Копию проверяют в изолированном
   контейнере, где она смонтирована по тем же абсолютным путям, что оригинал,
   а сам оригинал не смонтирован. Скрипт поставляется не в архиве, а в
   исходниках: запускайте его из checkout той версии DevContour, архив
   которой проверяете:

   ```sh
   git clone <репозиторий DevContour> dc && cd dc && git checkout <тег или SHA версии>
   node scripts/copy-precheck.mjs --root R --workspace W --archive devcontour-<версия>.tgz
   ```

   `R` — общий каталог, внутри которого лежат workspace и все репозитории
   его конфигурации (иначе скрипт отказывает и называет пути вне `R`). Скрипт
   проверяет, что во временном каталоге (`TMPDIR`) хватит места на копию `R`,
   копирует `R` целиком (Git-объекты, базы всех компонентов вместе с
   `-wal`/`-shm`), ставит архив новой версии в контейнер Docker (нужны Docker
   и доступ к образу `node:24.3.0-bookworm`) и выполняет в нём
   `devcontour doctor --scope data` над копией. Сравниваются только входы
   проверки данных (каталоги данных, конфигурация компонентов, профили из
   репозиториев, `devcontour.workspace.json`, HEAD репозиториев): во время
   проверки должны стоять writers базы, а прочая работа Git в `R` (worktrees,
   index) итог не меняет. При отказе скрипт называет расходящиеся пути и
   удаляет свою копию.

   Это **проверка совместимости данных**, а не готовности среды: проверяются
   конфигурация штатного загрузчика и её принадлежность workspace, владение
   баз компонентов, версия каждого исходного документа (центральной базы или
   coordinator и каждой базы компонента), версия движка и роль controller,
   документ исполнения строгими схемами движка. Начиная с 0.4.0-alpha.6
   каждая база открывается только для чтения: проверка не запускает проекции
   и журнал, не создаёт баз и таблиц и не присваивает владельца; отсутствующая
   база или база компонента без владельца — отказ. С 0.4.0-alpha.7 версия
   каждого документа базы компонента проверяется и у пустого workspace, где
   coordinator ещё не записал реестр компонентов, — при любом чтении и до
   любой записи. Модели, CLI агентов, песочница и live-проверки в
   контейнере не проверяются — их нет в образе, и их отсутствие не делает
   данные несовместимыми. Итог — JSON: `scope: "data-compatibility"`, код
   выхода проверки данных (`dataCheckExit`, 0 — данные совместимы),
   `compared` (сравниваемые каталоги данных), `originalUnchanged` (их
   отпечаток в оригинале до и после), `copyChanged` (какие файлы этих
   каталогов в копии изменились, например перевод базы с журналом DELETE в
   WAL) и
   `copyDataChanged` (базы, у которых изменилось содержимое таблиц; ожидается
   пусто). Проверка несовместимой версии не меняет данные.

## Обновление

- **Установка DevContour** — новая версия из npm (`npm install --global
devcontour@<version>`) или новый архив: `npm install --omit=dev
--ignore-scripts ./devcontour-<version>.tgz`. Закреплённый движок npm
  ставит из registry точной версией этой версии DevContour; остальные
  зависимости разрешаются при установке (lock не публикуется).
- **Смена закреплённого движка в checkout DevContour** — только
  опубликованная версия: `node scripts/pin-harness.mjs <version> --commit
<SHA исходников> --archive ./devcontour-harness-<version>.tgz`, затем
  `npm ci` и `npm run check`. Меняются только `package.json`,
  `package-lock.json` и `vendor/harness/README.md`; пакет сам не
  обновляется. Check репозитория harness для уже проверенного архива не
  повторяется: [руководство разработчика](development.md#три-уровня-проверки).

После обновления — **обязательно полный** `devcontour doctor --workspace W`
на хосте, до возобновления writers: это проверка среды (CLI агентов,
песочница, роли, профили), которую проверка данных на копии не заменяет.
Только при `ready: true` — запуск **одного** controller (`devcontour serve` или `devcontour run`). Попытки, активные во
время остановки, со старыми токенами не продолжаются: живую роль controller
процесса другой версии новая версия не перенимает; после истечения роли
попытка завершается явно, и задача ждёт явного повтора
(`devcontour retry --task T`) — новая попытка получает новое владение и новые
проверки. Установка не меняет профиль, закрепления контекста, инструкции
агентам и принятые результаты.

## Откат

| Ситуация                                                                                             | Действие                                                                                                                                  |
| ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Только движок, формат совместим (новая версия остановлена штатно, роль снята)                        | Остановить writers → вернуть прежние `package.json`, `package-lock.json`, `vendor/harness` → `npm ci` → `devcontour doctor` → возобновить |
| Новая версия изменила формат (например, роль controller с `engineVersion` после аварийной остановки) | Прежняя версия отказывает до записи. Остановить writers → восстановить копию всех баз вместе с совместимой версией → сверить Git (ниже)   |
| DevContour откатывается к версии без `gateIdentity` после Git sync новой версии                      | Ниже, «Откат после Git sync»                                                                                                              |

### Сверка Git после восстановления копии

База и Git не образуют одну транзакцию. Если после копии новая версия
приняла задачу, target ref продвинут, а восстановленная база об этом не
знает.

1. Для каждого репозитория найдите коммиты работы, не покрытые принятыми
   задачами восстановленной базы:
   `git rev-list main ^<result SHA каждой принятой задачи> -- . ':(exclude).devcontour'`.
2. Каждый такой коммит — принятие, выполненное вне восстановленного
   состояния. Его нельзя молча «забыть»: повторите задачу новой попыткой
   (`devcontour retry`/обычная очередь — её интеграция продолжит текущий
   target ref) либо явно задокументируйте это принятие.
3. Не выполняйте `git reset --hard` и не переписывайте target ref ради
   совпадения с базой — это не откат, а потеря принятой работы.

Откат успешен, только когда каждый коммит работы на target ref учтён
принятой задачей восстановленного состояния.

### Откат после Git sync новой версии

Начиная с 0.4.0-alpha.1 receipt принятой задачи содержит необязательное поле
`gateIdentity` (тождество проверок, по которым задача принята). Версии до
этого поля отклоняют такой receipt: Git sync прежней версии останавливается,
ничего не записав.

Варианты:

- **оставить всю команду на новой версии** — receipts прежних версий она
  читает;
- **откатиться**: остановить writers → восстановить копию баз, сделанную до
  обновления → в каждом репозитории сделать `git revert` коммитов
  `.devcontour`, выпущенных новой версией (историю не переписывать) → Git
  sync прежней версией → сверка Git (выше): задачи, принятые новой версией
  после копии, повторяются прежней версией.

## Проверка процедур

На копии этого checkout во временном каталоге, без моделей и реальных
workspace:

```bash
# обновление закреплённого движка (T40/T41)
npm run check:upgrade -- ./devcontour-harness-<from>.tgz ./devcontour-harness-<to>.tgz --to-commit <SHA to>
# если checkout закреплён не на <from> — добавьте --from-commit <SHA from>
# прерванное обновление, откат пакета, восстановление копии, откат DevContour (T42)
npm run check:upgrade -- ./devcontour-harness-<from>.tgz ./devcontour-harness-<to>.tgz --to-commit <SHA to> \
  --rollback --baseline-commit <SHA прежней версии DevContour>
```

T42 выполняется в обеих топологиях хранения на настоящих Git-репозиториях:
прерванная установка не трогает базы и refs, первое открытие новой версией
ничего не переписывает; откат только движка продолжает работу; после
аварийной остановки новой версии прежняя отказывает до записи, копия
восстанавливается, сверка Git называет принятие, о котором копия не знает,
и успех объявляется только после повторной попытки; откат DevContour после
Git sync новой версии проходит через копию баз и `git revert` общих записей.

### Обновление DevContour вместе с движком

Режим выше закрепляет оба движка под одними исходниками DevContour и годится
только для смены одной зависимости. Когда меняются и исходники DevContour
(новые imports движка), каждая сторона проверяется своим source snapshot:

```bash
npm run check:upgrade -- ./devcontour-harness-<from>.tgz ./devcontour-harness-<to>.tgz \
  --from-commit <SHA исходников from> --to-commit <SHA исходников to> \
  --from-devcontour-commit <полный SHA DevContour «до»> \
  --to-devcontour-commit <полный SHA DevContour «после»> \
  [--to-worktree] [--out <manifest.json>]
```

Оба snapshot — клоны этого репозитория во временном каталоге на указанных
SHA; ветка, HEAD и index checkout не меняются. Каждый snapshot обязан сам
поставлять свой архив (зависимость, lock, integrity, байты в
`vendor/harness` и строка `vendor/harness/README.md` с SHA-256 архива и
commit исходников движка) и ставит только свой lock: прежний движок под
новые исходники не ставится. `--to-worktree` (когда
`--to-devcontour-commit` — HEAD checkout) переносит в snapshot «после»
незакоммиченные изменения и сверяет их байты. Fixture создаёт DevContour
«до» своим движком: живая роль и активная попытка, принятые задачи с
настоящими коммитами и receipts Git sync в топологиях central и component.
DevContour «после» не перенимает живую роль, после истечения продолжает с
новым владением, открывает состояние без перезаписи баз, сохраняет историю,
SHA и прежние receipts и продолжает цепочку задач; прежний DevContour над
живой ролью новой версии не пишет и не выдаёт работу. Fingerprints обеих
сторон (commit, tree, digest `git ls-tree -r`, архив и его commit) — в
`upgrade-check.json` и `--out`. Записи нового вида, которые пишет DevContour
«после» (поручение быстрого маршрута, заметка обсуждения, отметка центра
внимания, запрос ведущему), шаг P3 хранит в манифесте по видам (`seeded`) и
сверяет по id с повторным чтением базы новым процессом и после аварийной
остановки; snapshot «после» без этих id не проходит P3.
