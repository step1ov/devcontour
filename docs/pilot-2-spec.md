# Пилот: заявки на доступ

## Цель и приложения

Сотрудник в веб-приложении создаёт заявку на доступ и видит её в списке после обновления страницы. Пользователь не должен потерять результат успешной отправки. API и веб-интерфейс — технические компоненты одного приложения. Мобильное приложение запланировано, но в этот релиз не входит; создание заявки для него явно deferred. Отдельная фича выгрузки списка в CSV отложена для веба и неприменима к мобильному приложению в данном релизе.

## REQ-create: Создать заявку

Имя сотрудника и название ресурса обязательны после удаления внешних пробелов, максимум 100 символов каждое. Сервер проверяет ввод независимо от клиента. Успех возвращает стабильный ID и сохраняет заявку в локальном файловом хранилище. Ошибка валидации не создаёт запись и видна рядом с формой. Повторные отправки и конкурентный доступ не входят в пилот; это ограничение явно документируется.

## REQ-list: Увидеть сохранённые заявки

После успешной отправки новая запись видна в списке. Обновление страницы и перезапуск сервера сохраняют данные. Пустой список имеет понятное состояние. При недоступном API интерфейс сообщает об ошибке и позволяет повторить загрузку. Форма доступна с клавиатуры и имеет подписи полей.

## REQ-scope: Граница пилота

Авторизация, облачная публикация, мобильная реализация, CSV и production-эксплуатация не входят в релиз. Используются только вымышленные тестовые данные, локальный сервер и временное хранилище. Проверки не обращаются к production-сервисам.

Ведущий агент самостоятельно выбирает минимальный стек, описывает контракт, готовит локальные INTENT и карту приложений/фич, декомпозирует работу на 3–5 связанных задач и настраивает исполняемые проверки. Как минимум одна зависимость связывает API и интерфейс. Общий релиз принимается через ChangeSet с releaseId. Готовый граф, утверждения или подсказанная реализация в исходные материалы не включены.
