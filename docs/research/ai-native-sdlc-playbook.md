# AI-native SDLC: дополнение к исследованию DevContour

Дата анализа: 17 сентября 2026 года. Сопоставление выполнено с DevContour 0.2, коммит `2eb0a26`. Статус: историческое исследование и предложения, не спецификация исполнения. Реализация в 0.3 описана отдельно: [требования](../requirements.md), [evals](../agent-evals.md), [метрики](../metrics.md), [workflow](../lead-workflow.md), [сигналы](../external-signals.md).

Источник: Louis Claxton, Anthropic, [The AI-Native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook), опубликован 21 августа 2026 года. Это практическое руководство поставщика, а не сравнительный эксперимент. Оно не доказывает ускорение или надёжность DevContour.

## Что добавляет источник

Playbook рассматривает весь цикл: планирование, дизайн, реализацию, проверки, выпуск и сопровождение. Результаты этапов передаются через версионируемые артефакты. Инструкции и skills дополняются исполняемыми ограничениями; качество конфигурации агента проверяется evals. Обратная связь из эксплуатации возвращается в планирование. Предлагаются метрики ожидания, качества и переделок. В ранних этапах предусмотрено участие владельца продукта, а в автономном сопровождении — независимые проверки и эскалации. [Источник](https://claude.com/blog/the-ai-native-sdlc-playbook).

Мой вывод для DevContour: следующий прирост полезности стоит искать в проверяемой передаче контекста и качестве решений ведущего агента. Увеличение количества workers имеет смысл после измерения задержек существующего процесса. Ниже — самостоятельная оценка нашего кода и предложения по его развитию.

## Предлагаемый порядок развития

### 1. Связать требования с проверками

Существующий `docs/spec.md` остаётся входом. Не нужно заставлять оператора вручную создавать ещё несколько документов. Агент может выделять требования с устойчивыми IDs, фиксировать предположения и связывать каждое требование с Task/Contract и проверяемым сценарием.

Предлагаемая связь: `requirementId → spec digest → task ID → gate/scenario → result SHA`. Локальные требования библиотеки остаются в её репозитории; общий workspace содержит межкомпонентные связи. План в Markdown, если он нужен человеку, следует генерировать из DAG, иначе появятся два расходящихся источника задач.

Критерий приёмки расширения: изменение требования делает прежнее подтверждение неактуальным, показывает затронутые задачи и создаёт корректировку принятой доски. Наличие файла не разрешает следующий этап автоматически.

### 2. Проверять качество ведущего агента и конфигурации

Это отдельная проверка поверх существующих unit/integration tests инструмента. Предлагаю начать с небольшого набора наших сценариев: неверная зависимость, устаревший контракт, недоступный обязательный gate, перенос памяти библиотеки, продолжение с устаревшего checkpoint, попытка принять непроверенный результат.

Для каждого случая нужны исходный Git fixture, цель, доступные инструменты и независимый проверяющий код. Результат сравнивается по поведению и доменным инвариантам, а не по совпадению текста ответа. Фиксируются версии модели, runtime, skill/context digest, число попыток, длительность и доступная информация о расходах.

Два режима: детерминированные сценарии протокола в обычном CI и явно запускаемые live-evals с бюджетом. Недоступность модели отмечается как непроверенный случай. При сравнении моделей нужны одинаковые исходные условия и несколько повторов; один удачный запуск недостаточен. Автор решения не определяет собственный PASS.

Критерий приёмки: заведомо ослабленная инструкция приводит к обнаруженной регрессии; исходная конфигурация проходит тот же сценарий. Ни секреты, ни полные диалоги не попадают в командную Git-память.

### 3. Измерять, где теряется время

Начать с отчёта по существующим событиям и runs, добавляя явные события для недостающих границ. Разделять ожидание зависимостей, выдачи задачи, окружения, review, тестов, интеграции и публикации человеком. Общее время не следует приписывать модели.

Показатели пилота: время до принятого ChangeSet, доля приёмок с первой попытки, количество корректировок после приёмки, ручные вмешательства и расходы на принятый результат. Неизвестную стоимость показывать как неизвестную. Сравнение 1/2/4 workers проводить на одинаковом наборе задач.

Критерий приёмки: каждая длительность объясняется событиями; незавершённые и прерванные попытки не исчезают из статистики. По отчёту можно обоснованно решить, нужны ли дополнительные workers.

### 4. Добавить устойчивый цикл ведущего агента

Только после предыдущих проверок стоит автоматизировать переход от принятого артефакта к следующей стадии. Предлагаемый механизм: сохраняемое событие с ключом идемпотентности, привязанным к workspace, стадии и digest входа; lease исполнителя; повтор после сбоя; ограничение повторов и расходов.

Task scheduler сохраняет владение попытками. Второй процесс ведущего агента не должен создавать дублирующие доски или отменять чужие leases. После изменения входа старая стадия не может принять новый результат под прежним digest.

Критерий приёмки: прерывание между действием и подтверждением, повтор одного события, конкурентный запуск и устаревший ответ не создают дубликатов и не обходят review. Это новая возможность; текущие checkpoints её не предоставляют.

### 5. Подключить внешние сигналы после пилота

Для первого адаптера достаточно read-only диагностики CI и создания предложенной работы. Нужны идентификатор внешнего события, дедупликация, маршрут к репозиторию-владельцу, ограничение частоты и ссылка на проверяемые данные. Закрытая доска получает корректировку, история не переписывается.

Критерий приёмки: повтор алерта не размножает задачи, исчезновение сигнала не подделывает успешную проверку, локальная проблема библиотеки не переносит её журнал в общий workspace. Подключение такого адаптера само по себе не даёт прав на push, deployment или rollback.

## Решения, которые сохраняем

- `approvalMode: agent` остаётся режимом по умолчанию. Из нового источника не следует возвращение ручного согласования каждого этапа. Неясные бизнес-требования и явно заданные операторские ограничения всё равно требуют разрешения.
- DevContour остаётся независимым от поставщика модели и Git forge. Настройки конкретного runtime адаптируются отдельно, а не копируются в общий договор.
- Для исправления ошибки можно закреплять воспроизводящий сценарий и защищать его от изменения исполнителем. Общий запрет редактировать любые тесты помешает новым требованиям: изменение AC оформляется новой постановкой и review.
- Правило в skill, Git hook и доменный gate имеют разную силу. Hooks дают раннюю обратную связь; приёмка остаётся в домене. Для будущего недоверенного исполнения понадобится отдельная изоляция ОС и прав доступа.
- Повторяющееся замечание сначала становится проверяемой находкой. В постоянные правила оно попадает после проверки области применимости; журнал не превращается автоматически в набор запретов.

Приоритет предложения: связи требований и проверки поведения агента, затем измерение задержек, затем устойчивое ведение стадий и внешние сигналы. В этом изменении сохранено исследование; новые режимы исполнения и live-вызовы не добавлены.
