# Сравнение исполнителей и стратегий

Изменение модели, runtime или правил должно иметь проверяемую причину. Сначала измерьте одинаковые задачи при одинаковых условиях; затем проверяйте выбранное изменение на отдельном наборе сценариев. Никакой отчёт этого раздела не устанавливает новую production-политику автоматически.

## Инженерный корпус

`devcontour engineering-evals` создаёт отдельный Git-репозиторий на каждый сценарий и повторение, утверждает фиксированную спецификацию корпуса и запускает обычный scheduler. Есть три небольших сценария:

1. Изменение формата ответа API одновременно с его потребителем.
2. Идемпотентная миграция настоящей SQLite с сохранением существующих данных и ограничением NOT NULL.
3. Регрессия пагинации: границы, валидация аргументов и неизменность входного массива.

Исполняемый oracle формирует JUnit; проверка проходит на candidate и integration SHA. Файл oracle защищён от принятия изменений агента. Worktrees, проверка diff, review и интеграция используют обычные правила DevContour. Репозитории, SQLite и сырые runtime logs удаляются после сценария, в итоговом JSON остаются агрегаты и измерения. Это не sandbox для недоверенного кода того же пользователя ОС; live запуск требует настроенных ограничений runtime.

По умолчанию `mode: engineering-fixture`: исполнитель записывает известное исправление, reviewer возвращает fixture-ответ, реальный тестовый oracle проверяет поведение. PASS подтверждает механизм корпуса, не качество LLM. Намеренно пустой исполнитель проверяется отдельным негативным тестом и проваливает каждый сценарий.

```sh
devcontour engineering-evals > fixture.json
devcontour engineering-evals --live --runtime codex --model AUTHOR_MODEL --reviewer-model REVIEW_MODEL --repetitions 3 --max-calls 27 > baseline.json
```

Live режим требует явных моделей автора и противоположного runtime-reviewer. При `codex` проверяет `claude`, и наоборот. Команда расходует лимиты обоих. `--prices /absolute/prices.json` передаёт JSON-массив тарифов в изолированный evaluator; формат элемента совпадает с prices в конфигурации. Это позволяет оценивать стоимость по токенам, когда runtime не отдаёт сумму. Без таблицы такой расход остаётся неизвестным. Параметры: repetitions 1–5 (default 1), max-calls 1–45 (default 9), timeout-ms 1000–900000 (default 120000 на попытку). Полный успешный корпус требует `3 сценария × 3 вызова × repetitions`: реализация и два review. Здесь calls означает запуск runtime, внутри которого может быть несколько обращений к модели. Денежный предел задавайте у провайдера.

Недостаток бюджета, ошибка окружения или недоступный runtime даёт `unverified`, а не PASS. Перед началом случая резервируется возможность трёх вызовов; оставшегося меньшего бюджета недостаточно даже для частичного случая. Ошибка исполняемого oracle/review даёт failed. Все сценарии должны пройти для нулевого exit code. Истинный статус задачи и evidence важнее самоотчёта исполнителя.

Это компактный корпус на Node/SQLite, а не универсальная оценка всех стеков. Он не проверяет PostgreSQL, UI в браузере, мобильные устройства или корпоративные библиотеки. Для выбора исполнителей конкретного продукта добавьте репрезентативные сценарии и отдельную контрольную выборку. Шесть сценариев [решений агента](agent-evals.md) дополняют корпус проверками DAG, полномочий и контекста.

## Сопоставление отчётов

```sh
devcontour eval-compare --baseline baseline.json --candidate candidate.json
```

Принимаются отчёты `evals` и `engineering-evals`. Требуются одинаковые priceTable/corpus/catalog digests, mode, repetitions, maxCalls и timeoutMs, а также уникальные совпадающие пары caseId/repetition и полный объявленный список caseIds. Старые отчёты без списка случаев нужно получить заново. Модели или инструкции могут отличаться — это и есть предмет эксперимента. Fixture, injected driver и live не смешиваются. Отчёты доверенные локальные данные, не аттестация провайдера.

Сравнение показывает пары исходов, доли PASS, общую длительность и стоимость при полном покрытии. Неизвестная стоимость остаётся null. Разность успешности усредняется по сценариям. Детерминированный paired bootstrap делает 2000 пересэмплирований сценариев целиком, сохраняя повторы внутри сценария. При unverified разность и интервал не выдаются. Три простых сценария дают слабую статистическую основу: узкий интервал на них не доказывает превосходство в разработке продукта.

Сохраняйте вместе с отчётом версию DevContour, ОС/Node, модели, версии runtime и условия запуска. Для честного эксперимента не меняйте одновременно набор задач и все настройки. Повторяйте проверку на задачах, которые не использовали для настройки инструкций. Учитывайте стоимость неудачных попыток и последующих исправлений; размер сгенерированного кода не является целевой метрикой.

## Журнал решений оркестратора

Каждый новый claim записывает в Run наблюдаемый набор допустимых вариантов: IDs задач/компонентов, число прошлых попыток, активные workers, concurrency и правило `fifo-ready-v1`. Выбор и запись фиксируются вместе в транзакции. У задачи сохраняются также runtime/model, policy digest, исходный SHA, context packs и снимок дополнительной памяти. Старые Run без этой записи остаются `unrecorded`.

`decision_report` читает записи выбранного владельца страницами через `limit` и `cursor`. Результат попытки присоединяется отдельно от входов решения. Полные описания задач других компонентов не копируются: допустимые альтернативы содержат только IDs и счётчик попыток. Журнал не записывает внутренние рассуждения модели.

```json
{
  "operation": "strategy_replay",
  "input": { "repositoryId": "chat", "policy": "fewest-attempts-v1" }
}
```

Доступны `fifo-ready-v1` и экспериментальное `fewest-attempts-v1`. Второе правило предпочитает допустимую задачу с меньшим числом попыток; при равенстве сохраняет исходный порядок. Оба видят только входы, доступные на момент claim. Фактический результат не участвует в выборе.

Если правило выбирает ту же задачу, отчёт считает matched и показывает наблюдавшийся исход. Другой выбор считается unsupported: история не содержит его результата при этих условиях. Это аудит независимых решений, не симуляция всей альтернативной разработки. Нельзя складывать наблюдавшиеся длительности как прогноз ускорения, переносить результат из другой версии кода или трактовать matched subset как доказательство превосходства. `promotable` всегда false. Replay не делает model calls и не меняет scheduler, gates, задачи или приёмку.

Журнал Run и подробные usage records локальны; Git receipts не переносят их в чужую рабочую копию. После накопления репрезентативных историй можно расширять экспериментальный набор стратегий и проводить ограниченный live-пилот. Для каждой новой стратегии нужны тест на отсутствие доступа к будущим исходам, контрольная выборка и способ вернуться к прежней политике.
