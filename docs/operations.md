# Эксплуатация и восстановление

Этот документ рассчитан на ведущего агента и разработчика, который сопровождает workspace. Команды выполняются из каталога DevContour с явным путём данных. Не восстанавливайте систему ручным выставлением `done`, редактированием evidence или удалением owner marker: это уничтожает основания приёмки.

## Начало и продолжение сессии

Для командного workspace после получения Git-изменений выполните при остановленном сервере и отсутствии других записывающих клиентов `sync-status`, затем `sync`. Одной паузы workers недостаточно, пока LeadRunner продолжает стадии. Согласование файлов с локальной БД, переход между ветками и восстановление после clone описаны в [командной синхронизации](team-sync.md). Полный backup процессов, логов и общей приёмки нужен отдельно.

1. Получите подтверждённый путь workspace из поручения или сохранённого контекста этой работы. Для нового проекта без пути задайте обязательный вопрос.
2. Прочитайте `<workspace>/docs/devcontour-progress.md`, конфигурацию, правила компонентов и последние события. Заметки объясняют намерение; состояние SQLite и Git определяет фактический прогресс.
3. Выполните `project_overview`, `workflow_status` для общего и нужных компонентных контуров, `doctor`; полный `export` используйте для диагностики задач/событий. Проверьте активные попытки, очистку, ресурсы и готовность jobs до старта сервера: зарегистрированный workflow может начать работу сразу.
4. Найдите действующий сервер этого workspace. В `/api/state` должны совпасть `dataRoot` и `config.workspaceRoot`. При отсутствии сервера запустите `serve` на свободном порту и сохраните URL в progress.
5. Продолжайте существующие доски. Повторный `import-plan` создаёт новую доску, поэтому не используйте его как команду возобновления.

```sh
npm run devcontour -- export --workspace /absolute/product-workspace
npm run devcontour -- doctor --workspace /absolute/product-workspace
npm run devcontour -- serve --workspace /absolute/product-workspace --port 4317
```

`export` собирает доменное состояние и события подключённых баз. Оно может содержать подробности локальных задач: это диагностический вывод, а не общая командная память. Jobs и signal receipts из `local_workflow` в него не включены; читайте `workflow_status` и `signal_status` у соответствующего владельца. Export не является полным backup, поддерживаемого обратного импорта нет.

## Пауза, отмена и остановка

| Действие                   | Последствие                                                                       |
| -------------------------- | --------------------------------------------------------------------------------- |
| `queue --pause`            | Прекращает выдачу новых задач; текущие попытки продолжаются                       |
| Отмена задачи в UI/API     | Отзывает владение, scheduler останавливает попытку; поздний результат отклоняется |
| `Ctrl+C` / SIGTERM сервера | Штатная остановка scheduler и процессов; очередь ставится на паузу                |
| Аварийное завершение       | Срабатывают lease/recovery; внешние сервисы могут потребовать очистки             |

Пауза очереди не приостанавливает review/приёмку workflow. Стадия ожидания задач сохраняет явную паузу, но стадия запуска нового board job может включить очередь снова. Отдельной команды остановки конкретного workflow пока нет. Для обслуживания штатно остановите сервер и исключите параллельные записи через MCP/CLI; это остановит LeadRunner и scheduler. При перезапуске после shutdown незавершённый workflow может возобновить выдачу. Подробности — [стадии и восстановление](lead-workflow.md).

```sh
npm run devcontour -- queue --pause --workspace /absolute/product-workspace
```

Для изменения конфигурации: сначала пауза, затем дождаться окончания либо явно отменить текущую работу, остановить сервер, сохранить копию настроек и состояния, изменить политику, выполнить проверку и перезапустить. CLI и долго работающий сервер должны видеть одну версию политики. Hot reload конфигурации не реализован.

## Setup отклоняет путь

Setup не пишет через symlink в пути назначения. На macOS временные пути `/tmp` и `/var` могут быть ссылками на `/private/...`; используйте проверенный канонический путь, не отключайте защиту. Для обычного workspace укажите непосредственно выбранный каталог проекта и проверьте его содержимое до повторного setup.

## Если задача не запускается

Для сохраняемого workflow сначала запросите `workflow_status` с правильным `repositoryId` (без него — общий ChangeSet). `stale` требует перечитать граф/политику и зарегистрировать новый вход; `failed` — разобрать причину и только затем вызвать `workflow_retry`. Retry стадии не повторяет упавшую Task и не сбрасывает её бюджет. Удалённый вход делает job устаревшим, но не блокирует другие jobs. Автомат работает только внутри `serve` и не продвигается в operator mode. [Договор восстановления](lead-workflow.md).

Проверяйте в таком порядке:

1. Правильный ли workspace открыт и есть ли работающий scheduler? `queue --start` меняет состояние, но сам не создаёт сервер.
2. Не стоит ли очередь на паузе? Принадлежит ли задача активной ревизии?
3. Задача `draft` или `ready`? Черновик сначала проходит утверждение плана.
4. Все ли `dependsOn` имеют `done`, существуют ли нужные контракты?
5. Есть ли свободный worker, не выполняется ли совместная Verification/Delivery, блокирующая новую выдачу?
6. Не ждёт ли уже выданная попытка ресурса? Ожидание ресурса входит в timeout попытки.
7. Нет ли конфликта ownership или открытой `devcontour/accepted` в чужом worktree?

У Task нет отдельного статуса `blocked`; список блокирующих зависимостей вычисляется. Не добавляйте фиктивный `done` зависимой задаче ради запуска потребителя.

## Если попытка завершилась ошибкой

Сначала откройте failure, phase, команды, exit code, JUnit и review соответствующего Run. Исправляйте причину, затем выполняйте `retry`; не повторяйте запуск бесконечно с неизменённым окружением.

| Причина                                  | Действие                                                                                                            |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| CLI не найден, недоступна авторизация    | Настроить CLI/явные env, проверить небольшим live-сценарием                                                         |
| Нет отчёта, пустой JUnit, skipped        | Исправить reporter или среду; обязательный сценарий должен реально выполняться                                      |
| Test gate изменил tracked-файлы или HEAD | Перенести генерацию в bootstrap/реализацию либо игнорируемый output; проверка не должна менять проверяемый исходник |
| Diff вышел за writePaths/protectedPaths  | Пересмотреть постановку или отдельное изменение политики; не ослаблять защиту для сокрытия сбоя                     |
| Candidate прошёл, integration упал       | Разобрать взаимодействие с уже принятыми изменениями; новая попытка стартует с актуальной базы                      |
| Reviewer вернул blocking finding         | Проверить аргумент и исправить результат; `approved: true` с blocking finding всё равно не PASS                     |
| Контекст/профиль не совпадает            | Сверить исходник, версию и digest, провести осознанное обновление                                                   |
| Исчерпан maxAttempts                     | Изучить все попытки, уточнить постановку/среду; увеличение лимита требует причины и фиксации решения                |

```sh
npm run devcontour -- retry --task T12 --workspace /absolute/product-workspace
```

Новая попытка получает новый worktree и контекст предыдущих неудач. Незакоммиченный результат прежнего worktree автоматически не переносится; при необходимости сначала сохраните и разберите его. Артефакты и рабочие каталоги не удаляются автоматически.

## Восстановление окружения и ресурсов

Если teardown не завершился, сначала прекратите выдачу новых задач и убедитесь, что владелец попытки действительно остановлен. Найдите сохранённый `environment.json` в артефактах соответствующей попытки, проверьте указанные ресурсы и команды очистки.

```sh
npm run devcontour -- environment-cleanup --receipt /absolute/path/from-run/environment.json --workspace /absolute/product-workspace
npm run devcontour -- resources --workspace /absolute/product-workspace
```

Receipt должен принадлежать выбранному workspace/компоненту, а политика очистки — соответствовать сохранённой. Команда не предназначена для произвольного JSON извне. Если конфигурация изменилась, сначала восстановите и проверьте подходящую cleanup policy.

После фактической остановки оставшихся сервисов/драйверов можно освободить оставшуюся аренду, подставив **текущие** key/token из `resources`:

```sh
npm run devcontour -- resource-release --key RESOURCE_KEY --token CURRENT_TOKEN --cleanup-confirmed --workspace /absolute/product-workspace
```

Живой PID или другой token блокируют освобождение. TTL означает потерю heartbeat, а не доказанную свободу устройства. Не удаляйте `~/.devcontour-local/resources.sqlite` для снятия блокировки: этим можно нарушить работу другого workspace.

## Журнал не обновился

SQLite commit и запись Markdown — разные операции. При ошибке диска состояние может быть корректно сохранено, а журнал отстать. Устраните файловую причину и пересоберите проекцию:

```sh
npm run devcontour -- journal --workspace /absolute/product-workspace
```

Проверяйте `journalError` в API/сообщение CLI. Ручная правка автоматического дневника не исправляет базу и будет потеряна при следующей проекции. Выводы человека или агента сохраняйте отдельно в ADR/memory.

## «database is locked»

Панель и CLI держат одно состояние из разных процессов. Проекция журнала берёт
только читающую транзакцию, поэтому запущенный сервер не мешает агенту писать:
в WAL читатель писателю не помеха. Ожидание блокировки — 20 секунд.

Если ошибка всё же появилась, ищите долгую **запись**, а не чтение: параллельный
`run`, миграцию состояния или `git sync`. Останавливать сервер ради команды CLI
не требуется.

## Runtime не авторизован

Окружение прогона минимальное: исполнитель не наследует всё, что есть у оператора. Но учётные данные runtime живут в системном хранилище, и найти их там нельзя, не зная имени учётной записи — поэтому `USER` и `LOGNAME` передаются всегда. Это адрес в хранилище, а не секрет.

Без них `claude` на macOS отвечает «Not logged in», и единственным выходом остаётся передать API-ключ через `environment.inherit` — то есть платить за то, что уже оплачено подпиской. Ключ нужен только там, где подписки нет.

`doctor --probe` проверяет авторизацию настоящим вызовом в том же окружении, которое получит исполнитель. Обычный `doctor` смотрит `--version`: это доказывает, что файл на месте, а не что им можно работать.

## Исчерпан лимит времени прогона

Попытка ограничена `runTimeoutMs`. Пятнадцати минут по умолчанию хватает на правку, но не на реализацию с нуля: агент упирается в предел посреди работы, и попытка расходуется впустую, оставив незавершённое.

Лимит объявляет профиль стека — он знает, сколько стоит его работа; из слоёв берётся наибольший. Прерывание по лимиту теперь названо в причине отказа: раньше оператор видел «код 143» и не мог отличить исчерпанное время от остановки сервера.

Такая попытка **засчитывается**: она израсходовала весь отведённый бюджет. Если задача велика настолько, что не укладывается и в поднятый лимит, делить нужно задачу, а не поднимать предел дальше.

## Пустой кандидат

Задача с областью записи обязана что-то изменить. Исполнитель, отчитавшийся «сделано» пустым коммитом, отклоняется до ревью: гейты на таком кандидате зелены ровно потому, что были зелены и до него, и вся проверка легла бы на независимое ревью — полный прогон ради ответа «diff пуст».

Отказ называет причину так, чтобы следующая попытка знала, что делать: выполнить работу по критериям приёмки либо объяснить в отчёте, почему изменения не требуются.

## Выдача остановилась сама

Отказ, который повторится на любой задаче — кончились кредиты провайдера, runtime не авторизован, ключ недействителен, — останавливает выдачу и попадает в журнал с причиной. Панель показывает её на вкладке разработки и в строке состояния оркестратора.

Так сделано потому, что причина лежит вне контура и одинакова для всех задач: очередь, которая продолжила бы перебор, сожгла бы бюджет попыток каждой задачи, не выполнив ни одной. Временные ошибки сети и лимиты частоты сюда не входят — останавливать из-за них значило бы звать человека без нужды.

Устраните причину и запустите очередь: `queue --start`. Задачам, чей бюджет уже израсходован, дайте попытку сбросом.

## Постановку нужно изменить до приёмки

Утверждённая постановка неизменна — под неё уже велась работа. Но пока задача не дала принятого результата, изменить её бывает необходимо: контракт исправлен до того, как доска принята, и переписывать под прежнюю редакцию нечего.

```sh
npm run devcontour -- reopen --task T-... --reason "Контракт исправлен: привязка ссылается на прежнюю редакцию" --workspace /absolute/product-workspace
```

Возврат разрешён только задаче без принятого результата. Прогоны остаются в истории; утверждение снимается, и доску нужно провести через `review-plan` заново — иначе это был бы обход независимого согласования. Задачу, которая уже дала результат, возвращает только корректировка доски.

## Попытка, потраченная не на задачу

Бюджет попыток задачи расходуется на работу исполнителя, а не на неполадки контура. Прогон, в котором runtime не выдал результата — не авторизован, оборвался, не получил закреплённый пакет контекста, — помечается `blocked`, и попытка возвращается: задача ни разу не была попробована. `retry` после такого отказа доступен.

Возврат действует, пока работа не начата. Таймаут ревьюера после готового кандидата — настоящая попытка: она стоила прогонов, и не засчитывать её значит разрешить дорогому циклу крутиться без предела.

Отличать это от настоящего провала важно: иначе задача упирается в лимит, ни разу не дойдя до исполнителя, и выглядит невыполнимой, хотя её никто не выполнял.

Когда бюджет всё же исчерпан настоящими провалами, а причина устранена, попытки сбрасываются явно:

```sh
npm run devcontour -- retry --task T-... --reset --reason "Окружение исправлено: runtime авторизован" --workspace /absolute/product-workspace
```

Сброс доступен и задаче в состоянии `ready`: после исправленной постановки задача снова готова, но израсходованный бюджет никуда не делся — диспетчер её не берёт, и без сброса она стоит молча. Причина обязательна и попадает в журнал рядом с числом сброшенных попыток. Прогоны не удаляются: история показывает, сколько раз задача не справилась, а не задачу, справившуюся с первого раза.

## Резервное копирование

Резервная копия нужна перед миграцией состояния, переносом workspace, крупным обновлением политики и очисткой артефактов. Поддерживаемой универсальной команды backup/restore в MVP нет.

Для согласованной файловой копии:

1. Поставьте очередь на паузу, дождитесь/отмените Run, Verification и Delivery, завершите cleanup.
2. Остановите сервер и все CLI, способные записывать это состояние. Одна пауза не запрещает другому клиенту менять черновики.
3. Сохраните весь workspace и `.devcontour-local/` всех компонентов, `devcontour.component.json`, правила и memory. Нужны все связанные `state.sqlite`, а не только coordinator. Для legacy WAL после штатного закрытия сохраняйте комплект имеющихся файлов БД вместе; не копируйте один live-файл.
4. Сохраните Git-репозитории с refs `devcontour/*`, служебными refs и metadata worktree/owner, включая незакоммиченные результаты. Обычный клон ветки main или только Git bundle не сохраняет весь этот набор.
5. Запишите канонические пути, ID компонентов, версию DevContour, profile locks и процедуру восстановления внешней среды. Значения секретов хранятся отдельным принятым в команде способом, не в открытом архиве настроек.

Ресурсный pool общий для хоста. Его нельзя восстанавливать поверх активных аренд других workspace. Сначала разберите внешние ресурсы; при переносе на новый хост настройте pool и ресурсы заново.

После восстановления сначала проверяйте Git refs, целостность всего комплекта БД и owner metadata, затем `doctor` и журналы, и только потом очередь. Пути входят в привязки владельца и артефактов: копия в другую папку не является прозрачной переносимой установкой состояния. Автоматического remap путей/ID нет.

## Обновление DevContour

1. Остановите обслуживаемые workspace и сделайте согласованные копии.
2. Прочитайте изменение схем/профилей/CLI. Не изменяйте profile lock вручную только ради устранения ошибки digest.
3. Установите зависимости из lockfile, соберите и выполните подходящие проверки инструмента.
4. На копии рабочего сценария проверьте загрузку конфигурации и сохранение принятой истории.
5. Сверьте новые переносимые правила с локальными соглашениями. Повторный setup сохраняет существующие файлы и не является автоматическим обновлением правил.
6. Возобновляйте работу после `doctor` и небольшого проверяемого этапа.

Для перехода central → component есть `storage-migrate`; он требует остановленной очереди и отсутствия активных попыток. [Точная процедура и ограничения](project-integration.md). Обратной автоматической миграции и присоединения независимой непустой базы библиотеки нет.

## Публикация и длительное ожидание

`handoff` формирует пакет для человека. `remote-check` — одна проверка текущего состояния. При `waiting` выясните, чего не хватает: push, PR/MR, merge или CI именно на итоговом SHA. Не создавайте новый ChangeSet только из-за ожидания CI; повторите наблюдение для того же результата.

Если удалённое дерево отличается от проверенного локального, старой Verification недостаточно. Разберите изменения и проведите новую проверку требуемого результата. Нет фонового polling/webhook, автоматического push и скрытого обхода remote completion.

Workflow ChangeSet проверяет наличие подходящего результата Delivery в локальном состоянии; он не вызывает `remote-check` и не опрашивает forge вместо ведущего агента. Внешний сигнал CI через `signal_ingest` также не заменяет Delivery или тестовое evidence. После подтверждённого `remote-check` работающий workflow сможет завершить приёмку.

## Обслуживание Git и диска

`devcontour/accepted` нельзя держать checkout-веткой: runner продвигает её через CAS. Для просмотра создайте detached worktree.

Прогон ответвляется от ветки интеграции, а контракты, схемы и каркас готовятся на рабочей ветке. Пока эти линии не сведены, исполнитель получает дерево без работы, ради которой его запустили. Автоматически это не переносится: диспетчер отказывается выдавать работу и останавливает очередь, называя, скольких коммитов не хватает базе. Перенос — отдельная планируемая операция:

```sh
npm run devcontour -- queue --pause --workspace /absolute/product-workspace
npm run devcontour -- base-update --workspace /absolute/product-workspace
npm run devcontour -- queue --start --workspace /absolute/product-workspace
```

Когда база — предок рабочей ветки, выполняется перемотка; когда обе линии несут работу, они сводятся слиянием `--no-ff` в отдельном worktree. История не переписывается ни в одном из случаев. После переноса проверьте базу гейтами: прогоны будут ответвляться уже от неё.

Перенос базы двигает вершину ветки кодом, которого гейты не видели. Приёмка доски этого не закрепляет: она фиксирует самый поздний результат задач доски — SHA, прошедший проверки на интеграции, — а не текущую вершину. Принятое всегда доказано, даже если ветка успела уйти вперёд.

Удалять старые worktree и артефакты можно только после проверки активности, незакоммиченных результатов, ссылок evidence и требований хранения. Автоматического retention/GC нет. Если удалить лог, запись приёмки останется, но полнота аудита ухудшится; такой архив нельзя называть полностью воспроизводимым.
