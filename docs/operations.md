# Эксплуатация и восстановление

Этот документ рассчитан на ведущего агента и разработчика, который сопровождает workspace. Команды выполняются из каталога DevContour с явным путём данных. Не восстанавливайте систему ручным выставлением `done`, редактированием evidence или удалением owner marker: это уничтожает основания приёмки.

## Начало и продолжение сессии

Для командного workspace после получения Git-изменений выполните при остановленном сервере и отсутствии других записывающих клиентов `sync-status`, затем `sync`. Одной паузы workers недостаточно, пока LeadRunner продолжает стадии. Согласование файлов с локальной БД, переход между ветками и восстановление после clone описаны в [командной синхронизации](team-sync.md). Полный backup процессов, логов и общей приёмки нужен отдельно.

1. Получите подтверждённый путь workspace из поручения или сохранённого контекста этой работы. Для нового проекта без пути задайте обязательный вопрос.
2. Прочитайте `<workspace>/docs/devcontour-progress.md`, конфигурацию, правила компонентов и последние события. Заметки объясняют намерение; состояние SQLite и Git определяет фактический прогресс.
3. Выполните `project_overview`, `workflow_status` для общего и нужных компонентных контуров, `doctor`; полный `export` используйте для диагностики задач/событий. Проверьте активные попытки, очистку, ресурсы и готовность jobs до старта сервера: зарегистрированный workflow может начать работу сразу.
4. Найдите действующий сервер этого workspace. В `/api/state` должны совпасть `dataRoot` и `config.workspaceRoot`. При отсутствии сервера запустите `serve` на свободном порту и сохраните URL в progress.
5. Продолжайте существующие доски. `import-plan` без `--board` создаёт новую доску, поэтому не используйте его как команду возобновления; следующий этап принятой доски импортируйте с `--board <ID>`.

```sh
npm run devcontour -- export --workspace /absolute/product-workspace
npm run devcontour -- doctor --workspace /absolute/product-workspace
npm run devcontour -- serve --workspace /absolute/product-workspace --port 4317
```

`export` собирает доменное состояние и события подключённых баз. Оно может содержать подробности локальных задач: это диагностический вывод, а не общая командная память. Jobs и signal receipts из `local_workflow` в него не включены; читайте `workflow_status` и `signal_status` у соответствующего владельца. Export не является полным backup, поддерживаемого обратного импорта нет.

## Пауза, отмена и остановка

| Действие                   | Последствие                                                                       |
| -------------------------- | --------------------------------------------------------------------------------- |
| `queue --pause`            | Прекращает выдачу новых задач; текущие попытки продолжаются                       |
| Отмена задачи в UI/API     | Отзывает владение, scheduler останавливает попытку; поздний результат отклоняется |
| `Ctrl+C` / SIGTERM сервера | Штатная остановка scheduler и процессов; очередь ставится на паузу                |
| Аварийное завершение       | Срабатывают lease/recovery; внешние сервисы могут потребовать очистки             |

Пауза очереди не приостанавливает review/приёмку workflow. Стадия ожидания задач сохраняет явную паузу, но стадия запуска нового board job может включить очередь снова. Отдельной команды остановки конкретного workflow пока нет. Для обслуживания штатно остановите сервер и исключите параллельные записи через MCP/CLI; это остановит LeadRunner и scheduler. Пока процесс `serve` останавливается, запуск очереди отклоняется: «Сервер останавливается: очередь не запускается» — и из него же (панель, `POST /api/scheduler`, агент `queue_set` через `/api/agent`), и из другого процесса (`queue --start` в CLI, `queue_set` отдельного MCP-сервера, снятие паузы `base-update`/`base-check`). В начале остановки сервер записывает в базу локальную отметку остановки (в sync не входит); отметка действует, только пока этот сервер держит живую роль controller. Остановка освобождает роль и снимает отметку — после неё `queue --start` снова работает. Если процесс упал посреди остановки, отметка перестаёт действовать, когда истечёт срок роли (`leaseMs`), а следующий запуск сервера её снимает. Ведущий цикл сервер прерывает первым, до отметки; стадия, которой во время остановки отказано в снятии паузы, возвращается в очередь без расхода попытки. Если `base-update` в режиме агента поставил ожидание переноса на идущей очереди, а снять его не может (сервер останавливается), ожидание становится паузой остановки: при отсутствии переноса команда отвечает отказом с этой причиной, при отказе переноса — его исходной ошибкой. Второй SIGINT/SIGTERM при зависшей остановке завершает процесс с кодом 130. При перезапуске после shutdown незавершённый workflow может возобновить выдачу. Подробности — [стадии и восстановление](lead-workflow.md).

```sh
npm run devcontour -- queue --pause --workspace /absolute/product-workspace
npm run devcontour -- queue --workspace /absolute/product-workspace
```

`queue` без флага печатает, почему очередь стоит, тем же видом, что `/api/state` (поле `queue`), `/api/preparation`, сводка панели и агентские `project_context`, `project_overview`, `workflow_status`: `paused`, `reason` (`operator`, `shutdown`, `runtime`, `base-check`, `reconfigure` или `not-started` — очередь ещё не запускали), `stopReason` — текст причины (усечён до 2000 знаков одинаково во всех ответах), `since` — когда остановили, `action` — что сделать, `failed` — остановка вызвана сбоем. Панель показывает тот же текст баннером «Очередь остановлена» в шапке любого экрана.

Причину выбирают по тому, что держит выдачу дольше:

1. Класс отказа (`pauseFailures`) — при любой `reason`, в том числе при паузе человека поверх него. Отказ провайдера: «Авторизуйте CLI исполнителя, пополните баланс или дождитесь сброса лимита, затем `queue --start`»; отказ окружения: устранить неисправность, затем `queue --start`, а в режиме агента с работой ведущего — сначала один повтор, который цикл делает сам. Если при этом ждёт проверка базы, подсказка добавляет «проверьте базу gates» перед `queue --start`: продолжение очереди снимает и ожидание.
2. Ожидание проверки базы — при любой `reason`: текст ожидания и «Проверьте базу gates, затем выполните `queue --start`». При паузе человека подсказка добавляет, что команда снимет и паузу, и ожидание. При `reason: base-check` в режиме агента с работой ведущего базу проверяет цикл ведущего сам; если проверка не прошла — исправить базу и выполнить `base-update`, цикл проверит её снова. Перенос, меняющий приёмку или настройку контура, по-прежнему снимает только `queue --start`.
3. Сама пауза:

| `reason`      | `stopReason`                                                       | `action`                                                                                |
| ------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| `operator`    | «Выдача остановлена человеком»                                     | `devcontour queue --start`                                                              |
| `shutdown`    | «Сервер был остановлен штатно»                                     | зависит от режима, см. ниже                                                             |
| `not-started` | «Очередь ещё не запущена»                                          | зависит от режима, см. ниже                                                             |
| `runtime`     | последний сбой диспетчера после остановки, например отставшая база | `base-update`, если причина — отставшая база; иначе устранить причину и `queue --start` |
| `base-check`  | ожидание проверки базы ещё не описано — перенос базы идёт          | дождаться окончания переноса                                                            |
| `reconfigure` | «Применяется новая конфигурация после изменения контракта»         | ничего: операция снимет паузу сама — и при отказе или ожидании базы                     |

Исходную и штатную паузы снимает цикл ведущего только в режиме `approvalMode: "agent"` и только при зарегистрированной работе (`workflow_start`, статус `queued` или `running`): тогда подсказка — «Ничего не требуется». В режиме агента без работы: если доска ведётся workflow — `workflow_start`, если вручную — `queue --start`; маршруты не смешивают. В режиме оператора — `queue --start`. Сбой такта диспетчера записывает время остановки, поэтому он не выдаётся за незапущенную очередь, даже когда его событие ушло из последних записей журнала.

Для изменения конфигурации: сначала пауза, затем дождаться окончания либо явно отменить текущую работу, остановить сервер, сохранить копию настроек и состояния, изменить политику, выполнить проверку и перезапустить. CLI и долго работающий сервер должны видеть одну версию политики. Hot reload конфигурации не реализован.

## Setup отклоняет путь

Setup не пишет через symlink в пути назначения. На macOS временные пути `/tmp` и `/var` могут быть ссылками на `/private/...`; используйте проверенный канонический путь, не отключайте защиту. Для обычного workspace укажите непосредственно выбранный каталог проекта и проверьте его содержимое до повторного setup.

## Если задача не запускается

Для сохраняемого workflow сначала запросите `workflow_status` с правильным `repositoryId` (без него — общий ChangeSet). `stale` требует перечитать граф/политику и зарегистрировать новый вход; `failed` — разобрать причину и только затем вызвать `workflow_retry`. Retry стадии не повторяет упавшую Task и не сбрасывает её бюджет. Удалённый вход делает job устаревшим, но не блокирует другие jobs. Автомат работает только внутри `serve` и не продвигается в operator mode. [Договор восстановления](lead-workflow.md).

Проверяйте в таком порядке:

1. Правильный ли workspace открыт и есть ли работающий scheduler? `queue --start` меняет состояние, но сам не создаёт сервер. При работающем `serve` команда дожидается двух его тактов: если очередь после них осталась на паузе (например, сервер нашёл отставшую базу прогонов и нужен `base-update`), она отвечает `paused: true` с причиной (`stopReason`) и завершается с ненулевым кодом. Без живого сервера ответ содержит `server: "none"`, при молчащем — `server: "unconfirmed"`.
2. Не стоит ли очередь на паузе? Принадлежит ли задача активной ревизии?
3. Задача `draft` или `ready`? Черновик сначала проходит утверждение плана.
4. Все ли `dependsOn` имеют `done`, существуют ли нужные контракты?
5. Есть ли свободный worker, не выполняется ли совместная Verification/Delivery, блокирующая новую выдачу?
6. Не ждёт ли уже выданная попытка ресурса? Ожидание ресурса входит в timeout попытки.
7. Нет ли конфликта ownership или открытой `devcontour/accepted` в чужом worktree?

У Task нет отдельного статуса `blocked`; список блокирующих зависимостей вычисляется. Не добавляйте фиктивный `done` зависимой задаче ради запуска потребителя.

## Если попытка завершилась ошибкой

Сначала откройте failure, phase, команды, exit code, JUnit и review соответствующего Run. Исправляйте причину, затем выполняйте `retry`; не повторяйте запуск бесконечно с неизменённым окружением.

| Причина                                  | Действие                                                                                                            |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| CLI не найден, недоступна авторизация    | Настроить CLI/явные env, проверить небольшим live-сценарием                                                         |
| Нет отчёта, пустой JUnit, skipped        | Исправить reporter или среду; обязательный сценарий должен реально выполняться                                      |
| Test gate изменил tracked-файлы или HEAD | Перенести генерацию в bootstrap/реализацию либо игнорируемый output; проверка не должна менять проверяемый исходник |
| Diff вышел за writePaths/protectedPaths  | Пересмотреть постановку или отдельное изменение политики; не ослаблять защиту для сокрытия сбоя                     |
| Candidate прошёл, integration упал       | Разобрать взаимодействие с уже принятыми изменениями; новая попытка стартует с актуальной базы                      |
| Reviewer вернул blocking finding         | Проверить аргумент и исправить результат; `approved: true` с blocking finding всё равно не PASS                     |
| Контекст/профиль не совпадает            | Сверить исходник, версию и digest, провести осознанное обновление                                                   |
| Исчерпан maxAttempts                     | Изучить все попытки, уточнить постановку/среду; увеличение лимита требует причины и фиксации решения                |

```sh
npm run devcontour -- retry --task T12 --workspace /absolute/product-workspace
```

Новая попытка получает новый worktree и контекст предыдущих неудач. Незакоммиченный результат прежнего worktree автоматически не переносится; при необходимости сначала сохраните и разберите его. Артефакты и рабочие каталоги не удаляются автоматически.

## Восстановление окружения и ресурсов

Если teardown не завершился, сначала прекратите выдачу новых задач и убедитесь, что владелец попытки действительно остановлен. Найдите сохранённый `environment.json` в артефактах соответствующей попытки, проверьте указанные ресурсы и команды очистки.

```sh
npm run devcontour -- environment-cleanup --receipt /absolute/path/from-run/environment.json --workspace /absolute/product-workspace
npm run devcontour -- resources --workspace /absolute/product-workspace
```

Receipt должен принадлежать выбранному workspace/компоненту, а политика очистки — соответствовать сохранённой. Команда не предназначена для произвольного JSON извне. Если конфигурация изменилась, сначала восстановите и проверьте подходящую cleanup policy.

После фактической остановки оставшихся сервисов/драйверов можно освободить оставшуюся аренду, подставив **текущие** key/token из `resources`:

```sh
npm run devcontour -- resource-release --key RESOURCE_KEY --token CURRENT_TOKEN --cleanup-confirmed --workspace /absolute/product-workspace
```

Живой PID или другой token блокируют освобождение. TTL означает потерю heartbeat, а не доказанную свободу устройства. Не удаляйте `~/.devcontour-local/resources.sqlite` для снятия блокировки: этим можно нарушить работу другого workspace.

## Журнал не обновился

SQLite commit и запись Markdown — разные операции. При ошибке диска состояние может быть корректно сохранено, а журнал отстать. Устраните файловую причину и пересоберите проекцию:

```sh
npm run devcontour -- journal --workspace /absolute/product-workspace
```

Проверяйте `journalError` в API/сообщение CLI. Ручная правка автоматического дневника не исправляет базу и будет потеряна при следующей проекции. Выводы человека или агента сохраняйте отдельно в ADR/memory.

## «database is locked»

Панель и CLI держат одно состояние из разных процессов. Проекция журнала берёт
только читающую транзакцию, поэтому запущенный сервер не мешает агенту писать:
в WAL читатель писателю не помеха. Ожидание блокировки — 20 секунд.

Если ошибка всё же появилась, ищите долгую **запись**, а не чтение: параллельный
`run`, миграцию состояния или `git sync`. Останавливать сервер ради команды CLI
не требуется.

## Runtime не авторизован

Окружение прогона минимальное: исполнитель не наследует всё, что есть у оператора. Но учётные данные runtime живут в системном хранилище, и найти их там нельзя, не зная имени учётной записи — поэтому `USER` и `LOGNAME` передаются всегда. Это адрес в хранилище, а не секрет.

Без них `claude` на macOS отвечает «Not logged in», и единственным выходом остаётся передать API-ключ через `environment.inherit` — то есть платить за то, что уже оплачено подпиской. Ключ нужен только там, где подписки нет.

`doctor --probe` проверяет авторизацию настоящим вызовом в том же окружении, которое получит исполнитель. Обычный `doctor` смотрит `--version`: это доказывает, что файл на месте, а не что им можно работать.

## Gate установки падает с EPERM в песочнице

Песочница проверок закрывает часть путей всегда, даже внутри worktree: конфигурацию shell и git, `.git/hooks`, `.mcp.json` и каталоги IDE. Каталоги IDE внутри `node_modules` открыты (D45), поэтому пакет с `.idea/` в зависимостях установку не ломает. Отказ песочницы записывается классом `environment`, и сообщение называет путь и правило. Правка кода такой отказ не снимет: путь вне каталогов записи нужно открыть в настройке инструмента (например, кэш пакетного менеджера) или отказаться от записи туда. `doctor --probe` проверяет установку в песочнице заранее (`isolation:install`): ставит пакет-фикстуру с `.idea/` на чистом дереве. Класс `environment` ставится только по журналу ядра macOS, а не по тексту вывода; на Linux отказ остаётся `gate`. Проверка или исполнитель, создавшие каталог IDE, конфигурацию shell, git или `.claude` в дереве проекта (в том числе переносом из `node_modules`), получают `scope-violation` с путями.

## Git отказался работать с checkout

«Git на хосте не запущен: …» значит, что checkout ведёт git не туда, где его создал контур: изменён файл `.git`, в `.git` появился `commondir`/`gitdir` или внутри дерева лежит вложенный репозиторий. Так проверка могла бы исполнить свою конфигурацию на хосте. Попытку стоит разобрать, а checkout пересоздать, а не чинить вручную.

## Исчерпан лимит времени прогона

Каждая фаза попытки — реализация, проверки кандидата, ревью, интеграция и её ревью — ограничена `runTimeoutMs` отдельно. Общий предел на всю попытку отдавал ревью остаток после реализации: долгая, но успешная реализация оставляла ревьюеру минуты, и готовый кандидат падал «по времени» без вердикта. Пятнадцати минут по умолчанию хватает на правку, но не на реализацию с нуля: агент упирается в предел посреди работы, и попытка расходуется впустую, оставив незавершённое.

Лимит объявляет профиль стека — он знает, сколько стоит его работа; из слоёв берётся наибольший. Прерывание по лимиту теперь названо в причине отказа: раньше оператор видел «код 143» и не мог отличить исчерпанное время от остановки сервера.

Такая попытка **засчитывается**: она израсходовала весь отведённый бюджет. Если задача велика настолько, что не укладывается и в поднятый лимит, делить нужно задачу, а не поднимать предел дальше.

Незакоммиченные изменения такой попытки не пропадают. Если попытка оборвалась до кандидата — по времени, сообщением «не закончил» или перезапуском сервера, DevContour сохраняет их патчем к базе в области записи задачи (`artifacts/<run>/implementation/partial.patch`, событие `run.partial`). Повтор той же постановки с теми же контрактами накладывает черновик на новую базу (`run.continuation` с `kind: unfinished` и причиной), и исполнитель получает указание продолжить его, а не начинать заново. Черновик не проверен и не ревьюирован: гейты и ревью проходят как обычно. Черновик, который не лёг на базу, отбрасывается, и попытка начинается с чистого дерева.

## Попытка без движения или зависла

Controller обходит идущие попытки и проверки и отмечает те, что не двигаются: нет вывода, расхода процессора дерева процессов и смены стадий. Пороги и действие задаёт `stallSweep` в config.json (`intervalMs`, `quietMs`, `stalledMs`, `action`); без поля действуют умолчания harness — обход раз в 30 секунд, «без движения» после 3 минут, «зависла» после 10, действие `report`. Можно задать часть полей: остальные берутся из умолчаний, и отказ называет действующее значение незаданного поля (например, один `quietMs: 20000` меньше `intervalMs` по умолчанию 30000). Поле эксплуатационное: его правка не требует повторного утверждения плана и не меняет digest исполнения; работающий `serve` применяет её без перезапуска по `devcontour config-apply --keys stallSweep` (без `--keys` команда применяет только `budgets` и `prices`).

Панель показывает состояние в ячейке «Сейчас», на карточке и строке задачи и в заголовке инспектора: «без движения N мин» — приглушённо, с последней командой (агент, проверка, шаг среды); «зависла N мин — проверьте среду» — янтарём и счётом в заголовке ячейки, потому что при `report` попытка идёт до своего предела времени и действовать должен человек. Строки для подписи зарезервированы: её появление не сдвигает карточки и инспектор. Пока попытка молчит, записей нет и опрос сводки отвечает `unchanged`, поэтому минуты простоя панель досчитывает своими часами от `lastMovementAt`.

Тот же вид отдают `/api/state` (`liveness`, `operations`) и MCP `workflow_status` (`liveness[]` — попытки: задача, попытка, компонент, простой, команда, `text`, `next`; `operations[]` — проверки вне попыток), поэтому ведущий агент видит зависание без запроса журнала. В `next` для агента названы порог и событие (`stallSweep`, `attempt.liveness`), в панели — только слова оператора. Снимок процессов и хвост вывода — в событии `attempt.liveness` журнала задачи; `/api/state` называет путь снимка относительно каталога данных.

Проверки вне попыток видны той же подписью: совместная проверка ChangeSet (событие `joint.liveness`) — в её строке ведущего цикла, проверка перенесённой базы и проверка доски на итоговом SHA (переходы `runGatesAt`, события журнала `base.check.liveness` и `board.coverage.liveness`) — отдельной строкой «Проверка базы» или «Проверка доски». Ограничения: у таких проверок нет поля живости в записи, вид строится по последнему переходу в последних 20 000 событиях журнала; проверка gates считается идущей, пока нет события её окончания, нет более нового начала проверки той же области (компонент базы, доска и компонент) и роль controller жива у того же владельца, под которым записан переход (оборванная перезапуском сервера проверка вида не даёт); отказ записи итога проверки тоже закрывает её событием `failed`; совместная проверка — пока она активна. Фильтр `repositoryId` в `workflow_status` совместную проверку не выдаёт: она относится ко всему workspace.

При `action: stop` controller сам останавливает зависшую попытку отказом класса `stalled`. Это не замечание к коду: правило восстановления один раз повторяет попытку, а повторное зависание — повод чинить среду (сеть, сервис, блокировку) или осознанно поднять порог. Совместная проверка и проверки gates при `stop` останавливаются с текстом зависания, без повтора.

## Ревью повторяет одно замечание

Находки ревью — путь, строка и следствие — сохраняются на прогоне и передаются следующей попытке вместе с историей прошлых. Сам отклонённый кандидат тоже не выбрасывается: повтор той же постановки начинает с его изменений как с незакоммиченных правок (`run.continuation` с `kind: candidate`; так же — кандидат, не прошедший проверку или ревью по времени, когда переиспользовать его как есть нельзя) и чинит находки поверх них, а если находка показывает, что неверен сам подход, заменяет его. Решают снова гейты и новое независимое ревью. Без них исполнитель узнавал только, что «ревью отклонило результат», и круг повторялся с тем же замечанием: гейты зелены, а причина отказа известна лишь ревьюеру.

Если замечание всё же повторяется третий раз, дело не в передаче: либо оно непонятно сформулировано, либо задача больше, чем одна попытка, и её нужно делить.

## Пустой кандидат

Задача с областью записи обязана что-то изменить. Исполнитель, отчитавшийся «сделано» пустым коммитом, отклоняется до ревью: гейты на таком кандидате зелены ровно потому, что были зелены и до него, и вся проверка легла бы на независимое ревью — полный прогон ради ответа «diff пуст».

Отказ называет причину так, чтобы следующая попытка знала, что делать: выполнить работу по критериям приёмки либо объяснить в отчёте, почему изменения не требуются.

## Выдача остановилась сама

Отказ, который повторится на любой задаче — кончились кредиты провайдера, runtime не авторизован, ключ недействителен, — останавливает выдачу и попадает в журнал с причиной. Панель показывает её баннером «Очередь остановлена» в шапке каждого экрана; тот же текст — в `queue.stopReason` ответа `/api/state` и в `devcontour queue`.

Так сделано потому, что причина лежит вне контура и одинакова для всех задач: очередь, которая продолжила бы перебор, сожгла бы бюджет попыток каждой задачи, не выполнив ни одной. Временные ошибки сети и лимиты частоты сюда не входят — останавливать из-за них значило бы звать человека без нужды.

Устраните причину и запустите очередь: `queue --start`. Задачам, чей бюджет уже израсходован, дайте попытку сбросом.

## Изменить бюджеты или тарифы работающего сервера

Задача стоит с причиной «Бюджет расходов не пускает задачу к выдаче» (карточка задачи, `progress.budgetBlock`), или нужно добавить тариф новой модели. Перезапуск `serve` не нужен:

1. Поправьте `budgets`/`prices` в `.devcontour-local/config.json` (или в `workspace.json` и выполните `workspace-init --file`: объявление сильнее локального значения).
2. Выполните `devcontour config-apply --keys budgets,prices --workspace ...`. Невалидный файл команда отклонит сразу, применённые значения останутся прежними.
3. Ответ `applied` — сервер уже работает с новыми значениями (событие `config.applied` в журнале панели). `pending` — сервер применит запрос, когда закончатся текущие работы; до этого новые попытки не выдаются. `refused` — в файле изменено что-то кроме названных ключей: верните прочие ключи или примените всё перезапуском.
4. `devcontour doctor` покажет тарифы и бюджеты из `config.json`; если они ещё не применены работающим контуром (digest файла отличается от применённого), проверка `budgets:applied` скажет «не применено» и как применить. Сервер запоминает digest каждого ключа применённой конфигурации, поэтому doctor называет отличающиеся ключи; если отличаются только прочие ключи (например, `contextPacks` после `context-lock`), вместо `budgets:applied` выводится `config:applied`: бюджеты и тарифы действуют. Способ применения назван по ключам: `stallSweep`, `inputPolicy` и `gateTimeoutFloorMs` работающий сервер применяет командой `config-apply --keys`, остальное — только перезапуск serve. Doctor также предупредит о моделях без тарифа и о `onUnknown: "stop"`, который остановит выдачу.

Новый тариф не переоценивает прошлые вызовы: стоимость, неизвестная на момент вызова, остаётся неизвестной. Повышение предела не снимает неопределённость бюджета — для неё нужен `onUnknown: "continue"`.

## Постановку нужно изменить до приёмки

Утверждённая постановка неизменна — под неё уже велась работа. Но пока задача не дала принятого результата, изменить её бывает необходимо: контракт исправлен до того, как доска принята, и переписывать под прежнюю редакцию нечего.

```sh
npm run devcontour -- reopen --task T-... --reason "Контракт исправлен: привязка ссылается на прежнюю редакцию" --workspace /absolute/product-workspace
```

Возврат разрешён только задаче без принятого результата. Прогоны остаются в истории; утверждение снимается, и доску нужно провести через `review-plan` заново — иначе это был бы обход независимого согласования. Задачу, которая уже дала результат, возвращает только корректировка доски.

## Попытка, потраченная не на задачу

Бюджет попыток задачи расходуется на работу исполнителя, а не на неполадки контура. Прогон, в котором runtime не выдал результата — не авторизован, оборвался, не получил закреплённый пакет контекста, — помечается `blocked`, и попытка возвращается: задача ни разу не была попробована. `retry` после такого отказа доступен.

Возврат действует, пока работа не начата. Таймаут ревьюера после готового кандидата — настоящая попытка: она стоила прогонов, и не засчитывать её значит разрешить дорогому циклу крутиться без предела.

Отличать это от настоящего провала важно: иначе задача упирается в лимит, ни разу не дойдя до исполнителя, и выглядит невыполнимой, хотя её никто не выполнял.

Когда бюджет всё же исчерпан настоящими провалами, а причина устранена, попытки сбрасываются явно:

```sh
npm run devcontour -- retry --task T-... --reset --reason "Окружение исправлено: runtime авторизован" --workspace /absolute/product-workspace
```

Сброс доступен и задаче в состоянии `ready`: после исправленной постановки задача снова готова, но израсходованный бюджет никуда не делся — диспетчер её не берёт, и без сброса она стоит молча. Причина обязательна и попадает в журнал рядом с числом сброшенных попыток. Прогоны не удаляются: история показывает, сколько раз задача не справилась, а не задачу, справившуюся с первого раза.

## Резервное копирование

Резервная копия нужна перед миграцией состояния, переносом workspace, крупным обновлением политики и очисткой артефактов.

Для одной базы (не компонентного хранения) есть `backup --out FILE`: согласованная копия SQLite снимается без остановки сервера. `restore --from FILE --to DIR` восстанавливает её в пустой каталог, не трогая действующий workspace, и проверяет результат: считает перенесённые события, снимает всё оперативное владение, активное в момент копии (его процессы остались на прежней машине), и сверяет SHA принятых результатов с Git текущей конфигурации. Снимаются попытки задач, выкладки preview вместе с их блокировкой, совместные проверки и поставки, лидерство контроллера и работы ведущего цикла; каждое завершается записью с причиной, история сохраняется. Отчёт перечисляет снятое по видам (`releasedOwnership`) и остаток (`remainingOwnership`, должен быть пуст). Доступность результатов в Git (`resultsAvailable`, `missingResults`) названа отдельно от готовности копии (`ready`: результаты доступны и владения не осталось). Недостающие SHA перечисляются, код выхода 1. База не содержит коммитов, логов и worktree: полная копия workspace по-прежнему делается по шагам ниже.

Как растут размер состояния, время записи, ответы панели, задержка event loop и время восстановления, показывает `npm run bench:storage -- [--sizes 100,1000,10000] [--out report.json]`. Корпус строится одной доской с настоящими доменными переходами, тиражированной с новыми идентификаторами; отчёт включает параметры хоста и его загрузку, без которых числа несравнимы.

### Что нельзя удалять

Автоматического retention нет. Вручную удалять можно только то, на что не ссылается доказательство:

- `state.sqlite` и события — история попыток, evidence и приёмок;
- каталоги `artifacts/<run>/`, на которые указывает `log` в evidence, — без них доказательство не перепроверить;
- ветки `devcontour/run-*` — кандидаты попыток: по ним ревью и повтор после сбоя окружения берут проверенный код, а receipt называет candidate SHA;
- ветка интеграции со всеми принятыми `resultSha`.

Рабочие каталоги worktree завершённых попыток убирает `worktree-cleanup` (`--dry-run` только показывает): ветки, достижимые коммиты и артефакты остаются, неподтверждённые правки сохраняются проверенным патчем в артефактах попытки. Игнорируемые файлы (`.env`, зависимости, сборка) патч не сохраняет: они перечислены в поле `ignored`. В сомнении дерево остаётся, а отказ назван: идущие и восстановимые попытки, вложенные репозитории, недостижимая вершина, изменённые правила игнорирования.

Для согласованной файловой копии всего workspace:

1. Поставьте очередь на паузу, дождитесь/отмените Run, Verification и Delivery, завершите cleanup.
2. Остановите сервер и все CLI, способные записывать это состояние. Одна пауза не запрещает другому клиенту менять черновики.
3. Сохраните весь workspace и `.devcontour-local/` всех компонентов, `devcontour.component.json`, правила и memory. Нужны все связанные `state.sqlite`, а не только coordinator. Для legacy WAL после штатного закрытия сохраняйте комплект имеющихся файлов БД вместе; не копируйте один live-файл.
4. Сохраните Git-репозитории с refs `devcontour/*`, служебными refs и metadata worktree/owner, включая незакоммиченные результаты. Обычный клон ветки main или только Git bundle не сохраняет весь этот набор.
5. Запишите канонические пути, ID компонентов, версию DevContour, profile locks и процедуру восстановления внешней среды. Значения секретов хранятся отдельным принятым в команде способом, не в открытом архиве настроек.

Ресурсный pool общий для хоста. Его нельзя восстанавливать поверх активных аренд других workspace. Сначала разберите внешние ресурсы; при переносе на новый хост настройте pool и ресурсы заново.

После восстановления сначала проверяйте Git refs, целостность всего комплекта БД и owner metadata, затем `doctor` и журналы, и только потом очередь. Пути входят в привязки владельца и артефактов: копия в другую папку не является прозрачной переносимой установкой состояния. Автоматического remap путей/ID нет.

## Обновление DevContour

1. Остановите обслуживаемые workspace и сделайте согласованные копии.
2. Прочитайте изменение схем/профилей/CLI. Не изменяйте profile lock вручную только ради устранения ошибки digest.
3. Установите зависимости из lockfile, соберите и выполните подходящие проверки инструмента.
4. На копии рабочего сценария проверьте загрузку конфигурации и сохранение принятой истории.
5. Сверьте новые переносимые правила с локальными соглашениями. Повторный setup сохраняет существующие файлы и не является автоматическим обновлением правил.
6. Возобновляйте работу после `doctor` и небольшого проверяемого этапа.

Для перехода central → component есть `storage-migrate`; он требует остановленной очереди и отсутствия активных попыток. [Точная процедура и ограничения](project-integration.md). Обратной автоматической миграции и присоединения независимой непустой базы библиотеки нет.

## Публикация и длительное ожидание

`handoff` формирует пакет для человека. `remote-check` — одна проверка текущего состояния. При `waiting` выясните, чего не хватает: push, PR/MR, merge или CI именно на итоговом SHA. Не создавайте новый ChangeSet только из-за ожидания CI; повторите наблюдение для того же результата.

Если удалённое дерево отличается от проверенного локального, старой Verification недостаточно. Разберите изменения и проведите новую проверку требуемого результата. Нет фонового polling/webhook, автоматического push и скрытого обхода remote completion.

Workflow ChangeSet проверяет наличие подходящего результата Delivery в локальном состоянии; он не вызывает `remote-check` и не опрашивает forge вместо ведущего агента. Внешний сигнал CI через `signal_ingest` также не заменяет Delivery или тестовое evidence. После подтверждённого `remote-check` работающий workflow сможет завершить приёмку.

## Обслуживание Git и диска

`devcontour/accepted` нельзя держать checkout-веткой: runner продвигает её через CAS. Для просмотра создайте detached worktree.

Прогон ответвляется от ветки интеграции, а контракты, схемы и каркас готовятся на рабочей ветке. Пока эти линии не сведены, исполнитель получает дерево без работы, ради которой его запустили. Если база — предок рабочей ветки (чистая перемотка: принятая история остаётся целиком, слияния нет), а перематываемые коммиты не трогают приёмку и настройку контура, диспетчер перематывает её сам, пишет событие `base.fast-forwarded` с веткой и SHA и ставит очередь на то же ожидание `base-check`, что и ручной перенос: проверьте базу гейтами и продолжите очередь. Условия: очередь работает, попыток нет, HEAD репозитория — ветка, а не detached, нет незавершённой операции `contract-change` и ожидающего применения конфигурации; коммиты не меняют документы и закреплённые артефакты контрактов, файлы закреплённых context packs, `protectedPaths`, `generatedPaths`, файл конфигурации компонента, `.devcontour/` и данные контура, а закреплённые редакции артефактов открытой работы на новой вершине прежние; сдвиг ref — CAS в транзакции, проверяющей очередь, попытки и роль controller ([D42](decisions.md)). Иначе — обе линии несут работу, HEAD detached, идёт операция, коммиты задевают приёмку (пути названы в причине) — диспетчер, как и прежде, отказывается выдавать работу и останавливает очередь, называя, скольких коммитов не хватает базе. Тогда перенос — отдельная планируемая операция:

```sh
npm run devcontour -- queue --pause --workspace /absolute/product-workspace
npm run devcontour -- base-update --workspace /absolute/product-workspace
npm run devcontour -- queue --start --workspace /absolute/product-workspace
```

Когда база — предок рабочей ветки, выполняется перемотка; когда обе линии несут работу, они сводятся слиянием `--no-ff` в отдельном worktree. История не переписывается ни в одном из случаев. После переноса проверьте базу гейтами: прогоны будут ответвляться уже от неё.

Обратного переноса команда не делает: принятая работа живёт в `devcontour/accepted`, а рабочая ветка её не получает. Правки контрактов, схем и файлов приёмки, подготовленные на такой ветке, ложатся на устаревшие версии файлов и при следующем переносе конфликтуют с принятыми. Поэтому `base-update` сообщает `workingBehind` и предупреждение, если в рабочей ветке нет принятых коммитов. Перед такой правкой выполните `git merge devcontour/accepted` в рабочей ветке: принятое уже доказано гейтами.

После переноса очередь ждёт проверки базы (`base-check`), если её не остановил человек: причина, по которой диспетчер остановил выдачу, устранена, и панель перестаёт её называть. Событие `base.updated` оставляет перенос в журнале. В режиме `approvalMode: "agent"` `queue --pause` перед `base-update` не нужен: перенос сам ставит работающую очередь без попыток на это ожидание, а запущенный board workflow проверяет базу gates и продолжает очередь ([lead-workflow.md](lead-workflow.md)). Пауза человека и режим оператора по-прежнему требуют `queue --start`.

Перенос базы двигает вершину ветки кодом, которого гейты не видели. Приёмка доски этого не закрепляет: она фиксирует самый поздний результат задач доски — SHA, прошедший проверки на интеграции, — а не текущую вершину. Принятое всегда доказано, даже если ветка успела уйти вперёд.

Старые worktree убирает `worktree-cleanup`. Удалять артефакты можно только после проверки активности, ссылок evidence и требований хранения. Автоматического retention/GC нет. Если удалить лог, запись приёмки останется, но полнота аудита ухудшится; такой архив нельзя называть полностью воспроизводимым.
