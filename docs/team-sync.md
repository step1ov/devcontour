# Командная память и синхронизация через Git

DevContour разделяет долговременную память команды, согласованное состояние задач и локальное исполнение. Git хранит знания и переносимые записи задач. SQLite управляет процессами на конкретном компьютере и сохраняет базу сравнения для следующей синхронизации.

Это режим обмена через обычные ветки, review и merge вашей команды. Он не зависит от GitHub или GitLab и не требует write-доступа MCP. Команды `sync`/`sync-status` не выполняют commit, push, pull, PR/MR или merge; отдельный runner задач создаёт локальные candidate/integration commits по своему договору. Ведущий агент готовит изменения командной памяти и проверяет их; внешнюю публикацию выполняет человек.

## Что находится в репозитории

```text
product-or-library/
  AGENTS.md
  CLAUDE.md
  .agents/                       # Правила ролей и инженерные инструкции
  docs/                          # Требования и документация
  memory/                        # Решения, знания о сервисах, lessons, handoffs
  .devcontour/                    # Версионируется в Git
    identity.json                # Постоянная идентичность этого хранилища
    tasks/T-<uuid>.json           # Постановка, зависимости, ответственный, прогресс
    boards/B-<uuid>.json          # Состав и ревизии доски: ссылки на задачи
    contracts/C-<uuid>.json       # Утверждённые контракты компонента
    receipts/<run-uuid>.json      # Свидетельства завершения на конкретных SHA
  .harness/                      # Игнорируется Git
    local/state.sqlite           # Локальное исполнение и sync baseline
    local/artifacts/             # Логи и результаты инструментов
    local/worktrees/             # Изолированные попытки
```

В отдельном Git-репозитории workspace каталог `.devcontour/` содержит общие задачи, общие контракты, межкомпонентные доски и `changesets/`. Тела задач библиотеки, её receipts и база сравнения остаются в репозитории библиотеки. Общая доска хранит ссылки, а не копии её задач. Repository IDs должны совпадать у всех участников; абсолютные пути к clone могут различаться.

Для одной библиотеки могут потребоваться общие контракты и ссылки на другие компоненты. Импорт проверяет полный граф зарегистрированного workspace. Он не подставляет заглушки вместо отсутствующих зависимостей: сначала получите соответствующие записи остальных репозиториев.

## Почему отдельные JSON-файлы

Один бинарный файл SQLite нельзя осмысленно объединять при одновременной работе. Один большой JSON тоже создавал бы частые конфликты в несвязанных задачах. Файл на сущность позволяет видеть постановку и изменения в обычном diff, независимо добавлять задачи и адресно разрешать разногласия.

Ключи JSON сортируются, формат стабилен, время экспорта не добавляется. Повторная синхронизация без изменений не создаёт diff. Новые Task, Board, Contract и ChangeSet получают UUID; старые ID сохраняются. Локальная последовательность больше не определяет глобальную идентичность сущности.

Нельзя использовать Git merge driver `union` для состояния. Он способен оставить синтаксически допустимые, но противоречивые зависимости и статусы. Сначала обычный Git merge, затем доменная проверка DevContour.

## Первый запуск для команды

Ведущий агент выполняет следующие действия после обычного setup:

1. Подготавливает отдельные Git-репозитории продукта, библиотек и workspace. Нужны именованные ветки и исходный commit. Каталоги не должны быть вложены друг в друга.
2. Проверяет `.gitignore`: `.harness/` исключена, `.devcontour/` не исключена. Не добавляет БД, credentials, локальную конфигурацию или resource leases в Git.
3. Выбирает устойчивый идентификатор разработчика, например `alice`. Участник — человек/рабочий контур, а не модель. Codex и Claude одного разработчика используют одно назначение. Две одновременно работающие машины с одним идентификатором требуют отдельной координации.
4. До запуска сервера и создания задач выполняет первый `sync`. Если сервер уже запущен, завершает активные операции и останавливает его. После синхронизации новые задачи автоматически назначаются локальному участнику, если назначение не задано явно.

Все следующие команды выполняются из установленного DevContour:

```sh
npm run devcontour -- sync --workspace /absolute/product-workspace --member alice
npm run devcontour -- sync-status --workspace /absolute/product-workspace
```

`--member` сохраняется только в локальной SQLite и не переносится через Git. У новой копии он задаётся заново. Существующие задачи без ответственного не запускаются в командном режиме; ведущий агент назначает их явно:

```sh
npm run devcontour -- assign-task --workspace /absolute/product-workspace --task T-<uuid> --member alice
```

Назначение можно менять после завершения активной попытки. Это организационные сведения, поэтому смена ответственного не меняет digest технической постановки и не аннулирует результат проверки. Новую спецификацию по-прежнему утверждают заново, а принятую задачу изменяют через корректировку.

После первого `sync` ведущий агент включает `.devcontour/` и файлы памяти в подготовленные коммиты соответствующих репозиториев. Человек публикует их обычным способом. Локальное создание commit остаётся допустимым действием агента по правилам проекта; сама команда `sync` его не выполняет.

## Ежедневный цикл

1. Остановить выдачу новых задач: `queue --pause`. Дождаться завершения активных workers, Verification и Delivery, затем штатно остановить сервер. Пауза не отменяет активные попытки и не блокирует стадии LeadRunner; новый workflow способен включить очередь. Исключить параллельные mutations через MCP/CLI.
2. Выполнить `sync-status`, затем `sync`. Это сохраняет локальные изменения в файлах и обновляет SQLite согласованным состоянием.
3. Подготовить коммиты, получить изменения коллег через обычный Git-процесс и разрешить текстовые merge conflicts. Публикацию выполняет человек.
4. После pull/merge снова выполнить `sync-status` и `sync`. До импорта результата получить также соответствующий код: один JSON с SHA не переносит Git-объект.
5. Ведущий агент проверяет назначения, новые требования, контракты и контекст. Читает `workflow_status` общего и нужных компонентных контуров, регистрирует новый вход для изменённого плана. После этого запускает сервер; отдельное включение очереди нужно для ручного маршрута или сохранённой явной паузы.

```sh
npm run devcontour -- queue --pause --workspace /absolute/product-workspace
# Дождаться активных операций и штатно остановить serve в его управляемой сессии.
npm run devcontour -- sync-status --workspace /absolute/product-workspace
npm run devcontour -- sync --workspace /absolute/product-workspace
# Обычный процесс commit / получения изменений / review / merge команды.
npm run devcontour -- sync --workspace /absolute/product-workspace
# После проверки графа запустить serve; готовые workflow продолжит сервер.
npm run devcontour -- serve --workspace /absolute/product-workspace --port 0
```

Для AI-native работы этот цикл ведёт агент: синхронизация входит в передачу работы, завершение этапа и возобновление сессии. Человек не должен вручную переписывать статусы. Файлы не обновляются на каждом heartbeat: активные процессы и их частые изменения остаются локальными.

После pull или правки `.devcontour/` scheduler обнаруживает отличие от последней базы синхронизации и прекращает выдачу новых задач до `sync`. Нельзя менять ветку или делать pull во время активных попыток: уже запущенные процессы этой проверкой не перемещаются и не отменяются.

## Как работает объединение

В одной SQLite-транзакции DevContour сравнивает:

- **base** — последний успешно согласованный снимок на этом компьютере;
- **local** — текущее состояние локальной БД;
- **git** — файлы текущего рабочего дерева после merge.

Изменение только с одной стороны принимается. Разные поля одной записи могут объединиться. Независимые добавления в состав одной ревизии доски объединяются как набор IDs. Противоречивые изменения одного поля, удаления и неоднозначные изменения массивов требуют решения. Автоматического выбора «побеждает самая новая дата» нет: часы разных компьютеров не выражают смысл изменения.

После объединения проверяются схема, владельцы сущностей, ссылки на контракты, DAG зависимостей, цепочки корректировок, история ревизий и свидетельства завершения. Даже Git merge без текстовых конфликтов может быть отклонён, например если две независимые правки образовали цикл.

`sync-status` показывает направления изменений и конфликтующие ключи, не меняя задачи и Git-файлы. При конфликте `sync` прекращается до записи. Для адресного выбора подготовьте файл решений:

```json
{
  "main/tasks/T-example": "git",
  "@workspace/boards/B-example": "local"
}
```

```sh
npm run devcontour -- sync --workspace /absolute/product-workspace --resolutions /absolute/resolutions.json
```

Замените примеры настоящими ключами из отчёта. Выбор относится ко всей конфликтующей записи. Он не отключает валидацию и не позволяет переписать принятый результат. Если нужно объединить смысл двух постановок, ведущий агент готовит согласованный черновик, а не выбирает сторону вслепую.

Удаление файлов с историей не поддерживается: отменяйте незавершённую задачу или создавайте следующую ревизию. Старые задачи и receipts остаются доступны. Это предотвращает потерю истории при случайном checkout более старой ветки.

Владелец записи после первого обмена остаётся прежним. Планируйте доски межкомпонентных изменений в workspace; не переносите существующий ID между Git-репозиториями вручную. Переезд записей между владельцами и объединение независимых старых баз с совпадающими последовательными IDs требуют отдельной миграции.

## Перенос завершённых задач

`done` переносится только вместе с receipt. В нём указаны ID задачи/попытки, digest утверждённой постановки и исходной политики, candidate/result SHA, runtime исполнителя и ревьюера, обязательные gates и результаты обеих фаз с digest артефактов. Токен, owner процесса, lease, worktree, локальные пути, команды, stdout и сами логи в receipt не переносятся.

Импорт проверяет соответствие постановке, PASS всех объявленных gates и независимого review на нужных SHA. Для обычного режима demo receipt запрещён. Новое принятое из Git завершение требует уже закоммиченные task и receipt. Candidate и результат должны существовать локально; result должен входить в принятую ветку компонента. В новом clone без `harness/accepted` проверяется HEAD, от которого scheduler позже создаёт эту ветку. Sync не двигает refs автоматически. Для merge/squash, не сохраняющего исходные SHA, нужен отдельный путь перепроверки; совпадение текста файлов само по себе не заменяет происхождение результата.

**Receipt — свидетельство другого участника доверенного, прошедшего review репозитория, а не повторный запуск тестов и не цифровая подпись.** Импорт не читает отсутствующие логи и не доказывает их содержимое по одному хешу. Контроль доступа и review Git защищают командную историю. Не импортируйте такую приёмку из произвольного внешнего репозитория. В карточке задачи видно, что результат получен из Git и локальная попытка не запускалась.

Перенос не объявляет прежние проверки проверками новой среды или новой политики. При изменении требований или окружения создайте корректировку. Совместная приёмка ChangeSet, Verification, Delivery и внешние CI-наблюдения не копируются в новую локальную БД: Git переносит постановку ChangeSet и состав досок. Новая копия выполняет общую проверку и при необходимости remote-check заново. История общих проверок прежней машины остаётся в её БД/backup; это ограничение текущего формата, а не полное восстановление workspace.

Старые завершённые попытки без сохранённого списка gates экспортируются, если доступна соответствующая исходная policy. Если политика уже изменилась, система откажется угадывать набор обязательных проверок: нужна исходная конфигурация или новый проверенный результат.

## Работа после clone и с ветками

После clone агент создаёт локальную конфигурацию с путями этой машины и прежними repository IDs, подключает профили, контекст и инструменты, затем выполняет `sync --member <id>`. Одна универсальная копия runtime не содержит пользовательских назначений и не становится workspace.

SQLite не переключается вместе с Git checkout. Baseline хранит имя ветки; переход требует явного `--allow-branch-change` после просмотра `sync-status`. Этот флаг разрешает смену имени ветки, но не удаление накопленной истории и не конфликтующие постановки. Для независимой или более старой ветки используйте отдельные clones компонентов, отдельный workspace и отдельные локальные БД. Не подключайте один и тот же checkout к двум coordinators.

Git не резервирует задачу между компьютерами в реальном времени. После общего merge за задачей закрепляют одного ответственного; его локальная очередь запускает только свои задачи. Пока два разработчика работают offline со старыми назначениями, строгой глобальной блокировки нет. Для такой гарантии нужен отдельный сетевой сервис координации. Git sync его не имитирует.

## Память и отказоустойчивость

`memory/`, `.agents/`, ТЗ, ADR и контракты в документации версионируются обычным Git. Знания библиотеки остаются в библиотеке; общие решения находятся в workspace. Контекстные пакеты по-прежнему закрепляются на Git SHA через `context-lock`; после изменения правил ведущий агент проверяет настройки новой машины, обновляет закрепление и перезапускает сервер. Sync не переносит executable-конфигурацию, credentials, host resources и весь диалог модели.

SQLite хранит baseline в `git_sync` соответствующей компонентной БД; coordinator не получает копии локальных постановок ради слияния. Новое поле таблицы создаётся при первом использовании; старые БД продолжают работать, старые IDs не переименовываются.

Привязки `Task.requirements` (текст, source, digest, gate и scenario) переносятся вместе с задачей. Передайте также Git-версию файла источника и код результата. Receipt сохраняет необходимое `requirement-source` evidence, но актуальность раздела после pull проверяется отдельно через `requirements-report`.

Jobs продолжения этапов и receipts внешних сигналов находятся в `local_workflow` базы владельца и не экспортируются. После clone новый controller регистрирует workflow заново по проверенному графу; Git sync не возобновляет старый процесс. Сигналы направляются одному controller: независимый clone не знает его delivery receipts и может создать повторную предложенную работу. Время стадий и сырые логи чужих Run тоже не переносятся; метрики импортированного результата не показывают локальный запуск.

Записи Git-файлов заменяются атомарно по одному файлу. Общей транзакции SQLite и нескольких Git-репозиториев нет. При ошибке записи транзакция БД откатывается; часть файлов может уже содержать новый снимок. Не коммитьте такой результат: повторите `sync`, который сравнит его с прежней baseline, затем проверьте `sync-status` и diff. Для восстановления незавершённых процессов и локальных логов по-прежнему нужен backup; Git переносит командные записи, а не весь компьютер.

## Типизированные знания

`.devcontour/knowledge/<uuid>.json` переносится обычным Git рядом с checkpoints и общей context identity. Эти записи не импортируются в таблицы задач. `memory_recall` читает каталог своего владельца и заново вычисляет актуальность источников, поэтому отдельный синхронизируемый поисковый индекс не нужен. Для замены используйте новые UUID и supersedes; для сводки — supports. Записи разных clones объединяются, смысловое противоречие остаётся видимым и требует явного решения. Источники библиотеки и её знания не переносятся в общий workspace. Подробности — [проектная память](project-memory.md).

Новые поля Run.memory/dispatch и local_workflow namespace usage остаются локальными. Они не добавляют detailed traces, денежные измерения или активные процессы в переносимые receipts. Clone получает знания и принятую историю задач, но не чужие измерения или право продолжить процесс.
