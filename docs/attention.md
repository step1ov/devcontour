# Центр внимания: данные

Центр внимания — один упорядоченный список того, что сейчас требует действия человека (оператора) или ведущего агента. Это проекция фактов, а не своя машина статусов: карточка существует, пока исходное правило говорит «нужно действие», и исчезает, когда решена исходная сущность — вопрос отвечен, редакция согласована, задача повторена или принята, пауза снята. Сам центр хранит только локальные отметки оператора «прочитано» и «увидел».

Центр работает до setup (вопросы и согласования подготовки) и после подключения движка на том же адресе и той же базе: ключи карточек и отметки сохраняются.

## Карточка

| Поле                  | Смысл                                                                                                                   |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `id`                  | `sourceKey#occurrenceId` — идентичность карточки                                                                        |
| `sourceKey`           | Предмет: вопрос, этап изменения, задача, доска, обращение, пауза, бюджет…                                               |
| `occurrenceId`        | Это появление предмета, выведенное из первичного факта источника                                                        |
| `sourceVersion`       | Непрозрачный токен версии; сравнивается только на равенство                                                             |
| `source`              | Правило источника (`prep-question`, `work`, `input`, `queue`, …)                                                        |
| `category`            | `access`, `budget`, `question`, `decision`, `technical`                                                                 |
| `actor`               | `operator` или `lead`                                                                                                   |
| `title`, `reason`     | Кратко (до 160 и 300 знаков); тексты отказов проходят маску секретов пакета передачи                                    |
| `impact`              | `tasks` — задачи, которые карточка покрывает; `waiting` — открытые задачи, которые их ждут; `boards`; `taskIds` (до 20) |
| `since`, `updatedAt?` | Время первичного факта появления и факта текущей версии                                                                 |
| `subject`, `evidence` | Ссылка на предмет в панели и на доказательства (до 5)                                                                   |
| `actions`             | Доменные действия оператора (`domain`), переход (`navigate`); у карточек ведущего — только переход и передача контекста |
| `state`               | `read`, `acknowledged`, `unread` — по отметкам оператора                                                                |

Порядок детерминирован и не зависит от времени чтения: блокировки доступа и бюджета, вопросы, продуктовые решения, технические действия ведущего; внутри категории — по влиянию, затем по давности, затем по `id`. Активный список ограничен 200 карточками (`truncated`).

## Идентичность

Одинаковые правила для всех источников:

1. **Появление** — исходное правило стало истинным; `occurrenceId` берётся из первичного факта: id вопроса, номер редакции, id попытки, id запроса, момент паузы или ожидания, id проверки, операция и момент её остановки.
2. **Повтор без дубликата** — опрос, heartbeat, продление lease и ход времени не меняют ни появление, ни версию. Версия не содержит времени без записи, счётчиков расхода и времени простоя.
3. **Существенное обновление** — факт решения изменился при том же появлении (исправленное обращение, сохранённый ответ, новый черновик плана): меняется `sourceVersion`, карточка снова не прочитана.
4. **Решение** — исходное правило стало ложным; меняет его только исходная сущность.
5. **Повторное появление** — тот же предмет снова требует действия по новому факту источника: новая попытка, новая редакция, новая пауза, новая обработка обращения. Это новое `occurrenceId`, карточка не прочитана, отметки прежнего появления к нему не относятся.

Каскад группируется: задача, вопрос исполнителя, удержание операцией изменения контракта или бюджет забирает свои задачи первым, а зависимые, которые лишь ждут, своих карточек не дают — они влияние корня. Сто задач, ждущих одну упавшую, — одна карточка с `impact.waiting = 100`. Отказ провайдера по задачам сворачивается в карточку паузы выдачи: одна учётная запись чинит их все.

Источник, у которого нет журнала фактов, называет ограничение. Быстрый маршрут: подключение привязано к поручению и HEAD репозитория, подготовка — к предложению setup и HEAD; та же причина, вернувшаяся при том же HEAD и том же предложении, остаётся прежним появлением.

## Прочитано и «увидел» — не «решено»

`POST /api/attention/marks {marks: [{sourceKey, occurrenceId, version, kind: "read" | "ack"}]}` (до 100 за запрос) отмечает показанную версию. Отметка — локальная запись оператора в базе workspace (пространство `attention`): она не пишет событие журнала и не меняет задачу, вопрос, согласование, бюджет, задание ведущего или паузу. Увиденная нерешённая карточка остаётся в списке.

- Отметка относится к появлению и версии: существенное обновление и новое появление снова не прочитаны, «увидел» снимается вместе с «прочитано».
- Отметка старой версии не отменяет отметку текущей. Отметка исчезнувшего появления не хранится и возвращается в `ignored`.
- Отметки исчезнувших карточек удаляются через 30 дней, всего не больше 2000 строк; удаление идёт только при записи отметок.
- Ведущий агент отметок не пишет и в `attention_list` их не получает.

## Чтение

`GET /api/attention?view=active|history&actor=&category=&component=` ничего не пишет: чтение идёт в одном снимке базы, и запись внутри него упала бы, а не закоммитилась. Модели не вызываются. Ответ: `revision` (ревизия данных снимка), `generatedAt`, `engineConnected`, `lead {present, lastActivityAt}` (присутствие ведущего по его журналу), `counts` (значок — непрочитанные карточки оператора), `items`, `truncated?`.

`view=history` — решённые появления по долговечным фактам решения, новые первыми, до 100: ответы на вопросы, решения по редакциям, решения ведущего по ответам, упавшие попытки с последующей попыткой или принятием, изменения контракта, завершённые после остановки, принятые ChangeSet. Паузы, ожидания, бюджеты, preview и зависания без факта снятия в историю не входят.

Агентская операция `attention_list {actor?, category?, limit?}` — тот же список для ведущего (по умолчанию `actor: lead`, до 50 карточек), только чтение, до и после setup. Она синхронна и не запускает Git: шаги быстрого маршрута ведущий видит в `preparation_status`.

## Действие с карточки

`POST /api/attention/act {sourceKey, occurrenceId, expectedVersion, action, input?, idempotencyKey?}` — только для доменных действий карточек оператора. Сервер пересчитывает карточку и сверяет появление и версию с показанными:

- карточки нет — 409 `attention-resolved`;
- появление или версия другие — 409 `attention-stale` с текущей карточкой: решение из старой вкладки не исполняется;
- действие не предлагается карточкой — 400.

Затем исполняется существующая доменная операция с её собственной проверкой (CAS) по пересчитанной карточке: ответ на вопрос подготовки, согласование этапа, утверждение плана с полями ревью, ответ в обсуждении с версией треда, ответ и применение ответа исполнителю, приёмка ChangeSet, подтверждение версии корпуса, запуск очереди. Синхронная операция и проверка — одна транзакция; такт очереди и выкладка preview начинаются после неё. Повтор с тем же `idempotencyKey` текстового действия возвращает прежнее сообщение (`replayed`), второго эффекта нет. Прежние маршруты карточки задачи и панели подготовки не меняются.
