# Продолжение этапов без активного чата

Ведущий агент сначала готовит workspace, среду, контракты и небольшой граф задач. Затем он регистрирует сохраняемый workflow через MCP `workflow_start` или CLI `agent --file request.json --workspace /absolute/workspace`:

```json
{
  "operation": "workflow_start",
  "input": { "kind": "board", "id": "BOARD_ID", "authorRuntime": "codex", "maxAttempts": 3 }
}
```

Укажите фактический runtime автора плана. Работа исполняется процессом `serve`: независимое review плана → запуск очереди → ожидание task gates и интеграции → приёмка доски. В demo используются явно обозначенные fixtures. В local mode вызываются настоящие runtime, поэтому регистрация workflow при работающем сервере может расходовать лимиты моделей. Сам MCP сервер исполнения не запускает.

Для общего результата зарегистрируйте отдельный workflow с `kind: changeset` и ID уже созданного ChangeSet. Он дождётся приёмки входящих досок, выполнит совместную проверку и примет проверенный результат. Remote completion ждёт наблюдаемую доставку; push, PR/MR, merge, deployment и rollback остаются действиями человека.

`workflow_status` принимает опциональный `repositoryId`. Без него возвращаются общие jobs, с ним — jobs компонента. CLI использует тот же JSON envelope. `workflow_retry` принимает `key` и тот же owner; сначала нужно разобраться в причине ошибки. Retry не обнуляет бюджет и не перезапускает упавшие задачи самостоятельно. Настройка `approvalMode: operator` блокирует автоматическое продвижение.

## Восстановление

Job привязан к владельцу, ревизии, постановкам, контрактам и конфигурации. Повтор регистрации того же входа возвращает прежний job. Изменённый или удалённый вход делает старый job `stale`, не останавливая остальные jobs; для нового плана нужна новая регистрация. Модель не получает права произвольно менять стадию или отмечать результат завершённым.

SQLite хранит stage, попытки, историю переходов и lease. Запись находится в `local_workflow` базы владельца доски, общий ChangeSet — в coordinator. Задачи и контракты не копируются в этот журнал. Эти оперативные записи не синхронизируются через Git; на другом компьютере цикл регистрируется по перенесённому графу заново.

После сбоя проверяется фактическое состояние: уже утверждённый план не получает повторного review, принятая доска не принимается второй раз, успешная актуальная Verification переиспользуется. Запоздалый reviewer проверяет lease в той же транзакции, что и утверждение. Ожидание задач не тратит лимит внешних попыток. Ошибка задачи требует диагностики; автоматического бесконечного repair-loop нет.

При перезапуске сервера цикл может возобновить очередь, остановленную штатным shutdown. Явную пользовательскую паузу он сохраняет. Очередь общая для workspace: её включение разрешает исполнение всех подготовленных задач согласно зависимостям, назначениям и обычной политике scheduler.

`maxAttempts` ограничивает число запусков одной стадии после ошибок/потери lease, а `runTimeoutMs` — внешнюю работу. Денежный лимит провайдера задаётся отдельно. `workflow_status` не выдаёт fencing tokens.

Это продолжение уже подготовленного графа, не сервис автоматического чтения произвольных новых ТЗ. Bootstrap, исправление противоречивых требований и существенное перепланирование выполняет ведущий агент. Сервер должен оставаться запущенным; установка npm сама по себе не создаёт системную службу.
