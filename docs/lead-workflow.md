# Продолжение этапов без активного чата

Новый продуктовый маршрут начинается с [раннего запуска панели и продуктовых согласований](staged-workflow.md): продукт утверждает пользователь, затем архитектуру и стек с C1/C2, затем дизайн-трек — референсы, а при применимом интерфейсе ещё концепт и дизайн-систему. Технические операции ниже выполняются после этих решений, а задачи исполнения — только после всей цепочки. `approvalMode` не отменяет их.

Ведущий агент сначала готовит workspace, среду, контракты и небольшой граф задач. Затем он регистрирует сохраняемый workflow через MCP `workflow_start` или CLI `agent --file request.json --workspace /absolute/workspace`:

```json
{
  "operation": "workflow_start",
  "input": { "kind": "board", "id": "BOARD_ID", "authorRuntime": "codex", "maxAttempts": 3 }
}
```

Укажите фактический runtime автора плана. Работа исполняется процессом `serve`: независимое review плана → запуск очереди → ожидание task gates и интеграции → приёмка доски. В demo используются явно обозначенные fixtures. В local mode вызываются настоящие runtime, поэтому регистрация workflow при работающем сервере может расходовать лимиты моделей. Сам MCP сервер исполнения не запускает.

Для общего результата зарегистрируйте отдельный workflow с `kind: changeset` и ID уже созданного ChangeSet. Он дождётся приёмки входящих досок, выполнит совместную проверку и примет проверенный результат. Для продуктового релиза создайте ChangeSet с releaseId из общей карты INTENT: runner обязательно закрепит карту и выполнит полную совместную проверку. После изменения карты завершённая стадия verification может стать неактуальной; acceptance откажет, нужна повторная проверка и retry workflow. Remote completion ждёт наблюдаемую доставку; push, PR/MR, merge, deployment и rollback остаются действиями человека.

`workflow_status` принимает опциональный `repositoryId`. Без него возвращаются jobs общих досок и ChangeSet, с ним — jobs локальных досок компонента. Это выбор владельца, а не фильтр по всем tasks: общая доска с работами нескольких репозиториев находится в общем контуре. Ответ `workflow_start.owner` показывает выбранного владельца. CLI использует тот же JSON envelope. Настройка `approvalMode: operator` блокирует автоматическое продвижение, включая jobs, зарегистрированные раньше.

## Стадии и наблюдение

| `stage` | Доска                                                                             | ChangeSet                                                                         |
| ------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 0       | Проверить план другим runtime и утвердить; уже утверждённый план переиспользуется | Дождаться принятых ревизий всех досок                                             |
| 1       | Включить очередь workspace, если задачи ещё не завершены                          | Выполнить совместные gates либо переиспользовать актуальную успешную Verification |
| 2       | Дождаться задач, проверить свежесть связанных требований, принять ревизию         | Дождаться Delivery в remote mode и применить доменные условия приёмки             |
| 3       | Workflow завершён                                                                 | Workflow завершён                                                                 |

Ответ `workflow_start` (как и `review-plan`) содержит прогноз `coverageGaps` и `warning`, если в области ни одной задачи доски нет каких-то gates профиля компонента. Регистрация при этом не отклоняется; решающее правило приёмки считается по записанному evidence (`uncoveredGates`). На стадии 2 приёмка выполнит такие gates с их предпосылками один раз на итоговом integration SHA доски, тем же исполнением, что integration задач, с записью evidence под lease workflow (`board-coverage`); повтор после частичного провала сохраняет уже прошедшие gates и исполняет только остальные. Предпосылки gate проверки доски выводятся из профиля: у gate с объявленным `dependsOn` (в том числе пустым) — его замыкание, у gate без поля `dependsOn` (профиль в режиме порядка массива) — все более ранние gates вида `check`, например установка и сборка; более ранние test gates не повторяются. Исполняются все непокрытые gates, а не до первого провала: доска принимается, только если все прошли, а отказ стадии называет каждый непрошедший gate. Gate с непрошедшей явной предпосылкой (`dependsOn`) не исполняется и назван с этой причиной; провал неявной (раннего check gate) тесты не пропускает — названы оба. Журнал получает события `board.coverage.started`, `board.coverage.passed` и `board.coverage.failed` с ids gates; отказ самой проверки (окружение, отмена) тоже пишет `failed` с причиной. Прогноз `coverageGaps` называет и предпосылки (`prerequisites`), и gates, которые проверка доски исполнила бы без всякой подготовки (`withoutSetup`: нет `dependsOn`, более ранних check gates и prepare, хотя задачи опирались на check gates своей области). Чтобы такой провал находила задача, а не приёмка, включите gate в область задачи, которая меняет проверяемый им код.

`queued` означает готовность к следующей попытке стадии или ожидание состояния задач/доставки; отдельного статуса `waiting` нет. `running` — стадия с действующим владельцем; это не обязательно работа модели. `completed` — завершённый цикл для закреплённого входа. `failed` требует диагностики; `stale` означает, что прежний вход больше нельзя продолжить. Ответ также содержит `attempts`, `maxAttempts`, `history`, возможный `error` и `operatorBlocked` в status-запросе.

Пример файла `status.json` для CLI `devcontour agent --file status.json --workspace /absolute/workspace`:

```json
{ "operation": "workflow_status", "input": { "repositoryId": "main" } }
```

`workflow_retry` принимает `key` из регистрации и `repositoryId` того же владельца (для общего job поле не передаётся). Сначала исправьте причину: повтор Task через `task_retry`/`retry --task` и повтор стадии workflow — разные действия. Retry допустим для failed job с неизменным входом и оставшимся бюджетом; он не обнуляет лимит. Повтор `workflow_start` также не сбрасывает бюджет и не меняет первоначальный `maxAttempts`.

Пока workflow ведёт доску/ChangeSet, не вызывайте для того же результата ручные review/verify/accept. Для полного прекращения автоматического продвижения остановите `serve`: отдельного API pause/cancel для job пока нет. Чтение статуса не запускает работу.

## Восстановление

Job привязан к владельцу, ревизии, постановкам, контрактам и политике workspace/компонентов. Повтор регистрации того же входа возвращает прежний job; другой runtime автора отклоняется. При следующей проверке незавершённого job изменённый или удалённый вход делает его `stale`, не останавливая остальные jobs. Для нового плана нужна новая регистрация. Завершённый job остаётся историей своего входа. На паузе стадии не берутся, и job с изменившимся входом остаётся `queued`. Поэтому статус job (`workflows[].inputStale`) и прогресс задач его доски (`progress.workflowStale`) называют устаревший вход чтением. Новый job той же доски, зарегистрированный и на паузе, снимает это сведение, а прежний закроется `stale` сам. Вход, который нельзя построить (например, продукт не согласован), называет своя причина задачи, а не это сведение. Отдельно от входа job утверждение плана закрепляет политику исполнения ([D43](decisions.md#d43-утверждение-плана-закрепляет-политику-исполнения)). Задача, утверждённая при другой политике, не выдаётся (`approval_stale`), и стадия согласования нового job проводит `review-plan` для таких задач так же, как для черновиков. Модель не получает права произвольно менять стадию или отмечать результат завершённым.

SQLite хранит stage, попытки, историю переходов и lease. Запись находится в `local_workflow` базы владельца доски, общий ChangeSet — в coordinator. Задачи и контракты не копируются в этот журнал. Эти оперативные записи не синхронизируются через Git; на другом компьютере цикл регистрируется по перенесённому графу заново.

После сбоя проверяется фактическое состояние: уже утверждённый план не получает повторного review, принятая доска не принимается второй раз, успешная актуальная Verification переиспользуется. Запоздалый reviewer проверяет lease в той же транзакции, что и утверждение. Ожидание задач не тратит лимит внешних попыток.

## Восстановление после сбоя задачи

Упавшая задача больше не останавливает цикл сама по себе. Класс отказа ставится там, где отказ обнаружен: провал проверки — в проверке, пустой коммит — при сборе diff, отклонение — в ревью, отказ провайдера и обрыв окружения — в планировщике. Класс и отпечаток записываются вместе с попыткой и переживают перезапуск.

| Класс                                                                | Действие             | Предел одинаковых |
| -------------------------------------------------------------------- | -------------------- | ----------------- |
| `gate`, `review`, `unfinished`                                       | повтор               | 2                 |
| `empty-result`, `scope-violation`, `timeout`, `merge`, `environment` | повтор               | 1                 |
| `provider-auth`, `stale-base`, `cancelled`, `needs-lead`, `unknown`  | остановка с причиной | —                 |

`empty-result` ставится, только если исполнитель не изменил ни файла и это не доказано как уже выполненная работа. Пустой результат проходит gates задачи на базе, а оба ревью получают обязательное поле `alreadySatisfied`: gates области (хотя бы один test gate и все проверки договоров задачи) и основание. Подтверждения ревьюера мало: контур сам ищет механическое основание — договор проверки задачи, все gates которого входят в её область, или зависимость задачи, чей принятый кандидат изменил файлы её области записи. С ним задача становится `done` без нового коммита в ту же попытку. Без основания попытка останавливается классом `needs-lead`: зелёный общий тест на базе не доказывает, что новая работа есть, и решение — принять задачу без изменений или поставить её заново — за ведущим. Красный gate на базе, отказ ревью или негодное подтверждение дают `empty-result`.

Повтор — обычный повтор в пределах бюджета попыток задачи. Отказ окружения или провайдера и истёкшее владение попытку не засчитывают, даже после кандидата: о работе они ничего не говорят. У них свой предел — три на задачу (`neutralFailures`); на нём повтор без сброса, выдача и восстановление отказывают. `unfinished` — исполнитель сообщил `completed: false`: повтор продолжает с сохранённого черновика. Сброс этого бюджета остаётся действием человека: он означает «причина устранена снаружи», и утверждать это за человека контур не вправе. Одинаковые отказы считаются по отпечатку сообщения, очищенного от SHA, идентификаторов, путей, чисел и времени; при разном тексте отпечатки расходятся — лишний повтор ограничен пределом класса, а ложная остановка обошлась бы дороже. Исчерпание предела останавливает цикл словами «одна и та же причина N раз, новой гипотезы нет».

Выдача останавливается целиком только для классов, которые повторятся на любой задаче: отказ провайдера и обрыв окружения. Пауза ставится в той же транзакции, что и запись отказа. Отказ окружения до кандидата попытку не засчитывает. Если цикл board workflow назначает повтор по `environment`, он той же транзакцией снимает этот класс паузы, и выдача возвращается на его следующем шаге, обычно через секунду. Поэтому под циклом разовый обрыв окружения выглядит как повтор без остановки очереди. Без цикла (прямые `retry`) пауза стоит, пока её не снимет человек (`queue --start`). Второй такой же отказ исчерпывает предел класса, цикл останавливается, а пауза остаётся. Причин может быть несколько одновременно — обрыв связи по одной доске и отсутствие кредитов по другой, — и все они хранятся вместе. Починив свою, восстановление убирает её из списка; выдача возвращается, когда не осталось ни одной. Решается это классом отказа, а не поиском слов в сообщении: замечание ревью про «401 Unauthorized» в разрабатываемом приложении иначе становилось отказом провайдера.

Пауза человека отдельна и не снимается автоматически ни восстановлением, ни шагом стадии: разрешение начать работу однажды не отменяет будущих остановок. Штатная остановка сервера — не решение о работе, её цикл снимает сам. Прерванная ею попытка не падает: черновик сохраняется, попытка помечается `interrupted: shutdown`, задача возвращается в очередь без траты попытки, и после снятия паузы остановки продолжается с кандидата или черновика. Интегрированная попытка так не возвращается — это обычный отказ с причиной в `scheduler.error`.

`repairBudget` (по умолчанию 6) ограничивает число автоматических восстановлений на всю работу, а не на задачу: локально допустимые повторы складываются, и без общего потолка доска из пятнадцати задач заняла бы пятнадцать бюджетов подряд. Счётчик и само восстановление записываются одной транзакцией, поэтому прерывание между решением и его исполнением не даёт ни повтора без учёта, ни учёта без повтора. Причина окончательной остановки попадает в `error` работы, в `/api/state` вместе с потраченным бюджетом и видна в панели: остановленное восстановление не должно выглядеть ожиданием свободного исполнителя.

Повтор после отказа, который ничего не говорит о коде (оборвался транспорт исполнителя или проверяющего, истёк срок владения, кончилось время), берёт кандидата непосредственно предыдущей попытки вместо новой реализации. Условие — совпадение всех оснований, записанных до реализации: утверждённой спецификации, контрактов, договора исполнения (проверки, окружение, роли, изоляция, память), runtime и модели, базы ветки интеграции, context packs, зависимостей, памяти и версии контура. Кандидат должен быть одним коммитом поверх той же базы и снова проходит проверку области; проверки кандидата, ревью и интеграция исполняются новой попыткой с новым владением. После отклонения ревью, провала проверки или любого расхождения оснований код пишется заново. Прежняя попытка и её расходы сохраняются; `metrics` показывает взятые реализации (`reuse`), их источник у каждой попытки (`reusedFrom`) и время по фазам с долей, потерянной в неудачных попытках (`phases`). Отключается настройкой `reuseImplementation: false`.

### Повторяющееся свойство

Два последовательных содержательных отказа задачи по одному объявленному свойству открывают эпизод: третья автоматическая выдача запрещена, обычный повтор по классу отказа к такой задаче не применяется. На стадиях ожидания цикл резервирует один разбор ведущего на эпизод (в `repairBudget`, до вызова модели), получает структурированное решение и исполняет только разрешённое: подтверждённые случаи корпуса и один повтор, либо один повтор с новой гипотезой. Предложение усилить проверку или разделить задачу, конфликт продуктового смысла и причина в среде останавливают работу с названной причиной. Прерванный разбор повторно не вызывается бесплатно; повторный провал после разрешённого повтора останавливает цикл. Пауза человека, наступившая после старта, и operator mode разбор не запускают. Подробнее — [договор проверки](check-contracts.md).

### Пробел приёмки

Ревьюер называет у блокирующей находки со входом нарушенное свойство или критерий и класс входов (`inputClass`) — генератор или семейство, а не экземпляр; следующий исполнитель получает задачу чинить класс. Тексты отказов от попытки к попытке разные, поэтому сверх отпечатка считается названное: два отказа ревью подряд по одному необъявленному свойству с тем же классом входов останавливают цикл как пробел приёмки (`gap` в решении восстановления) вместо третьей слепой попытки. Совпадение только свойства или только класса требует трёх отказов подряд. Отказ окружения серию не меняет; отказ gate, другое название и новое основание задачи её обрывают. Решение ведущего — закрепить класс проверкой (корпус, эталонный набор, свойство договора проверки) или разделить задачу.

Отмена человеком никогда не превращается в повтор и проверяется раньше выбора чинимой задачи.

На стадии ожидания задач цикл может возобновить очередь, остановленную штатным shutdown; явную пользовательскую паузу эта стадия сохраняет. Стадия 1 нового board workflow включает очередь, если её никто не останавливал; паузу оператора, поставленную после регистрации работы, она сохраняет. Очередь общая для workspace: её включение разрешает исполнение всех подготовленных задач согласно зависимостям, назначениям и обычной политике scheduler. Перед Git sync, сменой политики или согласованным backup остановите сервер и другие записывающие клиенты.

`maxAttempts` (по умолчанию 3, диапазон 1–5) ограничивает число запусков одной стадии после ошибок/потери lease, а `runTimeoutMs` — внешнюю работу runner. Это не отдельный срок жизни всего workflow: ожидание зависимостей и human publication может продолжаться дольше. Денежный лимит провайдера задаётся отдельно. `workflow_status` не выдаёт fencing tokens. Ограничение ответа — 64 KiB, пагинации jobs пока нет; `export` не заменяет чтение этой таблицы.

Это продолжение уже подготовленного графа, не сервис автоматического чтения произвольных новых ТЗ. Bootstrap, исправление противоречивых требований и существенное перепланирование выполняет ведущий агент. Сервер должен оставаться запущенным; установка npm сама по себе не создаёт системную службу.
