# Визуальная приёмка

Unit-тесты компонентов и сборка бандла не видят отрисованный экран: фон, закрытый сплошной заливкой, кнопку под экранной клавиатурой и предупреждения среды выполнения. Визуальная приёмка проверяет такие дефекты детерминированными утверждениями над наблюдениями реального экрана и сообщает результат обычным JUnit `test` gate.

Разделение ответственности:

- **Продукт объявляет**, какие состояния экрана существуют и что в них должно выполняться, — в спецификации, закреплённой как артефакт контракта. Её изменение — новая ревизия контракта, а не правка в попытке.
- **DevContour определяет**, как состояние достигается, измеряется и оценивается. Утверждения — код инструмента, а не продукта: исполнитель не может ослабить проверку своей работы.

Модель-ревьюер может оценивать снимки, но приёмку не заменяет: блокируют только утверждения ниже.

## Что реализовано

| Часть                                                   | Состояние                                                                                      |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Формат спецификации и строгая схема                     | Реализован                                                                                     |
| Утверждения `visible`, `tap-hits`, `background`, журнал | Реализованы над записанными наблюдениями                                                       |
| `devcontour visual evaluate` и JUnit                    | Реализованы                                                                                    |
| `devcontour visual run` (клиент broker, прогон, JUnit)  | Реализован для `ios`; драйвер `web` ещё нет — прогон даёт ошибку окружения                     |
| Device broker и runner XCUITest (`visual broker start`) | **Ещё не реализованы**: `visual run` говорит с broker по договору ниже, команда broker — отказ |
| Сохранение снимков в evidence задачи                    | Через `artifacts` gate: harness копирует `.reports/visual` после gate                          |

Пока broker не входит в поставку, визуальный gate на iOS требует внешнего broker с тем же договором; без него gate красный с ошибкой окружения, а не пропущен.

## Спецификация

Файл JSON в репозитории продукта, например `contracts/ui-states/app.json`, не больше 256 КБ. Лишние поля отклоняются.

```json
{
  "version": 1,
  "platform": "ios",
  "host": "dev-client",
  "defaults": { "settleMs": 400, "stateTimeoutMs": 15000 },
  "log": {
    "forbid": ["deprecated|obsolete", "^WARN\\b"],
    "allow": [{ "pattern": "WARN Require cycle", "reason": "известный долг, задача DEBT-12" }]
  },
  "states": [
    {
      "id": "UI-checkout-focused",
      "steps": [{ "launch": true }, { "tap": "amount-input" }, { "type": "135" }],
      "assert": [
        { "kind": "visible", "element": "checkout-submit" },
        {
          "kind": "tap-hits",
          "element": "checkout-submit",
          "expect": { "visible": "checkout-result" }
        },
        { "kind": "background", "surfaces": ["checkout-card"], "maxFlatShare": 0.5 }
      ]
    }
  ]
}
```

- `platform`: `ios` или `web`. Для `web` экранной клавиатуры нет, и `notUnder: ["keyboard"]` отклоняется.
- `host`: где исполняется приложение. Для `ios` — `dev-client` (по умолчанию) или `expo-go`, для `web` — `browser`. Expo Go допустим в gate задачи, но проверка уровня релиза (`visual run --release`) его не принимает: у Expo Go свои версии React Native и нативных модулей. Хост, который сообщил broker, пишется в evidence (`run.json` и testcase `visual.host.accepted`). Спецификация с `expo-go` под `--release` проваливает `visual.host.accepted` ещё до обращения к broker; Expo Go, о котором сообщил broker под `--release`, — тоже провал. Без `--release` хост broker, отличный от спецификации, — ошибка окружения на всех проверках: состояния не выполняются, и ни одна проверка не становится зелёной.
- `device`: `model`, `runtime`, `appearance` (`light`/`dark`), `locale`. Требования уходят broker в `hello` (параметр `expect`), чтобы он настроил устройство, а устройство из ответа сверяется с ними: модель — точно, `runtime` `iOS 18` допускает `iOS 18.5`, но `iOS 18.5` не допускает `iOS 18.50`, локаль — без учёта регистра и `-`/`_`. Расхождение — ошибка окружения на всех проверках, как и чужой хост.
- `route` состояния открывается deep link `<app.scheme>://<route>` до шагов (для `web` — от `app.url`); без `app.scheme`/`app.url` спецификация отклоняется. Если в шагах есть `launch`, route открывается сразу после последнего запуска, иначе до шагов. `seed` передаётся приложению аргументами запуска `-DevContourSeed <seed>` на каждом шаге `launch`; `seed` без шага `launch` отклоняется.
- `id` состояния — `UI-<экран>-<состояние>`. Тот же id называет состояние в разделе «UI states» текстового контракта.
- `steps` — закрытый словарь:
  - `{"launch": true}` — запустить приложение;
  - `{"tap": <цель>}` — касание по координате центра видимой рамки элемента, а не касание элемента средствами фреймворка: точка фреймворка может попасть в незакрытую полоску кнопки, которую пользователь не видит;
  - `{"type": "<текст>"}` — набор в поле в фокусе;
  - `{"clear": <цель>}` — очистить поле: фокус и удаление всего текста;
  - `{"wait": <цель>, "timeoutMs": 5000}` — дождаться элемента;
  - `{"scroll": "<контейнер>", "to": <цель> | "end", "maxSwipes": 10}` — прокрутить именованный контейнер до элемента или до конца, не больше `maxSwipes` (1–20) жестов. `end` зарезервирован: элемент с id `end` целью прокрутки быть не может.
- `element` — testID / accessibility identifier.
- Цель шага — id элемента или селектор для id, создаваемых во время работы: `{"prefix": "item-add-", "index": 0}` — `index`-й (0–49) элемент на экране, чей id начинается с префикса (2–64 символа), в порядке чтения: сверху вниз, затем слева направо. Утверждения называют элементы только точным id.
- Пределы: не больше 12 состояний; у состояния 1–16 утверждений и до 32 шагов; бюджет состояния `stateTimeoutMs` (по умолчанию 15 с, не больше 60 с, переопределяется полем `timeoutMs` состояния); сумма бюджетов не больше 420 с — времени gate; `settleMs` до 3 с.
- Два утверждения одного вида в состоянии различаются полем `name`. `tap-hits` в состоянии не больше одного: касание меняет экран, и второе оценивалось бы по рамкам, снятым до первого. Второе касание — отдельное состояние.
- `decorative` — id элементов, которые не принимают касаний (фоновое изображение, декоративная подложка), до 64, без повторов. Им нельзя быть целью `tap`/`clear` или элементом `tap-hits`, а префикс цели касания не может покрывать декоративный id. `decorative` влияет только на то, как драйвер без hit-test вычисляет `hit`: он исключает эти id. Оценщик их не прощает: `hit`, названный декоративным id, — промах (касание приняло то, что касаний принимать не должно), как и запись шага, чья цель декоративна.
- Все id спецификации должны существовать на каждом SHA, где она запускается. Новый экран или переименование — новая ревизия спецификации; старый SHA без id даёт провал `reach` с названным id, а не тайм-аут.

## Утверждения

Каждое утверждение даёт один testcase `visual.<stateId>.<name>`, где `name` — явное имя или вид утверждения. Этот id можно указать как `testId` требования.

Кроме того, каждое состояние даёт testcase `visual.<stateId>.reach` (имя `reach` для утверждений занято). Он проходит, если состояние достигнуто и ни одно касание шага не ушло мимо цели. Касание шага заблокировано, если его точка под клавиатурой, касание принял не целевой элемент или изменился текст поля в фокусе. Заблокированный шаг — провал `reach` с доказательством касания, даже если драйвер после этого не смог достичь состояния; утверждения такого состояния тогда тоже падают со ссылкой на `reach`. Провалом `reach` также становятся цель шага вне окна (видимого центра нет) и цель, которой не было на экране за всё время шага. Недостигнутое состояние без таких доказательств — ошибка окружения.

Точка под клавиатурой и чужой `hit` проверяются у каждой записи с касанием, даже если в записи есть нарушение договора: такое касание остаётся заблокированным шагом. Записи касаний шагов обязательны: у достигнутого состояния — ровно одна на каждый шаг `tap` и `clear`, у недостигнутого — на каждый такой шаг до последнего записанного (или до шага из `missing`). Отсутствующая или повторная запись, запись не того шага, касание не по центру и неверный выбор по префиксу — нарушения договора драйвером: без заблокированного шага это ошибка окружения, а при найденном заблокированном шаге `reach` падает, и сообщение перечисляет нарушения отдельной строкой.

| Вид          | Проходит, если                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `visible`    | Рамка элемента целиком внутри окна (с `inset: "safe-area"` — внутри safe area) и не пересекает клавиатуру. Провал называет закрытые точки: «закрыто 36 из 56 pt по высоте». `notUnder: []` отключает проверку клавиатуры и требует поля `reason` с причиной.                                                                                                                                                                                                             |
| `tap-hits`   | Касание сделано в центре рамки элемента, обрезанной окном; точка не под клавиатурой; касание принял сам элемент; объявленный эффект (`visible` — элемент появился, `hidden` — скрылся) наступил именно после касания; текст поля в фокусе не изменился.                                                                                                                                                                                                                  |
| `background` | В области (`content` — safe area минус рамки `surfaces`, либо прямоугольник в долях окна) доля трёх самых частых цветов не больше `maxFlatShare` (по умолчанию 0.5, не выше 0.9). Рамка клавиатуры из области исключается: она не фон приложения. Пиксели берутся сеткой до 96×96 точек и квантуются до 5 бит на канал. Фото или текстура дают низкую долю, сплошная заливка — высокую. Доля, число точек и три цвета пишутся в `<system-out>` и при зелёном результате. |
| журнал       | Ни одна строка журнала прогона не совпадает с `log.forbid`, кроме разрешённых `log.allow` с указанной причиной. Один testcase на прогон: `visual.log.no-forbidden`; его `<system-out>` называет число проверенных строк и сколько строк пропустило каждое разрешение.                                                                                                                                                                                                    |

Шаблоны журнала — регулярные выражения без учёта регистра в ограниченном виде: без групп, квантификаторов (`*`, `+`, `?`, `{}`), обратных ссылок и lookaround; альтернативы `|` — только на верхнем уровне. Классы символов, `^`, `$`, `\b`, `.` и escape допустимы. Тогда проверка строки линейна по её длине, поэтому строки журнала не обрезаются: журнал читается целиком (до 32 МБ; больше — ошибка окружения, а не проверка начала). `.*` недопустим: вместо `Warning: .* is deprecated` пишут самую характерную часть строки (`is deprecated`) или перечисляют варианты альтернативами (`is deprecated|is obsolete`, `deprecat[a-z]`).

Разрешение должно быть уже запрета. Каждая альтернатива `log.allow` отклоняется, если она:

- покрывает пустую или нейтральную строку (`a`, `ok`, `0`);
- покрывает пример строки запрета: альтернатива запрета, где класс `[...]` заменён его членом, `\b` — пробелом, якоря опущены (`^WARN\b` → `WARN `);
- не содержит буквального текста не короче 8 символов;
- после удаления из этого текста совпадений запрета и разделителей сохраняет меньше 4 букв или цифр.

Так `:`, `warn`, `WARN ` или `deprecated` при запрете `deprecat[a-z]` отклоняются, а `WARN Require cycle` при запрете `^WARN\b` принимается.

Порог `background` — эвристика: тёмные темы, размытые фоны и градиенты калибруются своим `maxFlatShare` или явной областью.

## `visual run` и device broker

Gate исполняется в песочнице ОС, где сервисы iOS-симулятора недоступны. Поэтому устройство обслуживает broker — процесс хоста, который запускает `lifecycle.setup` репозитория, а gate говорит с ним только по localhost:

```json
{
  "resources": [
    { "id": "ios-sim", "kind": "device", "value": "iPhone 16 Pro / iOS 18.5" },
    { "id": "visual-broker", "kind": "port", "value": "8093" }
  ],
  "gates": [
    {
      "id": "visual-mobile",
      "kind": "test",
      "command": ["devcontour", "visual", "run", "--spec", "contracts/ui-states/mobile.json"],
      "resources": ["ios-sim", "visual-broker"],
      "timeoutMs": 420000,
      "report": { "type": "junit", "path": ".reports/visual.xml" },
      "artifacts": [".reports/visual"]
    }
  ],
  "gateGroups": { "visual": ["visual-mobile"] }
}
```

- Порт broker — ресурс `port` с id из `--broker` (по умолчанию `visual-broker`), устройство — первый ресурс `device`; оба приходят в `DEVCONTOUR_RESOURCES_JSON`. Токен прогона — `DEVCONTOUR_VISUAL_TOKEN`.
- Протокол: `POST http://127.0.0.1:<port>/rpc`, `Authorization: Bearer <token>`, тело `{"method", "params"}`, ответ `{"result"}` или `{"error": {"message"}}`. Набор вызовов закрыт: `hello`, `frames`, `keyboardFrame`, `tapPoint`, `typeText`, `drag`, `screenshot`, `launch`, `openURL`, `logSize`, `logRead`. Ответ сверяется со схемой; ответ не по договору — ошибка окружения.
- Рамки и точки — в pt окна, снимок `screenshot` — PNG в пикселях устройства. `hit` вычисляет сам `visual run` по рамкам снимка (правило драйвера без hit-test ниже), а не broker.
- Прогон пишет в `--out` (по умолчанию `.reports/visual`, внутри рабочего дерева; каталог должен быть в `.gitignore`): `<stateId>.frames.json`, `<stateId>.png`, `<stateId>.after-<имя>.png` после касания `tap-hits`, `log.txt` и `run.json` (платформа, хост, устройство, время состояний, причина сбоя окружения). Перед прогоном, ещё до разбора спецификации, удаляются только записи с этими именами. `--out` и каталог `--report` должны оставаться внутри рабочего дерева и после разрешения символических ссылок; подложенная ссылка с именем наблюдения или отчёта удаляется, а файлы создаются заново, без перехода по ссылкам. Затем каталог оценивается так же, как `visual evaluate`.
- Касание шага, заблокированное клавиатурой или другим элементом, выполняется, как его выполнил бы пользователь, и записывается доказательством для `reach`.
- Рамки для касания и измерения читаются по устойчивому снимку: клавиатура не меняется два чтения подряд через 200 мс, затем рамки элементов — пока два снимка подряд не совпадут (до трёх чтений).
- Набор идёт по одному символу с проверкой поля после каждого (одна повторная проверка через 500 мс). Поле пароля broker помечает `secure: true`: вместо текста приходит маска, поэтому сравнивается длина, а текст в отчёт не попадает.
- Экран, не ответивший на шаг, — провал `reach` (запись `failure`), а не ошибка окружения. Это: набор без поля в фокусе, ушедший фокус, текст не тот; после касания `clear` в фокусе не цель или после удаления остался текст; контейнер прокрутки не на экране или вне окна; цель не показана в видимой части за `maxSwipes` жестов. Если цели прокрутки нет в дереве вовсе, пишется `missing` с целью шага. Ошибкой окружения остаются только сбои broker, симулятора и связи, а также исчерпанный бюджет состояния: прогон заканчивается отчётом раньше timeout gate.
- Клиент не следует перенаправлениям, ограничивает ответ 48 МБ и проверяет сигнатуру PNG снимка.

Ошибка окружения не пропускает проверку: каждое объявленное утверждение получает `<error type="environment">` с причиной. Так оформляются gate не на macOS («iOS-симулятор доступен только на macOS»), нет ресурсов или токена, broker не отвечает или нарушает договор, хост или устройство broker не совпадают со спецификацией (без `--release`). Код выхода `visual run` и `visual evaluate`: 0 — всё прошло; 1 — провал утверждения, пустой прогон или неверная спецификация; 75 — провалов нет, но есть ошибки окружения. Harness считает красным любой ненулевой код; тип `<error>` в JUnit и код 75 различают сбой окружения и дефект продукта для читателя evidence.

## Наблюдения и `visual evaluate`

```
devcontour visual evaluate --spec contracts/ui-states/app.json --observations .reports/visual --report .reports/visual.xml
```

Каталог наблюдений:

- `<stateId>.frames.json` — `{"version": 1, "state", "window", "safeArea", "keyboard", "elements", "taps", "stepTaps", "log"}`. Прямоугольники в pt: `{x, y, width, height}`. `keyboard: null` — клавиатуры на экране нет.
  - `taps` — касания утверждений `tap-hits` по имени: `{element, point, hit, before, after}`, где `before`/`after` — `{visible: [id...], focused: {element, text} | null}`. `text` — значение поля, а не подсказка: пустое поле — `""`, даже если платформа отдаёт placeholder как значение. Текст поля сравнивается, только пока фокус остаётся на том же поле: отправка формы законно снимает фокус.
  - `stepTaps` — касания шагов `tap` и `clear`: `{step, element, frame, window, keyboard, point, hit, before, after}`, где `step` — номер шага с нуля, `element` — фактический id (для селектора — найденный), `frame`, `window` и `keyboard` — рамки в момент касания. Для `clear` `after` снимается сразу после фокусирующего касания, до удаления текста: само касание текст менять не должно, а удаление проверяет драйвер (не удалось — сбой шага). Пустое поле в `after` при непустом `before` значит, что снимок сделан после удаления, — нарушение договора драйвером. Для цели-префикса запись обязательно содержит `candidates: [{id, frame}]` — все элементы на экране с этим префиксом; оценщик сам упорядочивает их: сначала группирует в строки по y (новая строка, если y дальше 0,5 pt от первого элемента строки), затем внутри строки — по x, и проверяет, что выбран `index`-й. Кандидаты без повторов; каждый id с префиксом из `before.visible` обязан быть среди кандидатов; рамка выбранного кандидата должна совпадать с `frame` записи (допуск 0,5 pt). Нарушение — ошибка договора драйвером. Если цель найдена, но её рамка вне окна, видимого центра нет: драйвер не касается и пишет `{step, element, frame, window, keyboard, "point": null}` без `hit`/`before`/`after` — это провал `reach` «цель шага вне окна». Шаг `scroll` таких записей не даёт: цель вне окна — его обычный случай.
  - `failure` — только у недостигнутого состояния: `{step, kind, message}`, где `kind` — `type`, `clear` или `scroll` и совпадает с шагом спецификации. Шаг выполнен, но экран не ответил так, как требует шаг; это провал `reach` с сообщением. Вместе с `missing` — нарушение договора.
  - `missing` — `{step, target, visible}`: цель шага (как её называет спецификация: id или `префикс*[index]`) не появилась на экране за всё время шага; `visible` — id на экране в конце ожидания. Это провал `reach` с названным id. Драйвер пишет `missing` только после полного бюджета шага, иначе медленный экран выглядел бы дефектом.
  - `log` — необязательное байтовое окно `log.txt`, записанное за время состояния: `{from, to}`, полуинтервал. Если окна есть, провал журнала называет состояние каждой запрещённой строки или «вне окон состояний». Окна осмысленны только при свежей загрузке JS в каждом прогоне (холодный bundler или принудительная полная перезагрузка): иначе предупреждение, выводимое один раз за загрузку, окажется в прошлом прогоне или вне окон.
  - Если драйвер не смог достичь состояния, он пишет `{"version": 1, "state", "error", "stepTaps", "log"}`: касания уже выполненных шагов обязательны, по ним `reach` отличает дефект продукта от сбоя драйвера.
- `hit` — лучшее доказательство драйвера о том, кто принял касание, обязательное поле: `{"kind": "element", "element": "<id>"}`, `{"kind": "keyboard"}` или `{"kind": "none"}`. Клавиатура называется явно, а не id элемента. Как драйвер его вычисляет:
  - драйвер с hit-test (web: `document.elementFromPoint`) — элемент в точке или ближайший предок с id;
  - драйвер без hit-test и без надёжного порядка отрисовки (XCUITest: порядок снимка дерева — не порядок отрисовки, полноэкранный фон может идти последним, контейнер — после своих детей): точка в рамке клавиатуры — `keyboard`; иначе наименьшая по площади рамка, содержащая точку, среди элементов с id, кроме `decorative` и элементов, о которых драйвер знает, что они не принимают касаний; иначе `none`.

  Элемент со своим id, вложенный в цель (подпись внутри кнопки), — то же касание в двух случаях: драйвер с настоящей иерархией (web) подтверждает потомка полем `"descendant": true`, или драйвер указал рамку (`"frame": {...}`), которая лежит внутри рамки цели и строго меньше неё (меньше по площади, хотя бы один край внутри больше чем на 0,5 pt). Слой с той же рамкой поверх цели — промах: так выглядит перекрытие. Без `frame` и `descendant` чужой `hit` — промах.

  `hit` — приближение, а не наблюдение: драйвер без hit-test не видит перекрытий без id, представлений, скрытых от доступности (`accessible=false`), и прозрачных слоёв, перехватывающих касания. Поэтому решающие признаки — геометрия (точка под клавиатурой) и наблюдаемый эффект (`tap-hits`, текст поля), а `hit` добавляет случаи явного перекрытия другим элементом.

- `<stateId>.png` (8 бит, RGB/RGBA, без interlace, с проверкой CRC, до 8192 px по стороне и 16 Мпикс) или `<stateId>.rgba` с размером в поле `screenshot` — снимок экрана; читается только для `background`. Нечитаемый PNG — ошибка, без перехода к `.rgba`.
- `log.txt` — журнал прогона в UTF-8, если спецификация задаёт `log`. Журнал без единой непустой строки — ошибка окружения: пустой файл не доказывает, что захват журнала работал. Байт NUL (обычно признак UTF-16) — ошибка окружения. Строки разделяют `\n`, `\r\n` и одиночный `\r` (прогресс bundler перезаписывает строку через `\r`); управляющие последовательности ANSI (цвет, курсор) удаляются до сравнения с шаблонами. Завершающий перевод строки не считается лишней строкой. Строка принадлежит окну состояния, с которым пересекается её байтовый отрезок; окно за пределами файла — ошибка окружения.

Правила отчёта:

- Провал утверждения — `<failure type="assertion">`.
- Сбой драйвера или окружения (нет наблюдений, нет снимка, касание не по центру, снимок не того размера) — `<error type="environment">`. Это не пропуск: `<skipped>` не пишется никогда.
- Каждое объявленное утверждение даёт testcase, даже без наблюдений.
- Пустой прогон — провал `visual.run.empty`; неверная спецификация — провал `visual.spec.valid` с причиной.

Код выхода 1, если хотя бы один testcase провален; 75, если провалов нет, но есть ошибки окружения. Как и любой `test` gate, визуальный gate объявляется с `report: { "type": "junit", "path": ... }` и подключается к задачам интерфейса группой gates.
