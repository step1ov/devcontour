# Договор проверки и обязательный корпус

Договор проверки описывает, **чем** проверяется существенное обязательство контракта: какие свойства, на каких входах, каким независимым способом и с каким минимальным покрытием. Он делает четыре вещи, которых не давали точечные тесты и реестр воспроизведений:

1. генеративный гейт не проходит при пустом или неполном покрытии;
2. подтверждённый эталоном контрпример становится обязательной проверкой без полного изменения контракта;
3. два отказа подряд по одному свойству останавливают слепые повторы и передают задачу ограниченному разбору ведущего;
4. каждое принятие связано с точной версией кода **и** проверок.

Пример ниже обезличен: рюкзак на малых входах и полнота достижимых сумм; эталон — полный перебор.

## Объявление в контракте

Предложение контракта получает поле `checks`. Каждое обязательство ссылается на существующие REQ/критерии приёмки — второго реестра требований нет.

```json
{
  "title": "Knapsack",
  "file": "docs/contracts/knapsack.md",
  "artifacts": [
    { "path": "oracle.mjs", "purpose": "эталон: полный перебор" },
    { "path": "check.mjs", "purpose": "генераторы и свойства" }
  ],
  "checks": {
    "version": 1,
    "gate": "properties",
    "corpus": { "format": "JSON-вход свойства", "extensible": true, "maxCases": 500 },
    "obligations": [
      {
        "property": "knapsack-optimal",
        "requirements": ["REQ-optimal"],
        "promise": "optimality",
        "domain": {
          "inputs": "целые w, v ≥ 0, до 8 предметов",
          "bounds": "вместимость 0..30",
          "invalid": "отрицательные и нецелые отклоняются"
        },
        "answer": { "rules": "точное значение оптимума", "ties": "равные оптимумы равнозначны" },
        "method": {
          "kind": "oracle",
          "description": "полный перебор",
          "applicability": "до 8 предметов",
          "artifacts": ["oracle.mjs", "check.mjs"]
        },
        "coverage": {
          "minCases": 100,
          "corpus": true,
          "families": [
            {
              "id": "boundary",
              "kind": "boundary",
              "description": "нулевые веса и ёмкость",
              "minCases": 30
            },
            {
              "id": "adversarial",
              "kind": "adversarial",
              "description": "много предметов, равенства",
              "minCases": 30
            }
          ]
        },
        "resources": { "subject": "< 1 с на вход", "oracle": "< 1 с на вход" },
        "hard": false
      }
    ]
  }
}
```

Типы обещаний: `functional`, `accuracy`, `optimality`, `completeness`, `performance`, `invariant`, `other` (с объяснением). Структурные пропуски отклоняются **до** вызова модели: нет области, способа проверки или покрытия; вычислительное обещание проверяется сценарием, а не эталоном/сертификатом/инвариантом; способ ссылается на незакреплённый файл; у производительности нет метода измерения; тяжёлое обязательство без эксперимента. Смысл — полноту классификации, независимость эталона от проверяемого кода, пределы применимости — оценивает ревьюер (правило `verifiability`). Необходимость эталона контур по словам «минимальный» или «быстрый» не определяет.

Для тяжёлого точного алгоритма или жёсткого времени (`hard: true`) нужен ограниченный эксперимент: `feasibility_spike` запускает команду эталона или прототипа на закреплённом SHA по размерам (`DEVCONTOUR_SPIKE_SIZE`) с seed и пределом времени и сохраняет времена, исход и пределы вывода. Обязательство ссылается на него `feasibility: { spike, digest }`. **Таймаут — `inconclusive` для выбранного способа и бюджета**: он не доказывает трудность или невозможность и не даёт права ослабить требование. Успех на выборке не доказывает верхней границы на любом входе.

Договор входит в digest контракта; контракт без `checks` сохраняет прежнюю формулу digest. Это не освобождает его от правила `verifiability`: ревью оценивает **каждую** новую редакцию, в том числе изменение контракта, утверждённого до появления договора проверки. Если контракт обещает точность, оптимальность, полноту или производительность, новая редакция без `checks` будет отклонена; уже утверждённая редакция и её задачи продолжают работать без изменений. Есть ли в тексте вычислительные обещания, решает ревьюер, поэтому контур не отказывает механически, а предупреждает до вызова модели: `contract-impact` и старт `contract-change` возвращают `warnings` с кодом `checks-missing` (CLI печатает их в stderr). Контракту без таких обещаний (CRUD, сценарии) `checks` не нужен. `checks` — поле файла предложения: чтобы добавить договор к отклонённой операции, не отменяя её и не снимая удержаний, передайте исправленный файл — `contract-change --id ID --revise --expected-version N --file proposal.json`; структура договора проверяется до вызова модели.

## Эталонные наборы (`verification: "reference"`)

Не каждое вычислительное обещание проверяют генератором. Оптимальность и полнота часто доказываются наборами ответов, посчитанными заранее независимым эталоном — точным решателем с объявленными пределами, полным перебором на малых входах, таблицей DP, — сверенными с другим способом на семействах входов и закреплёнными как артефакты контракта. Gate прогоняет входы набора на реализации и сверяет ответы. Такое обязательство объявляется способом `reference`; его gates — обычные test-gates без генератора.

```json
{
  "property": "test.knapsack-optimal",
  "promise": "optimality",
  "gates": ["golden-small", "golden-large"],
  "verification": "reference",
  "coverage": {
    "minCases": 300,
    "families": [
      { "id": "typical", "kind": "typical", "description": "случайные входы", "minCases": 200 },
      { "id": "boundary", "kind": "boundary", "description": "нулевые веса", "minCases": 40 }
    ]
  },
  "reference": {
    "oracle": {
      "description": "MILP-решатель, оптимум доказан повторным решением",
      "limits": "до 30 с на вход; входы, не решённые за предел, в набор не входят"
    },
    "crossChecks": [
      {
        "family": "до 10 предметов",
        "against": "полный перебор",
        "matches": 800,
        "total": 800,
        "artifacts": ["golden/cross-check.log"]
      }
    ],
    "sets": [
      {
        "gate": "golden-small",
        "artifacts": ["golden/small.json"],
        "minCases": 150,
        "families": [
          { "id": "boundary", "minCases": 40 },
          { "id": "typical", "minCases": 60 }
        ]
      },
      {
        "gate": "golden-large",
        "artifacts": ["golden/large.json"],
        "minCases": 150,
        "families": [{ "id": "typical", "minCases": 150 }]
      }
    ],
    "gaps": "входы больше 60 предметов и входы, которые решатель не решил за предел, наборы не покрывают"
  }
}
```

(поля `requirements`, `domain`, `answer`, `method`, `resources` — как у любого обязательства.)

- `gates` — gates обязательства; без поля — `checks.gate`. Генеративное обязательство (без `verification`) проверяет полное покрытие на каждом своём gate, и каждый из них генеративный.
- `sets[]` — доля каждого gate: файлы набора (среди `artifacts` контракта), минимум входов и минимумы семейств. Сумма долей покрывает `coverage.minCases` и минимум каждого семейства; у каждого gate обязательства есть набор.
- `crossChecks[]` — сверка эталона с другим способом: семейство, способ, совпало из всего. Расхождение (`matches < total`) — отказ: такой эталон ответы не закрепляет. `artifacts` — закреплённый скрипт или журнал, воспроизводящий сверку (среди `artifacts` контракта); сверку без них ревьюер оценивает как непроверенное утверждение автора.
- `gaps` — чего наборы не доказывают: обобщение за пределы входов, классы вне наборов. Ревьюер видит эталонные обязательства отдельным блоком (`references`): обещание, опирающееся только на `gaps` без другого способа (генеративного свойства, инварианта, аналитического основания), — блокирующая находка `verifiability`.

Пропуски отклоняются до вызова модели: gate обязательства без набора, набор чужого gate, файл набора не артефакт контракта, недобор долей, семейство не из покрытия, расхождение сверки, файл сверки не артефакт контракта; корпус у эталонного обязательства не включается (он пополняет генератор).

Доказательство — тот же отчёт свойств, что у генеративного gate. Для задачи, выбравшей свойство, контур передаёт gate путь отчёта (`DEVCONTOUR_PROPERTY_REPORT`) и селектор (`DEVCONTOUR_PROPERTIES`) и без `property` в профиле gate. Gate обязан записать отчёт `{ "version": 1, "properties": [{ "testId": "test.knapsack-optimal", "status": "passed", "cases": 150, "families": { "boundary": 40, "typical": 110 } }] }` и testcase с тем же ID в JUnit. Манифест gate — его доля; недобор входов или семейства, отсутствие отчёта или testcase — отказ при exit 0 и зелёном JUnit. Приёмка требует запись с манифестом от каждого gate обязательства. Файлы наборов закреплены контрактом: попытка их изменить не может.

**ID свойства и testcase.** Property ID, `testId` отчёта и testcase JUnit — один ID, а ID testcase — `classname.name`. JUnit-репортёр node:test всегда пишет `classname="test"`: тест `test('knapsack-optimal', …)` получает ID `test.knapsack-optimal`, поэтому в примере свойство так и названо. Собственный JUnit checker без `classname` даёт ID, равный имени. Если testcase с ID свойства нет, а есть `<classname>.<ID>`, отказ его называет.

**Ответы наборов — не подсказка реализации.** Файлы наборов лежат в рабочем дереве. Исполнитель и ревьюер кода получают их список; ревьюер отклоняет код реализации, который читает наборы, вшивает их ответы или особо обрабатывает их входы. Кандидат, чей изменённый файл содержит путь или имя файла набора, отклоняется до gates (`scope-violation`). Имя, собранное во время исполнения, и копию ответов без имени файла механически не поймать — это остаётся ревью кода (D41).

Обязательство без `verification: "reference"` на gate без `property` отклоняется при любом обещании, и для `invariant`: задача такое свойство выбрать не может.

## Область задачи

Задача включает механизм полем `properties` — свойствами, которые она обязана подтвердить сейчас. Поле входит в утверждаемую постановку: включение для существующей задачи проходит обычное ревью плана, автоматической миграции нет. Ревью плана видит, какие задачи требуют каждое свойство (`propertyScope`), и отклоняет задачу, которой нужен результат непринятого следующего узла (правило `acceptability`). Общий файл проверок допустим: контур передаёт `DEVCONTOUR_PROPERTIES`, и harness запускает только свойства задачи. Свойство обязательства с несколькими gates требует каждого из них в области задачи; сценарий требования, названный ID свойства, может идти через любой из них.

## Манифест и покрытие

Для задачи с `properties` гейт получает закреплённый манифест: свойства, минимальные выборки по свойству и семействам, обязательные случаи корпуса. Отчёт сверяется с ним в контуре. Отказ при exit 0 и зелёном JUnit: пустой отчёт; свойство `passed` с нулём входов; пропущенное или повторяющееся свойство; недобор выборки или семейства; пропущенный случай корпуса; расхождение property ID и testcase; обрезанный список testcases; id, изменённый redaction. Полнота корпуса доказывается свидетельством — hash отсортированных `id:pass|fail` по выполненным случаям, — а не счётчиком; она сверяется и при провалах, а провал любого случая корпуса — отказ, даже если отчёт оставил свойство зелёным. Evidence хранит уровень (`manifest` или `legacy`), digest манифеста и проблемы покрытия. Задача без `properties` проверяется на прежнем уровне, названном явно, но ноль проверенных входов не проходит и там.

## Корпус и быстрый маршрут

Воспроизведение из находки ревью — наблюдение. Обязательный корпус хранится отдельно в БД компонента-владельца и переносится через Git.

Новый случай (`checks_case_submit`, а в agent mode — автоматически для воспроизведений ревью по объявленному свойству):

1. канонизируется (ключи JSON сортируются, порядок массивов и типы сохраняются) и проверяется: свойство объявлено, договор разрешает расширение, механизм включён для задачи, вход не замаскирован и в пределах размера;
2. на дефектном SHA сверяется, что checker — закреплённая редакция; затем тот же checker в режиме одного случая (`DEVCONTOUR_CASE`) дважды считает ответ эталона и реализации;
3. ожидание источника, расходящееся с эталоном, **опровергается**; совпадение реализации с эталоном — тоже опровержение; таймаут, ошибка эталона или невоспроизводимость — `inconclusive`; вне области, не JSON, замаскированный вход или неизвестное свойство — `rejected`;
4. подтверждённый случай попадает в новую неизменяемую версию корпуса (digest канонического файла, Git blob) в той же транзакции, что и решение, вместе с отложенным принятием явно перечисленными задачами;
5. задача принимает версию; посреди активной попытки принятие ждёт её окончания, удерживая выдачу. Принятая задача не меняется. Версия адресуется digest: после объединения клонов номера версий могут совпасть, и неоднозначный номер отклоняется. В operator mode агент только запрашивает принятие — выдача задачи удерживается до ручного подтверждения `devcontour checks-approve --suite S --pending P` (или из панели).

Команда воспроизведения ревьюера не исполняется никогда; данные входа — не shell. Локальные пути в диагностике — причинах решений, принятий и версий, выводе исключения реализации — заменяются меткой `<local-path>` при записи и при экспорте в Git; вход и ожидание не меняются. Очищаются точные локальные корни установки (workspace, репозитории, в том числе одиночный, каталог данных, временный и домашний каталоги — в заданном до realpath, разрешённом и macOS-`/private` написании, Windows-корни и в JSON-экранированном виде), токены без пробелов от `/Users/…`, `/home/…`, `C:\Users\…`, `C:/Users/…` и URL `file://`. Путь распознаётся и после двоеточия и JSON-экранированного перевода строки или табуляции; у `file://` очищается только сам путь, обрамление ссылки остаётся. Прочие URL (с query, любые схемы), маршруты, относительные пути на любом алфавите (с комбинируемыми знаками) и соседний текст не меняются; повторная очистка ничего не меняет.

Диагностический текст не входит в идентичность факта корпуса: случаи, версии, решения и принятия сравниваются при объединении клонов по нормативным полям, и конфликт возникает только при их расхождении. Если факт различается лишь диагностикой (её очистили по корням другой установки или сохранила прежняя версия), остаётся значение из Git: все клоны сходятся к нему и показывают его в локальной проекции, уже опубликованная история не переписывается.

**Ограничения:** путь вне известных корней (например, `/data/x`) по тексту не отличить от маршрута API, поэтому он не очищается — в причины пишут смысл, а не локальные пути. Запись, выгруженная прежней версией с путём в диагностике, остаётся в Git как есть. Ручная правка одного лишь диагностического текста в Git конфликтом не считается. Журнал событий хранит только id и итоги принятия, а не тела случаев. Перепривязка задачи к новой редакции контракта снимает привязку к корпусу прежнего договора: его случаи подтверждаются заново под новым эталоном. Ключ идемпотентен; сбой между записью корпуса и принятием возобновляется без второго подтверждения. Конкурентные добавки объединяются от текущей головы. Быстрый маршрут **только добавляет**: удаление случая, замена ожидания, допуск, покрытие, новый checker или команда — обычный `contract-change` с ревью, а при изменении продуктового смысла — решение пользователя.

Корпус материализуется из закреплённых байтов в каталоге контура вне worktree, только для чтения, на обеих фазах. Двигать принятую ветку, обновлять context или перезапускать сервер ради нового входа не нужно.

## Версия проверок

Действующая версия проверок задачи — digest утверждённой постановки, контрактов, политики и принятого корпуса. Она закрепляется в попытке при выдаче, штампуется на каждое evidence (evidence другой версии отклоняется), требуется finish, восстановлением и переиспользованием кандидата и переносится в receipt. Утверждённый `approvedDigest` при этом не меняется.

## Самопроверка исполнителя

Исполнитель получает команду `node <каталог>/selfcheck.mjs`: тот же закреплённый checker, полный активный корпус, генератор с воспроизводимым seed и селектор своей задачи — на рабочем, незакоммиченном дереве. Ненулевой код называет свойство, точный вход и причину. Результат диагностический: контур всё равно исполняет гейты на commit SHA. Для человека или ведущего то же даёт `devcontour self-check --task ID [--cwd DIR]`.

## Восстановление по свойству

Отказ гейта или ревью связывается только с объявленными property ID (свободная строка ревьюера сохраняется для разбора, но счётчик не выбирает). Два последовательных содержательных отказа одной задачи по одному свойству в одном эпизоде запрещают третью автоматическую выдачу. Отказ провайдера или окружения не увеличивает и не обнуляет счёт; несколько находок одной попытки — один отказ; эпизод завершает проверенное прохождение свойства или утверждённое изменение постановки и контрактов.

В agent mode сервер выполняет один разбор ведущего на эпизод (вызов учитывается в `repairBudget` до запуска модели) и исполняет только разрешённое: подтверждённые случаи под существующим эталоном и один повтор; один повтор с новой гипотезой, переданной исполнителю с источником. Усиление checker и разделение задачи записываются предложением для обычного ревью; уточнение обязательства ждёт пользователя; причина в среде — остановка с диагностикой. Повторный провал после разрешённого повтора останавливает цикл; попытки не сбрасываются. Ручное решение — `recovery_decide` с ожидаемой версией записи. Пауза человека, отмена и operator mode не обходятся; независимые задачи продолжают выполняться. Подробнее — [продолжение этапов](lead-workflow.md).

## Где смотреть

`checks_view` (и `GET /api/tasks/:id/checks`) — версия проверок, свойства и фактическое покрытие, подтверждённые/предложенные/спорные случаи страницами, история отказов по свойствам, эпизод, бюджеты и следующий шаг с тем, кто действует: контур, ведущий или пользователь. Карточка задачи в панели показывает то же. Измерения обратной связи — в [метриках](metrics.md).
