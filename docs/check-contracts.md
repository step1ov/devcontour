# Договор проверки и обязательный корпус

Договор проверки описывает, **чем** проверяется существенное обязательство контракта: какие свойства, на каких входах, каким независимым способом и с каким минимальным покрытием. Он делает четыре вещи, которых не давали точечные тесты и реестр воспроизведений:

1. генеративный гейт не проходит при пустом или неполном покрытии;
2. подтверждённый эталоном контрпример становится обязательной проверкой без полного изменения контракта;
3. два отказа подряд по одному свойству останавливают слепые повторы и передают задачу ограниченному разбору ведущего;
4. каждое принятие связано с точной версией кода **и** проверок.

Пример ниже обезличен: рюкзак на малых входах и полнота достижимых сумм; эталон — полный перебор.

## Объявление в контракте

Предложение контракта получает поле `checks`. Каждое обязательство ссылается на существующие REQ/критерии приёмки — второго реестра требований нет.

```json
{
  "title": "Knapsack",
  "file": "docs/contracts/knapsack.md",
  "artifacts": [
    { "path": "oracle.mjs", "purpose": "эталон: полный перебор" },
    { "path": "check.mjs", "purpose": "генераторы и свойства" }
  ],
  "checks": {
    "version": 1,
    "gate": "properties",
    "corpus": { "format": "JSON-вход свойства", "extensible": true, "maxCases": 500 },
    "obligations": [
      {
        "property": "knapsack-optimal",
        "requirements": ["REQ-optimal"],
        "promise": "optimality",
        "domain": {
          "inputs": "целые w, v ≥ 0, до 8 предметов",
          "bounds": "вместимость 0..30",
          "invalid": "отрицательные и нецелые отклоняются"
        },
        "answer": { "rules": "точное значение оптимума", "ties": "равные оптимумы равнозначны" },
        "method": {
          "kind": "oracle",
          "description": "полный перебор",
          "applicability": "до 8 предметов",
          "artifacts": ["oracle.mjs", "check.mjs"]
        },
        "coverage": {
          "minCases": 100,
          "corpus": true,
          "families": [
            {
              "id": "boundary",
              "kind": "boundary",
              "description": "нулевые веса и ёмкость",
              "minCases": 30
            },
            {
              "id": "adversarial",
              "kind": "adversarial",
              "description": "много предметов, равенства",
              "minCases": 30
            }
          ]
        },
        "resources": { "subject": "< 1 с на вход", "oracle": "< 1 с на вход" },
        "hard": false
      }
    ]
  }
}
```

Типы обещаний: `functional`, `accuracy`, `optimality`, `completeness`, `performance`, `invariant`, `other` (с объяснением). Структурные пропуски отклоняются **до** вызова модели: нет области, способа проверки или покрытия; вычислительное обещание проверяется сценарием, а не эталоном/сертификатом/инвариантом; способ ссылается на незакреплённый файл; у производительности нет метода измерения; тяжёлое обязательство без эксперимента. Смысл — полноту классификации, независимость эталона от проверяемого кода, пределы применимости — оценивает ревьюер (правило `verifiability`). Необходимость эталона контур по словам «минимальный» или «быстрый» не определяет.

Для тяжёлого точного алгоритма или жёсткого времени (`hard: true`) нужен ограниченный эксперимент: `feasibility_spike` запускает команду эталона или прототипа на закреплённом SHA по размерам (`DEVCONTOUR_SPIKE_SIZE`) с seed и пределом времени и сохраняет времена, исход и пределы вывода. Обязательство ссылается на него `feasibility: { spike, digest }`. **Таймаут — `inconclusive` для выбранного способа и бюджета**: он не доказывает трудность или невозможность и не даёт права ослабить требование. Успех на выборке не доказывает верхней границы на любом входе.

Договор входит в digest контракта; контракт без `checks` сохраняет прежнюю формулу.

## Область задачи

Задача включает механизм полем `properties` — свойствами, которые она обязана подтвердить сейчас. Поле входит в утверждаемую постановку: включение для существующей задачи проходит обычное ревью плана, автоматической миграции нет. Ревью плана видит, какие задачи требуют каждое свойство (`propertyScope`), и отклоняет задачу, которой нужен результат непринятого следующего узла (правило `acceptability`). Общий файл проверок допустим: контур передаёт `DEVCONTOUR_PROPERTIES`, и harness запускает только свойства задачи.

## Манифест и покрытие

Для задачи с `properties` гейт получает закреплённый манифест: свойства, минимальные выборки по свойству и семействам, обязательные случаи корпуса. Отчёт сверяется с ним в контуре. Отказ при exit 0 и зелёном JUnit: пустой отчёт; свойство `passed` с нулём входов; пропущенное или повторяющееся свойство; недобор выборки или семейства; пропущенный случай корпуса; расхождение property ID и testcase; обрезанный список testcases; id, изменённый redaction. Полнота корпуса доказывается свидетельством — hash отсортированных `id:pass|fail` по выполненным случаям, — а не счётчиком. Evidence хранит уровень (`manifest` или `legacy`), digest манифеста и проблемы покрытия. Задача без `properties` проверяется на прежнем уровне, названном явно, но ноль проверенных входов не проходит и там.

## Корпус и быстрый маршрут

Воспроизведение из находки ревью — наблюдение. Обязательный корпус хранится отдельно в БД компонента-владельца и переносится через Git.

Новый случай (`checks_case_submit`, а в agent mode — автоматически для воспроизведений ревью по объявленному свойству):

1. канонизируется (ключи JSON сортируются, порядок массивов и типы сохраняются) и проверяется: свойство объявлено, договор разрешает расширение, механизм включён для задачи, вход не замаскирован и в пределах размера;
2. на дефектном SHA сверяется, что checker — закреплённая редакция; затем тот же checker в режиме одного случая (`DEVCONTOUR_CASE`) дважды считает ответ эталона и реализации;
3. ожидание источника, расходящееся с эталоном, **опровергается**; совпадение реализации с эталоном — тоже опровержение; таймаут, ошибка эталона или невоспроизводимость — `inconclusive`; вне области, не JSON, замаскированный вход или неизвестное свойство — `rejected`;
4. подтверждённый случай попадает в новую неизменяемую версию корпуса (digest канонического файла, Git blob) в той же транзакции, что и решение, вместе с отложенным принятием явно перечисленными задачами;
5. задача принимает версию; посреди активной попытки принятие ждёт её окончания, удерживая выдачу. Принятая задача не меняется.

Команда воспроизведения ревьюера не исполняется никогда; данные входа — не shell. Ключ идемпотентен; сбой между записью корпуса и принятием возобновляется без второго подтверждения. Конкурентные добавки объединяются от текущей головы. Быстрый маршрут **только добавляет**: удаление случая, замена ожидания, допуск, покрытие, новый checker или команда — обычный `contract-change` с ревью, а при изменении продуктового смысла — решение пользователя.

Корпус материализуется из закреплённых байтов в каталоге контура вне worktree, только для чтения, на обеих фазах. Двигать принятую ветку, обновлять context или перезапускать сервер ради нового входа не нужно.

## Версия проверок

Действующая версия проверок задачи — digest утверждённой постановки, контрактов, политики и принятого корпуса. Она закрепляется в попытке при выдаче, штампуется на каждое evidence (evidence другой версии отклоняется), требуется finish, восстановлением и переиспользованием кандидата и переносится в receipt. Утверждённый `approvedDigest` при этом не меняется.

## Самопроверка исполнителя

Исполнитель получает команду `node <каталог>/selfcheck.mjs`: тот же закреплённый checker, полный активный корпус, генератор с воспроизводимым seed и селектор своей задачи — на рабочем, незакоммиченном дереве. Ненулевой код называет свойство, точный вход и причину. Результат диагностический: контур всё равно исполняет гейты на commit SHA. Для человека или ведущего то же даёт `devcontour self-check --task ID [--cwd DIR]`.

## Восстановление по свойству

Отказ гейта или ревью связывается только с объявленными property ID (свободная строка ревьюера сохраняется для разбора, но счётчик не выбирает). Два последовательных содержательных отказа одной задачи по одному свойству в одном эпизоде запрещают третью автоматическую выдачу. Отказ провайдера или окружения не увеличивает и не обнуляет счёт; несколько находок одной попытки — один отказ; эпизод завершает проверенное прохождение свойства или утверждённое изменение постановки и контрактов.

В agent mode сервер выполняет один разбор ведущего на эпизод (вызов учитывается в `repairBudget` до запуска модели) и исполняет только разрешённое: подтверждённые случаи под существующим эталоном и один повтор; один повтор с новой гипотезой, переданной исполнителю с источником. Усиление checker и разделение задачи записываются предложением для обычного ревью; уточнение обязательства ждёт пользователя; причина в среде — остановка с диагностикой. Повторный провал после разрешённого повтора останавливает цикл; попытки не сбрасываются. Ручное решение — `recovery_decide` с ожидаемой версией записи. Пауза человека, отмена и operator mode не обходятся; независимые задачи продолжают выполняться. Подробнее — [продолжение этапов](lead-workflow.md).

## Где смотреть

`checks_view` (и `GET /api/tasks/:id/checks`) — версия проверок, свойства и фактическое покрытие, подтверждённые/предложенные/спорные случаи страницами, история отказов по свойствам, эпизод, бюджеты и следующий шаг с тем, кто действует: контур, ведущий или пользователь. Карточка задачи в панели показывает то же. Измерения обратной связи — в [метриках](metrics.md).
