# Продукт, каналы и карта фич

В embedded общий intent находится в корневом `INTENT.md`, локальные истории единственного репозитория — в `docs/implementation-intent.md`. Используйте `source`, возвращённый render/snapshot, вместо предположения об имени файла. В separate оба владельца сохраняют собственный `INTENT.md`. [Режимы размещения](workspace-modes.md).

Карта отвечает на два вопроса: из чего состоит продукт и что пользователь сможет сделать в выбранном релизе. Ведущий агент готовит её из ТЗ и существующего кода, затем поддерживает при изменении требований. Оператору достаточно передать ТЗ и workspace; отдельный ручной реестр вести не требуется.

## Какие границы мы различаем

| Понятие               | Что означает                                  | Пример                                                 |
| --------------------- | --------------------------------------------- | ------------------------------------------------------ |
| Продукт               | Общая цель и пользователи                     | Система корпоративного общения                         |
| Приложение            | Точка взаимодействия пользователя с продуктом | Админка, мобильный клиент, CLI, публичное API          |
| Технический компонент | Часть реализации                              | Интерфейс, сервис, библиотека, фоновый обработчик      |
| Репозиторий           | Граница Git, локальной памяти и интеграции    | Монорепозиторий каналов или отдельная библиотека    |
| Фича                  | Наблюдаемая возможность и ожидаемый результат | Модератор блокирует нарушителя                         |
| Локальная история     | Вклад компонента в возможность                | API применяет ограничение, клиент показывает состояние |

Фронтенд и бэкенд не обязаны быть отдельными каналами. Один канал может включать оба, один сервис может обслуживать несколько каналов, один Git — содержать несколько технических компонентов. Библиотека сохраняет своих исполнителей, задачи и память рядом с кодом.

Приложение связывается с `componentIds`. Технический компонент содержит `repositoryId`, относительный `path` (`.` для корня) и `dependsOn`. Поле `kind` — свободное короткое обозначение назначения: схема не ограничивает технологии. Циклы и неизвестные ссылки отклоняются. Репозиторий должен быть зарегистрирован в workspace.

Путь — описание размещения кода, а не отдельная единица исполнения. Карта не создаёт каталог, не запускает команд и не меняет `writePaths`. Агент отдельно настраивает область записи, cwd тестов и зависимости задач. Интеграция сериализуется на уровне Git-репозитория; несколько каналов внутри него не получают независимые конкурентные merge. Граф `repository.dependsOn` для сборки и affected-проверок по-прежнему настраивается отдельно. Автоматического анализа внутренних пакетов монорепозитория нет.

## Где находится карта

Общий committed `INTENT.md` в Git workspace расширяет существующую карту релизов:

- `product.channels` — ID, название, назначение, пользователи и технические компоненты каналов;
- `product.components` — размещение кода и технические зависимости;
- `product.features` — устойчивые ID, названия и ожидаемые результаты фич;
- `releases[].features` — участие фич в конкретном релизе, ссылки на локальные истории и сквозные проверки;
- `releases[].components` — закреплённые карты релизов репозиториев, как в обычном workspace INTENT.

Локальный `INTENT.md` репозитория продолжает содержать подробные истории и критерии. Общая карта ссылается на `{repositoryId, storyId}` и не копирует тексты библиотечных требований или задач. У монорепозитория остаётся одна локальная карта и одна память задач; разные каналы могут ссылаться на разные истории этой карты.

Общая цель, влияющая на реализацию, должна быть отражена ведущим агентом в локальных историях или общих контрактах. Карта workspace сама не подменяет закреплённый prompt исполнителя. Поэтому изменение смысла фичи требует проверки локальных критериев и достаточности тестов.

В Git передаётся сам INTENT и переносимая память. В SQLite нет отдельной изменяемой таблицы статусов фич: отчёт вычисляет их из требований, задач и проверок. Это предотвращает расхождение «готово в карте» и реального результата.

## Явный объём релиза

Для каждой фичи в каждом объявленном релизе нужно указать все каналы, выбрав один вариант:

| Scope            | Значение                                               | Обязательные данные         |
| ---------------- | ------------------------------------------------------ | --------------------------- |
| `included`       | Возможность входит в этот релиз канала             | Ссылки на локальные истории |
| `deferred`       | Возможность нужна, но отложена за пределы этого релиза | Причина                     |
| `not-applicable` | Возможность для этого канала не нужна              | Причина                     |

Пропущенная строка или колонка не считается исключением. Например, отсутствие мобильного сценария блокировки должно быть осознанным решением, а не незаметной ошибкой декомпозиции. В будущем релизе та же фича сохраняет ID и может получить другой scope. Отложенные возможности не считаются выполненными и не блокируют текущий релиз.

Для включённого сценария истории должны принадлежать указанному релизу репозитория и компонентам канала, включая их транзитивные зависимости. Все локальные истории объявленного релиза должны быть связаны хотя бы с одной фичей. Одна история может обеспечивать несколько каналов; одна фича — несколько историй в разных репозиториях. Неизменённая библиотека может оставаться в технических зависимостях и проверяемом manifest без выдуманной задачи разработки.

Если у фичи есть включённые каналы, у неё обязательны `checks`: ID настроенного `workspaceGates` типа `test` с JUnit и понятный сквозной `scenario`. Полностью отложенная/неприменимая фича имеет пустой список checks. Один настоящий gate может проверять несколько фич, если его тесты действительно покрывают их сценарии. Строка `scenario` описывает ожидание; система не умеет доказать семантическую достаточность теста по его названию. Это обязанность ведущего агента и независимого ревью.

## Подготовка агентом

1. Изучить ТЗ, пользователей и существующие каналы. Составить карту без принудительного разделения репозиториев или выбора стека по названию канала.
2. Выбрать первый полезный сценарий и границы релиза. Значимую неоднозначность цели уточнить у оператора; обратимые решения и предположения зафиксировать самостоятельно.
3. Подготовить локальные REQ, истории и критерии, провести review и закрепить их в Git. Общие контракты согласовать до параллельной реализации.
4. Настроить настоящие совместные тесты. Подготовить общую карту по [примеру определения](../packs/example-product-intent.json), заменив ID репозиториев, историй, релизов и gates на реальные.
5. Выполнить `intent-render`, проверить полученный Markdown и закоммитить его как `INTENT.md` workspace. Генератор возвращает текст, сам не записывает и не утверждает файлы.
6. Связать локальные задачи со snapshots историй и подробных требований. Вести выполнение через существующий DAG и workflow. Разработка остаётся параллельной после согласования контрактов.

```sh
devcontour intent-render --file /absolute/product-definition.json --workspace /absolute/workspace > /absolute/workspace/INTENT.next.md
```

Авторское JSON-определение — вход генератора. Источником истины после проверки и коммита служит INTENT, а не два независимо редактируемых документа. Для одного канала достаточно одного channel и одного компонента с `path: "."`; остальные связи добавляются по необходимости.

## Наблюдение за прогрессом

```sh
devcontour product-view --release mvp --workspace /absolute/workspace
devcontour intent-report --release mvp --require-complete --workspace /absolute/workspace
```

MCP и общий agent API предоставляют `product_view` с необязательным `releaseId` и существующий `intent_report`. `product_view` без релиза выбирает первый объявленный. HTTP `GET /api/product?release=mvp` возвращает то же представление. Все эти операции read-only, без вызовов моделей. Они не принимают задачи или релиз.

На вкладке **Продукт** есть два представления: «Возможности для пользователя» и «Приложения и компоненты». Можно выбрать релиз и перейти от ссылки на локальную историю к графу соответствующего репозитория. Карта обновляется, пока вкладка открыта. Если карта ещё не подготовлена, UI объясняет следующий шаг. Повреждённый INTENT показывает ошибку, не пустую зелёную доску.

Вычисляемые состояния фичи:

- `unplanned` — хотя бы для одной включённой истории нет задач;
- `in-progress` — задачи есть, но покрытие ещё не подтверждено или устарело;
- `awaiting-verification` — локальные требования покрыты, нужна актуальная совместная проверка релиза;
- `verified` — совместная версия прошла проверки, приёмки релиза ещё нет;
- `accepted` — есть актуальная приёмка связанного продуктового ChangeSet;
- `deferred` / `not-applicable` — в выбранном релизе нет включённых каналов.

Это дискретные состояния, а не процент готовности по количеству задач. Десять завершённых технических задач не компенсируют один неработающий пользовательский сценарий.

## Обязательная приёмка продуктового релиза

После локальных досок создайте ChangeSet с `releaseId`, соответствующим общему INTENT:

```json
{
  "title": "Первый релиз модерации",
  "description": "Блокировка участника работает в админке, API и мобильном клиенте.",
  "boardIds": ["B-product", "B-library"],
  "releaseId": "mvp"
}
```

Используйте реальные ID досок. В agent API поле находится внутри `changeset_create.changeSet`. В UI оно доступно в форме нового ChangeSet. Агент регистрирует обычный workflow этого ChangeSet; дополнительный ручной этап не вводится.

Для `releaseId` система обязательно проверяет:

1. Продуктовая карта существует, ссылки корректны, покрытие всех объявленных историй и REQ актуально.
2. Текущие ревизии выбранных досок приняты. ChangeSet включает все задачи локальных историй релиза, включая актуальные замены после корректировок.
3. В Verification закреплены `releaseId`, digest общего INTENT, ID сквозных gates, принятые SHA, отпечатки файлов требований и состояния локальных задач/доказательств.
4. Проверяемые SHA содержат актуальные карты/REQ и результаты задач. Одного свежего документа в основном checkout недостаточно.
5. Выполнены **все** workspace gates, даже если обычный режим настроен как affected. На границе продуктового релиза полная проверка защищает от неверно описанных зависимостей и пропущенного общего сценария.
6. До фиксации приёмки не изменились карта, состав задач, политика или принятые SHA компонентов. Сохраняются обычные требования completionMode, включая Delivery для remote. Полный аудит проводится до начала lease Verification; при закреплении manifest, завершении тестов и приёмке сравниваются его исходные данные. Запись каждого gate и heartbeat не запускают повторный аудит всех историй.

В `approvalMode: agent` приёмку выполняет workflow автоматически. `operator` добавляет подтверждение человеком после тех же проверок. Прямой вызов ядра без runner, умеющего проверить INTENT/Git, не может принять связанный продуктовый релиз.

```sh
devcontour changeset-create --file /absolute/release-change.json --workspace /absolute/workspace
devcontour workspace-verify --changeset CHG-ID --workspace /absolute/workspace
devcontour changeset-accept --changeset CHG-ID --workspace /absolute/workspace
devcontour product-view --release mvp --require-accepted --workspace /absolute/workspace
```

Этот ручной маршрут применяют, когда ChangeSet не выполняет сохраняемый workflow. Последняя команда завершается с exit 1, если актуальной приёмки нет. `intent-report --require-accepted` поддерживает ту же проверку для общей карты. `--require-complete` подтверждает только покрытие требований: это более ранний этап.

Обычный ChangeSet без `releaseId` остаётся полезен для технического этапа. Его приёмка никогда не выдаётся за приёмку продуктового релиза. Карты INTENT без секции product продолжают работать как аудит локальных историй/релизов, но не получают продуктовое `releaseAccepted: true`.

## Корректировки и командная работа

При изменении фичи агент сохраняет её ID, фиксирует причину, пересматривает затронутые каналы, локальные критерии, контракты и тесты. После изменения локальных карт регенерирует общую. Для принятых задач использует обычную корректировку; для принятого ChangeSet — новый ChangeSet с `supersedes` и тем же releaseId либо новым релизом по смыслу изменения.

Digest общей карты консервативно связывает всю карту, включая другие релизы. Даже изменение отложенной фичи требует новой общей проверки, прежде чем текущая версия снова будет показана как принятая. Отпечатки источников учитывают файлы целиком, а отпечаток локального состояния — задачи и их доказательства в участвующих репозиториях. Поэтому изменение будущего требования в том же файле или плана того же репозитория тоже требует повторной проверки. Автоматического точечного анализа влияния продуктового текста пока нет. Изменение принятой ветки любого проверяемого репозитория также делает прежнюю совместную проверку неактуальной. Историческая приёмка при этом не удаляется.

Git sync переносит `ChangeSet.releaseId`, карту и локальные истории через их владельцев. Verification, manifest и приёмка релиза не становятся чужим локальным PASS: на другом компьютере нужно выполнить совместную проверку. Изменить привязку уже принятого ChangeSet через sync нельзя.

Чтение разных Git-репозиториев остаётся последовательным. Отчёт использует согласованный набор чтений в рамках одного вызова, но не является распределённой Git-транзакцией. Перед приёмкой исключите внешних писателей; worker claims блокируются действующей Verification. Тесты доказывают заявленное поведение конкретной версии, а фактическую пользу для пользователей подтверждают наблюдения и обратная связь после применения продукта.
