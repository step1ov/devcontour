# Проверка интеграционных расширений

Дата: 2026-09-17. Изменяется сам DevContour; корпоративные проекты и их доступы не подключались.

## Результат

- `npm run check`: lint токенов, TypeScript/Vite build и все **68 unit/integration тестов прошли**, без пропусков. Полный check завершился с ошибкой на этапе браузерных E2E.
- Playwright: **1 HTTP E2E прошёл; 3 браузерных E2E не смогли запустить Chromium**. Причина среды macOS: `MachPortRendezvousServer: Permission denied (1100)`. Эти три сценария не считаются проверенными; их нужно повторить в среде с доступным запуском браузера.
- После последних изменений обработки HTTP-ошибок, копирования документации и подписей UI: повторная сборка прошла; **10 тестов HTTP/setup/scope прошли**. Это подмножество общего набора, а не ещё 10 уникальных сценариев.
- Chrome DevTools MCP: проверена новая вкладка изменений на настоящем локальном сервере с Git/SQLite fixture. Подготовка handoff создаёт инструкцию, read-only command adapter переводит результат в ожидание публикации; кнопки финальной приёмки нет. Отображаются локальное хранение и отдельная локальная приёмка доски. Неизвестный ChangeSet при handoff возвращает HTTP 409 с объяснением. Обычная работа UI — без console errors. На desktop и viewport 390×844 горизонтального переполнения нет; узкий экран просмотрен визуально. Это smoke новой функциональности, не замена полным Playwright-сценариям и accessibility-аудиту.
- Runtime CLI-флаги сверены с установленными CLI и официальной документацией; live-вызовы моделей не выполнялись.

Vite сообщает advisory о JS chunk больше 500 kB; сборку это не блокирует. Node 24 сообщает экспериментальный статус `node:sqlite`.

## Что проверено новыми сценариями

1. Явное окружение, отсутствие посторонних env, блокировка отсутствующих секретов, маскирование логов, запрет подмены DEVCONTOUR_*.
2. Явные MCP-профили, разрешённые инструменты и ограниченный набор встроенных инструментов ревьюера.
3. Teardown после ошибки setup и отмены; ошибка cleanup сохраняет исключительное владение ресурсом.
4. Реальные задачи двух Git-репозиториев, зависимость продукт → библиотека, совместная проверка и приёмка. Спецификации, локальные контракты и исторические snapshots отсутствуют в общей SQLite; локальный журнал не содержит задач другого компонента. Изменение владельца задачи локальной доски отклоняется.
5. Ошибка записи одного attached-файла откатывает изменения всех участвующих баз.
6. Подмена артефакта закреплённой зависимости обнаруживается до приёмки.
7. Doctor обнаруживает отсутствующие команды; donor import сохраняет SHA и не заменяет изменённый импортированный документ.
8. В одном workspace используются GitLab и GitHub HTTP fixtures и настоящие bare Git remotes. До ручного push ветка отсутствует. Все запросы адаптеров — GET. Неверный source SHA, CI на другом SHA и failure блокируют приёмку. Merge с новым SHA, но тем же деревом принимается только с CI на итоговом SHA. Push в тесте явно выполняет имитатор человека.
9. Миграция прежней центральной SQLite сохраняет события/IDs и удаляет тела локальных задач из её физических страниц.
10. SIGKILL незавершённого SQLite writer не повреждает граф после восстановления. Неправильное открытие component/coordinator DB отклоняется до смены journal mode.
11. Doctor учитывает tool profile локальной роли и выполняет preflight с lifecycle в отдельном worktree, не изменяя основной checkout.
12. Восстановление cleanup использует окружение своего компонента и отклоняет живого владельца либо посторонний рабочий каталог.

## Практические границы

- Один controller и один хост, до 10 attached компонентов. Это раздельное хранение под общей оркестрацией, а не федерация независимых scheduler.
- Нативные GitLab/GitHub адаптеры ожидают PR/MR и успешный CI каждого компонента manifest. Повторная приёмка неизменённых зависимостей и установки с более чем 100 checks/jobs требуют проектного read-only адаптера; см. [интеграционный процесс](project-integration.md).
- Реальные корпоративный MCP, private Registry, PostgreSQL, удалённые GitLab/GitHub API и Codex/Claude-сессии не проверялись. Lifecycle проверен процессами fixture, а не PostgreSQL-контейнером. Для конкретного продукта агент должен настроить scripts и провести пилот по его ТЗ.
- Тесты доказывают инварианты DevContour на fixtures, а не полноту тестов будущего продукта. Проектные gates и критерии приёмки остаются обязательными.
