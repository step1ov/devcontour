# Продукт → архитектура → разработка

DevContour ведёт один проект, но различает три процесса. Сначала определяем нужное пользователю поведение. После его утверждения выбираем устройство системы и стек. После второго утверждения начинаем техническую реализацию. Это позволяет согласовывать конкретные решения и видеть, почему работа ещё не перешла к коду.

## Панель появляется первой

После выбора [режима размещения и пути workspace](workspace-modes.md) ведущий агент запускает долгоживущий процесс:

```sh
devcontour start --workspace-mode embedded --workspace /absolute/product --port 0
```

Пример использует embedded; для отдельной папки выберите separate и её путь. В исходном checkout используйте `npm run devcontour -- start ...`. Порт `0` выбирает свободный порт; агент передаёт пользователю напечатанный URL и сохраняет его в progress-документе. Для пустого workspace пока нужны только папка и локальное состояние. Git продукта, профиль, контракты и команды тестов не требуются. Фиктивная конфигурация разработки не создаётся.

Панель сразу показывает список продуктовых изменений и этапы. Ведущий агент читает ТЗ, общается с пользователем и сохраняет промежуточные версии через CLI/MCP. Появление файла с ТЗ само по себе модель не запускает. Сервер хранит и показывает работу; содержательную проработку выполняет активная сессия ведущего агента.

После обоих согласований агент создаёт или подключает репозитории и выполняет setup. Сервер проверяет появление конфигурации и подключает scheduler на том же адресе. Ошибка конфигурации показывается в панели; продуктовая часть остаётся доступной. Создавать второй сервер или параллельный scheduler не нужно. Последующие изменения уже подключённой исполняемой конфигурации требуют штатной остановки и перезапуска.

## 1. Проработать и утвердить продукт

Основная единица — **изменение продукта**, например «Модератор блокирует участника». Оно может затрагивать несколько каналов и репозиториев. Фича остаётся устойчивой частью карты продукта; несколько изменений могут последовательно развивать одну фичу.

В постановке фиксируем проблему, ожидаемый результат, каналы, релизы и фичи. Продукт читается по частям:

| Сущность    | Что описывает                                                           | Обязательна |
| ----------- | ----------------------------------------------------------------------- | ----------- |
| **Канал**   | Где продукт встречается с человеком: мобильное приложение, админка, веб | да          |
| **Релиз**   | Граница объёма: что должно существовать первым, с версией по SemVer     | да          |
| **Персона** | Имя, роль, цели и боли того, для кого мы решаем задачу                  | нет         |
| **Фича**    | Единица чтения и приёмки: результат, каналы, сценарии и критерии        | да          |

Каждая фича называет каналы, которые её реализуют. Каждый сценарий может назвать персону, которая его проживает; её цели и боли — основание, на котором агент разрешает неоднозначность так же, как решил бы этот человек. Каждый критерий приёмки назван релизом, поэтому одна фича может начаться в раннем релизе и завершиться в позднем, не разрезаясь надвое.

Агрегаты выводятся, а не объявляются дважды: аудитория фичи — из её сценариев, диапазон релизов — из её критериев, готовность релиза — из задач, привязанных к фичам с его критериями. Версии релизов обязаны возрастать по SemVer; релиз без критериев, канал без фич и висячая ссылка на персону, релиз или канал отклоняются.

Исключения и материалы фиксируются отдельно. Открытые вопросы видны отдельно и ведутся как долговечные записи: агент их задаёт, пользователь отвечает в панели, агент превращает ответ в решение с обоснованием. Пока у этапа есть неотвеченный вопрос, версию нельзя отправить на утверждение. Ссылки на макеты и референсы сопровождаются пояснениями; внутренние требования конкретной библиотеки остаются у библиотеки.

Агент сохраняет черновики по мере обсуждения. Когда обязательные поля заполнены и открытые вопросы решены, отправляет текущую версию пользователю. **Пользователь нажимает «Утвердить версию» либо возвращает её на доработку с комментарием.** Отправка на согласование сама ничего не утверждает.

До этого решения нельзя сохранять архитектурную постановку или создавать задачи исполнения. Читать существующий код и выяснять ограничения можно: это помогает подготовить реалистичные требования. Выбирать и внедрять новый стек заранее не следует.

## 2. Проработать и утвердить архитектуру и стек

Архитектор получает закреплённую продуктовую версию. Он описывает границы ответственности, интерфейсы, хранение данных, выбранные технологии, причины выбора, альтернативы, риски и стратегию тестирования. Для существующего проекта явно показывает, что используется повторно и что потребуется изменить.

В панели обязательны две диаграммы:

- **C1 — контекст системы:** целевая система, люди и внешние системы, связи между ними. Здесь важны назначение и границы. [Определение C1](https://c4model.com/diagrams/system-context).
- **C2 — контейнеры:** приложения, сервисы и хранилища внутри границы системы, их ответственность, технологии и взаимодействия. Container здесь не обязательно Docker. [Определение C2](https://c4model.com/diagrams/container).

Диаграммы хранятся как узлы и связи, а не исполняемый HTML или произвольный JavaScript. UI строит интерактивное представление и даёт текстовый список элементов и связей. Проверяются уникальность ID, существование концов связей, целевая система, технологии контейнеров и соответствие внешних участников C1/C2. Семантическую достаточность архитектуры оценивают архитектор, независимое ревью и пользователь: структурная валидация не доказывает, что архитектура хороша.

После проработки агент отправляет архитектуру на согласование. Пользователь рассматривает **вместе архитектуру, стек, обоснование и обе диаграммы**. Только его утверждение текущей версии разрешает подготовку проекта и разработку.

## 3. Реализовать и принять результат

Агент настраивает согласованный стек, реальные проверки и локальность памяти, готовит контракты и DAG. После независимого технического ревью запускаются исполнители. У каждой задачи сохраняется ссылка на ID продуктового изменения и отпечатки обеих утверждённых постановок. Эти ссылки входят в digest задачи и Git-память её репозитория.

Дальше действует существующий harness: worktree → candidate tests/review → интеграция → повторные tests/review → приёмка. Карта INTENT, покрытие требований и продуктовый ChangeSet продолжают проверять полноту и совместимость результата. Утверждённый замысел не означает готовый код, а число закрытых задач не заменяет приёмку релиза.

`approvalMode: agent` относится к **техническим** контрактам, планам и приёмке. Два продуктовых решения пользователя обязательны независимо от этого режима. `operator` может добавить ручные технические согласования. Push, merge и публикацию по-прежнему выполняет человек.

## Что видно в панели

Карточка изменения показывает текущие продуктовую и архитектурную версии, их статусы, замечания, историю, следующий разрешённый этап и связанные технические доски. Панель различает:

- агент прорабатывает черновик;
- версия ожидает решения пользователя;
- пользователь запросил доработку;
- версия утверждена;
- архитектура устарела относительно новой постановки;
- разработка разрешена, но конфигурация ещё готовится;
- техническое исполнение подключено.

Счётчики задач — производные от существующего tracker. Дополнительного вручную выставляемого флага «продукт готов» нет. Интерфейс разработки остаётся доступен после подключения runtime, а продуктовая карточка позволяет вернуться к причинам принятых решений.

## Версии и корректировки

Каждое сохранение создаёт новую версию с причиной и ожидаемым digest предыдущей. Устаревшая запись или кнопка утверждения возвращает конфликт. Решение привязано к показанной версии: после изменения содержимого оно не переносится автоматически.

Изменение продукта требует нового согласования продукта и новой архитектурной версии. Изменение архитектуры требует повторного архитектурного согласования. Прежние решения сохраняются. Во время активных попыток соответствующего изменения или совместной проверки переписывать входы нельзя: сначала нужно дождаться остановки исполнения.

Утверждённые задачи не перепривязываются автоматически. Черновик можно обновить обычным task-edit. Для принятого результата создаётся корректировка и новые задачи; для ещё не принятого плана ведущий агент явно разбирает незавершённые задачи и готовит новый план. Проверки очереди и приёмки не позволяют принять задачу со старой привязкой как текущий результат.

## Память и команда

В embedded вся память находится в единой SQLite внутри репозитория; в separate продуктовые версии, решения и общие схемы хранятся в общей SQLite workspace. Подробные задачи сохраняют локального владельца: в embedded это тот же репозиторий, в separate — собственные хранилища компонентов. При Git sync продуктовый процесс попадает в `.devcontour/preparations/workspace-preparation.json`, а связи задач — в обычные локальные task records.

Подготовку можно синхронизировать **до настройки стека**. Агент инициализирует Git в общей папке, добавляет `.devcontour-local/` в `.gitignore`, создаёт исходный commit, штатно останавливает сервер и выполняет:

```sh
devcontour sync --member developer-id --workspace /absolute/workspace
```

Затем коммитит переносимую память в workspace. На другой машине та же команда импортирует её из clone. После появления технической конфигурации работает полный sync всех владельцев. Согласования из доверенного Git остаются историей решений команды; локальные запуски, leases и результаты проверок этим не создаются.

В первой реализации общий процесс — одна Git-запись. Одновременное изменение списка версий разными разработчиками вызывает явный конфликт, без автоматического объединения решений. Базы не передаются через Git; при невалидном импорте SQLite и baseline сохраняют прежнее состояние. Переключение ветки ранней подготовки требует отдельного workspace.

## Интерфейс ведущего агента

Все операции используют общий envelope `{ "operation": "...", "input": {} }` через `agent --file`, HTTP и MCP:

| Операция                   | Назначение                                               |
| -------------------------- | -------------------------------------------------------- |
| `preparation_status`       | Текущие версии, замечания, блокеры и связанные доски     |
| `preparation_create`       | Новое изменение продукта                                 |
| `preparation_activate`     | Выбрать изменение для новых задач                        |
| `preparation_product`      | Новая продуктовая версия с `expectedDigest` и причиной   |
| `preparation_architecture` | Новая архитектурная версия после утверждения продукта    |
| `preparation_submit`       | Проверить полноту и передать текущую версию пользователю |
| `preparation_progress`     | Короткая заметка о текущей работе агента для панели      |
| `preparation_question`     | Открытые вопросы пользователю; ответ даёт только он      |
| `preparation_resolve`      | Принятое решение с обоснованием и ссылкой на вопрос      |

Схемы: `devcontour capabilities`. MCP, открытый до setup, подхватывает техническую конфигурацию при последующих вызовах. Он не запускает scheduler. HTTP `/api/preparation` работает с самого начала; `/api/state` появляется после подключения технического исполнения.

В агентском каталоге **нет операции утверждения этих этапов**. Решение поступает из отдельной формы панели. Ведущий агент не должен вызывать этот маршрут от имени пользователя. Это разграничение обязанностей в доверенной локальной среде, а не аутентификация человека или защита от процесса с полным доступом к его компьютеру. Панель доступна только на loopback и проверяет Origin/Host.

## Существующие workspace

Для включения нового процесса остановите старый сервер и активные операции, затем запустите `start --workspace`. Существующие принятые задачи не удаляются и не получают выдуманных согласований. Новые работы нужно связать с утверждёнными версиями; старые черновики можно обновить. Старые настроенные workspace, открытые через `serve`, сохраняют прежний режим до явного включения нового процесса. Удаление включённого процесса через sync запрещено.

Новый стандартный маршрут — `start`, согласования, setup, выполнение. Это один controller и одна веб-панель, а не три независимо синхронизируемых трекера.
