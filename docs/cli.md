# CLI и локальное API

## Первый запуск и размещение

[Готовые примеры с опциями и поручениями агенту](start-examples.md).

`start --workspace-mode embedded --workspace /absolute/product --port 0` открывает панель внутри одного репозитория. `start --workspace-mode separate --workspace /absolute/workspace --port 0` использует отдельную папку. Первый выбор обязателен; последующие команды читают сохранённый `devcontour.workspace.json`. Без режима/пути CLI объясняет, что уточнить у пользователя. [Границы режимов](workspace-modes.md). Смена размещения существующей памяти не выполняется флагом.

`stop --workspace /absolute/workspace` штатно останавливает сервер workspace (`start` или `serve`), как Ctrl+C в его терминале: ждёт завершения идущих операций (`--timeout-ms`, по умолчанию 60000) и выводит `{status: "stopped", pid, url}`. После начала прослушивания сервер пишет `.devcontour-local/server.json` с pid, адресом и идентификатором экземпляра и удаляет его при остановке. `stop` посылает сигнал, только если сервер по записанному адресу сам подтверждает тот же pid, экземпляр и каталог данных этого workspace (`GET /api/server`); чужой процесс под тем же pid, другой сервер на том же порту или сервер, чью запись скопировали вместе с workspace (`cp -r`), не останавливается — команда завершается ошибкой с pid и путём записи. Нет записи или запись завершившегося процесса (она удаляется как устаревшая) — `stop` читает роль controller из базы без записи, как doctor: роли нет или она истекла — `not-running` (код 0); роль живая — `{status: "running-unrecorded", owner, leaseUntil, detail, manualStop}` с кодом 1. Так выглядит сервер, запущенный версией 0.4.0-alpha.19 или раньше: такие версии записи не пишут. DevContour ему сигнал не посылает и способа сделать это не даёт; `manualStop` перечисляет шаги для оператора. Роль хранит только случайный идентификатор владельца, без pid и хоста, поэтому pid находят по командной строке (`ps -ax -o pid,command | grep -F -- /absolute/workspace`) или по порту панели (`lsof -nP -iTCP:4317 -sTCP:LISTEN`). Сервер в терминале останавливают Ctrl+C; сервер, запущенный в фоне (`nohup`, `&`, менеджер процессов), — `kill -TERM <pid>` после проверки, что командная строка — `serve`/`start` этого workspace (SIGTERM — та же штатная остановка, что Ctrl+C). Затем повторите `stop`: ожидается `not-running`. Вместо ручного `kill` такой сервер останавливает `stop --pid <pid> --workspace /absolute/workspace`. Роль controller pid не хранит, поэтому DevContour подтверждает сам процесс и посылает SIGTERM, только если выполнено всё: записи `server.json` с другим живым pid нет; роль controller живая; `lsof -a -p <pid>` показывает открытую базу `state.sqlite` этого каталога данных (или её `-wal`) и слушающий TCP-сокет; argv процесса (`ps -o command=`) разбирается как `node [флаги node] <программа devcontour> serve|start …` или сам исполняемый `devcontour serve|start …` — программа `.../devcontour` либо `cli.js`/`cli.ts` в каталоге `devcontour`, подкоманда сразу за ней, затем `--workspace` этого workspace или `--data` его каталога данных (путь как передан или его realpath); время запуска pid (`ps -o lstart=`) не изменилось за время проверок. Обёртки (`bash -c`, `ssh`, `tmux`, `sudo`, `env`, `nohup` в argv, `npx`), `node -e`, путь с пробелами, относительный путь или ссылка, отсутствующий `lsof` — отказ с причиной, без сигнала; такой сервер останавливайте вручную. Ответ — `{status: "stopped", pid, verified: "database-listener-command-line", command}`; если pid совпадает с живой записью, `stop --pid` идёт обычным путём подтверждения по записи.

## Просмотр профиля до настройки workspace

```sh
devcontour profile-show --repository /absolute/product --profile ./profiles/service.json
```

Без выполнения команд возвращает resolved (проверки и источники состава), metadata (запись config.packs), pin (запись packs.lock.json). Для компонента с другим ID задайте --repository-id. Допускается встроенный ID вместо пути. Workspace не требуется: владелец файлов задан через --repository. Тот же профиль принимает setup/init --profile или поле profile в workspace-init registry. [Правила состава и обновления](mcp-and-profiles.md).

Из исходников команды вызываются через npm; [установленный пакет](distribution.md) предоставляет executable `devcontour`. Глобальная установка для работы не нужна:

```sh
npm run devcontour -- help
npm run devcontour -- COMMAND --workspace /absolute/product-workspace
```

`COMMAND` и условные IDs заменяются фактическими значениями. `--workspace` разрешается в `<workspace>/.devcontour-local`; альтернативный `--data` указывает папку с `config.json` напрямую. Их нельзя передавать вместе. Для старой конфигурации без workspaceRoot используйте `--data`.

CLI не задаёт интерактивный вопрос о workspace: это обязанность ведущего агента. Без выбранного контекста продуктовая команда завершается ошибкой. `demo` — отдельная явная команда с собственными данными.

Предложение контракта ссылается на файл в репозитории: `{"title": "...", "file": "docs/contracts/load-engine.md"}`. Содержимое читается из дерева в момент ревью, поэтому рецензент и реестр видят одну и ту же редакцию, а принятый digest относится к файлу, а не к чьей-то копии. Путь сохраняется в `Contract.source`. Inline-поле `content` остаётся для предложений, у которых файла ещё нет; указывать оба сразу нельзя.

Нормативные файлы договора — схему, приёмочные тесты, эталон — контракт перечисляет в `artifacts`: `{"title": "...", "file": "docs/contracts/load-engine.md", "artifacts": [{"path": "src/schema.ts", "purpose": "Схема ответа"}]}`. Каждый артефакт закрепляется закоммиченной ревизией HEAD компонента: путь, blob и digest содержимого; незакоммиченная правка, symlink, неотслеживаемый или отсутствующий файл отклоняются до ревью. Ревьюер получает закреплённое содержимое, digest контракта охватывает документ и артефакты, и изменённая схема при прежнем тексте — новый контракт с новым ревью, а не `already-approved`. Если за время ревью изменился документ или артефакт, одобрение не регистрируется. Задача, привязанная к прежней редакции, не запускается; прогон блокируется, если база не содержит закреплённых blob, а кандидат, изменивший артефакт, отклоняется как нарушение границы. Контракт без `artifacts` работает по прежнему договору, закрепляя только документ, и ответ ревью называет это предупреждением. Контракт, созданный оператором через HTTP, артефактов не закрепляет.

Закреплённый JS/TS-файл может импортировать соседние helpers и данные. Граница кандидата защищает только закреплённые и защищённые пути, поэтому до ревью вычисляется статическое замыкание локальных зависимостей каждого артефакта на ревизии закрепления: относительные `import`/`export … from`, `import('…')`, `require('…')`, `require.resolve('…')`, `createRequire(…)('…')`, `import.meta.resolve('…')`, JSON-импорты и `new URL('…', import.meta.url)` — транзитивно, с разрешением `.js`→`.ts`, расширений и `index` (при `h.js` и `h.ts` рядом зависимостями считаются оба); пакетные спецификаторы не учитываются, вычисляемые не видны. Зависимость, которая не закреплена в `artifacts` и не лежит под `protectedPaths`/`generatedPaths` компонента (в том числе файл, которого ещё нет в Git), отклоняет предложение до ревью — `review-contract` и старт `contract-change`; `contract-impact` показывает её в `closure`. Исправление — добавить файл в `artifacts` или в `protectedPaths`. Реализацию, которую приёмка проверяет намеренно, предложение перечисляет в `underTest` — точными путями файлов, которые пишет исполнитель (ещё не созданный файл тоже можно), а не каталогами: каталог освобождал бы и helper рядом с реализацией, поэтому отклоняется. Пример: `{"artifacts": [{"path": "tests/accept.test.ts", "purpose": "Приёмка"}], "underTest": ["src/solver.ts"]}`. Замыкание в эти файлы не заходит; каждый достигнутый файл `underTest` вместе с импортёром попадает в `closure.exempted` отчёта `contract-impact` и в снимок ревьюера (`underTestImports`), и ревьюер отклоняет договор, если в таком файле логика приёмки, а не реализация. `underTest` хранится в контракте и входит в digest, поэтому другой список — новый договор с ревью, а `underTest`, совпадающий с артефактом или объявленный без `artifacts`, отклоняется. Выход из репозитория, symlink, исходник, который лексер не разобрал до конца (незакрытые строка, шаблон, regex, комментарий или скобка), и превышение предела обхода (2000 файлов, 32 МиБ исходников) — отказ с именем файла, а не пропуск. Утверждённые раньше контракты не отзываются: `doctor` называет их неполное закрепление проверкой `contract-closure:<id>:<компонент>` со статусом `not-checked`, повтор того же предложения отвечает `already-approved` с предупреждением, а исправляет новая редакция через `contract-change`.

Перед изменением контракта `contract-impact --file proposal.json` показывает, что оно затронет, ничего не меняя: статус (`new`, `unchanged`, `changed`), изменился ли документ и каждый артефакт (`added`, `removed`, `changed`, `same`), задачи, привязанные к любой редакции контракта, и их транзитивных потребителей по `dependsOn` — с действием по состоянию (`rebind-after-review` для черновиков, готовых и упавших, `wait-or-cancel-run` для идущих, `correction` для принятых: их история не переписывается), недостающие в базе прогонов файлы и нужные ревью контракта и планов, а также `warnings` — структурные предупреждения до ревью (`checks-missing`: предложение без `checks` будет оценено по правилу `verifiability`) `limits` — превышения пределов предложения и `size` — размер документа относительно предела (ниже, «Пределы предложения» и «Размер документа контракта»). Документ и артефакты должны быть закоммичены: отчёт строится по HEAD. Применение — отдельный шаг после ревью.

Изменение контракта проводит одна команда `contract-change --file proposal.json --author-runtime codex|claude`. Это сохраняемая операция из идемпотентных шагов:

1. `hold` — удержать затронутые задачи и их зависимые: выдача их пропускает.
2. `drain` — дождаться идущих попыток; операция их не отменяет и ждёт (`waiting`, `waitingFor`).
3. `review` — ревью контракта по той редакции, с которой операцию начали; сдвинутая рабочая ветка или другое содержимое делают операцию устаревшей (`stale`). Исключение — этап, меняющий несколько контрактов: если до переноса базы (и до ревью плана) новый HEAD — потомок прежнего и изменил только документы и артефакты других живых операций `contract-change` того же компонента, а собственные пути операции в этом изменении не участвуют и её digest по новому HEAD прежний, операция принимает новый HEAD (запись истории `rebased`) и не устаревает. Ревьюер этой операции видел прежнюю редакцию соседа; новую одобряет ревью соседа ([D49](decisions.md)).
4. `rebind` — перепривязать черновики, готовые и упавшие задачи к новой редакции; они возвращаются в черновик.
5. `base` — перенести в базу прогонов изменение контракта; рабочая ветка, несущая другие изменения или подготовку другого компонента, не переносится заодно — операция останавливается с их списком. Сравнивается итог ветки от общей с базой точки, а не каждый commit: правка, отменённая в той же ветке, перенос не останавливает. Этап, меняющий несколько контрактов, коммитит их документы вместе, чтобы ревьюер каждого видел соседей. Путь соседнего контракта переносится вместе с этим, если его проводит другая живая операция того же компонента, уже прошедшая ревью, и её редакция — последняя одобренная для документа (одобрение агента с независимым ревьюером по `review.contract`, без открытых задач на прежней редакции). Документ — обычный файл, чей blob на проверенном commit равен blob одобренного текста; закреплённый артефакт — обычный файл с закреплённым blob, не документ контракта и не файл context pack, и другой контракт открытой работы не закрепляет его в другой редакции. Режим файла (бит исполнения) — тот же, что на commit ревью соседа. Защищённые, генерируемые и конфигурационные пути и данные контура так не переносятся. Снятия сверяются по состоянию ещё раз в транзакции сдвига ref: соседа отменили, заменили или зарегистрировали новую редакцию его документа — сдвига нет, операция останавливается и при продолжении пересчитывает снятия (запись истории `siblings` называет перенесённые пути). Если остальные пути принадлежат соседним операциям, ещё не дошедшим до базы, и они смогут перенести пути этой операции, операция ждёт их (`waiting`, `waitingFor` — их id); иначе — отказ сразу. Базу переносит та, что дойдёт до неё последней; операции, ждавшие её, продолжаются сами в том же вызове (`continued` в ответе) и записывают `carried` со ссылкой на перенёсшую операцию (её id хранится и в записи самой операции, `carriedBy`). Вызов включает оставшиеся шаги ждавших, в том числе их ревью планов, поэтому длится тем дольше, чем их больше. Код выхода — по самой операции; продолженные, остановившиеся `failed` или `stale`, CLI называет строкой в stderr. Вызов, оборванный посреди шага (например, таймаутом оболочки), оставляет операцию `running` с истёкшим lease; «Внимание» показывает её ведущему как прерванную, продолжение — `contract-change --id ID`. Ожидание, чьи соседи больше не идут к базе (отменены, заменены, устарели), показывается в «Внимании» ведущему: продолжите его `contract-change --id ID`. Проигранный сдвиг ref при переносе той же базы соседом не отказ, если база уже содержит проверенный commit. Отказ называет посторонние пути, пути соседей не в одобренной редакции, пути, ждущие ревью соседей, и ушедших соседей, а также выход: `base-update --by host` на остановленной очереди, затем `contract-change --id ID`; такой перенос документов и артефактов без доказательства ревью затем ждёт подтверждения оператора (`base-check`).
6. `context` — перезакрепить context packs, которые закрепляют документ контракта, по перенесённой ревизии. `config.json` пишется, только если его digest равен ожидаемому операцией; правка файла вне операции — отказ с обоими digest. Повтор после сбоя узнаёт уже записанный файл по digest и не пишет его заново.
7. `reconfigure` — применить новую конфигурацию. Операция ставит свою паузу (паузу человека не трогает), останавливает выдачу попыток, совместных проверок, поставок, preview, контрольных операций корпуса и этапов ведущего (`context-lock` в это время отказывает) и ждёт окончания идущих. Затем применяет конфигурацию в своём процессе, а работающий сервер применяет её по запросу из базы и подтверждает тем же digest. Отличаться может только закрепление context packs; остальное требует перезапуска сервера. Без запроса операции сервер правки `config.json` не подхватывает.
8. `plan` — ревью планов затронутых досок, только по перепривязанным черновикам. Рецензент видит задачи уже на новой базе — с той редакцией контракта, артефактами и контекстом, с которыми они будут выполняться.
9. `release` — снять удержание. Свою паузу операция снимает в конце `reconfigure`; пауза человека остаётся.

Операции, начатые до шагов `context` и `reconfigure`, продолжают по своему порядку: если пакет контекста закрепляет документ контракта в прежней редакции, такая операция останавливается перед ревью планов и не снимает удержание; после `context-lock` и перезапуска сервера `contract-change --id ID` продолжает с того же шага.

Отклонённое предложение после правки документа продолжается той же операцией: `contract-change --id ID --revise --expected-version N` берёт текущий закоммиченный HEAD явно (обычное продолжение по прежнему входу его не подхватывает). С `--file FILE` пересмотр берёт исправленный файл предложения того же контракта (те же `file`, `title`, `repositoryId` в записанном виде и компонент; файл, зарегистрированный под другим компонентом, — отказ, как при старте) — новый текст, `artifacts`, `checks`, `underTest` — и до записи и вызова модели проходит те же предпроверки, что старт: закрепление артефактов, замыкание их локальных зависимостей и структуру договора проверки. Операция, её удержания и история остаются прежними; запись `revisions[]` хранит digest предложения прежней редакции (`proposal`), а запись истории `revised` — digest нового. Без `--file` пересмотр берёт прежнее предложение. Ревью связываются с операцией по каталогу решения, а не по названию: запись истории получает ссылку `review` только на попытку, которую провёл этот шаг. Тот же пересмотр в агентском API — `contract_change_revise` с `proposal`. До регистрации новой редакции операция сохраняет прежнюю редакцию и её ревью в истории, пересчитывает влияние и удержания одной транзакцией и повторяет ревью; поздний ответ прежнего ревьюера ничего не утверждает. После регистрации, перепривязки или переноса базы эффекты не откатываются: создаётся связанная следующая операция, которой удержания передаются атомарно. Ревью плана внутри операции видит все задачи затронутой ревизии, а утверждает только перепривязанные и явно включённые `--include` подготовленные черновики; изменение показанного контекста во время ревью делает его устаревшим. Пакет контекста с прежней редакцией переводит операцию в ожидание `context-lock` с точным следующим шагом, отдельное от паузы человека. Перенос базы — техническое ожидание проверки базы (`base-check`), а не пауза человека.

`checks-approve --suite S --pending P` — ручное техническое подтверждение принятия версии корпуса в operator mode (в агентском API этой операции нет).

`self-check --task ID [--cwd DIR] [--seed N]` — диагностика рабочего дерева тем же закреплённым checker, полным корпусом, seed и селектором свойств задачи; ненулевой код называет свойство, вход и причину. Gates эталонных наборов (`verification: "reference"`) запускаются тем же путём и отчитываются тем же отчётом свойств. Evidence контура не заменяет.

Код выхода `contract-change` — 1, если операция закончилась `failed` (например, ревью отклонено) или `stale`; JSON операции при этом печатается в stdout как обычно. `waiting`, `completed`, `abandoned` и `unchanged` — код 0: ожидание продолжают `contract-change --id ID`. Предупреждения старта (`warnings`) CLI печатает в stderr строками `Предупреждение:` до вызова модели. Запись `history[]` хранит `detail` не длиннее 500 знаков, сокращённый по границе фразы или слова с «…»; запись шага `review` ссылается на попытку ревью полем `review` (`id`, `artifact`): полный итог и находки — `GET /api/contract-attempts` и `GET /api/contract-attempts/:id/findings`, файлы ревью — в `artifact`. Удержанная операцией задача показывает в `progress.reasons` причину `held_by_operation`, а в `progress.hold` — операцию, её вид (`contract-change`) и причину.

Принятые задачи не перепривязываются: они перечислены в `corrections` для корректировки. Выполняет шаги только владелец операции (lease и token); прогресс сохраняется после каждого шага, и `contract-change --id ID` продолжает с сохранённого шага — после сбоя процесса, ожидания или устранённой причины отказа, не повторяя ревью. Живого владельца другой процесс не перехватывает. Вторая операция по другой редакции того же контракта отклоняется; задача, удерживаемая другой операцией, — конфликт. `--abandon` снимает удержание; перепривязанные задачи остаются черновиками. Пауза оператора не снимается; отмена снимает паузу операции и неприменённый запрос (уже записанный `config.json` остаётся и читается при следующем запуске сервера). В режиме operator команда отказывает: изменение проводит оператор.

Каждое обязательство контракта называет область входов и пределы размеров, точность или оптимальность (либо допустимое приближение), худший случай, допустимые отказы, модель ресурсов и способ измерения. Ревью контракта проверяет это для каждого обязательства; невыполнимое при заявленных пределах или неизмеримое обязательство — блокирующая находка класса `feasibility` с названным входом, и отказ называет её отдельно: её чинят ограничениями, допущениями или изменением требования, а не правкой формулировки. Трудность задачи сама по себе не невыполнимость: точный ответ для трудной задачи допустим при ограниченном входе, обоснованных допущениях или документированном запасном пути. Пример: «O-2: оптимальная упаковка для n ≤ 20, точный оптимум; больше 20 — отказ TooLarge; ≤ 1 с при n = 20 по приёмочному бенчмарку; память ≤ 256 МБ».

`--author-runtime` обозначает фактического автора предложения, не произвольный выбор reviewer. Review по умолчанию выбирает runtime другого вендора; тот же вендор — только по явному `review.plan|contract.vendor: same-vendor-allowed`. Команды review вызывают модель и расходуют её лимиты. Точное совпадение уже утверждённого контракта может вернуть `already-approved`.

Файл contract proposal содержит `title`, `file` или `content`, опционально `repositoryId`, `artifacts` и `checks` — договор проверки ([check-contracts](check-contracts.md)). Без `checks` ревью оценивает контракт по правилу `verifiability`: контракт с вычислительными обещаниями (точность, оптимальность, полнота, производительность) отклоняется, и это относится и к изменению контракта, утверждённого до появления `checks`. Отсутствие repositoryId означает общий контракт.

**Пределы предложения.** `artifacts` — не больше 50 элементов, `purpose` каждого — не больше 200 знаков (без пробелов по краям), `underTest` — не больше 50 путей; `title` — до 180 знаков, `content` — до 60000. Пределы те же, что у записи контракта в синхронизации команды: контракт сверх них не перенёсся бы в другой клон. `contract-impact` называет превышения в `limits` (`max`, `issues[]`: `limit`, `actual`, `over`, у `purpose` — `index` и `path`; `refusal` — текст отказа), рядом с `closure`. `review-contract` и `contract-change` (старт и `--revise --file`) отказывают до ревью сообщением, где названы предел, элементы и величина превышения, и способы исправления. Обычно помогает убрать из `artifacts` журналы и данные, которые закреплённые файлы не импортируют и на которые не ссылается `checks`, и защитить их через `protectedPaths` компонента; журналы сверки свести в один сводный артефакт; сократить `purpose` до одной фразы.

**Размер документа контракта.** Документ — inline `content` или файл `file` — не длиннее 60 000 знаков. Размер файла схема предложения не видит, поэтому его проверяют сами операции: `contract-impact` называет его в `size` (`chars`, `max`, `warnAt`; `hint` — от 75 % предела, совет консолидировать; `warning` — документ занимает 90 % предела и больше, `refusal` — предел превышен), `review-contract` и `contract-change` (старт и `--revise --file`) отказывают при превышении до ревью, а ответ `review-contract` при 90 % и больше несёт предупреждение в `warning`. Прежде превышение для файла обнаруживалось только при регистрации — после оплаченного ревью. Действующий контракт, который поправками дорос до 75 % предела, `doctor` называет проверкой `contract-size:<id>` с советом консолидировать документ (статус `passed`), от 90 % — предупреждением (статус `degraded`, готовность не снимает) с запасом до предела; документ от 30 000 знаков после шести поправок с первой регистрации или последней консолидации — предупреждением `contract-consolidate:<id>` (`degraded`). Отказ по размеру и предупреждения называют сначала консолидацию, затем файл-продолжение. `contract-impact` и `review-contract` от 75 % несут тот же совет в `size.hint` и `warning`.

**Консолидация контракта.** Контракт растёт поправками от этапа к этапу: «правило 4.2 заменено», «добавлено в этапе 3». Когда документ дорос до 75 % предела или после шести поправок (смысловых редакций после первой регистрации или последней консолидации) у документа от 30 000 знаков, перепишите его в чистое описание текущего поведения и проведите командой `contract-change --consolidate --file FILE --author-runtime codex|claude` (предложение — то же, что у изменения: `title`, `file`, `artifacts`, `checks`, `underTest`). Консолидация меняет только текст: смысл каждого правила, `artifacts`, `checks` и `underTest` остаются прежними. До удержаний и вызова модели операция отказывает, если у документа нет зарегистрированной редакции, название другое, закреплённые артефакты, `checks` или `underTest` отличаются от действующей редакции, новый текст не короче действующего, из текста пропал ID-токен правила (`REQ-12`, `ТР-4`, `req-1.2` — буквенный префикс от двух букв в любом алфавите и регистре, дефис, номер с подномерами; `UTF-8`, `SHA-256`, `ISO-8601` и подобные обозначения правилами не считаются) или пропал заголовок либо якорь, на который ссылается другой зарегистрированный контракт (`catalog.md#prices`). Затем отдельное ревью равносильности получает прежний и новый текст, закреплённые файлы, список ID, выдержки соседних контрактов и открытые вопросы исполнителей о документе; ревьюер пишет в итог полное отображение старого текста в новый («старое → новое») и отклоняет выпавшее, ослабленное, расширенное или новое правило и воскрешённую формулировку, которую заменила поздняя поправка. Выполнимость и проверяемость неизменных правил это ревью не оценивает. Итог одобренного раунда контур сверяет сам: отображение — строки `старое → новое` (или `->`), правая часть называет ID, заголовок или якорь нового текста, и каждый ID-токен и каждый заголовок прежнего текста (целым словом или якорем, без учёта разметки Markdown) должен стоять в левой части такой строки; в строке не больше одного прежнего заголовка, а у каждого прежнего ID — своя цель справа (тот же ID или отдельный заголовок либо якорь). Перечисление без стрелок и одна строка на всё не считаются. Иначе раунд записывается отклонённым (правило `consolidation`, «Неполное отображение»), а следующий раунд получает пропуски в `incompleteMapping` и вызывает ревьюера заново. Редакция, зарегистрированная во время ревью, делает операцию `stale`. Отказ ревью — операция `failed` на шаге `review`, ничего не зарегистрировано; продолжение и `--revise` — как у изменения (после регистрации консолидация не пересматривается). Шаги: удержание, ожидание идущих попыток, ревью, перенос базы, перезакрепление context packs, применение конфигурации, снятие удержания — без перепривязки и ревью планов. Новая редакция несёт `consolidates: {from, review}`; задачи, привязанные к прежней редакции, сохраняют привязку, digests и утверждение и выполняются без повторного ревью плана, принятые остаются принятыми без корректировки. Исполнитель читает консолидированный документ (база и context pack), `task_briefing` показывает текущий текст. Следующая смысловая редакция заменяет обе — прежнюю и консолидацию — и перепривязывает задачи обеих, как обычно. Порядок редакций документа задают ссылки записей (`previous` — предыдущая редакция при регистрации, `consolidates.from`), а не позиция в реестре: после Git sync он тот же. Git sync проверяет новую для клона консолидацию один раз: она консолидирует непосредственно предыдущую редакцию (`previous` = `from`), с теми же обязательствами, текст короче и ID правил на месте (ссылки соседей на якоря — только при регистрации); принятые ранее записи не пересуживаются. Параллельная поправка той же редакции на другом клоне встаёт после консолидации и заменяет её. Две параллельные поправки одной редакции `doctor` называет развилкой `contract-fork:<компонент>:<файл>` (`degraded`): обе редакции и действующую; сведите их новой редакцией — предупреждение снимается, как только поверх действующей зарегистрирована смысловая редакция. В режиме `operator` консолидация, как и изменение контракта, недоступна агенту. MCP-инструмента для старта операции нет: ведущий запускает её командой, `contract_change_status` и `contract_change_revise` работают и с консолидацией.

**Файл-продолжение.** Если контракт приближается к пределу, сначала консолидируйте его (см. выше): чаще всего место занимают накопленные поправки. Если правила не помещаются и после консолидации, вынесите часть правил в отдельный файл и проведите его как второй контракт, например `docs/contracts/catalog.md` и `docs/contracts/catalog-2.md`. В начале продолжения назовите основной контракт и перечислите, какие его правила продолжение меняет или дополняет (по номерам или заголовкам разделов), например: «Продолжение `catalog.md`: заменяет правило 4.2, дополняет раздел 5». Правило, которое не названо, действует по основному контракту. Задачи, которых касаются оба документа, привязывают оба контракта (`contracts` задачи — список). Изменение основного контракта, которое затрагивает перечисленные правила, проводится вместе с правкой продолжения: ревью каждого документа видит только его текст и артефакты.

Plan содержит `title`, `description`, `tasks` (1–30), у каждой задачи — локальный `key`, роль, description, acceptance, contracts, dependsOn и при необходимости repositoryId/scope/context/writePaths/resources. `dependsOn` принимает ключ из этого плана либо существующий Task ID. Пример: [example-plan.json](../packs/example-plan.json).

Возвращённые B/T/C/CHG IDs нужно читать из результата; значения `B1`, `T12`, `CHG-12` в документации условны. Повторный import не является idempotent-обновлением существующей доски.

Через device broker она достигает состояний спецификации, записывает наблюдения и снимки PNG и пишет JUnit. Код выхода 0 — всё прошло, 1 — провал утверждения, 75 — провалов нет, но есть ошибки окружения. `--budget-ms` — срок прогона; отчёт пишется до него, timeout gate объявляется на 30 с больше. `--release` — проверка уровня релиза: в ней Expo Go не принимается. `visual evaluate --spec FILE --observations DIR --report FILE` оценивает уже записанный каталог наблюдений с теми же кодами выхода. `visual broker start|stop` пока не реализован и завершается ошибкой.

`run` не утверждает черновики и не выполняет весь продукт автоматически. Его успешный exit сам по себе не доказывает, что не осталось draft/blocked задач или непринятых досок. Проверяйте итоговое состояние и порученный объём.

Совместная проверка, прерванная до результата gates (остановка сервера, потеря владения), предел набора не тратит; у таких проверок свой предел. Отказы `workspace-verify` и карточка остановленного задания ChangeSet называют `changeset-budget-reset`, когда предел исчерпан проверками без результата gates. DevContour сам сброс не вызывает.

`accept`/`changeset-accept` не создают ещё один LLM-review готового отчёта. Они применяют доменные условия к уже полученным доказательствам. При `approvalMode: operator` агентский вызов возвращает `awaiting-operator`; оператор подтверждает в UI. Статус такого ответа нужно обработать, а не читать любой exit 0 как приёмку.

`--by` у `retry`, `cancel`, `base-update` и команд `input-*` называет актёра события harness: `operator` (по умолчанию) — человек, `host` — ведущий агент, выполняющий подсказку контура. Отчёт об эффекте относит к действиям человека только `operator` ([метрики](metrics.md)).

## Решения за владельца

Решения, которые ведущий принял за владельца без его ответа (`discussion_post` с `kind: stand-in`, см. [решения за владельца](agent-interface.md#решения-за-владельца)). Команды — действие владельца: флага `--by` нет, агентский API этих операций не имеет. Как и другие команды оператора, CLI доверяет тому, кто его запустил; ведущему агенту вызывать их запрещено правилом.

```bash
devcontour decisions [--all] --workspace /absolute/workspace
devcontour decision-confirm --message DM-... [--text "комментарий"] --workspace /absolute/workspace
devcontour decision-reverse --message DM-... --text "что сделать взамен" --workspace /absolute/workspace
```

`decisions` без `--all` печатает ждущие подтверждения (`state: unconfirmed`): `messageId`, задачу, вопрос, решение, влияние и версию треда; с `--all` — и решённые (`confirmed`, `reversed`). Отмена становится обращением к ведущему агенту: оно ждёт его обработки в `discussion_inbox`, и отклонить её ведущий не может. Версия треда по умолчанию — текущая (`--version N` — явная), ключ повтора — новый (`--key K` — свой).

## Вывод и ошибки

Большинство управляющих команд выводят JSON в stdout; ошибки — сообщение и ненулевой exit code. npm добавляет собственный banner, поэтому при машинном разборе используйте `npm run --silent devcontour -- ...` и отдельно учитывайте stderr. SQLite может печатать experimental warning в stderr.

`doctor` возвращает scope и результаты со статусами `passed`, `blocked`, `not-checked` и `degraded` (работает, но слабее ожидаемого не по явному выбору — например, claude-ревьюер без профиля инструментов; строка называет исправление). `ready` снимает только `blocked`. `run` возвращает статусы задач и ненулевой exit при failed, но не заменяет acceptance. `contract-change` возвращает exit 1 при операции в состоянии `failed` или `stale`, печатая её JSON. `serve` печатает URL и режим, затем работает до сигнала. Отдельной стабилизированной версии машинного CLI-протокола пока нет; интеграции должны проверять структурированный ответ и зафиксированную версию инструмента.

**Пределы приёма.** Файл из `--file` и `--resolutions` команд постановки, контрактов, sync и `agent` — до 4 MiB; больше — отказ до разбора. Задача: до 100 `relatedRepositories`, до 100 `dependsOn`, до 30 `acceptance` и до 30 `contracts`; те же пределы действуют в задачах плана при `import-plan`, `plan_import`, `task_create` и `task_edit`. HTTP принимает до 1000 `taskIds` в `POST /api/boards/:id/approve` и до 100 `roots` в `POST /api/boards/:id/correct`. Запись, сохранённая раньше сверх этих пределов, читается как прежде; отказ получит только новая постановка или правка.

## HTTP API

Предпочтительный интерфейс ведущего агента — CLI. HTTP нужен UI и локальным интеграциям. Сервер слушает loopback; публикация в интернет не поддерживается без отдельного слоя аутентификации. Для mutating-запросов обязательны `Content-Type: application/json` и `X-DevContour-Request: 1`, Host/Origin проходят проверку.

| Метод и путь                                                       | Назначение                                                                                                                   |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/summary?board=ID&boardRevision=N&task=ID&revision=N`     | Ограниченная сводка для опроса панели; при той же ревизии — только номер                                                     |
| `GET /api/tasks/:id?limit`, `/api/tasks/:id/runs?before=ID`        | Задача целиком и страницы попыток (новые сначала, ≤ 50, курсор по id, хвосты логов)                                          |
| `GET /api/tasks?q=&limit&cursor`                                   | Поиск задач компактными строками                                                                                             |

`config` в `GET /api/summary` и `GET /api/state` несёт данные элемента порога: `inputPolicy` (действующее значение или `null` — порог 7), `inputPolicyDeclared` (`workspace.json` объявляет `inputPolicy`: маршрут ответит 409, панель показывает значение только для чтения), `configDigest` (ожидаемый digest для `POST /api/config/input-policy`) `configPending` — занятый слот запроса применения конфигурации `{operation, requestedAt, keys?, appliedAt?, error?}` или `null` (то же правило, что у маршрута: запрос другой операции занят и после применения или отказа, пока она его не сняла; пока слот занят, правка порога получает 409) и `configDrift` — `config.json` отличается по смыслу от действующей конфигурации сервера `{fileDigest, reason}` (`fileDigest: null` — файл не принят) или `null`; маршрут сверяет файл, поэтому при расхождении правка тоже получает 409, пока правку файла не применят `config-apply` или файл не вернут.

Операторские endpoints записывают ручное действие. Автоматический ведущий агент использует команды независимого review, а не выдаёт себя за оператора через HTTP для обхода процесса. В local single-user MVP это договор workflow; полноценной авторизации по ролям ещё нет.

Неизвестный маршрут возвращает 404, ошибка JSON/schema — 400, нарушение локальной границы — 403, доменный конфликт обычно — 409. Тело содержит `error`. Точные тела и ограничения находятся в `src/server/http.ts`. Нет endpoint для прямой загрузки PASS или установки `done`.

## Командный Git sync

| Команда                                         | Поведение                                                                                                          |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `sync-status`                                   | Сравнивает baseline, SQLite и `.devcontour/`; показывает изменения/конфликты без импорта задач и записи Git-файлов |
| `sync --member alice`                           | Первый обмен и локальная идентичность участника; далее `--member` можно опускать                                   |
| `sync`                                          | При остановленных workers объединяет и проверяет записи, обновляет файлы и локальную SQLite                        |
| `sync --resolutions /absolute/resolutions.json` | Выбирает `local`/`git` для указанных конфликтующих записей; доменные проверки остаются обязательными               |
| `sync --allow-branch-change`                    | Разрешает проверенную смену имени ветки без удаления истории и обхода конфликтов                                   |
| `assign-task --task <ID> --member alice`        | Меняет ответственного при отсутствии активной попытки; командная очередь берёт только свои задачи                  |

Все команды принимают `--workspace /absolute/workspace` или прежний `--data`. Sync требует `workspaceRoot` и отдельные Git-репозитории; он не делает commit/pull/push. Операционный `export` остаётся диагностикой, его JSON не является переносимым sync-форматом. Новые IDs содержат UUID; используйте возвращённые IDs, не вычисляйте следующий номер. Подробные сценарии, примеры файлов решений и границы доверия — [team-sync.md](team-sync.md).

## Эксперименты без продуктового workspace

`engineering-evals` использует собственные временные Git-репозитории. По умолчанию это fixture без модели; live требует `--live --runtime codex|claude --model ID --reviewer-model ID`; ревьюер — runtime другого вендора, `--reviewer-runtime codex|claude` называет его явно (тот же вендор, что автор, разрешается в конфигурации прогона только так). `eval-compare --baseline ABS.json --candidate ABS.json` сравнивает совместимые отчёты без вызова модели. Полные параметры и ограничения — [эксперименты](experiments.md).

`contract-evals` проверяет суждение ревьюера о выполнимости обязательств контракта на неизменном корпусе обезличенных постановок: выполнимых, невыполнимых и без однозначного ответа. Балл считается только по выполнимости: ложные отказы (`falseRejections`) и пропуски (`missed`) — отдельно; постановки без однозначного ответа записывают вердикт без балла. Без модели это фикстура, которая отвечает ожидаемым вердиктом и проверяет только протокол: `judgementMeasured: false`. Live требует `--live --runtime codex|claude` (автор) и `--reviewer-model ID`; ревьюер — runtime другого вендора или явно названный `--reviewer-runtime codex|claude` (тот же вендор — только так), число вызовов ограничено `--max-calls` (по умолчанию — размер корпуса).

Для memory_retain/recall, usage_report, decision_report, strategy_replay, а также preparation__, discussion__, input_* и attention_list без отдельной команды используйте общий `agent --file request.json --workspace ...`; точные схемы показывает capabilities.
