# Справочник конфигурации

Новый продуктовый маршрут начинается с [раннего запуска панели и продуктовых согласований](staged-workflow.md): продукт утверждает пользователь, затем архитектуру и стек с C1/C2, затем дизайн-трек — референсы, а при применимом интерфейсе ещё концепт и дизайн-систему. Технические операции ниже выполняются после этих решений, а задачи исполнения — только после всей цепочки. `approvalMode` не отменяет их.

Форматы заданы в `src/core/model.ts`, `integrations.ts`, `runner/config.ts` и `workspace-setup.ts`. JSON-блоки ниже — фрагменты, если не сказано иначе. Не заменяйте ими весь созданный config. Перед изменением политики приостановите очередь, завершите активные операции и остановите сервер/другие записывающие клиенты; после правки проверьте настройки и запустите его заново. Пауза workers не блокирует все стадии workflow.

## Выбор размещения

`devcontour.workspace.json` содержит `{ "version": 1, "mode": "embedded" }` либо `separate`; он сохраняется в Git и выбирается пользователем до первого запуска. Рабочий config содержит соответствующий `workspaceMode`. Embedded требует один репозиторий в корне workspace и `storage: central`; separate сохраняет отдельный workspace и component storage. Локальный selection pin и загрузчик отклоняют расхождение режимов. Изменение поля не является миграцией. [Подробности](workspace-modes.md).

## Уровни и файлы

| Файл                                        | Назначение                                                                               |
| ------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `<workspace>/workspace.json`                | Входной реестр для первичного `workspace-init`; относительные пути разрешаются от него   |
| `<workspace>/.devcontour-local/config.json` | Рабочая общая конфигурация, которую CLI/server загружают при старте                      |
| `<repo>/devcontour.component.json`          | Настройки конкретного компонента, подключаемые через `configFile`; следует хранить в Git |
| `<data>/packs.lock.json`                    | Версии и digests установленных stack profiles                                            |
| `<repo>/.agents/`, `AGENTS.md`, `CLAUDE.md` | Читаемые человеком и агентом правила; выбранные файлы закрепляются context packs         |

`workspace.json` — не автоматически синхронизируемый control plane. Повторный `workspace-init` сохраняет имеющуюся конфигурацию того же набора ID/путей. Изменённое объявление (gates, роли, профили инструментов, context packs, `review`) он переносит и отвечает `declaration-updated`. Правка исходного реестра сама по себе не меняет уже работающий сервер.

В component mode coordinator хранит ссылки `{id, path, dependsOn, configFile}`. При загрузке содержимое component config переопределяет локальные настройки, но `id`, `path`, `dependsOn` и `configFile` берутся из общей записи. Так глобальная топология остаётся согласованной, а команды/роли живут рядом с кодом.

При списке `repositories` верхнеуровневые `gates` и `protectedPaths` — производная копия первого компонента. Загрузчик берёт их из компонента, а не из копии в `config.json`, поэтому панель и `doctor` показывают тот список, по которому работает исполнение, даже если файл компонента изменили без `workspace-init`. При единственном компоненте действуют и его привязки ролей с ревьюером: `workspace-init` обновляет верхнеуровневые копии таких ролей и копии `gates`/`protectedPaths` в самом файле (`declaration-updated`). При нескольких компонентах верхнеуровневые `roles` — общий запасной выбор, и он не трогается.

`setup --workspace`/`workspace-init` выбирают central storage для embedded и component для separate. Default самой схемы — central для совместимости старых конфигураций. Не переключайте действующее хранилище одним полем: для central → component используется `storage-migrate`.

| `reuseImplementation`            | `true`                                                              | Повтор после отказа окружения или времени берёт кандидата предыдущей попытки, если совпали все основания реализации; проверки и ревью идут заново. `false` — каждая попытка пишет код с нуля |

| `checkoutRoot`                   | кэш пользователя (`~/Library/Caches/devcontour-harness/<hash>`)     | Корень рабочих деревьев попыток и проверок вне репозиториев; абсолютный путь, лучше на томе репозиториев (жёсткие ссылки и reflink менеджера пакетов)                                        |

Schema defaults и выбранный профиль — разные уровни. Например, `protectedPaths` в generated setup шире default схемы; чтение одного model.ts не показывает готовую политику продукта. `doctor` проверяет загруженную конфигурацию.

`workflow_start.maxAttempts` — отдельный лимит 1–5, по умолчанию 3, на стадию сохраняемого workflow. Ожидание задач его не расходует. Он не увеличивает бюджет попыток Task или Verification. Пределы расходов и времени вызовов моделей задаёт `budgets` (раздел «Бюджеты» ниже); лимиты у провайдера — отдельная защита. [Подробности восстановления](lead-workflow.md).

## Компоненты и роли

Компонент задаёт `id`, `name`, `kind: product|library`, `path`, `targetBranch`, `gates`, `protectedPaths`. Дополнительно: `roles`, `reviewer`, `generatedPaths`, `environment`, `prepare`, `preflight`, `lifecycle`, `dependencyBuild`, `dependencyArtifacts`, `forge`. Состав `dependsOn` принадлежит registry и описывает прямые входные компоненты.

Роли объявляет workspace, а не инструмент. `architect`, `backend`, `frontend`, `qa` создаются при setup как умолчание для нового контура; продукт добавляет свои — `mobile`, `qa-web`, `qa-mobile` — там, где область записи и инструментарий разные. Идентификатор: строчные латинские буквы, цифры и дефис. Задача может ссылаться только на объявленную роль; у неизвестной нет ни runtime, ни ревьюера, ни области записи.

Два поля роли кроме исполнителя и ревьюера:

- `title` — как роль называется в панели («Мобильный разработчик» вместо `mobile`). Без него панель делает имя из идентификатора.
- `requiresContract` — роль реализует общую поверхность, и её задача без утверждённого контракта не принимается. По умолчанию так для `backend` и `frontend`; мобильной разработке, реализующей тот же API, это нужно объявить.

В компоненте разрешено частичное переопределение и объявление ролей, которых нет в общей конфигурации. Роли профиля принадлежат тому компоненту, чей это профиль: react-native на втором репозитории приносит `mobile` и `qa-mobile` именно ему.

У пакета два уровня. `files` вкладываются в промпт — это правила, нужные в большинстве обращений. `references` исполнителю **называются**: путь и закреплённая ревизия, без содержимого; он читает их в рабочем дереве, когда тема всплыла. Библиотека стандартов на сотни килобайт иначе не помещается, а выбросить её значит потерять именно те детали, ради которых её писали. Содержимое справки входит в digest наравне с правилами: изменилась справка — закрепление недействительно.

Пакет достаётся роли, если он её называет, — либо задаче, если она перечислила его явно. Роль без своих пакетов получает только общие, и об этом стоит помнить, заводя новую: инструкция не появляется сама.

Исполнитель по умолчанию получает shell, чтобы запускать тесты и проверку типов во время реализации, а не узнавать о провале только от гейтов после попытки. У claude это набор `Read`, `Glob`, `Grep`, `Edit`, `Write`, `Bash`, если профиль не называет `claudeTools`; у codex — shell CLI, если профиль не задаёт `codexShell: false`. Shell исполняется в песочнице ОС по `isolation`: без песочницы запуск отказывает, а не идёт без изоляции. Явный отказ соблюдается — `claudeTools` без `Bash` или `codexShell: false`; `doctor` называет такого исполнителя строкой `writer:<компонент>:<роль>`, одинаково для обоих рантаймов.

Ревьюер запускает проверки только если профиль инструментов дал ему это право: у claude — `Bash` в `claudeTools`, у codex — `codexShell`. Право даётся одинаково в обоих рантаймах; раньше codex-ревьюер получал shell по умолчанию, а claude-ревьюер был ограничен чтением, и одно и то же ревью было сильнее или слабее в зависимости от рантайма. У codex нет инструмента чтения файлов, кроме shell, поэтому без профиля codex-ревьюер получает shell в песочнице только для чтения: запись открыта лишь во временный каталог, сети нет, каталоги контура и учётных данных закрыты. Иначе он видел бы только текст подсказки. Явный `codexShell: false` соблюдается. Ревью, которое читает только diff, не найдёт того, что видно лишь прогоном; `doctor` называет такую роль отдельной строкой `reviewer:<компонент>:<роль>`. Claude-ревьюер без профиля инструментов (нет ни `toolProfile` ревьюера, ни `toolProfiles["claude-review"]`) получает статус `degraded`: заменив codex-ревьюера без профиля, он молча потерял бы право запускать проверки. Строка называет исправление — профиль `claude-review` с `"claudeTools": ["Read", "Glob", "Grep", "Bash"]` или `toolProfile` ревьюера с `Bash`. Готовность `degraded` не снимает. Профиль, явно не давший shell, — выбор оператора, и строка остаётся `not-checked`.

Править проверяемый код ревьюеру запрещено всегда, и это не держится на одном запрете инструмента: после ревью контур сверяет состояние worktree и HEAD с исходным, и любое изменение отменяет одобрение.

### Изоляция исполнителя, ревьюера и проверок

Граница доступа описана одной политикой и применяется механизмом, родным для каждого участника: проверки (gates) исполняются через sandbox-runtime (Seatbelt на macOS, bubblewrap на Linux), shell codex — через профиль прав codex, shell claude — через sandbox Claude Code. По умолчанию `isolation.mode: "os"`:

- запись — только в свой worktree (ревьюеру — никуда) и во временный каталог; проверка получает отдельный scratch в `TMPDIR`;
- чтение закрыто для каталогов контура (база, артефакты других прогонов), рабочих деревьев других попыток, исходных checkout репозиториев (открыт только их `.git`, нужный linked worktree) и каталогов учётных данных (`~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.npmrc` и др.); собственный worktree и закреплённые зависимости открыты;
- внешняя сеть закрыта, кроме доменов из `isolation.domains`; проверкам доступен localhost; сеть исполнителя codex — по `codexNetwork` профиля.

  Проверка, упавшая с отказом прокси песочницы (`403`, `Forbidden`, `connect EPERM`) при обращении к домену не из списка, записывается отказом окружения с названием домена, а не провалом кода: повтор реализации его не исправит. Проверкам установки зависимостей обычно нужен домен реестра пакетов, например `registry.npmjs.org`.

Рабочие деревья лежат вне каталога контура и вне репозиториев — в одном корне рабочих деревьев workspace (`checkoutRoot` или кэш пользователя): checkout, вложенный в закрытый песочницей каталог, упирал инструменты, которые ищут конфигурацию вверх по дереву (browserslist, Metro/Expo, postcss, tsconfig, prettier), в EPERM вместо ENOENT. Деревья других попыток под этим корнем закрыты, свой checkout открыт. Если кэш пользователя на другом томе, чем репозиторий, деревья остаются в каталоге состояния, а `doctor` (проверка `checkouts`) называет это ослаблением: задайте `checkoutRoot` на томе репозитория.

Встроенные файловые инструменты claude (Read, Edit) получают те же запреты правилами прав: песочница Claude Code охватывает только Bash. Процессы проверки и агента не переживают их: потомки, сменившие группу или сессию, находятся по метке окружения и завершаются, а проверка не считается законченной, пока хотя бы один жив.

Без механизма песочницы проверка не запускается, а `doctor` называет причину. Снять изоляцию проверок можно только явно: `isolation.mode: "none"`. Песочницы рантаймов при этом остаются. На Linux для проверок нужны `bubblewrap`, `socat` и `ripgrep`; Ubuntu 24.04 требует разрешить непривилегированные user namespaces.

Остальной домашний каталог остаётся доступным на чтение: там лежат проверяемый checkout и инструменты. Codex оставляет временный каталог открытым на запись. Проверки закрывают каталог контура и исходные checkout целиком. У codex и файловых инструментов claude скрытый каталог над рабочим закрывается поэлементно: известные элементы каталога контура закрыты и тогда, когда появятся позже, а соседний worktree или новый файл верхнего уровня, созданные после старта агента, агенту видны на чтение. Шаги lifecycle (подъём сервисов, preflight) исполняются процессом хоста: им нужны права, которых у проверки нет.

Поведение песочниц рантаймов подтверждается явным live-запуском `npm run test:live:isolation` (вызывает модели claude и codex); обычные тесты проверяют передаваемые настройки и настоящую изоляцию проверок.

У каждой объявленной роли должен быть свой файл инструкции `.agents/roles/<роль>.md` — на него ссылается порождаемый пакет контекста, и без файла `context-lock` откажет. Выбор binding роли: `repository.roles[role]`, иначе `config.roles[role]`. Выбор reviewer: reviewer выбранного role binding, иначе repository reviewer, иначе общий reviewer. Объект binding заменяется целиком; поля глобального binding не сливаются по одному.

```json
{
  "roles": {
    "frontend": {
      "runtime": "codex",
      "writePaths": ["src/ui/", "tests/ui/"],
      "reviewer": { "runtime": "claude" }
    }
  }
}
```

Это фрагмент **component config**. `model` необязателен: если он отсутствует, выбор остаётся у CLI. `effort` (`low`, `medium`, `high`, `xhigh`) задаёт уровень рассуждения модели роли или ревьюера и передаётся codex как `model_reasoning_effort`; для других runtime поле отклоняется при загрузке. Так дешёвые роли, например тестировщики по готовому сценарию, тратят меньше токенов. Без поля прогон использует значение CLI по умолчанию: пользовательская конфигурация codex в прогонах не читается. `toolProfile` выбирает именованный профиль инструментов. Ревьюер того же вендора (runtime), что исполнитель, по умолчанию отклоняется, и разные model names этого не меняют; разрешить его можно только явно — см. «Правила ревью и вендор ревьюера» ниже.

### Правила ревью и вендор ревьюера

Вендор — runtime DevContour (`codex`, `claude`). Правило вендора ревью:

- `different-vendor` — умолчание: ревьюер другого вендора, чем исполнитель (у плана и контракта — чем автор). Конфигурация, где роль проверяет ревьюер её же runtime без явного разрешения, не загружается.
- `same-vendor-allowed` — явное разрешение ревьюера того же вендора. Это по-прежнему отдельная роль ревьюера: отдельный вызов CLI без сохранения сессии, без истории исполнителя, с той же схемой ответа, теми же правами инструментов и теми же условиями приёмки — gates, сверка worktree после ревью, протокол находок. Разрешение снимает только запрет на совпадение вендора, а не требования к ревью.

Где задаётся:

```json
{
  "review": {
    "code": { "vendor": "same-vendor-allowed" },
    "plan": { "reviewer": { "runtime": "claude" }, "vendor": "same-vendor-allowed" },
    "contract": { "reviewer": { "runtime": "claude" }, "vendor": "same-vendor-allowed" }
  }
}
```

- `review.code.vendor` — правило ревью кода для всех ролей; `review.code.reviewer` — reviewer ревью кода по умолчанию вместо общего `reviewer`.
- `reviewVendor` роли (в `roles` workspace или компонента) — правило ревью кода этой роли; оно сильнее `review.code.vendor`. Роль без своего `reviewer` относит правило к ревьюеру, которого получила бы (компонента или общему).
- `review.plan` и `review.contract` — ревьюер и правило технического ревью плана и контракта. Без своего ревьюера выбирается живой runtime другого вендора, чем автор (упорядоченный список `codex`, `claude`); с ревьюером — он, и при совпадении с автором нужно `same-vendor-allowed`, иначе ревью отказывает до вызова модели.

`review` — объявление workspace, как `toolProfiles`: его задаёт `workspace.json`, и `workspace-init --file` переносит его в `config.json` (`declaration-updated`), до записи проверив тем же загрузчиком, что и сервер. Неизвестное правило или ревьюер того же вендора без разрешения отклоняются, `config.json` остаётся прежним. Реестр без поля `review` правилами не управляет: выбор, уже записанный в `config.json`, сохраняется. Виды переносятся по отдельности: реестр, объявивший только `code`, заменяет `review.code`, а `plan` и `contract` из `config.json` остаются. Объявленный вид только переопределяет выбор в `config.json` и не удаляет его: чтобы снять вручную заданное `same-vendor-allowed`, объявите для этого вида `"vendor": "different-vendor"` явно. Изменение `review`, ролей, верхнеуровневого `reviewer`, gates и других полей политики исполнения меняет её digest. Утверждение плана закрепляет digest ([D43](decisions.md#d43-утверждение-плана-закрепляет-политику-исполнения)), поэтому задачи утверждённых планов не выдаются, а прогресс называет `approval_stale`, пока `review-plan --board ID` не утвердит план заново. `reviewVendor` роли задаётся там же, где роль, — в `roles` реестра или в файле компонента.

Как это видно:

- `doctor`, строка `role:<компонент>:<роль>`: `writer <runtime> → reviewer <runtime>; правило вендора: <правило>`, при совпадении — с пометкой «(ревью тем же вендором)»; совпадение без разрешения — `blocked`.
- `doctor`, строки `review:plan` и `review:contract`: кто проверит автора `codex` и автора `claude`, с пометкой «(тот же вендор)» или «отказ правила вендора».
- Панель: в карточке задачи у ревьюера того же вендора — «· тот же вендор», у ревью плана в живой работе — «(тот же вендор)».

Меняя ревьюеров на claude, проверьте строку `reviewer:<компонент>:<роль>`: без профиля инструментов claude-ревьюер только читает (см. выше).

`gates` задачи задают её **область доказательства** — подмножество проверок профиля компонента, которым эта задача доказывает себя. Прогон требует именно его. Полный набор остаётся обязательным для приёмки доски. Gate текущего профиля компонента, который не прошёл integration ни в одной задаче доски, приёмка (`accept`, стадия 2 workflow) выполняет один раз на итоговом integration SHA доски тем же исполнением, что integration задач, и принимает доску, только если он прошёл; провал называет gate. Такой пробел виден заранее: `review-plan` и `workflow_start` возвращают `coverageGaps` и `warning` по постановкам задач. Считается только собственное evidence задачи на её принятом SHA — evidence проверки потребителя не в счёт, — и для любой области: задача без явной области выполнялась профилем своего времени, и gate, добавленный в профиль позже, ею не покрыт. Область обязана включать хотя бы один gate с `kind: test`: проверки типов и стиля проходят и на нереализованном коде. Требование задачи может ссылаться только на gate внутри её области. Без объявленной области задача доказывает себя всем профилем, как раньше.

Повторяющийся набор объявляется один раз именованной группой компонента — `gateGroups: { "regression": ["typecheck", "@core"], "core": ["unit", "engine"] }` (в конфигурации компонента или workspace для единственного компонента) — и подключается к задаче ссылкой `"@regression"`. Группа раскрывается в явный список, записанный в попытке при выдаче: вложенные группы допустимы (общая подгруппа раскрывается один раз), цикл, неизвестная группа и gate вне профиля отклоняются; групп у компонента — не больше 100. Предел 20 относится к ссылкам задачи. Область проверок задачи (`gates` и `consumers`) закрепляется утверждением отдельно от digest постановки (`approvedScope`): правка области во время ревью плана делает одобрение устаревшим, правка после утверждения останавливает выдачу, а квитанция несёт утверждённую область, и импорт отклоняет расхождение. Утверждения до появления этого поля остаются действительными без него. Квитанция сверяется с раскрытием области в импортирующем клоне: если оно требует gate, которого квитанция не проверяла (квитанция урезана или группы клонов разошлись), квитанция отклоняется. Ничего не подключается неявно: ни gates зависимостей компонентов, ни весь профиль. Определение групп входит в договор исполнения: изменённая группа делает прежние попытки устаревшими.

`consumers` задачи — явная область **проверок потребителей**: `[{ "repositoryId": "product", "gates": ["@regression"] }]`; один потребитель называется один раз. Потребитель обязан зависеть от компонента задачи (`dependsOn`, прямо или транзитивно); его gates раскрываются в его профиле и включают test gate. На integration каждый потребитель проверяется в собственном рабочем дереве на голове своей целевой ветки по своему договору окружения (`lifecycle`, `prepare`, gates, cleanup). Компонент задачи подставлен в снимок зависимостей потребителя её интегрированным результатом до сборки: промежуточные зависимости собираются уже против него. Прочие зависимости потребителя — снимок их целевых веток. Рабочие деревья проверки убираются и при отказе; отказ очистки не скрывается. Завершение требует PASS каждой проверки потребителя; его evidence несёт `consumer` и не закрывает ни собственные gates задачи, ни её критерии, ни покрытие профиля. Ресурсы выбранных gates потребителя резервируются вместе с ресурсами задачи на всю попытку. Если очистка окружения потребителя (`lifecycle.teardown`) не завершилась, его рабочие деревья сохраняются как контекст повторной очистки, а отказ называет `environment.json`; отказ удаления деревьев приводится вместе с отказом самой проверки. Что проверено — голова потребителя, снимок всех его зависимостей и свежесть каждого фактического входа (прочих зависимостей и самого потребителя) на момент окончания проверки — записывается в попытку и квитанцию; завершение без этой записи невозможно, а решающий PASS потребителя в квитанции должен быть получен под версией проверок попытки; импорт сверяет состав снимка с зависимостями потребителя и то, что компонент задачи в нём — принятый результат. Политика потребителей (их gates, группы, окружение) входит в договор попытки задачи: её смена делает прежнюю попытку устаревшей. Без объявления потребители не проверяются на уровне задачи — только совместной проверкой workspace. Выбранная область gates (задачи и каждого потребителя) замкнута по `dependsOn`: предпосылку выбранного gate нужно добавить явно, иначе постановка отклоняется. Завершение отклоняется до публикации, если квитанция не уместилась бы в предел переносимой записи (2 MiB); тогда сократите `dependencyArtifacts` или область проверок.

Перед завершением задачи снимок её зависимостей сверяется с головой целевой ветки каждой зависимости, и результат фиксируется в попытке (`dependencyFreshness`) и квитанции: SHA снимка, голова ветки, совпадение. Сдвиг не отклоняет результат — параллельная работа законно двигает ветки зависимостей; реальное сочетание версий проверяет совместная проверка workspace по закреплённому манифесту, а метрики называют результаты, проверенные на устаревшем снимке. Снимок зависимостей (компонент, SHA, tree, голова, digest артефактов) и проверки потребителей переносятся в квитанцию; импорт сверяет состав снимка с зависимостями компонента. Квитанция без поля `dependencies` — прежнего формата: её снимок неизвестен и не проверяется.

Это нужно параллельной декомпозиции: когда несколько задач делят один общий набор проверок, зелёный gate не различает, чьи ожидания закрыты, и задача может не закрыть ни одного. С областью у каждой задачи свой файл приёмки и свой test gate: тесты настоящие, а не пропущенные, и красный gate блокирует только свою задачу.

Область доказательства задачи (`gates`) определяет, какие проверки её прогон выполняет и по каким требует PASS. Полный набор профиля остаётся обязательным при приёмке доски (см. выше): требовать его от каждой задачи значит, что ни одна не пройдёт, пока не сделаны все соседние — красный gate соседа ложился бы на того, кто к нему не притрагивался.

Роль без `writePaths` не ограничивает ничего: область записи — пересечение роли и задачи, и когда её задаёт только задача, всё держится на том, что она указана в каждой. Роль, владеющая сквозными решениями, оказывается при этом самой широкой. `doctor` называет роли, у которых границы нет.

`writePaths` задачи и роли задают допустимые пути/префиксы; разрешённая область — их пересечение, если заданы оба. Это не glob: `src/ui/` подходит, `src/**/*.tsx` — нет. Protected paths, исходники context packs и generatedPaths исключаются дополнительно. Такой контроль проверяет принимаемый diff, не является OS sandbox.

## Gates

```json
{
  "gates": [
    { "id": "types", "kind": "check", "command": ["npm", "run", "typecheck"] },
    {
      "id": "tests",
      "kind": "test",
      "dependsOn": ["types"],
      "command": ["npm", "run", "test:devcontour"],
      "timeoutMs": 240000,
      "report": { "type": "junit", "path": ".reports/junit.xml" }
    }
  ]
}
```

| Поле          | Правило                                                                                 |
| ------------- | --------------------------------------------------------------------------------------- |
| `id`          | Уникален внутри набора gates                                                            |
| `kind`        | `check` — команда проверки; `test` — тест с обязательным JUnit                          |
| `command`     | Непустой массив executable/argv; переменные и `&&` не раскрываются shell автоматически  |
| `dependsOn`   | IDs внутри этого набора; циклы и неизвестные IDs запрещены                              |
| `cwd`         | Относительный каталог внутри worktree; default — корень                                 |
| `timeoutMs`   | Default 120000; deadline этой команды                                                   |
| `report.path` | Путь относительно **корня worktree**, независимо от cwd; отчёт предварительно удаляется |
| `resources`   | IDs объявленных host resources                                                          |
| `property`    | Генеративная проверка: `{}`; путь отчёта выбирает контур, см. ниже                      |

В каждом локальном наборе нужен test gate. Workspace gate дополнительно имеет `repositoryId` и `artifacts`: файлы, хеши которых сохраняются как часть доказательства. Их пути также относительны корню компонента. Совместная конфигурация должна покрывать интеграционным test gate каждый продукт.

### Генеративная проверка

Test gate с `property` проверяет обещание, а не отдельные примеры: эталон (например, полный перебор на малых входах), генератор входов, свойства и уменьшение входа живут в проекте, а контур задаёт seed, читает отчёт и хранит его как доказательство. Эталонный harness без зависимостей — `packs/property/harness.mjs` в установке DevContour: скопируйте его в проект и опишите свойства. Эталон и генератор объявляйте нормативными `artifacts` контракта: тогда они закреплены ревизией, исполнитель их не меняет, а evidence ссылается на их blob.

Контур передаёт `DEVCONTOUR_SEED` — свой для каждой попытки, фазы и gate, но записанный заранее, — и `DEVCONTOUR_PROPERTY_REPORT`: путь отчёта в собственном временном каталоге контура вне worktree (поле `property.path` принимается для совместимости и не используется). Проверка пишет внутрь этого каталога, но в песочнице ОС не может заменить сам каталог ссылкой наружу; файл читается только как обычный, без следования за symlink. При `isolation: none` этой защиты нет — как и любой другой: команда без песочницы и так читает файлы пользователя. Отчёт (`version: 1`, `properties: [{ testId, status, cases, current?, counterexample? }]`, до 64 КБ, после redaction) читается при любом исходе: при провале в нём исходный и уменьшенный контрпример с ожидаемым и фактическим ответом, при таймауте — вход, на котором проверка шла (`status: running`, `current`). Команда без отчёта или с нарушенным свойством не проходит даже с кодом выхода 0. Evidence сохраняет seed, команду повтора `DEVCONTOUR_SEED=<seed> <command>`, отчёт, digest контрактов задачи и blob закреплённых артефактов; итог gate называет контрпример, и следующая попытка видит его. `testId` свойства стабилен и совпадает с testcase JUnit: связь критерия с проверкой не меняется от запуска к запуску. Малые входы не доказывают производительность на больших — для неё отдельные семейства входов и пределы.

Задача с объявленными свойствами договора проверки получает закреплённый манифест: контур передаёт `DEVCONTOUR_PROPERTIES` (селектор свойств задачи), при принятом корпусе — `DEVCONTOUR_CORPUS` (файл только для чтения вне worktree) и сверяет отчёт с манифестом: непустота, отсутствие повторов, минимальные выборки по свойствам и семействам (`families`), свидетельство выполнения корпуса (`corpus.witness`), совпадение со testcases JUnit. Режим одного случая (`DEVCONTOUR_CASE`, `DEVCONTOUR_CASE_RESULT`) нужен контуру для подтверждения примера эталоном. Harness с нулевой выборкой сам отказывает. Подробно — [договор проверки](check-contracts.md).

`contractArtifacts` задаёт раздельные пределы закрепления нормативных артефактов: `maxFileBytes` (16 МБ), `maxTotalBytes` (64 МБ) и `reviewTextBytes` (400000) — текст, выдаваемый ревьюеру. Полный файл закрепляется по sha256 точных байтов; ревьюер получает манифест, статистику и выборку, помеченную как выборка. `maxFileBytes` не может превышать `maxTotalBytes`.

Граф задаёт порядок, а не параллельный запуск gates: текущий runner выполняет их последовательно в топологическом порядке. Без dependsOn сохраняется порядок массива. Все локальные gates повторяются для candidate и integration SHA.

`prepare` — команды подготовки до реализации/проверок, `preflight` — probes doctor, `dependencyBuild` — сборка закреплённых входных библиотек. Их step имеет `id`, `command`, `timeoutMs` (default 120000, максимум 3600000). Не маркируйте установку зависимостей как выполненный тест.

## Окружение и lifecycle

```json
{
  "environment": {
    "inherit": ["NODE_EXTRA_CA_CERTS"],
    "values": { "APP_ENV": "test" },
    "secrets": { "NPM_TOKEN": "PRIVATE_REGISTRY_READ_TOKEN" }
  },
  "lifecycle": {
    "setup": [{ "id": "start", "command": ["node", "scripts/test-env.mjs", "start"] }],
    "ready": [{ "id": "ready", "command": ["node", "scripts/test-env.mjs", "ready"] }],
    "teardown": [{ "id": "stop", "command": ["node", "scripts/test-env.mjs", "stop"] }]
  }
}
```

Базовые PATH/HOME/TMPDIR/CI дополняются явно перечисленными переменными. `secrets` хранит отображение целевого имени в имя переменной процесса; значений секретов в JSON нет. Отсутствие заявленного inherit/secret — ошибка. DEVCONTOUR_* зарезервированы. Tool profile может дополнить среду вызова runtime; настройки агента в открытом диалоге не копируются в worker автоматически.

Lifecycle требует хотя бы один teardown step; setup/ready могут быть пустыми. Команды start должны завершаться после запуска управляемого сервиса, а не оставаться бесконечным foreground-процессом. Teardown должен быть повторяемым и безопасным после частичного setup. Для общей проверки используется `workspaceLifecycle`.

Подробные примеры MCP, приватных зависимостей и Postgres — в [интеграции](project-integration.md). Установка сервиса, миграции, seed и проверка готовности реализуются проектными скриптами, а не автоматически из имени поля.

## Context, profiles и forge

`contextPacks`: `id`, `version`, `repositoryId`, `roles`, `files`, затем закреплённые `revision` и `digest`. Пустые roles означают только явное включение через Task.contextPacks. `context-lock` читает коммиты, не незакоммиченные файлы. [Подробности](engineering-context.md).

`toolProfiles` описывает runtime, environment, MCP servers и capability settings. Claude: `claudeTools`/`claudeAllowedTools`; Codex: `codexShell`/`codexNetwork`. MCP transport — stdio с command/args/env либо http с url/bearerTokenEnv; `tools` — явный allowlist. Имена инструментов сверяются с конкретным сервером. Встроенный reviewer остаётся read-only; права серверов MCP тоже должны быть ограничены.

`forgeConnections` — общие подключения `gitlab | github | command`. `repository.forge` — connection, project, remote, удалённая targetBranch и requiredChecks. Не путайте её с локальной `repository.targetBranch: devcontour/accepted`. Настройка `completionMode: remote` требует полного рабочего пути проверки Delivery; одного URL GitLab недостаточно.

## Безопасное изменение политики

Зафиксируйте причину, выполните паузу/остановку и сохраните прежнюю конфигурацию. Адаптируйте локальные файлы правил и Git-коммит, затем context-lock при необходимости. После проверки config/doctor перезапустите сервер. Попытки и Verification связаны с policy digest: старый PASS нельзя переиспользовать для изменённого договора только потому, что код остался прежним.

При обновлении профиля сравниваются версия и digest всего состава с extends. В config.packs локальный профиль имеет source с repositoryId/path; lock различает одинаковые ID разных владельцев. Подключение и явное обновление описаны в [профилях](mcp-and-profiles.md). Defaults копируются при bootstrap; загрузка проверяет lock и не применяет их заново. В MVP нет автоматических миграций stack profiles и разрешения конфликтов capabilities. Изменения существующей принятой истории через новую конфигурацию не выполняются.

## Память и тарифные оценки

`memoryPolicy.maxBytes` ограничивает дополнительную выдачу [проектной памяти](project-memory.md): 0–24000 UTF-8 bytes, default 8000. Значение 0 отключает её в новых попытках. Полные требования и context packs передаются отдельно. Изменение этой настройки меняет execution policy; выполняйте его после остановки активной работы.

`prices` — необязательный список тарифов за миллион токенов (не текущие цены поставщиков). Ниже исключительно учебные значения:

```json
{
  "memoryPolicy": { "maxBytes": 8000 },
  "prices": [
    {
      "runtime": "codex",
      "model": "EXAMPLE_MODEL",
      "effectiveAt": "2026-01-01T00:00:00Z",
      "input": 1,
      "output": 4,
      "cacheRead": 0.1,
      "cacheWrite": 1
    }
  ]
}
```

Выбирается последний effectiveAt не позже начала вызова для точного runtime/model. Не задавайте две записи с одинаковыми runtime/model/effectiveAt. Если model не указан явно или счётчиков недостаточно, оценка недоступна. Новая таблица не пересчитывает старые вызовы: применённый тариф сохранён в каждом измерении. Сама таблица предела не устанавливает: его задаёт `budgets`. Не требуется настраивать цены для обычной работы.

## Бюджеты

`budgets` — необязательные пределы расходов (`usd`) и суммарного времени (`timeMs`) вызовов моделей на задачу, доску и workspace; у каждого предела хотя бы одно поле:

```json
{
  "budgets": {
    "task": { "usd": 5 },
    "board": { "usd": 40, "timeMs": 14400000 },
    "workspace": { "usd": 200 },
    "onUnknown": "stop"
  }
}
```

Расход считается по сохранённым записям вызовов (раздел «Расходы вызовов» в [метриках](metrics.md)), а не по счётчикам попыток: `retry --reset`, возврат попытки после отказа окружения, переход этапа ведущего и перезапуск процесса его не уменьшают. В расход входят ошибочные вызовы, идущие и прерванные падением процесса. Запись вызова закрепляет задачу и доску на момент вызова. Область задачи — вызовы её попыток, вызовы о ней и вызовы о её доске целиком (ревью плана, восстановление доски): долевой атрибуции нет, вызов о доске не считается для задачи нулевым. Доска — вызовы, закреплённые за ней при вызове: перенос задачи на другую доску расход не переносит, а сама задача остаётся и под бюджетом прежней доски. Вызов о доске закрепляет её открытые на тот момент задачи. Записям с неполной атрибуцией недостающее дозаполняется по текущему графу до того, как синхронизация или планировщик его изменят: вызову о задаче — задача и доска, вызову о доске — все задачи доски; уже закреплённое не меняется. Время прерванного вызова фиксируется при восстановлении по монотонным часам. Workspace — все вызовы. Сообщённая провайдером и оценённая по тарифу суммы складываются в предел, но показываются отдельно. Учёт локален: записи вызовов не переносятся между клонами; `storage-migrate` переносит записи компонентов в их базы вместе с состоянием.

Стоимость известна, если её сообщил провайдер (в том числе 0, при ошибке или прерывании вызова) или она оценена по тарифу у завершённого вызова; оценка прерванного вызова — лишь нижняя граница, и его стоимость неизвестна. Оценка строится только по полным счётчикам и по модели, которую сообщил runtime: запрошенная модель тариф не подтверждает. Runtime, который модель не сообщает, оставляет стоимость неизвестной — для него задайте `onUnknown: "continue"` или бюджет времени.

Денежный бюджет **не определён**, если в области есть завершённый вызов с неизвестной стоимостью или попытка, выданная до появления учёта вызовов, в которой модель вызывалась (есть кандидат или замер реализации), а записи реализации нет; посторонние и более поздние вызовы этот пробел не закрывают. У попытки, выданной с учётом, отсутствие записи значит, что вызова не было (например, отказ бюджета до вызова). Бюджет времени не определён, если у вызова неизвестно время: время измеряется монотонными часами процесса, а у прежних записей с противоречивыми метками (часы переведены назад) считается неизвестным, а не нулевым. `onUnknown: "stop"` (по умолчанию) останавливает выдачу и вызовы в неопределённой области; `"continue"` продолжает по нижней границе — известной сумме, — и обзор показывает, что остаток не определён. Повышение предела неопределённость не снимает. Идущий вызов с подтверждённо живым владельцем бюджет неопределённым не делает: он начат в пределах бюджета, и иначе любой идущий вызов останавливал бы параллельную работу области. Живой владелец подтверждается по pid и точному совпадению момента старта процесса по данным ОС: pid, доставшийся другому процессу, владельцем не считается. Вызов умершего процесса, неподтверждённого владельца или старше двух `runTimeoutMs` неизвестен сразу, не дожидаясь восстановления. Время идущего вызова считается по монотонным часам: своего — по часам процесса, чужого — по монотонным часам ОС, общим для процессов машины в пределах одной загрузки (запись хранит идентификатор загрузки; часы другой загрузки не сравниваются), поэтому перевод системных часов его не уменьшает. Без сравнимых монотонных часов (ОС не сообщает загрузку или она другая) время чужого идущего вызова неизвестно, и бюджет времени при `stop` не определён; его сохранённый монотонный замер всё равно входит в расход как нижняя граница, поэтому исчерпание по известной части видно и при `continue`. Прерванный вызов, время которого при восстановлении нельзя измерить монотонно, сохраняет неизвестное время.

Бюджет проверяется перед выдачей попытки и перед каждым вызовом модели; проверка и регистрация идущего вызова — одна транзакция записи. Вызов о доске проверяется и по бюджетам её открытых задач. Превышенный или (при `stop`) неопределённый бюджет — отказ класса `budget` с причиной: какой бюджет, сколько сообщено и оценено, сколько вызовов с неизвестной стоимостью и попыток без учёта, сколько времени. Уже идущие вызовы не прерываются, поэтому итог может превысить предел на столько вызовов, сколько шло одновременно. Задача, которую бюджет не пускает к выдаче, несёт причину (`budgetBlock`) в цепочке ожидания; поднять предел можно только изменением конфигурации, и выдача возобновится сама; выключение `budgets` снимает удержание. Вызовы без данных остаются неизвестными: точная стоимость прошлого не выдумывается. Внутренние оценочные прогоны контрактов и инженерных сценариев считают только число вызовов и в бюджеты не входят. Итоги считаются по полной истории вызовов при каждой проверке: при очень длинной истории проверка заметно дороже; без `budgets` история не читается, а поиск прерванных вызовов идёт не чаще раза в минуту.
