# Профили стеков, модели и MCP

Здесь описаны внешние инструменты, которые используют исполнители. Собственный MCP-сервер DevContour для управления графом и контекстом описан отдельно: [MCP и skill](mcp-server.md). Это разные стороны интеграции: DevContour предоставляет задачи ведущему агенту и подключает выбранные инструменты к рабочим runtime.

DevContour разделяет четыре выбора: стек продукта, роль исполнителя, runtime/модель и доступные инструменты. Их не стоит объединять в один «универсальный профиль»: backend на Go и frontend на React могут использовать одинаковый runtime, но разные инструкции, команды и ресурсы.

## Выбор стека

| Профиль            | Когда полезен                                                                                   | Что нужно решить в проекте                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `react-vite-admin` | Админка или внутренний интерактивный интерфейс                                                  | Авторизация, маршруты, данные, компоненты, доступность и реальные E2E             |
| `next-product`     | Публичный продукт с требованиями к серверному/статическому рендерингу и контенту                | Какие страницы статические, какие динамические; кеширование, metadata, deployment |
| `go-api`           | Сервис с требованиями к предсказуемому исполнению, конкурентной обработке и простому deployment | API, БД, границы, наблюдаемость и измеримые требования нагрузки                   |
| `mobile-maestro`   | Мобильное приложение с проверкой пользовательских flows на устройстве                           | Сборка текущего SHA, устройство, установка, seed/авторизация, отчёты и cleanup    |

Профиль — стартовая политика команд, а не генератор законченного продукта. Имена profiles не заменяют анализ: публичный сайт может быть статическим, а производительность API может ограничиваться SQL и сетью независимо от языка. Для существующего проекта сначала учитывайте его соглашения и стоимость перехода.

Встроенные профили — готовые примеры. `setup` и `init` принимают также `--profile ./profiles/service.json` из репозитория продукта; `workspace-init` читает такое же поле `profile` отдельно у каждого компонента. Добавление стека не требует изменения исходников DevContour. Роли, AI-runtime и разрешения инструментов задаются отдельно.

Дополнительные стартовые наборы:

| Профиль        | Что включает                                             | Что готовит агент                                                                                                                                               |
| -------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `python-api`   | `uv sync --locked`, Ruff и pytest с JUnit                | Закреплённые зависимости в pyproject.toml/uv.lock, Python, реальные API/DB-тесты. Для другого менеджера или проверок — локальный профиль.                       |
| `nest-api`     | `node-checks`, сборка, отдельные integration-тесты       | Scripts typecheck, build, test:devcontour и test:devcontour:integration; JUnit в `.reports/junit.xml` и `.reports/integration.xml`, тестовое окружение сервиса. |
| `react-native` | `node-checks` и `mobile-maestro`                         | Unit-тесты, сборка и установка текущего SHA, устройство, mobile flows и cleanup.                                                                                |
| `expo-mobile`  | `react-native` с метаданными Expo и защитой конфигурации | Совместимые с SDK зависимости, фактический способ сборки/установки и проверки приложения.                                                                       |

`node-checks` содержит npm ci, typecheck и test:devcontour; это переиспользуемая часть, а не полноценная приёмка любого продукта. Для прежних Node-профилей дополнительно нужен build. Scripts должны выдавать реальные отчёты, а не заглушки. Для Go требуется согласованная версия runner, формирующего JUnit. Maestro задаёт способ E2E-проверки и сочетается с React Native/Expo. `mobile:devcontour:prepare` обязан установить проверяемую сборку; наличие Expo Go или старой сборки не подтверждает текущий SHA. Автоматического EAS build, публикации и управления устройствами профиль не добавляет.

## Собственный профиль и составные части

Агент сначала изучает существующий стек, lock-файлы и команды. Если встроенный набор не подходит, он создаёт JSON-файлы внутри компонента. Следующий пример состоит из трёх независимых частей; все четыре файла сохраняются в Git.

`profiles/service.json` — состав:

```json
{
  "id": "team-service",
  "version": "1.0.0",
  "extends": ["./stack.json", "./checks.json", "./environment.json"]
}
```

`profiles/stack.json` — соглашения стека:

```json
{
  "id": "python-stack",
  "version": "1.0.0",
  "capabilities": ["python", "api"],
  "protectedPaths": ["pyproject.toml", "uv.lock", "scripts/verify.py"]
}
```

`profiles/checks.json` — воспроизводимые команды проекта:

```json
{
  "id": "service-checks",
  "version": "1.0.0",
  "gates": [
    { "id": "install", "kind": "check", "command": ["uv", "sync", "--locked"] },
    {
      "id": "tests",
      "kind": "test",
      "dependsOn": ["install"],
      "command": ["uv", "run", "--no-sync", "pytest", "--junitxml=.reports/junit.xml"],
      "report": { "type": "junit", "path": ".reports/junit.xml" }
    }
  ]
}
```

`profiles/environment.json` — окружение без значений секретов:

```json
{
  "id": "service-environment",
  "version": "1.0.0",
  "environment": {
    "values": { "APP_ENV": "test" },
    "secrets": { "DATABASE_URL": "TEST_DATABASE_URL" }
  }
}
```

TEST_DATABASE_URL должна существовать в окружении запуска. Настройка не создаёт БД; подготовку/готовность/очистку можно описать через lifecycle в этой же части. Этот пример показывает формат, а не готовую конфигурацию конкретного сервиса.

```sh
devcontour profile-show --repository /absolute/product --profile ./profiles/service.json
devcontour setup --repository /absolute/product --workspace /absolute/workspace --profile ./profiles/service.json
```

profile-show читает файлы, проверяет состав и возвращает resolved, metadata и pin. Команды проекта не выполняются; workspace и установленная конфигурация для просмотра не нужны. Для компонента с другим ID добавьте `--repository-id library`. Установка выполняется обычным setup/init/workspace-init; отдельного MCP bootstrap нет.

Правила объединения:

- `extends` принимает встроенные IDs и относительные пути от файла, который их объявил. Корневой CLI-путь отсчитывается от `--repository`, путь в registry — от репозитория соответствующего компонента. Абсолютные пути, URL, выход из владельца и symlinks отклоняются.
- Части обходятся в порядке extends, затем добавляется собственное содержимое. Повторная ссылка на один файл учитывается один раз; циклы запрещены. Итоговые gates исполняются с учётом dependsOn. Повтор gate ID или prepare step ID — ошибка, скрытого замещения команд нет.
- capabilities, protectedPaths и generatedPaths объединяются. prepare складывается по порядку. Все локальные файлы состава автоматически добавляются в защищённые пути. capabilities — описательные метки, а не выданные права.
- environment и lifecycle каждый могут быть определены только одной частью; неоднозначное объединение отклоняется. Lifecycle содержит setup/ready/teardown по обычной схеме. concurrency берётся как наименьший указанный предел, 1–4.
- Самостоятельная часть может не иметь тестов. Готовый состав требует test gate с JUnit, допустимые пути и корректный граф проверок. Профиль не может задавать approvalMode, отключать review или выдавать разрешения AI-инструментам.
- Лимиты: 32 файла, глубина extends до 16 переходов, 128 KiB на файл, до 16 родителей и 100 gates на часть. Формат JSON; version имеет вид `1.2.3` или `1.2.3-beta.1`.

Для изменения существующих команд подготовьте собственные части с нужными IDs, вместо наследования несовместимого набора. Явные gates/environment/lifecycle/prepare в registry остаются настройкой компонента поверх defaults профиля. Файлы состава остаются защищёнными и при заданном protectedPaths. Ресурсы, preflight и связи библиотек задаются обычной конфигурацией проекта.

## Фиксация версии и обновление

`packs.lock.json` закрепляет версию и digest всего состава, включая содержимое наследуемых файлов. Конфигурация хранит ссылку `{repositoryId, path}` локального профиля; одинаковые ID в разных компонентах не конфликтуют. Абсолютный путь машины в digest не входит. Переносимые исходники профиля остаются в Git владельца; локальные config/lock подготавливаются для новой машины отдельно.

Изменение любой части, её версии или даже форматирования обнаруживается при следующей загрузке конфигурации. Старые встроенные профили без extends сохраняют прежний digest и не требуют миграции. Setup повторно сохраняет пользовательскую политику; он не обновляет команды автоматически и отклоняет замену выбранного профиля.

Обновление выполняет ведущий агент: останавливает serve и активные операции, сравнивает старую политику и новый profile-show, меняет настройки компонента и metadata/pin соответствующей записи config/lock, обновляет локальную копию корневого manifest в `<data>/profiles/`, если она существует. После этого проверяет загрузку, doctor, реальные команды и коммитит исходники профиля. Если поменялось условие принятой работы, использует обычную корректировку и новую проверку. Изменение одного lock не применяет новые defaults к рабочей конфигурации.

Тестовый Python-сценарий DevContour подтверждает выполнение произвольных команд через обычную приёмку. Готовые профили проверены как настройки; работоспособность конкретного Python/Nest/Expo-продукта подтверждается его собственным сквозным пилотом, а не именем профиля.

## Runtime и независимая проверка

Роль выбирает `codex` или `claude`, необязательную `model`, tool profile и при необходимости собственного reviewer. Demo разрешён только в учебном режиме. По умолчанию setup назначает Claude для реализации и Codex для ревью.

Фрагмент component config:

```json
{
  "roles": {
    "frontend": {
      "runtime": "codex",
      "reviewer": { "runtime": "claude" }
    }
  }
}
```

Можно добавить проверенный в вашей среде model ID в binding исполнителя и reviewer. Если поле отсутствует, используется выбор CLI. Не храните придуманные model IDs как рабочий default. В local mode reviewer обязан иметь другой runtime; два названия модели одного runtime не удовлетворяют проверке.

DevContour вызывает установленные CLI. Авторизация, доступные модели, тарифы и совместимость альтернативного провайдера находятся на стороне runtime. Подписка на веб-приложение сама по себе не является подтверждением доступного CLI/API. Маршрутизатор провайдеров можно подключить штатными средствами CLI, но он не заменяет адаптер DevContour, его формат ответа и политику инструментов.

Универсального переноса диалога/сессии между runtime нет. Общий интерфейс передаёт постановку, инструкции, модель, cwd, разрешённые tools и нормализует результат. Поэтому можно сочетать «Claude реализует, Codex проверяет», не требуя общей внутренней истории двух продуктов.

## Три вида профилей

- Stack profile задаёт начальные capabilities и gates продукта.
- Context pack передаёт согласованные знания и правила роли из Git.
- Tool profile разрешает runtime инструменты/MCP и окружение.

Наличие правила «проверяй приложение в браузере» не устанавливает браузер и MCP. Наличие MCP не создаёт воспроизводимый gate. Все три части готовит ведущий агент, а `doctor` показывает, какие факты действительно проверены.

Tool profile ищется по явно выбранному `toolProfile` либо ключу runtime, для review — ключу с `-review`. Настройки review не должны разрешать изменение кода. Права на стороне MCP сервера должны соответствовать договору: клиентский allowlist полезен, но не заменяет read-only token.

## MCP в worker

В `toolProfiles` задаются transport, адрес/команда, явные tool names и имена env. Конкретные имена инструментов берутся из реального MCP, а не из условного примера. Подключение в чате ведущего агента и доступ subprocess-worker — разные настройки.

Claude получает строгий MCP config и allowlist. Codex при явном profile получает собственную конфигурацию MCP/capabilities, поэтому настройки провайдера и managed policies нужно проверить в используемом CLI. Bypass-permissions DevContour не включает. Отказ runtime остаётся ошибкой задачи.

## Как превращать исследование в gate

MCP помогает изучить UI/устройство и подготовить сценарий. Затем зафиксируйте его как повторяемую команду проверки с наблюдаемыми assertions и отчётом. Например, в целевом Playwright config reporter может использовать:

```ts
reporter: [['junit', { outputFile: process.env.DEVCONTOUR_REPORT_PATH ?? '.reports/junit.xml' }]],
```

Это фрагмент настройки reporter, не полный TypeScript-модуль. `test:devcontour` должен выполнять настоящие тесты, писать отчёт и завершаться ненулевым кодом при сбое. `.reports/` исключается из Git. Runner удаляет прежний отчёт, требует хотя бы один testcase и отклоняет skipped/failure/error.

Для Maestro действуют те же условия: нужная сборка, фактическое устройство, повторяемый flow, отчёт, изоляция ресурсов и cleanup. Интерактивное исследование помогает найти сценарий, но произвольный текст «я проверил» не заменяет evidence.

## Подключение новой среды

1. Настройте runtime и реальные команды проекта.
2. Опишите env/MCP/ресурсы и проверяемый preflight без раскрытия секретов.
3. Выполните doctor и настроенные probes на остановленной очереди.
4. Проведите небольшой live-сценарий до integration/acceptance.
5. Только затем расширяйте очередь и подключайте дополнительные компоненты.

Новый AI-runtime требует адаптера; локальный профиль нового стека его не создаёт. Встроенные manifests обнаруживаются по ID файла, собственные подключаются из компонента. Автоматических миграций, загрузки профилей из сети, менеджера плагинов и федерации controller нет. Общий договор приёмки сохраняется для любого выбранного стека.
