# Установка, сборка и обновление

DevContour поставляется одним npm-архивом: CLI, локальный сервер, собранный UI, профили, шаблоны и документация. Это одна версия совместимых частей. Внутри кода домен, runner, HTTP и интерфейсы агентов разделены по ответственности; отдельные публичные пакеты нужны только тогда, когда у них появятся независимые потребители или цикл обновления.

## Установка из npm

Требуется Node.js 24.3+ и Git. Предварительные версии публикуются в npm с меткой `alpha`:

```bash
npm install --global devcontour@alpha
devcontour help
```

Движок исполнения `devcontour-harness` — обычная зависимость с точной версией (без `^`/`~`, не `peerDependencies`): npm ставит его из registry сам — при установке в проект рядом с DevContour в `node_modules`, при глобальной установке внутри каталога пакета DevContour. Отдельно его ставить не нужно. Установка DevContour не подтягивает другую версию harness: смена версии — новый выпуск DevContour. npm не публикует `package-lock.json`, поэтому при установке из npm или из архива lock checkout не действует: точно закреплена только версия `devcontour-harness`, а опубликованная версия неизменяема — это те же байты, integrity которых при закреплении сверена с проверенным архивом. Остальное дерево — зависимости harness (например, `^`-диапазоны `@anthropic-ai/sandbox-runtime`) и `^`-зависимости самого DevContour — npm разрешает в момент установки.

Публикацию выполняет человек: `npm publish --tag alpha` из чистого checkout выпущенного коммита после `npm ci`; `prepack` собирает пакет. Без `--tag` npm 11 ставит предварительной версии метку `latest`, и `publishConfig.tag` этого не меняет. Поэтому `prepublishOnly` (`scripts/publish-guard.mjs`) отказывает в публикации версии с суффиксом `-…`, если метка не задана или равна `latest`, и подсказывает `npm publish --tag alpha`. Готовый архив (`npm publish ./devcontour-<version>.tgz`) и `--ignore-scripts` эту проверку обходят: npm не запускает для них скрипты пакета, поэтому публикуйте из checkout.

## Установка из проверенного архива

Тот же пакет можно собрать и передать архивом, без registry. В checkout разработчика:

```bash
npm ci
npm pack
```

`prepack` проверяет типы, компилирует Node-код в `lib/` и собирает UI в `dist/`. Полученный `devcontour-<version>.tgz` можно передать коллеге или установить из доверенного внутреннего хранилища:

```bash
npm install --global /absolute/devcontour-<version>.tgz
devcontour help
# Для уже подготовленного workspace:
devcontour start --workspace /absolute/product-workspace --port 0
```

Глобальная установка необязательна. Можно установить архив в отдельный каталог инструментов и вызывать его `node_modules/.bin/devcontour`. Сборщик, TypeScript, `tsx`, тестовые библиотеки и исходники не нужны для запуска. Профили и статические файлы читаются относительно установленного пакета. Текущий каталог процесса не выбирает ни UI, ни продуктовый workspace.

`--port 0` поручает ОС выбрать свободный порт; CLI печатает фактический адрес после старта. По умолчанию сохраняется порт 4317. Два проекта используют разные workspace и серверы. Установка не содержит настройки «активный проект» и не является местом хранения задач.

Команды `npm run devcontour -- ...` в руководствах — форма запуска из исходников. В установленной версии их эквивалент — `devcontour ...`. `--dev` используется только при разработке самого DevContour с установленными dev dependencies; рабочая поставка отдаёт готовый UI.

## Контроль поставки

`npm run test:package` выполняет реальную проверку архива:

1. Собирает и упаковывает текущую версию.
2. Устанавливает архив с `--omit=dev` и отдельным npm cache вне исходного репозитория.
3. Проверяет CLI без `src/` и `tsx`, явный выбор workspace, профили и скрытые файлы правил.
4. Запускает установленный сервер из посторонней папки, получает HTML и JS, читает agent API.
5. Проверяет завершение учебной задачи через настоящий Git workflow из установленного пакета.
6. Регистрирует board workflow через HTTP и ждёт автоматической приёмки сервером; проверяет метрики, отсутствие lease token в ответе и дедупликацию внешнего сигнала, остающегося draft.
7. Запускает установленный evaluator с детерминированным driver без моделей.

Каждый процесс установленного пакета (CLI, MCP, сервер, gates) пишет журнал загруженных модулей и открытых файлов; путь внутри исходного checkout — провал проверки. Файлы DevContour в архиве не содержат путей машины автора, приватных каталогов и ключей. Архив ничего не вкладывает (`node_modules` в нём нет); движок исполнения закреплён точной версией в `package.json`. Проверка сверяет, что установлена именно эта версия с integrity из lock checkout (registry.npmjs.org); остальные зависимости установки npm разрешает сам, как у пользователя.

Выпущенный архив проверяется той же процедурой без сети: `npm run check:install -- ./devcontour-<version>.tgz` (нужен прогретый npm cache с runtime dependencies, включая закреплённый `devcontour-harness`; `npm ci` checkout его прогревает). Архивы DevContour 0.4.0-alpha.29 и старше вкладывают harness в пакет; их проверяют из checkout той же версии, а не из нового.

Смена закреплённого пакета harness проверяется на копии checkout во временном каталоге: `npm run check:upgrade -- ./devcontour-harness-<from>.tgz ./devcontour-harness-<to>.tgz --to-commit <SHA>`. Архивы — локальные копии опубликованных версий (`npm pack devcontour-harness@<версия>`); проверке нужна сеть: закрепление сверяет integrity с registry и ставит пакет оттуда. Архив прежнего движка, вложенный в DevContour до 0.4.0-alpha.29 включительно, берётся из checkout той версии (`git show <commit>:vendor/harness/<архив>`): снимок прежней формы сверяется с ним побайтно. Проверка закрепляет копию тем же `scripts/pin-harness.mjs` и сверяет, что меняются только зависимость, lock и запись `vendor/harness/README.md`, а integrity в lock равна байтам архива; что новая версия не перенимает живую роль controller процесса прежней версии и не продолжает его попытку (после истечения роли — recovery и новая попытка с новым владением), принятые задачи не меняются; что архив DevContour с новой зависимостью проходит smoke; что возврат прежнего lock ставит прежний пакет, а прежняя версия отказывает над состоянием новой до записи и выдачи. Рабочее дерево и реальные workspace проверка не затрагивает. С `--rollback --baseline-commit <SHA>` та же команда проверяет прерванное обновление, откат пакета, восстановление копии и откат DevContour после Git sync (T42) — порядок действий в [обновлении и откате](upgrade.md).

Тест требует доступа к npm registry для обычных runtime dependencies. Он не вызывает модели, не публикует архив и не использует корпоративные сервисы. Временные процессы и каталоги удаляются после проверки. Это проверка установленного продукта, отдельная от unit-тестов исходников.

## Обновление команды

Команда выбирает одну проверенную версию DevContour и фиксирует её в своём каталоге инструментов или инструкции окружения. Перед обновлением завершите активные операции и остановите сервер и другие записывающие клиенты: одной паузы очереди недостаточно для остановки workflow. Подготовьте резервную копию, проверьте Git sync и незакоммиченные изменения компонентов. Не запускайте разные версии runner одновременно над одной базой.

Новая установка не перезаписывает правила существующего продукта: `setup` сохраняет уже созданные файлы. Обновления шаблона переносит ведущий агент осознанным diff с учётом соглашений проекта. Формат пакета, версия agent API и версия состояния — разные договоры совместимости; изменение упаковки не является миграцией продуктовых задач.

При переходе с 0.2 на 0.3 старые Task без `requirements` допустимы, но не получают прослеживаемость автоматически. Новые времена стадий появляются у новых попыток; старые неизвестные значения не восстанавливаются задним числом. `local_workflow` создаётся при первой записи workflow/сигнала. Workflow запускаются только после явной регистрации; обновление пакета само по себе их не создаёт. После переноса новых продуктовых инструкций выполните commit и `context-lock` по обычной процедуре, затем проверьте готовность и запустите сервер.
