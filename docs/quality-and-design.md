# Требования, качество, дизайн и командная память

DevContour проверяет выполнение заданного договора. Качество самого договора — инженерная работа ведущего агента и независимого reviewer. Система не выводит автоматически полное тестовое покрытие из произвольного ТЗ и не доказывает отсутствие любых дефектов.

## Превратить большое ТЗ в проверяемую работу

Сначала выделите пользовательские сценарии, ограничения, существующие интеграции и риски. Отдельно запишите неизвестное: например, семантику пагинации, права администратора или поддержку офлайн-режима. Существенную продуктовую неоднозначность уточняют у оператора; обратимые технические предположения агент принимает и фиксирует сам.

Таблица требований живёт в workspace и связывает смысл с работой. Например:

| Требование            | Критерий                                                               | Задачи/контракт              | Проверка                                            | Результат                                        |
| --------------------- | ---------------------------------------------------------------------- | ---------------------------- | --------------------------------------------------- | ------------------------------------------------ |
| R-01: поиск чатов     | Поиск по названию возвращает ожидаемые чаты; пустой результат объяснён | API-v1, backend и экран      | Контрактные тесты + E2E с seed                      | Ссылка на Verification/evidence после выполнения |
| R-02: блокировка чата | Только разрешённая роль меняет статус, повтор безопасен                | Permission contract, API, UI | 403 для запрещённой роли, success и повтор операции | Заполняется фактическими доказательствами        |

Это документ трассировки, а не второй tracker со своими конкурирующими статусами. Оперативные состояния читаются из SQLite. Не записывайте «проверено» без ссылки на реальное доказательство.

Первый этап должен проходить через нужные слои до наблюдаемого результата: данные → API → интерфейс → тест. Backend/frontend могут быть отдельными задачами внутри среза. Список сотен заранее утверждённых реализационных деталей откладывает проверку основных предположений и повышает стоимость перепланирования.

## Хорошая задача

В постановке нужны: цель и контекст требования, один repositoryId, роль, согласованные входные контракты, dependsOn, допустимые пути изменения и наблюдаемые AC. Размер задачи позволяет закончить её за ограниченное число попыток; одно предложение «разработать всю админку» слишком крупное для управляемого retry.

Слабый AC: «работает правильно, покрыто тестами». Проверяемый AC: «администратор видит 20 первых чатов из seed; поиск по отсутствующему имени показывает empty-state; запрос запрещённой роли возвращает 403 и не меняет данные». Ожидаемый результат берётся из требования/контракта, а не копируется из поведения написанного кода.

Работа вне write scope оформляется отдельной задачей или подготовительным изменением политики. Удобство одной попытки не оправдывает одновременную незаметную правку правил, тестов и всех библиотек.

## Контракт перед параллельной разработкой

Для API опишите запрос/ответ, авторизацию, ошибки, пагинацию, идемпотентность и совместимость там, где это нужно. Для библиотек добавьте примеры вызова, поведение на границах и ожидаемые изменения потребителей. Для UI — состояния, поведение действия и ограничения доступности.

Контракт может быть OpenAPI/JSON Schema, текстом или ссылками на содержимое спецификации, включёнными в согласованное предложение. Приёмку обеспечивает зарегистрированное неизменяемое содержимое Contract, а не плавающая ссылка на «последнюю версию». Важные части договора должны быть доступны worker и reviewer.

При изменении API используйте обратимую последовательность, когда это возможно: добавить совместимый интерфейс, перевести потребителей, затем удалить старый. Не требуйте одновременного мгновенного обновления всех репозиториев, если реальный процесс публикации этого не гарантирует.

## Набор проверок

| Уровень                    | Что проверяет                            | Пример                                                    |
| -------------------------- | ---------------------------------------- | --------------------------------------------------------- |
| Статический check          | Согласованность типов, форматов и сборки | TypeScript, token lint, build                             |
| Unit                       | Правило изолированного модуля            | Расчёт прав, нормализация запроса                         |
| Контрактный                | Соблюдение общего интерфейса             | Ошибки API, сериализация, совместимость SDK               |
| Интеграционный             | Реальные границы с инфраструктурой       | Postgres, миграции, использование собранной библиотеки    |
| E2E                        | Завершённое действие пользователя        | Найти чат, изменить статус, увидеть сохранённое состояние |
| Визуальный / accessibility | Представление и доступность              | Темы, viewport, focus, контраст, состояния                |

Не каждый проект требует одинаковой пирамиды, но каждый обязательный риск должен иметь подходящую проверку. Build не проверяет авторизацию API, screenshot не доказывает запись в БД, unit mock не доказывает совместимость с реальной библиотекой.

Runner требует минимум один test gate с настоящим JUnit; все объявленные gates обязательны. Skipped/error/failure, пустой или отсутствующий отчёт блокируют принятие. После candidate они повторяются для integration SHA, чтобы проверить взаимодействие параллельных изменений.

Тесты должны быть воспроизводимыми: явные входные данные, изолированная среда, стабильные ожидания, управляемые часы/случайность при необходимости, очистка после ошибки. Проверяйте результат действия, а не только факт клика или наличие элемента.

## Независимое ревью

Reviewer проверяет соответствие ТЗ/контракту, безопасность изменения, регрессии потребителей, достаточность тестов и соблюдение локальных правил. Замечание должно содержать конкретное место или условие, последствие и основание. Не нужно генерировать замечания ради количества.

Blocking finding означает, что результат нельзя принять. `approved: true` не отменяет blocking finding. Code review выполняет другой runtime. Review не заменяет машинные gates, а gates не заменяют смысловую проверку. Приёмка доски/ChangeSet использует полученные доказательства; отдельного LLM-review общего JUnit на этом шаге нет.

## Дизайн-процесс

1. **Референсы.** Зафиксируйте локальные изображения/макеты и конкретные свойства: плотность, навигация, типографика, поведение фильтров. Формулировка «сделай красиво как пример» не задаёт проверяемого результата.
2. **Направление.** Опишите аудиторию, главное действие, информационную иерархию, размер экранов, плотность данных и характер интерфейса.
3. **Макет и состояния.** Покажите ключевой сценарий, loading/empty/error/success, validation, disabled, focus, длинные тексты и адаптацию. Прототип проверяет взаимодействие до массовой реализации.
4. **Guidelines и токены.** Закрепите правила компонентов и канонический источник визуальных значений.
5. **Контракт.** Зарегистрируйте согласованную версию поведения/дизайна и привяжите к frontend-задачам.
6. **Реализация и проверка.** Используйте общие примитивы, затем функциональные, визуальные и accessibility-проверки на нужных viewport/темах.

Полезные файлы продукта: `design/references.md`, `direction.md`, макеты, `guidelines.md`, источник tokens. Шаблон процесса находится в `templates/project/design/README.md`; он не поставляет автоматически готовый дизайн продукта.

## Токены и готовые библиотеки UI

Три уровня токенов:

- Primitive: исходная палитра и шкалы размеров.
- Semantic: `surface`, `text-muted`, `action-primary`, `danger`, `focus-ring` — значение по смыслу.
- Component: применение семантики к кнопке, таблице, навигации и их состояниям.

Числовые/цветовые значения определяются в каноническом источнике, а не повторяются в JSX/CSS компонентов. Для DevContour это `src/web/tokens.css`; продукты выбирают собственный технический формат, сохраняя принцип. Любое неизбежное локальное исключение должно иметь понятную причину; копирование случайных hex-цветов такой причиной не является.

Если одновременно используются Mantine и shadcn, задайте общие semantic tokens, темы, spacing/typography, focus и правила слоёв overlays. Определите владельца каждого типа компонента: например, одна таблица и одна модель form validation. Дублирование одинаковых примитивов создаёт разное поведение клавиатуры, темы и ошибок. Это решается договором и адаптацией, а не присутствием двух зависимостей в package.json.

## MCP, браузер и мобильное устройство

MCP полезен для исследования интерфейса, дерева доступности, состояния устройства и подготовки сценария. Повторяемую приёмку удобно закреплять CLI-командой с отчётом: её можно повторить на том же SHA и включить в gate. Наличие MCP в чате ведущего агента не означает его доступность внутри worker.

Для мобильного сценария с Maestro подготовьте проверяемую сборку именно текущего кода, устройство из discovery, устойчивые selectors/test IDs, seed/авторизацию тестового аккаунта, flows и JUnit. Ресурс устройства должен быть объявлен и зарезервирован; команды MCP и тестового драйвера не должны одновременно управлять им.

Проверяйте конечный эффект на устройстве и при необходимости в backend. Очистка обязательна после успеха, ошибки и отмены. Если нет устройства, доступа или нужной сборки, сценарий не выполнен. Mobile profile и Markdown-инструкция не являются свидетельством мобильного теста.

## Устойчивая командная память

Локальная память хранится в компоненте; общие архитектурные решения — в workspace. Рекомендуемые записи:

- ADR: контекст, решение, альтернативы, последствия, статус, автор/ответственный и дата проверки.
- Паспорт сервиса/библиотеки: ответственность, публичные интерфейсы, инварианты, зависимости и расположение тестов.
- Lesson: симптом → подтверждённая причина → исправление → условия применимости.
- Handoff сессии: цель, точные версии, что сделано/не принято, проверки, блокер и следующий шаг.

Knowledge проходит путь `proposed → validated → superseded`, когда есть основания. Это соглашение документации команды; отдельного автоматического knowledge workflow в SQLite MVP нет. Источник, версия и проверка позволяют отличить устойчивое правило от догадки прошлой сессии.

Импорт знаний другого проекта копирует выбранные committed-файлы с digest и source SHA. Эти материалы не запускаются как инструкции автоматически. Ведущий агент проверяет применимость и переносит подтверждённое знание в правильный компонент, затем обновляет context pack.

Находки вне задачи становятся draft discoveries с местом, наблюдением, последствиями и способом воспроизведения. Они не получают автоматический приоритет или validated. Ведущий агент воспроизводит находку, добавляет в подходящий этап и проводит обычное утверждение. Так память остаётся компактной, а работы — в единственном tracker.
