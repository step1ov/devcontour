# Продуктовое намерение и полнота релиза

`INTENT.md` связывает цель продукта, пользовательские истории и проверяемые требования. Он помогает обнаружить работу, которая вообще не попала в граф задач: выполнение всех созданных задач ещё не доказывает полноту порученного ТЗ.

## Подготовка агентом

Оператор передаёт ТЗ и workspace обычным способом. Ведущий агент читает документы, выделяет устойчивые `## REQ-id: Название` разделы, коммитит источники и формирует карту. Цель, пользователи, ограничения и исключённые возможности остаются явными; предположения записываются отдельно. Значимую неоднозначность продуктовой цели нельзя молча превратить в требование.

Истории имеют устойчивые IDs, releaseId и критерии со своими IDs. Все истории выбранного релиза обязательны для его отчёта. Будущая работа относится к другому релизу. Требования, сознательно исключённые из продукта, перечисляются в exclusions с причиной. Отсутствие задачи не означает исключения.

ТЗ содержит подробные требования; INTENT — карту и ссылки; AGENTS.md — правила работы; память — опыт и обоснования. Оперативные статусы вычисляются из задач и evidence. Отдельный изменяемый список done в INTENT не ведётся.

## Определение компонента

Ниже пример входа генератора, который готовит агент. В committed `docs/spec.md` уже должен существовать раздел `## REQ-search: Поиск сообщений`:

```json
{
  "kind": "component",
  "title": "Админка чата",
  "purpose": "Помочь модератору находить сообщения для разбора обращений.",
  "audience": ["Модераторы поддержки"],
  "constraints": ["Поиск соблюдает существующие права доступа."],
  "nonGoals": ["Отправка сообщений от имени пользователя не входит в продукт."],
  "assumptions": [],
  "sources": ["docs/spec.md"],
  "releases": [{ "id": "mvp", "title": "Первый рабочий релиз" }],
  "stories": [
    {
      "id": "search-messages",
      "title": "Модератор ищет сообщение",
      "releaseId": "mvp",
      "criteria": [
        {
          "id": "search-results",
          "text": "Поиск показывает подходящие сообщения и явное пустое состояние.",
          "requirements": [{ "source": "docs/spec.md", "id": "REQ-search" }]
        }
      ]
    }
  ],
  "exclusions": []
}
```

Определение — временный вход агента, а не второй постоянно редактируемый источник истины:

```sh
devcontour intent-render --repository-id chat --file /absolute/intent-definition.json --workspace /absolute/workspace > /absolute/chat/INTENT.next.md
```

Команда возвращает Markdown в stdout. Она читает обычные committed-файлы выбранного компонента, закрепляет SHA и digest каждого REQ, но ничего не записывает и не утверждает. Операция `intent_render` общего API возвращает документ в поле markdown. repositoryId выбирает компонент; отсутствие поля явно выбирает общий workspace.

Агент проверяет результат, сравнивает его с существующим INTENT.md и заменяет подготовленной версией. Не направляйте stdout сразу в существующий INTENT.md: shell обнулит файл до завершения генератора. Незнакомый существующий документ сначала прочитайте; setup его не создаёт и не перезаписывает. После проверки закоммитьте карту и получите привязки:

```sh
devcontour intent-snapshot --repository-id chat --story search-messages --workspace /absolute/workspace
```

История порождает раздел `REQ-intent-<storyId>`. Snapshot возвращает точные source/id/text/digest. Добавьте их в Task.requirements вместе с реально настроенным test gate и наблюдаемым scenario. Также добавьте подробные REQ, которые реализует задача, через requirements_snapshot. История может иметь несколько задач, задача — несколько историй. Сохраняйте IDs при переименовании, декомпозиции и корректировках.

Секция истории содержит цель, пользователей, ограничения, nonGoals, assumptions, критерии и закреплённые ссылки. Она входит в постановку, plan review и prompt автора и обоих reviewers, независимо от поиска в дополнительной памяти. Обычный requirement-source проверяет совпадение на candidate/integration SHA; Git sync переносит те же привязки.

## Поддерживаемый формат

Профиль DevContour версии 1 содержит один fenced-блок `devcontour-intent` и детерминированное Markdown-представление в том же файле. Snapshot проверяет их совпадение: правка только видимого текста не проходит незаметно. Генератор добавляет version, sourceSha и digests ссылок. При следующем render передавайте авторское определение без вычисляемых полей, сохраняя IDs.

Произвольный одноимённый Markdown не становится машинной спецификацией автоматически. Агент может нормализовать его в этот профиль, сохранив смысл, идентификаторы и источники. Внешний SaaS, аккаунт или отдельный MCP не требуются.

Лимиты: 30 источников, 20 релизов, 100 историй, 20 критериев на историю, 20 ссылок на критерий, 200 исключений, файл до 1 MB. На сгенерированную REQ-секцию действует предел 12000 символов. Общий API ограничен 100000 байтами входа и 64 KiB ответа: большие карты обрабатывайте прямым CLI; snapshot можно сузить до одной истории. CLI сохраняет ограничения самого формата.

## Проверка полноты

```sh
devcontour intent-report --repository-id chat --release mvp --require-complete --workspace /absolute/workspace
```

Без require-complete ненулевой exit означает ошибку чтения/формата. С флагом неполное покрытие также даёт exit 1, сохраняя JSON-отчёт. В CLI/HTTP/MCP доступен intent_report с repositoryId и releaseId. Операция не вызывает модели и не меняет состояние.

Отчёт читает карту и источники из одного HEAD владельца и проверяет:

1. Каждая история выбранного релиза имеет задачи. Забытые истории видны даже при пустом графе.
2. Все критерии имеют подробные REQ; их задачи связаны и с требованием, и с актуальным разделом истории. Задача с подробным REQ, но без привязки к известной истории остаётся непроверенным вкладом: её нельзя скрыть за другой выполненной задачей. Явная привязка к другой истории сохраняет её собственный релизный scope.
3. Все актуальные задачи истории завершены, их постановка совпадает с утверждённой, источники свежие, result SHA присутствует в принятой ветке.
4. На result SHA есть успешные integration test evidence заданных gates и requirement-source. Доверенный Git receipt допускается, но не считается локальным повторным запуском.
5. Все REQ объявленных sources распределены по историям любого релиза либо явно исключены. Новый нераспределённый REQ, изменённое исключение, пустой или недоступный источник блокируют полноту.

coverageComplete означает полноту цепочки для объявленных источников. Для компонентной карты и workspace без product поле releaseAccepted всегда false. Для [карты продукта](product-map.md) общий отчёт показывает актуальную приёмку ChangeSet с releaseId; сам отчёт не выполняет приёмку. Проверки досок, совместной версии, условий публикации и достаточности тестов сохраняются. Историческое evidence не означает, что весь продукт заново протестирован на текущей комбинации версий.

Полноту sources проверяет ведущий агент при review: необъявленный файл и текст вне REQ-формата автоматически не обнаруживаются. Связь с gate не доказывает смысловое соответствие теста критерию. Независимый reviewer проверяет сценарии и достаточность тестов.

## Продукт и библиотеки

Подробные истории, ТЗ и задачи остаются у компонентов. Общая карта workspace содержит цель и ссылки на релизы. Для продуктовой работы добавьте [приложения и фичи](product-map.md); ниже минимальная карта ссылок без продуктовой приёмки:

```json
{
  "kind": "workspace",
  "title": "Управление чатом",
  "purpose": "Совместно подготовить админку и совместимую библиотеку чата.",
  "releases": [
    {
      "id": "mvp",
      "title": "Совместный релиз",
      "components": [
        { "repositoryId": "admin", "releaseId": "mvp" },
        { "repositoryId": "chat", "releaseId": "moderation-api" }
      ]
    }
  ]
}
```

Рендер без repositoryId закрепляет digest committed-карты каждого компонента. Общий intent_report возвращает ссылки, свежесть, счётчики и полноту, без task text и критериев компонентов. Неизвестная/недоступная карта или другой digest блокируют полноту. Чтение независимых Git-репозиториев последовательное, а не атомарное: остановите изменения во время итогового аудита, совместные SHA проверяйте через ChangeSet.

Общую цель, влияющую на исполнителей, агент отражает в контрактах и локальных историях. Workspace-карта сама не добавляет инструкции в чужой prompt. Второй scheduler или общая база подробных библиотечных задач не создаются.

Состав компонентов релиза проверяет ведущий агент: полнота относится к объявленным ссылкам, а не ко всем репозиториям, когда-либо добавленным в workspace. Неизменённая библиотека может участвовать в совместной проверке версий без новой истории разработки.

INTENT.md и его источники передаются обычными Git-коммитами вместе с кодом. Команда sync переносит привязки задач, но не коммитит карту за агента. Параллельные правки карты объединяются средствами Git с сохранением IDs; при конфликте смысла ведущий агент готовит согласованное определение и повторяет render. Snapshot отклонит несовпадение структурного блока и представления. Markdown-статусы при таком merge не восстанавливаются: отчёт заново читает задачи и evidence.

## Корректировка

Новое знание может предложить изменение. Исполнитель не переписывает критерии под результат. Ведущий агент фиксирует причину, меняет ТЗ при необходимости, регенерирует карту, проверяет diff в действующем режиме согласований и коммитит источники. Изменение критериев или общего контекста меняет REQ-intent digest. Независимая история сохраняет digest, если её содержание и общий контекст прежние.

requirements-correct создаёт draft-замены на принятой доске. Пересмотрите AC, сценарии, контракты, scope и влияние на потребителей, выполните plan review и workflow. Новый ранее не связанный REQ требует отдельной задачи; удалённая история — явного перепланирования. Прежние ревизии сохраняются.

Новый HEAD документа не обновляет принятую ветку автоматически. Закреплённые разделы должны попасть в candidate/integration через разрешённое подготовительное изменение или задачу. Не двигайте refs вручную ради проверки. Перед завершением порученного релиза повторите intent_report, устраните пропуски и выполните обычную приёмку результата.
