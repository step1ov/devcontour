# Контекст агента и продолжение работы

Новый продуктовый маршрут начинается с [раннего запуска панели и продуктовых согласований](staged-workflow.md): продукт утверждает пользователь, затем архитектуру и стек с C1/C2, затем дизайн-трек — референсы, а при применимом интерфейсе ещё концепт и дизайн-систему. Технические операции ниже выполняются после этих решений, а задачи исполнения — только после всей цепочки. `approvalMode` не отменяет их.

Для продуктового планирования используйте [карту приложений и фич](product-map.md). Read-only операция `product_view` возвращает выбранный релиз, участие фич в приложениях и вычисленную готовность. Итоговый `changeset_create.changeSet` получает `releaseId`; завершение порученного продукта требует `product_view.releaseAccepted`, а не только полного списка done. Подробные истории и задачи остаются у владельцев репозиториев.

Продуктовый объём задаёт [INTENT.md](intent.md). intent_render готовит документ без записи, intent_snapshot возвращает закреплённые секции историй, intent_report проверяет выбранный релиз от полного списка историй и объявленных REQ-источников. Все три операции read-only. Для компонентов repositoryId обязателен; без него выбирается общий workspace. Полнота покрытия не утверждает релиз.

Длинная сессия не должна быть единственным носителем знаний о продукте. Ведущий агент получает факты из DevContour, читает документы выбранного компонента и оставляет короткую точку продолжения. Новый агент восстанавливает ситуацию по актуальному состоянию, а не считает прошлый разговор достоверным статусом выполнения.

## Единый запрос

Команда `npm run devcontour -- agent --workspace /absolute/workspace --file /absolute/request.json` принимает JSON:

```json
{ "operation": "project_overview", "input": { "repositoryId": "main", "limit": 20 } }
```

Тот же объект принимает `POST /api/agent` работающей локальной консоли. Нужны `Content-Type: application/json` и `X-DevContour-Request: 1`. Это интерфейс доверенных локальных процессов, без сетевой аутентификации. Для HTTP используется workspace запущенного сервера; для CLI он обязателен в каждой команде. Нельзя полагаться на текущий каталог или последнюю сессию. CLI `agent --file` (включая операции `preparation_*`) и `setup --change … --plan` работают и при запущенном сервере: они пишут в ту же базу, сервер останавливать не нужно.

| Операция             | Назначение                                                                                                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `project_context`    | Режимы согласования и завершения, компоненты, расположение репозиториев, количество локальных задач и возможности интерфейса                                                  |
| `project_overview`   | Краткие записи выбранного контура, состояния и причины ожидания задач                                                                                                         |
| `task_briefing`      | Задание, критерии, закреплённые контракты, ограничения записи, проверки задачи, исполнители и ссылки на context packs; необязательный `repositoryId` сверяет компонент задачи |
| `checkpoint_save`    | Неизменяемая точка продолжения на основе проверенной ревизии обзора                                                                                                           |
| `checkpoint_changes` | Добавленные, изменённые и удалённые записи относительно checkpoint, изменение настроек или исполнения                                                                         |

Проверки в `task_briefing` — то, что исполнит попытка задачи: `execution.gates` — её область `gates` с раскрытыми группами (`gateScope: task`) или, без области, весь профиль компонента (`gateScope: profile`), с `kind` и `when` у условного gate (такой gate исполняется, только если diff фазы задевает `when.paths`, иначе записывается как неприменимый); у задачи с требованиями последней идёт проверка источника требований `requirement-source` (`kind: requirement`), которую попытка добавляет сама. `outsideScope` — gates профиля вне области задачи: их исполняет другая задача доски, а не исполненные ни одной — приёмка доски один раз на итоговом SHA (то же правило, что у предупреждения «Области задач доски не включают gates» ревью плана и `workflow_start`). `consumerGates` — проверки потребителей задачи в их компонентах; область, которую профиль уже не раскрывает, — `gatesError`. Заголовок задачи несёт `specDigest` и `scopeDigest`: `gates` и `consumers` в digest постановки не входят и закрепляются отдельно — ревью плана сверяет `scopeDigest` каждого черновика при утверждении, утверждение записывает его (`approvedScope`), карточка утверждения оператором получает новую версию при его смене. Поэтому правка одних gates (`task_edit`, только у черновика) возвращает прежний `specDigest` и новый `scopeDigest`, а план, прочитанный ревью до правки, не утверждается. Правка, несущая `gates` или `consumers`, передаёт и `expectedScopeDigest` из `task_briefing`: при несовпадении она отклоняется, как устаревший `specDigest`, — иначе правка по устаревшему виду молча вернула бы чужую правку gates (поле необязательно; без него сверяется только `specDigest`). Правка одних gates — правка черновика и для `discussion_resolve`: обращение о gates принимается ссылкой на эту задачу; у утверждённой задачи gates меняются только возвратом в черновик и новым ревью плана.

Без `repositoryId` обзор и checkpoint относятся к общему workspace. С `repositoryId` — только к выбранному компоненту. Локальные карточки и контракты не копируются в общий checkpoint. Сведения о зависимостях могут содержать ID задач других компонентов: это связи графа, необходимые для координации.

Операции изменения контракта идут через тот же запрос. `contract_change_status` читает операцию; `contract_change_revise` (`id`, `expectedVersion`, необязательные `include` и `proposal`) пересматривает отклонённую, устаревшую или ждущую операцию. `proposal` — исправленное предложение того же контракта в формате файла `contract-change --file` (текст или `file`, `artifacts`, `checks`, `underTest`); `file`, `title`, `repositoryId` в записанном виде и компонент должны совпадать с операцией. До записи и вызова модели оно проходит предпроверки старта — закрепление артефактов, замыкание их зависимостей, структуру договора проверки, отказ при файле, зарегистрированном под другим компонентом. Операция, её удержания и история сохраняются. Без `proposal` берётся прежнее предложение.

## Вопросы исполнителя

Writer, которому для продолжения нужно решение, останавливает попытку вопросом (класс отказа `needs-input`, код остановки `INPUT_REQUIRED`): задача держится вопросом, автоматического повтора нет, очередь не останавливается, `task_retry` отказывает. Канонический запрос хранит harness (`input-requests` у компонента задачи); DevContour добавляет права, снимок контекста с ответом, его ревью и проекции.

| Операция          | Вход                                                                                        | Только чтение       | Что делает                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `input_list`      | `taskId?`, `repositoryId?`, `state?`                                                        | да                  | Запросы без текста: состояние, серьёзность, минимумы, версия, кто действует следующим                                                                                                                                                                                                                                                                                                         |
| `input_show`      | `requestId`                                                                                 | да                  | Вопрос, варианты, последний ответ целиком, прежние — digest и начало до 500 знаков, раунды ревью, цель, доставка                                                                                                                                                                                                                                                                              |
| `input_answer`    | `requestId`, `text`, `optionId?`, `kind?` (по умолчанию `clarification`), `expectedVersion` | нет                 | Ответ ведущего: только вопрос без минимумов в режиме `agent`, иначе 403 — отвечает оператор в панели. Работу не возобновляет                                                                                                                                                                                                                                                                  |
| `input_propose`   | `requestId`, `text`, `optionId?`, `kind?`, `reasoning`, `expectedVersion`                   | нет                 | Предложение ответа ведущего на вопрос, на который отвечает оператор (минимумы или режим `operator`), пока ответ ждёт оператора (`awaiting-answer`, `review-rejected`). Ответом не является: оператор подтверждает его в панели одним нажатием или отвечает иначе. Новое предложение заменяет прежнее. Вопрос, на который ведущий отвечает сам, — 409 `LEAD_ANSWERS`                           |
| `input_context`   | `requestId`, `messageIds?` (до 20 ID сообщений обсуждения задачи)                           | нет (async)         | Снимок: действующий снимок задачи и `input/<id>.md` с manifest; хранится по digest, не активируется                                                                                                                                                                                                                                                                                           |
| `input_review`    | `requestId`, `contextDigest`, `authorRuntime`                                               | нет (async, модель) | Раунд ревью снимка (предмет `input-<id>`); отказ до вызова модели, если снимка нет или в нём не последний ответ. Идут попытки доски задачи — `warning` и `activeAttempts`: применение подождёт их                                                                                                                                                                                             |
| `input_target`    | `requestId`, `contextDigest`                                                                | да                  | Основание продолжения (или переноса заменённого вопроса) и причины, по которым применение сейчас откажет; `rebound: true` — постановка изменилась только перепривязкой контракта, ответ переносится применением (F39)                                                                                                                                                                         |
| `input_apply`     | `requestId`, `answerDigest`, `expectedVersion`, `contextDigest`, `targetDigest`, `reset?`   | нет                 | Одна транзакция: активирует снимок для задачи (`Task.inputContext`) и возвращает её в очередь. В режиме `operator` — `APPROVAL_REQUIRED`, применяет оператор в панели. После одной перепривязки контракта (`rebound`) заменяет вопрос той же задачей и переносит ответ одной транзакцией                                                                                                      |
| `input_cancel`    | `requestId`, `expectedVersion`, `reason`                                                    | нет                 | Снять вопрос; блокирующий — по тому же праву, что ответ. Закрывает и follow-up                                                                                                                                                                                                                                                                                                                |
| `input_supersede` | `requestId`, `expectedVersion`, `reason`, `successorTaskId`                                 | нет                 | Заменить вопрос, когда постановка задачи изменилась: вернуть задачу в черновик, изменить постановку, заменить вопрос той же задачей, перенести ответ в черновике и затем утвердить задачу (`nextStep` результата называет порядок). Пока постановка прежняя — в том числе в черновике — 409 `SPEC_UNCHANGED`; блокирующий вопрос — по тому же праву, что ответ (иначе 403 `OPERATOR_ANSWERS`) |

Состояния (`state`): `awaiting-answer`, `answer-saved`, `context-review`, `review-rejected` (ревью отклонило ответ: вердикт и находки — в `input_show` и карточке; в режиме оператора применение — только с подтверждением показанного раунда: панель передаёт `confirmRejectedRound`, CLI — `--confirm-rejected-round R`; новый раунд требует нового подтверждения), `ready-to-apply`, `applied-awaiting-claim`, `delivered` (только после начала вызова writer попытки с ответом), `stale` (применённое основание устарело до выдачи — нужен новый снимок), `cancelled`, `superseded` (при ждущем переносе `next` называет шаги переноса).

Порядок изменения требований: `reopen` → `task_edit` (новая постановка в области записи роли) → `input_supersede` той же задачей → перенос в черновике (`input_context`, `input_review`, `input_target` в режиме `carry`, `input_apply`) → утверждение задачи (`workflow_start` или `review-plan`). Утверждение ровно той постановки, к которой ответ перенесён, сохраняет перенесённый ответ: снимок с ответом остаётся действующим, и цепочку не нужно проходить второй раз. Правка постановки после переноса снимок не наследует — ревью видело другую редакцию; применение устареет (`stale`), и цепочку повторяют по новой редакции. Ревью ответа в черновике тоже привязано к редакции: после правки нужен новый раунд. Заменённый вопрос выдачу не держит, поэтому перенос после утверждения требует паузы очереди. Если на доске нет ни одной утверждённой задачи (граф не выпущен — например, единственная задача доски вернулась в черновик), основания для переноса нет: `input_target` называет это, `input_apply` отказывает `NOT_READY`, подсказки `next` и `nextStep` называют порядок — пауза, утверждение, перенос, снятие паузы.

Область записи роли. Путь задачи, целиком лежащий вне области записи её роли, исполнитель изменить не вправе: попытка закончилась бы отказом по области записи. Поэтому `task_create`/`task_edit` и `plan_import` (по каждой задаче плана) отвергают добавленный путь вне области роли (400) и называют роль, которой он принадлежит: нужна отдельная задача этой роли, от которой задача зависит. Пути, записанные раньше (или до сужения роли), правка не отвергает, но перенос ответа в такую постановку — отказ `ROLE_SCOPE` до вызова модели (`input_context`, `input_review`, `input_apply`) и причина в `input_target`. Ревью ответа получает область записи роли и отклоняет ответ, решение которого требует правки вне неё. Актёр задаёт транспорт: агентский API — ведущий, панель — оператор, CLI — `--by operator|host` (по умолчанию `operator`, человек; `host` — ведущий агент и подчиняется правилу ведущего). Замену вопроса оператор выполняет командой `devcontour input-supersede`. Отмена задачи закрывает её вопросы, поэтому задачу с вопросом, который ведущий не вправе решить, отменяет только оператор (`devcontour cancel` без `--by host` или панель); ведущему — 403 `OPERATOR_ANSWERS`. Попытка, выданная после применения, закрепляет снимок (`pinned.contextDigest`): writer и оба reviewer видят файл ответа. Задача с вопросом в `ready` не входит, а `blockers` называет `input:<requestId>`. Возврат задачи в черновик (`reopen`) открытый вопрос не снимает: после утверждения той же постановки ответ применяется обычным `input_apply`; если постановка изменилась, `input_target` называет выход — `input_supersede` с преемником-той же задачей и перенос ответа (`input_context`, `input_review`, `input_target` в режиме `carry`, `input_apply`). Остановка вопросом держится, пока не изменилось содержание постановки задачи. Исключение (F39) — перепривязка контрактов к их более поздним редакциям (всех или части), после которой задача снова утверждена: остановка продолжается тем же ответом (`input_target` — `rebound: true`, `input_apply` одной транзакцией заменяет вопрос той же задачей и переносит ответ); проверка точная — digest содержания постановки с прежними редакциями обязан совпасть с запомненным при вопросе. Для вопроса с минимумами перепривязку обязана провести завершённая операция contract-change, перепривязавшая задачу после вопроса (шаг `rebind`; вопрос попытки, которую операция дожидалась, тоже годится), чья новая редакция — этот контракт и чья перепривязка включает задачу: ответ оператора не переносится на редакцию, зарегистрированную в обход операции (ручная регистрация и правка задачи); пока операция идёт, остановка ждёт, и `input_target` первой причиной называет её и выход (продолжение `contract-change --id ID`, затем `input_target` и `input_apply` или проход сервера) вместо совета заменить вопрос; у упавшей операции — также пересмотр (`--revise --expected-version N`) или отмена (`--abandon`), после отмены остановка получает `moved: true`. Если остановка не держится, `input_show` и `input_list` возвращают `moved: true`, `next` и `actor` называют выход (снять или заменить вопрос; у вопроса с минимумами — оператор), проход сервера останавливается фазой `resume.phase: moved` (`detail` — кто решает) без вызова моделей, а `session_handoff` — шаг `apply-moved`. В него входят и значения из конфигурации — область записи роли и пакеты контекста роли: их правка между вопросом и ответом тоже считается новой постановкой, и продолжение идёт через замену вопроса и перенос ответа. Действующая серьёзность вопроса — самооценка writer, поднятая до 10 минимумами (`floors`), которые модель понизить не может: `declared` — вопрос или допущение называет критическую область либо сам оценён в 10, `critical-path` — попытка изменила путь из `inputPolicy.criticalPaths`. Вопрос с минимумами критический: отвечает только оператор. Порог вопросов — `inputPolicy` в конфигурации (1–10 — порог серьёзности остановки, 11 — автономный режим, в котором решения writer записываются follow-up; без поля — 7), меняет его оператор (`config-apply --keys inputPolicy` или панель — «Настройки» → «Вопросы исполнителя», маршрут `POST /api/config/input-policy`); агентской операции нет. Модели ролей и ревьюеров тоже выбирает оператор (экран «Настройки», `config-apply --keys models`); агентской операции для них нет. Маршруты панели защищены от чужих страниц, но не от локальных процессов того же пользователя: ведущий агент не вызывает их и не выдаёт себя за оператора.

Коды отказа (409, поле `code`): `INPUT_REQUIRED` — у вопроса ещё нет ответа (`input_context` и `input_review`); `NOT_READY` — `input_context` строит снимок только для блокирующего вопроса в `answered` или заменённого, `input_review` нужен только запросу в `answered` или `superseded`; `REVIEW_REJECTED` — оператор применяет ответ, последний раунд ревью которого отклонён, не подтвердив именно этот раунд (`confirmRejectedRound`); `REVIEW_IN_PROGRESS` — ревью ответа на этот запрос уже идёт (в этом или другом процессе той же базы): `input_review` держит аренду запроса на время вызова reviewer (локальная запись со сроком `leaseMs`, продлевается, пока ревью идёт; аренда упавшего процесса истекает сама), второй одновременный вызов отказывает до вызова модели — дождитесь окончания и прочитайте раунд в `input_show` или повторите `input_review` позже (повтор с тем же одобренным раундом модель не вызывает); `APPROVAL_REQUIRED`, `OPERATOR_ANSWERS` и `SPEC_UNCHANGED` описаны в таблице.

Ответ можно дать и сообщением обсуждения задачи: `discussion_post` с `kind: "answer"` и `input {requestId, expectedVersion, optionId?, kind?}` (CAS — версия запроса, а не треда); ответ оператора в панели записывается так же. Одна транзакция: ответ попадает в запрос (`messageRef` — ID сообщения), сообщение ссылается на версию ответа, а текст хранится один раз — в запросе (`discussion_read` подставляет его). Исправление своего ответа — новый ответ с `supersedes`, новая версия ответа; применённый ответ не исправляется (409, изменение — обращение к ведущему). Ответ на уже снятый или заменённый вопрос сохраняется историей обсуждения (`input.accepted: false`) и задачу не возобновляет. `input_context` вносит в manifest снимка сообщения, которыми записаны ответы, и выбранные `messageIds` (ID, seq, digest; текст сообщений в снимок не входит).

Маршруты панели: `GET /api/tasks/:id/input`, `POST /api/tasks/:id/input/:requestId/answer` (`text`, `optionId?`, `kind?`, `expectedVersion`), `…/apply` (`expectedVersion`; снимок и цель — по последнему раунду ревью; в режиме `agent` — 409), `…/cancel` (`expectedVersion`, `reason`) и `…/confirm-proposal` (`proposalDigest`, `expectedVersion`).

Продолжение после ответа. В `approvalMode: agent` при работающем сервере цепочку после ответа оператора (`input_context` → `input_review` → `input_target` → `input_apply`; ответ оператора — в том числе подтверждённое предложение ведущего) ведёт сам DevContour — с заданием доски и без него: те же операции, тот же ревьюер, та же аренда ревью и те же отказы; сессия ведущего не нужна. Каждое ревью — отдельный полёт сервера, цикл ведущего его не ждёт; одновременно идут не больше двух. Рантайм автора для правила вендора ревьюера — автор утверждения задачи (ревью плана), иначе задание той же доски; он закрепляется за ответом при первом шаге и пишется в журнал с источником (`authorSource`); неизвестен — проход ждёт ведущего (`needs-lead`), в учебном режиме ревьюер учебный. Свои ответы ведущий доводит сам: проход их не берёт. Проход не ведёт и ответ вида `requirement-change` (новая постановка — ведущему), заменённый вопрос, отклонённое ревью (исправляет оператор) и режим `operator` (моделей сам не вызывает). Пока очередь стоит на паузе человека, остановки сервера, применения конфигурации, отказа рантайма или проверки базы, проход ждёт и моделей не вызывает (пауза проверяется и между снимком и ревью; уже идущий вызов ревьюера она не обрывает — раунд сохраняется, применение ждёт снятия паузы) (фаза `paused`, панель: «Ответ принят — продолжу после снятия паузы»); пауза ведущего (`queue_set`) и исходная пауза «очередь ещё не запускали» держат только выдачу. Попыток ревью одного ответа у прохода не больше трёх: попытка учитывается, когда аренда ревью взята, до вызова модели; сбой вызова считается, а повтор одобренного раунда и обрыв остановкой сервера без раунда — нет; пока ревью ведёт другой (аренда занята), проход ждёт без записей и журнала; после сбоя — пауза 30 с, удваивающаяся; на пределе — фаза `failed`. Устаревшее применение (`stale`) не по контексту нового ревью не требует: одобренный раунд того же ответа и утверждения даёт новую цель. Пока на доске идут попытки, проход только читает их список (перепроверка с 5 до 60 с, без записей) и применяет ответ после их окончания. `input_list` и `input_show` называют проход полем `resume` (`phase`, `auto`, `trigger`, `detail`, `until`); при `auto: true` действовать никому не нужно — `next` так и говорит, центр внимания карточки не показывает, а карточка задачи, «Ход работ» и метка доски называют фазу («Ответ принят — DevContour продолжает: проверка ответа / применение ответа», «Ответ принят: после паузы»); ответ, который доводит сам ведущий, метка доски называет «Ответ дан: ведущий применяет». Остановка прохода (`failed`, `blocked`, `needs-lead`) — карточка ведущего и шаг `session_handoff` `apply-input` с кодом `apply-auto`, `params.phase` и `params.detail`; пока проход идёт — шаг `wait` с тем же кодом. Журнал: `input.resume` (фаза, ревизия и digest ответа, кто ответил, рантайм автора и его источник) и `input.applied` с `origin: server`. Без сервера цепочку, как прежде, ведёт ведущий.

Предложение ответа ведущего. На вопрос с минимумами (или в режиме `operator`) отвечает только оператор, но решение часто следует из зарегистрированных контрактов и принятых файлов. Тогда ведущий записывает предложение `input_propose` (CLI — `devcontour input-propose --by host`): текст, вариант, вид ответа и обоснование. Это локальная запись, одна на запрос; ответа в запросе она не создаёт. `input_list` показывает у запроса `proposal` (digest, автор, время), `input_show` — предложение целиком с `current`: `false`, если версия запроса изменилась или ответ уже не ждёт оператора. Карточка задачи и карточка центра внимания показывают ответ и обоснование и действие «Подтвердить ответ ведущего»: сервер сверяет digest предложения и версию запроса (иначе 409 `PROPOSAL_CHANGED` или `REVISION_CONFLICT`) и записывает обычный ответ оператора с этим содержимым — дальше та же цепочка `input_context` → `input_review` → `input_target` → `input_apply`. Карточка центра внимания предлагает подтверждение, только если показывает ответ и обоснование целиком и без маски; длинное предложение или предложение со скрытыми данными она называет и отправляет в карточку задачи, где текст полный. Повторное подтверждение того же предложения возвращает прежний ответ (`replayed: true`). Подтверждение пишет в журнал событие `input.proposal-confirmed` (запрос, digest предложения, кто и когда предложил, ID сообщения ответа) — так видно, что ответ пришёл из предложения ведущего. Ответить иначе — прежняя форма. Предложение не принимается, если у вопроса уже предельное число ответов (409 `ANSWER_LIMIT`). Агентский API подтверждения не имеет: это правило для агентов, а не граница доступа — маршрут панели, как и маршрут ответа оператора, доступен любому локальному клиенту панели. Запись предложения снимается только подтверждением: после ответа формой, снятия или замены вопроса она остаётся и показывается с `current: false`. Проверки предложения и подтверждения идут до транзакции записи; предложение, заменённое другим процессом в этот промежуток, устаревает по версии запроса. Шаг `session_handoff` для такого вопроса — `answer-operator` с `params.version` и `params.proposed`.

Развилки ниже порога writer решает сам и записывает допущениями; движок сохраняет их в попытке (`assumptions`: `question`, `chosen`, `rationale`, `severity`, `affects`, действующая серьёзность `effectiveSeverity` и минимумы `floors`). Панель показывает их оператору рядом с результатом попытки — блок «Решения исполнителя» (вопрос — выбор — основание — серьёзность) в «Ходе попыток» карточки задачи и в результате быстрого изменения. Данные — детали задачи (`GET /api/tasks/:id`, `runs.items[].assumptions`), попытка (`GET /api/runs/:id`) и результат быстрого изменения (`run.assumptions`): до 20 решений, тексты сокращены; попытка без решений поля в деталях не несёт. У попытки, остановленной вопросом, развилка, ставшая вопросом, в блок не входит — она видна карточкой вопроса. Развилку делает вопросом движок, и только если исполнитель завершил работу (самая серьёзная не ниже порога); если исполнитель спросил сам, вопрос — его запрос, а развилки только записаны и все остаются в блоке. Поэтому скрывается лишь развилка, совпавшая с вопросом запроса попытки (вопрос, выбранный вариант и основание); нет совпадения — не скрывается ничего. Другие развилки не ниже порога у попытки, остановленной вопросом, остаются в блоке с `unresolved: true` и подписью «не решено: не ниже порога вопросов»; у попытки, не остановленной вопросом, движок развилки не оценивал, и пометки нет. Учебный исполнитель записывает две такие развилки для задачи с маркером `[demo:assume]` в описании (fixture, не модель).

`attention_list` (`actor?` — по умолчанию `lead`, `category?`, `limit` до 50; только чтение, до и после setup) — центр внимания: один упорядоченный список актуальных действий по тем же правилам источников, что у панели; каскад — одна корневая карточка с влиянием. Прочитать карточку не значит выполнить действие: действуйте операцией источника. Отметки оператора в ответ не входят. Договор карточки и правила идентичности — [центр внимания](attention.md).

## Обсуждения задач

У каждой задачи есть тред обсуждения: заметки и обращения к ведущему от оператора (панель) и от ведущего агента. Обсуждение — локальная история владельца задачи (таблица `discussion` его хранилища): оно не меняет постановку, согласования, очередь и попытки, и Git sync его не переносит. Сообщения не удаляются; исправление — новая версия с `supersedes`, и исправляется только последняя версия своего сообщения. Обращение с окончательным исходом (`accepted`, `rejected`) не исправляется: дальнейшее изменение — новое обращение. Исправление сохраняет `replyTo` прежней версии (без `replyTo` оно наследуется, другое значение — 400): исправленный ответ на `needs-answer` остаётся ответом на тот же исход.

У ответа на вопрос исполнителя CAS — версия запроса, а не треда. Текст и причина — до 16 KiB UTF-8 без управляющих символов, кроме перевода строки и табуляции; длиннее — 413. Другие отказы: ссылка `replyTo`/`supersedes` на сообщение другой задачи — 400; `change-request` с `replyTo` на исход — 400 (обращение — новый запрос; ответ на `needs-answer` — заметка); исправление чужого сообщения — 403; уже исправленное сообщение — 409 `already-superseded`; исправление обращения после `accepted`/`rejected` — 409 `request-resolved` (дальнейшее изменение — новое обращение); исход исправленного обращения — 409 `request-superseded` (обработайте новую версию); повторный исход после `accepted`/`rejected` — 409 `already-resolved`; принятие со ссылкой на ревизию или задачу старше обращения (без правки черновика после него; принятая ревизия правкой не обновляется) — 409.

Прочитать обращение — не значит обработать его. Изменение требований вносится обычной корректировкой доски или новой задачей, а не правкой принятой; обращение лишь фиксирует исход. Необработанные обращения также приходят в `session_handoff` (`host.discussion`) и в центр внимания. Маршруты панели: `GET /api/tasks/:id/discussion` (`cursor`, `before`, `latest=1`, `limit`) и `POST /api/tasks/:id/discussion` (вход `discussion_post`, автор — оператор).

### Решения за владельца

Когда ведущий без ответа владельца выбирает за него продуктовое поведение (объём, сценарий, «самый короткий путь» по умолчанию), он сразу записывает это решение в обсуждение задачи, чья постановка или контракт его воплощает: `discussion_post` с `kind: "stand-in"`, `text` — решение и основание, `standIn {question, impact}` — какой вопрос владельца закрыт и на что решение влияет (до 2 KiB UTF-8 каждое). Пока владелец не решил, ведущий может исправить запись (`supersedes`, вид сохраняется); в очереди — только последняя версия.

Неподтверждённые решения видит владелец: карточка центра внимания (источник `stand-in`, категория «решение», ключ `discussion:si:<первое сообщение>`) с действиями «Подтвердить» и «Отменить решение», бейдж в треде задачи и CLI `devcontour decisions [--all]`, `decision-confirm --message DM-... [--text ...]`, `decision-reverse --message DM-... --text ...`. Подтверждение и отмена — действие владельца: в агентском API такой операции нет, `discussion_post` поле решения не принимает, служба отклоняет решение другого автора (403 `owner-only`), у CLI нет `--by host`. Как и другие команды оператора, CLI доверяет тому, кто его запустил: агент с доступом к shell технически может вызвать `decision-confirm`, поэтому ведущему это запрещено правилом, а не возможностью. Ведущий видит ждущие решения в `attention_list` только с фильтром `actor: "operator"` (по умолчанию список — его собственный, `lead`).

Инструмент сам записывает решение за владельца в той же транзакции, когда ведущий отвечает на вопрос исполнителя изменением требований (`kind: requirement-change`) или закрывает follow-up как принятое допущение (`input_cancel`); ответы и закрытия оператора — его собственные решения и записью не становятся. Такая запись — от автора `runtime` (в панели «DevContour за ведущего агента»): агентский API под ним не пишет, поэтому ведущий не занимает её ключ и не исправляет её. Повтор операции дописывает недостающую запись; новая версия ответа с изменением требований заменяет нерешённую запись прежней версии — одна карточка на вопрос. Ответ-уточнение (`clarification`), который на деле выбирает продуктовое поведение, снятие блокирующего вопроса ведущим и замену вопроса или follow-up преемником (`input_supersede`) инструмент не записывает: такое решение ведущий записывает сам. Follow-up, закрытый движком вместе с отменой задачи, принятым допущением не считается.

Решение владельца — ответ на последнюю версию записи с полем `ruling`: подтверждение — заметка (`ruling: "confirmed"`); отмена — обращение к ведущему (`ruling: "reversed"`) с вопросом, прежним решением и вариантом владельца. Отмена приходит ведущему как любое обращение — `discussion_inbox`, `session_handoff` (`host.discussion`), карточка центра внимания — и обрабатывается `discussion_resolve`: принятие ссылается на новую ревизию или задачу, «нужен ответ» спрашивает владельца; отклонить отмену нельзя (403 `owner-ruling`). Тред задачи показывает состояние отмены по исходу её обработки. Отмена с вопросом и цитатой решения (выдержка до 4000 байт со ссылкой на сообщение) не длиннее 16 KiB UTF-8, иначе 413. Решение владельца окончательно: повторное — 409 `already-ruled`, решение по исправленной версии — 409 `stand-in-superseded`, исправление решённой записи — 409 `already-ruled`, исправление самого решения владельца — 409 `ruling-final`. Оператор не пишет `stand-in` (403 `lead-only`): его собственное решение — заметка или обращение.

## Размер и актуальность контекста

Ответ ограничен 64 KiB. Обзор, briefing и изменения используют `limit` (1–50, по умолчанию 20), `hasMore` и `nextCursor`. Чтобы дочитать ответ, повторите тот же запрос с возвращённым cursor. Cursor привязан к операции, контуру и ревизии. Если состояние изменилось, сервер возвращает конфликт: нужно начать чтение заново, а не объединять страницы разных состояний. Ответ агентского API (HTTP `/api/agent`, MCP, CLI `agent --file`), не поместившийся в предел, отклоняется кодом 413. Текст называет операцию и отсылает к полям её входа, если они есть (фильтры, `limit`, `cursor` — `inputSchema` операции в `capabilities`); у операции без таких полей сузить ответ нечем, и текст это не скрывает. У `workflow_status` текст называет конкретные поля `key`, `kind` и `id`, `active`, `limit`, но сама операция сворачивает ответ и отказывает только тогда, когда сокращать нечего. Некоторые операции укладываются в предел сами: `session_handoff` отбрасывает записи пакета и считает их в `truncated`, `requirements_report` отдаёт страницу строк с `complete: false` и `nextCursor`.

Большие описания и контракты в briefing разбиты на последовательные секции `kind/id/part/text`. Следует прочитать все страницы релевантного задания. Деление сохраняет Unicode и не означает сокращения требований. Полный текст закреплённых Git context packs получается отдельной командой `context-show --task ID`; briefing содержит их версии и отпечатки.

Закреплённые REQ-разделы также передаются секциями briefing. Сам `requirements_report` проверяет их актуальность относительно Git HEAD. Не путайте границы двух ответов: briefing даёт постановку, отчёт — состояние её связей с доказательствами.

В этих ответах нет fencing tokens, команд окружения и журналов runtime. Произвольный текст задания или заметки всё равно может содержать чувствительные сведения: этот интерфейс не является DLP и не предназначен для публичного доступа. Полный старый `/api/state` остаётся внутренним интерфейсом доверенной консоли; панель опрашивает ограниченную сводку `/api/summary` (D35).

## Точка продолжения

Сначала получите `revision` через `project_overview`. В шаблоне ниже замените `<revision из обзора этого компонента>` точным 64-символьным значением из ответа и затем отправьте запрос. Сам placeholder не проходит схему API:

```json
{
  "operation": "checkpoint_save",
  "input": {
    "repositoryId": "main",
    "expectedRevision": "<revision из обзора этого компонента>",
    "summary": "Выбрана схема пагинации; план пока в draft.",
    "nextStep": "Проверить контракт, затем передать план независимому reviewer."
  }
}
```

Ответ содержит `checkpointId` и путь. Файлы находятся в `.devcontour/checkpoints/<uuid>.json`; идентичность контура — в `.devcontour/context-identity.json`. Их можно коммитить обычным Git. Общие checkpoints лежат в workspace, локальные — в соответствующем репозитории. Они не добавляются в SQLite задачи и не меняют правила `sync`: Git переносит их как самостоятельные неизменяемые документы. UUID позволяет двум разработчикам сохранять разные точки без перезаписи одного общего файла.

При `workspaceMode: embedded` общий checkpoint остаётся под `.devcontour/`, а локальные checkpoints и их identity находятся под `.devcontour/components/<repositoryId>/` в том же Git. Используйте путь, возвращённый API. `project_context` сообщает выбранный режим. Операции `intent_render` и `intent_snapshot` также возвращают фактический `source`: в embedded локальные истории лежат в `docs/implementation-intent.md`, общая карта — в `INTENT.md`.

При первом сохранении используется уже существующая Git identity из `sync`, если она есть. Поэтому два участника, независимо создавшие первые checkpoints после clone, получают одинаковую identity и разные UUID заметок: Git объединяет их без конфликта. Инициализируйте и закоммитьте общую Git identity до командного старта. Для одиночного проекта без `sync` identity создаётся локально и должна попасть в исходный Git-коммит до раздачи clone.

`checkpoint_changes` принимает этот ID и тот же `repositoryId`. После clone путь может отличаться: идентичность переносится вместе с файлами. Другой контур, неправильный ID, symlink и устаревший `expectedRevision` отклоняются. В checkpoint сохраняются отпечатки записей и короткая заметка, без тел задач, логов, leases и evidence. Изменение локальных путей после clone может дать `controlChanged: true`; это повод перечитать настройки, а не потеря истории.

Checkpoint — подсказка для продолжения. Он не разрешает переход в `done`, не подтверждает тесты и не возобновляет очередь. После восстановления ведущий агент сопоставляет заметку с текущим графом, состоянием Git и настройками. Для завершённой доски он создаёт корректировку, сохраняя принятую ревизию.

Для продолжения исполнения существует отдельный [workflow job](lead-workflow.md) в локальной SQLite. Читайте `workflow_status` независимо от checkpoint: он показывает стадии review/очереди/приёмки и ошибки. Действующие jobs (`queued`, `running`) идут целиком; законченные (`completed`, `failed`, `stale`) по умолчанию свёрнуты — последние 10 и все повторяемые упавшие в компактном виде без истории, остальные числом в `finished` (с разбивкой по статусам). Для опроса одного job передайте его `key`, для jobs одной доски или ChangeSet — `kind` и `id`; подробности — в [workflow](lead-workflow.md#стадии-и-наблюдение). Checkpoint переносится через Git, job — нет. После clone новая сессия сначала проверяет импортированные данные и затем регистрирует job, а не пытается восстановить чужой lease. Новые возможности и точные входы перечислены в [MCP-каталоге](mcp-server.md).

## Почему задача ждёт

Пауза очереди называет того, кто её поставил: `queue.by: "lead"` и «Выдача остановлена ведущим агентом (queue_set)» — пауза ведущего агента через `queue_set`; без поля — пауза человека. В `session_handoff` шаг `queue_set` с кодом `pause-operator` несёт `params.by: "lead"`, только если паузу поставил сам ведущий агент через `queue_set` и под ней нет ожидания проверки базы (снятие паузы сняло бы его без проверки, а под такой паузой ожидание снимает только человек): тогда ведущий снимает свою паузу сам, когда её причина устранена. Без `by` пауза — решение человека, и её снимают только по решению пользователя. Пауза ведущего поверх паузы человека ничего не меняет: решение остаётся за человеком.

`progress.reasons` разделяет причины: `plan_review_required`, `dependencies_incomplete`, `queue_paused`, `assigned_to_another_member`, `workers_busy`, `workspace_operation_active`, `inactive_revision`, `failure_requires_diagnosis`, `attempts_exhausted`, `held_by_operation`, `approval_stale`, `budget_blocked`, `input_required`, а также `product_approval_required`. Порядок фиксирован: сначала продуктовые `product_approval_required`, `held_by_operation`, `budget_blocked`, `approval_stale`, `inactive_revision` и `input_required`, затем общие причины исполнения (у черновика — `plan_review_required`, у сбоя — `failure_requires_diagnosis` или `attempts_exhausted`, у готовой задачи — `dependencies_incomplete`, `attempts_exhausted`, `queue_paused`, `workers_busy`), затем `assigned_to_another_member` и `workspace_operation_active`. Общие причины вычисляет движок исполнения, продуктовые добавляет DevContour. `input_required` — задачу держит вопрос исполнителя без применённого ответа: `progress.input.requestId` называет запрос. Остановку вопросом движок записывает статусом `failed`, но это ожидание ответа, а не сбой: `failure_requires_diagnosis` у такой задачи нет, повтор отказал бы, продолжение — ответ и его применение ([вопросы исполнителя](#вопросы-исполнителя)). Попытка, остановленная вопросом, не засчитывается в `maxAttempts` и не тратит предел незасчитанных отказов: ответ на вопрос последней попытки применяется без сброса. Возврат попытки ограничен: у задачи не больше `maxAttempts` таких остановок за всю её жизнь (счёт по записям попыток, сброс его не обнуляет); следующая остановка вопросом засчитывается как обычная попытка (`attempt.diagnosed` с `counted: true`), так что цикл вопросов, на которые отвечает модель, и отмена с повтором вместо ответа кончаются `attempts_exhausted`. Сброс с причиной (`reset`) нужен, только если попытки исчерпаны — другими отказами или вопросами сверх этого предела. Остановка, вернувшая попытку, и её продолжение имеют один номер попытки; остановку отличает класс отказа `needs-input`. `held_by_operation` — задачу удерживает операция (изменение контракта): `progress.hold` называет `operation`, `kind` (`contract-change`) и `reason`; выдача ждёт снятия удержания и после снятия паузы. `approval_stale` — план задачи утверждён при другой политике исполнения ([D43](decisions.md#d43-утверждение-плана-закрепляет-политику-исполнения)). Задача не выдаётся до повторного утверждения, и `eligible` ложно. `progress.approvalStale` называет `boardId`, `reason` и `hint` (`review-plan --board ID`, в агентском режиме — новое задание доски `workflow_start`). `budget_blocked` — бюджет расходов не пускает задачу к выдаче: `progress.budgetBlock` называет `reason` (какой предел и сколько израсходовано), `at` (когда выдача записала этот блок, если записала) и `hint`: у исчерпанного предела — поднять его и выполнить `config-apply --keys budgets`, у неопределённого (стоимость вызовов неизвестна) — задать `onUnknown: "continue"` (тариф в `prices` оценит только новые вызовы) и выполнить `config-apply --keys budgets,prices`. Блок считается по действующим пределам при каждом чтении, а не берётся из записи последней выдачи: после применённого повышения предела он снимается сразу. Задание ведущего доски, начатое по прежнему входу, — не причина, а сведение `progress.workflowStale` (`boardId`, `workflow`, `reason`, `hint`). Выдачу оно не держит, а новое задание доски его снимает. `eligible` — наблюдение о возможности выдачи задачи сейчас. Получить право записи можно только через scheduler и его lease; обзор не бронирует задачу.

Heartbeat сам по себе не меняет ревизию контекста. Новая попытка, фаза, результат, правка задания, член команды, настройки и состояние общей проверки меняют соответствующие отпечатки. Это уменьшает шум при чтении и сохраняет видимость содержательных изменений.

## Знания и наблюдения выполнения

`memory_retain`/`memory_recall` сохраняют и выбирают [типизированные знания](project-memory.md) в выбранном владельце. Overview/checkpoint отражают смену каталога и актуальности источников отдельной записью knowledge. Дополнительная память не заменяет все страницы task_briefing или закреплённые context packs.

`usage_report` и `decision_report` имеют limit/cursor, меняющийся отчёт требует начать чтение заново. `strategy_replay` — read-only аудит двух фиксированных правил, без выдачи задач. [Метрики](metrics.md) и [эксперименты](experiments.md) определяют знаменатели, unknown и ограничения сравнения.
