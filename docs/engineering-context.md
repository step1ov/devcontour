# Контекст агентов, библиотеки и тестовые ресурсы

Закреплённый контекст делает инструкции воспроизводимыми, область записи ограничивает принимаемый diff, граф компонентов определяет потребителей, а аренды ресурсов предотвращают конкуренцию за одну тестовую среду. Эти механизмы дополняют проверки кода и работают под одним controller.

## Три разных графа

- `Task.dependsOn`: какую работу необходимо принять до начала следующей задачи.
- `repositories[].dependsOn`: какие компоненты использует продукт или библиотека.
- `gates[].dependsOn`: какие проверки/подготовительные команды должны закончиться до этой проверки.

IDs и зависимости проверяются, циклы и неизвестные вершины отклоняются. Gates выполняются в топологическом порядке; без dependsOn сохраняется порядок массива. Все локальные gates обязательны для candidate и integration SHA. Typecheck/build не заменяют test gate с реальным JUnit.

`gate.cwd` — каталог относительно корня worktree; `report.path` и `artifacts` остаются относительно корня компонента. Генераторы могут создавать игнорируемые производные файлы, но не изменять отслеживаемые исходники проверяемого SHA. Потребитель не должен использовать старые dist из рабочего checkout: проверка идёт в свежем worktree.

## Пакеты контекста

Универсальный источник — Markdown в репозитории, одинаковый для Codex и Claude. `setup` копирует `.agents/roles`, `.agents/context`, AGENTS.md и CLAUDE.md, сохраняет существующие файлы и добавляет определения context packs. Ведущий агент адаптирует инструкции к настоящему проекту, коммитит bootstrap и выполняет:

```sh
npm run devcontour -- context-lock --workspace /absolute/product-workspace
```

По умолчанию закрепляется HEAD каждого исходного репозитория. `--ref devcontour/accepted` выбирает интегрированную версию, если такая ветка есть во всех источниках. Команда не читает незакоммиченные документы. Затем перезапустите сервер. Не обновляйте конфигурацию при активных попытках.

Пример определения в `config.json` / `workspace.json`:

```json
{
  "contextPacks": [
    {
      "id": "product-backend",
      "version": "1.0.0",
      "repositoryId": "product",
      "roles": ["backend"],
      "files": [".agents/roles/backend.md", ".agents/context/contracts.md"]
    },
    {
      "id": "custom-sdk",
      "version": "2.1.0",
      "repositoryId": "library",
      "roles": [],
      "files": ["docs/agent-guide.md", "docs/api-examples.md"]
    }
  ]
}
```

`context-lock` дописывает `revision` и `digest`. Runtime проверяет digest, читает обычные Git-файлы из этой revision, добавляет содержимое в промпт исполнителя и независимого ревьюера. Symlink вместо инструкции отклоняется. Выбранные версии и текст сохраняются в `artifacts/<run>/implementation/context.json`, receipt — в Run. Нет закрепления, файл отсутствует или хеш отличается — попытка завершается ошибкой до вызова модели.

Пакеты с подходящей ролью подключаются автоматически только задачам своего repositoryId. Дополнительные, включая инструкции библиотеки из другого репозитория, перечисляются в `Task.contextPacks`. Пустой roles означает только явное подключение. Лимиты: 30 файлов в pack, 60 000 символов файла и 160 000 символов общего контекста. Это выбор по роли и явным IDs; семантический поиск по всем скиллам пока не реализован.

```json
{
  "repositoryId": "product",
  "title": "Подключить новую версию SDK",
  "description": "Адаптировать сервис к утверждённому контракту SDK.",
  "role": "backend",
  "dependsOn": ["T12"],
  "contracts": ["C3"],
  "contextPacks": ["custom-sdk"],
  "writePaths": ["src/integrations/", "tests/integrations/"],
  "acceptance": ["Контрактные и интеграционные тесты проверяют реальное использование SDK."]
}
```

До утверждения ведущий агент назначает область записи. `Task.writePaths` и `roles.<role>.writePaths` — относительные пути/префиксы, не glob; разрешено их пересечение. Protected paths, исходники объявленных context packs и `repository.generatedPaths` исключаются. Runner проверяет фактический diff, включая удаления и переименования, до коммита. Это контроль интеграции, не OS sandbox. Неописанная область не угадывается: старые конфигурации работают с прежними protectedPaths. Новому проекту область задаёт ведущий агент.

Изменение библиотеки сопровождайте новой версией её инструкции, примерами, контрактом и тестами потребителей. Исходники закреплённых инструкций меняет ведущий агент в подготовительном изменении после сверки; worker не может незаметно поменять собственные правила. Политика контекста включена в digest попытки.

## Выбор проверок потребителей

В `repositories` укажите, например, `product.dependsOn: ["library"]`, `library.dependsOn: []`. Это зависимости целых Git-репозиториев; внутри монорепозитория MVP проверяет весь репозиторий, а не отдельные npm-пакеты.

По умолчанию `verificationMode: "all"`: все workspaceGates запускаются для каждого ChangeSet. Опциональный `"affected"` сравнивает SHA всех компонентов с последней подходящей принятой комбинацией, включает изменённые компоненты, транзитивных потребителей и prerequisites выбранных gates. Изменение package.json, lockfile или конфигурации учитывается так же, как изменение исходников: path-glob фильтра нет.

При первой проверке, другой политике, неполном графе (хотя бы один dependsOn отсутствует), неизменных SHA или отсутствии достаточных выбранных test gates выполняется полный набор. Даже в affected конфигурация обязана содержать интеграционный test gate каждого продукта. Незатронутые компоненты сравниваются с принятой baseline; эта оптимизация зависит от полноты явно объявленного графа. При сомнении используйте all.

План проверки сохраняется в Verification.impact, `workspace-checks/<id>/impact.json` и дневнике ChangeSet: changed, affected, baseline, mode, reason, gateIds. Приёмка требует PASS каждого выбранного gate и сохраняет manifest всех компонентов. Исторические записи не переписываются.

## Резервирование ресурсов

```json
{
  "resources": [
    { "id": "ios-qa", "kind": "device", "value": "REAL-DEVICE-ID-FROM-DISCOVERY" },
    { "id": "api-port", "kind": "port", "value": "4381" },
    { "id": "qa-user", "kind": "account", "value": "test-environment:qa-user-1" }
  ]
}
```

`Task.resources` и `Gate.resources` перечисляют IDs. Значения содержат адрес ресурса/имя аккаунта, не пароль или токен. Одинаковая пара kind/value обозначает один физический ресурс во всех workspace; локальные IDs могут отличаться. ID устройства берётся из discovery, не выдумывается. Для аккаунтов и сервисов используйте единое имя с окружением.

На одном хосте все процессы по умолчанию используют `~/.devcontour-local/resources.sqlite`. `resourceDatabase` переопределяется абсолютным путём, например в тестах; разные базы не координируются, поэтому связанные workspace должны использовать одну. Это единственное общее оперативное состояние: локальные доски и задачи хранятся в SQLite своих компонентов, общая координация — в SQLite workspace, каталог devcontour не меняется.

Набор захватывается атомарно целиком, удерживается с heartbeat и освобождается после остановки работы. Для task-run резервируются ресурсы задачи и всех её локальных gates; для workspace-verify — объединение ресурсов workspaceGates. Последний вариант консервативно резервирует и ресурсы невыбранных gates. Ожидание входит в общий runTimeoutMs. Команды и runtime получают `DEVCONTOUR_RESOURCES_JSON`, ресурсный контекст также включается в промпт. Порты/симуляторы автоматически не создаются и процессы, работающие вне DevContour, не блокируются.

Истечение TTL не означает, что старый драйвер перестал работать. Аренда не перехватывается автоматически; после аварии ведущий агент проверяет владельца и останавливает оставшиеся процессы. Только после фактической очистки:

```sh
npm run devcontour -- resources --workspace /absolute/product-workspace
npm run devcontour -- resource-release --key <key> --token <token> --cleanup-confirmed --workspace /absolute/product-workspace
```

Очистка отклоняется, если PID владельца ещё существует или token изменился. Не удаляйте файл SQLite для «разблокировки». Для процессов другого пользователя/хоста и распределённой федерации этот механизм не предназначен. На устройстве внутри одной попытки также используйте MCP и CLI последовательно.

## Находки и ревью

Результат реализации/ревью поддерживает массив `discoveries`: kind bug/debt, title, path, line, observation, consequence, reproduction. Runner создаёт draft-задачи на доске «Находки агентов», сохраняет исходный repositoryId/task/run/SHA, дедуплицирует открытые находки. Они видны в существующем графе/списке задач, экспортируются и попадают в SQLite events. Новые задачи не получают approved/done автоматически и не включаются молча в ChangeSet.

Ведущий агент воспроизводит находку, отделяет дефект от предположения, задаёт приоритет, контракты, scope и зависимости; далее действует обычное независимое ревью плана. Только подтверждённое знание становится validated в memory. Не создавайте конкурирующий TODO с отдельными статусами.

Findings ревью поддерживают path/line/rule/consequence/evidence; причинные регрессии у неизменённых потребителей тоже учитываются. Прежние fixtures с severity/message совместимы. Проверка моделью содержания этих полей не заменяется JSON schema: независимое ревью и реальные тесты остаются обязательны.

## Дизайн и мобильные тесты

Переносимые инструкции находятся в `.agents/context/design.md`, `testing.md`, `mobile-maestro.md`. Они требуют готовых примитивов, полного набора дизайн-токенов, темизации сторонних компонентов, устойчивых селекторов, проверки результата действия и cleanup после падения. Авторизацию/окружение автоматизирует ведущий агент в выделенной тестовой среде. Если доступ невозможен, фиксируется блокер, а обязательный сценарий не выдаётся за PASS.

Реальный Maestro, приложения на iOS/Android и live-модели не входят в fixture-проверки самого шаблона. Подключение MCP к конкретному adapter и установка тестовой инфраструктуры требуют проверки в проекте; одни Markdown-инструкции эти инструменты не запускают.
