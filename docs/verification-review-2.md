## Договор и ограничения reviewer

[Формат, совместимость и sandbox probe](reviewer-execution.md) описывают миграцию. Старые evidence не меняются и не получают выдуманный список команд. Новые review records содержат inspection; в UI видны commands, diff-only либо отсутствие сведений для исторических записей. Поле execution в ответе модели не считается наблюдением runtime.

Дополнительно исправлена проверка неизменности worktree: новый незапрошенный untracked-файл reviewer также отклоняет приёмку. Git fixture действительно создаёт такой файл и проверяет отказ интеграции. Это защита приёмки после изменения, не утверждение, что ОС запретила сам системный вызов записи. Проверка запрета записи на уровне ОС — отдельный sandbox probe.

`codex sandbox macos --help` и probe завершаются с `sandbox-exec: sandbox_apply: Operation not permitted`, exit 71. Ошибка возникает до модельного вызова; разрешение записи служебной SQLite не решает запрет вложенного sandbox. Read-only профиль Codex сохранён. Bash для Claude не добавлен без системной изоляции. Включение shell в writable копии репозитория не защитило бы оригинальный checkout, доступный по абсолютному пути.

## Что ещё требуется от среды и человека

Из корня репозитория в обычном терминале, вне sandbox агента:

```sh
npx playwright install chromium && npm run check
```

Для CI нужен полный `verification.log` из артефакта verification-evidence либо участок вывода с первым упавшим тестом/командой. Строка `Process completed with exit code 1` сообщает лишь итог оболочки. После публикации исправлений человеком понадобится ссылка на новый запуск; текущие локальные коммиты сами не делают master в GitHub зелёным.

Для живого пилота нужны работающий sandbox, точные модели, явное разрешение и денежный бюджет. Готовые материалы: [план пилота](pilot-2-plan.md). Единого долларового hard cap двух CLI и ведущей сессии нет; способ наблюдения и остановки описан в плане.

## Что менять только после измерений

Для примера с одним репозиторием, тремя историями и одним REQ-файлом продуктовый маршрут требует минимум 11 обращений общего API: два intent_render (локальный и общий), три intent_snapshot, один requirements_snapshot, один plan_import, один workflow_start доски, один changeset_create, один workflow_start ChangeSet и итоговый product_view. Подготовка конфигурации, Git-коммиты, review контрактов, уточнения и повторные чтения сюда не включены. Это оценка маршрута по интерфейсу, а не измеренные модельные вызовы.

CLI соответствует операциям: intent-render → intent-snapshot / requirements-snapshot → import-plan → agent --file board-workflow.json → changeset-create → agent --file release-workflow.json → product-view --require-accepted. Файлы workflow-запросов содержат `operation: "workflow_start"` и соответствующий input; отдельной CLI-команды workflow-start нет. Форматы аргументов задают CLI help и [agent interface](agent-interface.md); JSON-определение, запись и commit INTENT остаются отдельными действиями ведущего агента.

Возможные упрощения после P2: подготовка render/валидации/diff одной операцией с явной записью; подбор досок ChangeSet по историям релиза с показом найденного состава. Нельзя автоматически утверждать план, скрывать пропуски или переписывать уже принятые записи. Более точный digest релиза допустим только после проверки влияния общих приложений, компонентов, критериев и gates; данных о цене нынешней инвалидации пока нет.

START и skill можно разделить на краткий маршрут и подгружаемые детали, когда трасса пилота покажет фактические чтения. До замены нужен отдельный eval: агент не должен забывать workspace, локальность памяти, фиксацию требований и продуктовую приёмку.

Текущие размеры: START — 27 533 символа, skill ведущего агента — 11 118. Это размеры файлов, не доказательство того, что модель загрузила или использовала всё содержимое.

## Типизация: следующий порядок

Исходный lint-report: 829 предупреждений, из них 683 относятся к no-unsafe-* и no-explicit-any. Крупнейшие файлы: component-storage (100), context tests (91), forge (85), intent tests (55), config (41), sync-model (40). Поэтому одного добавления zod вокруг JSON.parse недостаточно.

После типизации CLI событий и изменения передачи данных графа повторный lint-report показал 711 предупреждений и 0 ошибок. Ни одно правило не отключалось ради этого уменьшения.

Следующие ограниченные изменения: типизированные локальные storage records и sync projections; схемы ответов forge; envelope загрузки config до обращения к свойствам; затем HTTP/UI responses. Каждая граница получает негативный тест, а правила ESLint повышаются до error лишь при нулевом числе нарушений. Для indexed access сначала core/delivery и явные проверки пустых массивов, затем store/sync, runner и тестовые helpers. Изменение типов не должно заменять runtime-валидацию внешних данных.

Массовая переделка хранения, новый container runtime и продуктовая оптимизация не включены в этот набор исправлений: первые требуют отдельных проверяемых изменений, последняя — данных пилота. Отказ от незапущенного платного эксперимента не означает, что замечания о реальной работе reviewer закрыты.
