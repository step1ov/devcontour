# Принятые инженерные решения

Этот документ объясняет действующие принципы DevContour. Для каждого решения указаны задача, выбранный подход, его цена и основания для пересмотра. Это не перечень обещанных возможностей: будущие варианты здесь служат критериями развития.

## D01. AI-native процесс с внешними условиями завершения

**Задача.** Уменьшить ручную настройку и количество подтверждений, сохранив проверяемость результата.

**Решение.** Оператор задаёт цель и workspace. Ведущий агент сразу открывает панель и последовательно готовит продуктовую постановку и архитектуру со стеком. Эти две версии утверждает пользователь (уточнение D31). После этого агент готовит проект и ведёт технические этапы; для них по умолчанию `approvalMode: agent`. Scheduler принимает работу только после обязательных проверок. `operator` включает ручные согласования, но не меняет технические условия `done`.

**Почему.** Человеческое подтверждение каждой карточки быстро становится формальностью и ограничивает скорость. Передача рутинных решений агенту полезна, если результат проверяет независимый механизм. Поэтому отмена ручного согласования не даёт модели права выставлять `done` или отключать тесты.

**Цена и пересмотр.** Агент может неверно понять продуктовую цель, даже пройдя тесты. Нужны хорошие AC, трассировка требований и вопросы при существенной неоднозначности. Для регулируемого процесса можно выбрать `operator`; полноценные роли доступа и многосторонние approvals потребуют отдельной модели авторизации.

## D02. Явный workspace и разделение установки с продуктом

**Решение.** Каждая продуктовая команда получает `--workspace` или `--data`; общего «активного проекта» нет. Если путь не задан, ведущий агент спрашивает его до настройки. Установка инструмента не хранит продуктовую память.

**Почему.** При нескольких сессиях неявный cwd или последний использованный проект легко направляет изменения в чужую базу. Явный контекст делает команды воспроизводимыми, а одну установку — пригодной для нескольких проектов.

**Цена.** Команды длиннее, нужен один начальный ответ человека. Это адресация работы, поэтому она обязательна даже при автоматических согласованиях. Упрощать ввод можно проверяемыми launch-конфигурациями, но не скрытым переключателем состояния.

## D03. Один controller, ограниченный параллелизм

**Решение.** В workspace один активный scheduler и 1–4 workers. Выдача задач защищена leader lease и транзакциями; интеграция сериализована отдельно для каждого репозитория.

**Почему.** Несколько независимых оркестраторов увеличивают число конкурирующих решений о задачах, версии кода и ресурсах. Ускорение определяется независимостью графа, временем тестов и интеграции, лимитами моделей и устройств. Добавление контроллеров не даёт бесконечного ускорения.

**Цена и пересмотр.** Один хост ограничивает масштаб. Следующий шаг оправдан измеренной очередью независимых работ. Для распределённого исполнения сначала нужны протокол владения, отмена, budgets, защищённые артефакты и доказательства, а не просто запуск ещё одного экземпляра.

## D04. Три графа и небольшие вертикальные этапы

**Решение.** Отдельно задаются зависимости работ, компонентов и проверок. Большое ТЗ разрабатывается последовательностью сквозных сценариев. Один импорт ограничен 30 задачами; планировщик ориентирован на небольшой первый срез.

**Почему.** Очередь из сотен подробных задач заранее закрепляет неподтверждённые предположения. Сквозной сценарий раньше выявляет проблемы API, среды и интеграции. Раздельные графы позволяют параллельно реализовать frontend/backend по контракту и всё равно проверить реальную комбинацию позже.

**Цена.** Ведущий агент обязан поддерживать трассировку всего ТЗ, иначе маленький этап ошибочно станет «готовым продуктом». Граф компонентов задаётся явно; неполное описание снижает пригодность оптимизации affected. Автоматическое извлечение зависимостей можно добавить как предложение, требующее валидации.

## D05. Контракты до параллельной реализации

**Решение.** Интерфейсы API, поведение ошибок, дизайн и архитектурные договорённости регистрируются как неизменяемые Contract с digest. Задачи закрепляют конкретные версии.

**Почему.** Параллельная разработка эффективна, когда участники согласны об интерфейсе заранее. «Последний файл контракта» может измениться во время работы и сделать результат невоспроизводимым. Новый Contract сохраняет связь старой задачи с её исходным ожиданием.

**Цена.** Изменение семантики требует новой версии и корректировки зависимых задач. Не нужно превращать каждую внутреннюю функцию в общий контракт: фиксируются границы, которые действительно разделяют исполнителей или компоненты.

## D06. Worktree на попытку и повторные проверки после merge

**Решение.** Worker работает в отдельном worktree. Runner создаёт candidate commit, проверяет его, затем объединяет с текущей принятой веткой в отдельном checkout и повторяет gates/review на integration SHA.

**Почему.** Два корректных изменения по отдельности могут сломать систему вместе. Worktree предотвращает случайное редактирование одних файлов в одной папке, но не решает конфликт поведения или конкурирующие миграции. Проверенный integration SHA и CAS связывают принятие с реально включённым кодом.

**Цена.** Тесты и ревью запускаются дважды, расходуются время и лимиты. Кеширование допустимо только с доказуемой идентичностью входов; пропуск интеграционной проверки ради скорости меняет гарантию системы.

## D07. Независимый runtime для ревью

**Решение.** В local mode исполнитель и code reviewer используют разные runtime: Codex и Claude. Для ревью плана/контракта выбирается runtime, противоположный указанному автору. Роли могут задавать собственные пары и модели.

**Почему.** Исполнитель склонен подтверждать собственные предположения. Независимый контекст и второй runtime уменьшают коррелированные ошибки и дают явный контрольный результат. Это практическое правило MVP, а не математическая гарантия независимости моделей.

**Цена и пересмотр.** Нужны оба CLI и их доступы. Разные model names внутри одного runtime сейчас не удовлетворяют политике. При расширении адаптеров можно ввести явную политику независимости, но она должна иметь проверяемый смысл, а не позволять автору называться ревьюером.

## D08. Evidence сильнее самоотчёта и hooks

**Решение.** Test gate требует успешный exit code и свежий непустой JUnit без failures/errors/skips. Review имеет валидируемый структурированный ответ. Evidence привязан к SHA, фазе и политике. Hooks и CI дополняют цикл, но не устанавливают локальный `done`.

**Почему.** Нулевой exit code может означать «тесты не найдены». Старый отчёт может относиться к другому коду. Фраза «всё протестировал» не позволяет воспроизвести проверку. Hooks можно обойти, поэтому они дают раннюю обратную связь, а не являются источником приёмки.

**Цена.** Нужна адаптация reporter и настоящие сценарии. Формат JUnit не доказывает смысл тестов: фиктивные assertions всё ещё возможны. Их предотвращают защищённая test policy, ревью и независимый источник ожидаемого поведения. Невыполнимый обязательный сценарий остаётся блокером.

## D09. Локальные данные компонента, общая координация

**Решение.** Задачи, попытки, роли, локальные контракты, снимки и журнал библиотеки хранятся в ней. Workspace хранит межкомпонентную работу, общие контракты, ChangeSet и ссылки. Контроллер собирает общий граф из этих баз.

**Почему.** Библиотека должна сохранять собственную инженерную историю и правила; продуктовый workspace не должен становиться архивом всех её внутренних работ. При этом общая оркестрация должна видеть зависимости и согласованно менять статусы.

**Цена.** Для работы общего контроллера нужны все базы; физическая локальность не означает автономность. Глобальные IDs и owner metadata связывают компонент с coordinator. Перенос в другой workspace и слияние двух независимых историй требуют отдельной миграции.

## D10. SQLite и ATTACH вместо внешнего сервиса состояния

**Решение.** На одном хосте состояние хранится в SQLite. Для component storage используется ATTACH-транзакция, rollback journal `DELETE` и `synchronous=FULL`; текущая граница — до 10 компонентов. Legacy central storage остаётся для совместимости.

**Почему.** Локальный запуск не требует сервера БД, аккаунтов и сетевого развертывания. Транзакция сохраняет согласованность задачи, попытки и событий между файлами компонентов. WAL не используется для этой многобазовой атомарности.

**Цена и пересмотр.** Нужна надёжная локальная файловая система и совместная резервная копия всех файлов. Есть один writer и ограничение ATTACH. При доказанной потребности нескольких хостов нужно пересмотреть хранилище и протокол блокировок целиком; переносить SQLite-файлы на сетевую шару как замену серверу не является готовым решением.

## D11. Неизменяемая приёмка и корректировки через supersedes

**Решение.** Принятые ревизии не открываются заново. Корректировка создаёт заменяющие задачи и консервативно включает транзитивных потребителей. Принятый ChangeSet заменяется новым.

**Почему.** Если старый `done` вернуть в работу, теряется ответ, какой код и какие критерии были приняты. История должна оставаться пригодной для объяснения регрессии и выпуска. Связь `supersedes` показывает эволюцию намерения без переписывания прошлого.

**Цена.** Задач и повторных проверок становится больше. Исключать зависимых потребителей можно лишь после появления проверяемого impact-review; сейчас консерватизм предпочтительнее незаметной регрессии.

## D12. ChangeSet и закреплённые зависимости

**Решение.** Попытка получает snapshots библиотек с SHA/tree и хешами объявленных артефактов. Общая приёмка проверяет manifest всех компонентов. Полная совместная проверка — default; `affected` является явной оптимизацией с подходящей baseline и полным графом.

**Почему.** «Тестировал с библиотекой из соседней папки» не определяет версию. Отдельные зелёные репозитории не гарантируют совместимость. Фиксация комбинации делает причину результата воспроизводимой и не требует преждевременной публикации промежуточных пакетов.

**Цена.** Интеграционные скрипты зависят от package manager и продукта. Runner не может сам доказать, что скрипт использовал именно snapshot. Нет общей Git-транзакции: локальные изменения библиотеки могут быть приняты до падения продуктового E2E; исправление оформляется новой работой.

## D13. Forge-neutral наблюдение, публикация человеком

**Решение.** GitLab/GitHub и command adapter возвращают факты через общий интерфейс. Встроенные HTTP-запросы — GET. Handoff подготавливает точные команды; push, PR/MR, merge и выпуск пакетов выполняет человек. `remote-check` сверяет источник, итоговое дерево, merge и CI.

**Почему.** Корпоративные доступы часто позволяют только чтение. Модель разработки не должна зависеть от названий MR/PR и способа авторизации одной платформы. Разделение локальной готовности и удалённой публикации соответствует реальным правам доступа.

**Цена.** Финальная публикация требует участия человека, даже при автоматических согласованиях этапов. `remote-check` выполняется явно, webhooks и серверной merge queue нет. Для command adapter доверенная read-only семантика должна обеспечиваться самим адаптером и credentials.

## D14. Явная среда, lifecycle и удержание ресурсов при сбое

**Решение.** Переменные передаются allowlist-конфигурацией; секреты указаны именами источников. Тестовые сервисы запускаются через setup/ready/teardown. Общий host pool резервирует устройства, порты и аккаунты. При неудаче cleanup ресурс остаётся занят до явного восстановления.

**Почему.** Передача всего окружения делает тесты зависимыми от случайного терминала и раскрывает лишние credentials. Истечение lease не доказывает, что оставшийся драйвер перестал управлять устройством. Лучше видимый блокер, чем два конкурирующих теста и ложный результат.

**Цена.** Нужны идемпотентные скрипты очистки и диагностика. Этот механизм координирует согласованные DevContour-процессы, не изолирует произвольный код и внешние процессы. Контейнерный sandbox — отдельное расширение.

## D15. Память и контекст как версионируемый код

**Решение.** Правила находятся в Markdown рядом с компонентом; context packs выбираются по роли/явным IDs и закрепляются по Git SHA/digest. Находка сначала proposed; validated требует проверки. Оперативный журнал строится из SQLite.

**Почему.** Копирование всей истории диалогов создаёт шум и неподтверждённые правила. Закреплённый минимальный контекст объясняет, по каким соглашениям работали автор и reviewer. Один источник статусов предотвращает расхождение доски, TODO и памяти.

**Цена.** Ведущий агент обновляет знания, примеры и locks при изменении API. Семантического поиска по всем навыкам нет. Донорские документы импортируются как непроверенные материалы; их инструкции не получают автоматического приоритета.

## D16. Выбор стека по требованиям и дизайн через токены

**Решение.** Профили предлагают стартовые команды для Vite/React, Next, Go и мобильных проверок. Существующий стек учитывается первым. Дизайн проходит путь референсы → макет/состояния → guidelines → токены → компоненты → функциональная и визуальная проверка.

**Почему.** Универсальный стек навязывает цену SSR админке или лишает публичный продукт необходимого рендеринга. Выбор Go сам по себе не решает медленный SQL. Токены и общие примитивы позволяют менять тему и согласованно соединять библиотеки UI без копирования значений по компонентам.

**Цена.** Профиль необходимо адаптировать, а дизайн — описать до массовой реализации. Объединение Mantine и shadcn требует общей темы и распределения ответственности компонентов; наличие двух библиотек не создаёт дизайн-систему автоматически.

## D17. Переносимое состояние задач в Git, локальное исполнение в SQLite

**Решение.** Командные записи хранятся по одной сущности в `.devcontour/`, получают UUID и согласуются с SQLite через three-way merge. Baseline принадлежит тому же компоненту, что и задача. Строгая проверка графа следует за Git merge. Локальные процессы, аренды и секреты не экспортируются. Назначение участнику фильтрует локальную очередь.

**Почему.** Разработчикам нужны обычные diff, review, ветки и перенос между компьютерами без центрального сервиса. SQLite остаётся удобным транзакционным хранилищем исполнения, но бинарный файл БД не подходит для объединения командных изменений. UUID устраняет пересечения локальных счётчиков, а сравнение с общей baseline обнаруживает потерю правок независимо от часов участников.

**Доверие к результату.** Историческое завершение переносится с receipt из доверенного Git, привязанным к постановке, candidate/result SHA и проверкам. Импорт проверяет структуру доказательства и доступность кода, не изображая новый запуск модели/тестов. UI показывает происхождение результата. Это расширяет прежнее локальное правило приёмки явным путём импорта командной истории; произвольное поле `done` по-прежнему недостаточно. Новый общий результат требует локальной Verification.

**Цена и пересмотр.** Git не даёт глобальных leases, поэтому offline-разработчики могут действовать по устаревшему назначению. Нет атомарного commit нескольких репозиториев, подписи receipt или доставки логов. Общая приёмка и конфигурация окружения не восстанавливаются автоматически. Если понадобится строгая межхостовая диспетчеризация, нужен отдельный протокол/сервис, а не сетевой SQLite или Git merge driver `union`. Полный договор — [командная синхронизация](team-sync.md).

## D18. Версия требования проверяется вместе с кодом

**Решение.** Task может закрепить Markdown REQ-раздел по тексту/digest и связать его с test gate и сценарием. Источник находится в репозитории задачи. Runner проверяет основной HEAD и обе проверяемые версии кода; изменение принятого требования создаёт корректировку, сохраняя историю.

**Почему.** Ссылка на изменяемое ТЗ не объясняет, какое поведение подтверждал старый зелёный тест. Digest отдельного раздела сохраняет точность без аннулирования несвязанных требований. Хранение текста в локальной задаче делает его доступным worker, reviewer и коллеге после Git sync.

**Цена и пересмотр.** Агент выделяет разделы и поддерживает реальные сценарии; совпадение текста не доказывает полноту тестов. Старые задачи без связей сохраняют прежние гарантии. Более строгий реестр всего ТЗ или сопоставление с testcase IDs имеет смысл, если пилот покажет пропуски, которые не ловит review. [Договор требований](requirements.md).

## D19. Сохраняемые стадии поверх существующих условий приёмки

**Решение.** Ведущий агент готовит граф, а работающий сервер продолжает зарегистрированный board/ChangeSet workflow. Job хранит digest входа, стадию, ограниченные попытки и lease в SQLite владельца. Он вызывает существующие доменные операции, не добавляя собственного способа поставить done.

**Почему.** Чат может завершиться между review и запуском очереди. Сохранённая стадия позволяет продолжить подготовленную работу; проверка уже совершённых эффектов уменьшает повторные model calls и дублирование приёмки. Fencing и повторная проверка входа запрещают позднему ответу утвердить изменившийся план.

**Цена и пересмотр.** Сервер должен работать. Новый этап и diagnosis остаются обязанностью ведущего агента. Jobs не переносятся через Git; после clone их регистрируют заново. Очередь общая, а отдельной паузы job нет: обслуживание требует остановки сервера. Расширять автомат до перепланирования следует после измерения причин остановок и определения бюджета, а не добавлением бесконечного retry. [Стадии и восстановление](lead-workflow.md).

## D20. Evals проверяют действия, fixture не оценивает модель

**Решение.** Изолированные сценарии задают начальное состояние и оценивают структурированное решение и фактические эффекты разрешённых операций. Детерминированный driver проверяет evaluator; live runtime/model выбирается явно с лимитами вызовов и времени.

**Почему.** Проверки синтаксиса skill недостаточно, чтобы обнаружить небезопасное решение о цикле DAG, устаревшем контексте или фиктивном done. Отдельный проверяющий код оценивает результат независимо от самооценки агента. Явный live-режим сохраняет воспроизводимость обычных тестов и контроль расходов.

**Цена и пересмотр.** Это небольшой набор решений в заданном состоянии, не benchmark полного продуктового цикла. Нужны повторения и отдельный live-пилот; денежный лимит задаётся у провайдера. Корпус расширяется проверенными обезличенными инцидентами, а не только примерами, удобными текущему skill. [Процедура eval](agent-evals.md).

## D21. Время ожидания и неудачи входят в измерения

**Решение.** Метрики сохраняют все локальные попытки и измеренные стадии, отдельно показывают ожидание зависимостей/выдачи и незакрытые интервалы. Неизвестная стоимость и отсутствующие исторические времена представлены как null.

**Почему.** Среднее только по успешным задачам скрывает retries и затраты на интеграцию. Пауза оператора или занятое устройство не являются временем модели. Определённый знаменатель позволяет сравнивать изменения процесса без приписывания ускорения смене состава задач.

**Цена и пересмотр.** Не все подготовительные действия инструментированы, импортированные receipts не несут локальных измерений. Отчёты разделены по владельцам, а не суммируют компоненты автоматически. Более сложная аналитика оправдана конкретным вопросом пилота; число commits или токенов не заменяет качество. [Метрики](metrics.md).

## D22. Внешнее наблюдение предлагает работу, но не подтверждает результат

**Решение.** Нормализованный сигнал создаёт локальный draft либо корректировку. Источник/event ID обеспечивают дедупликацию, incident ID — связь наблюдений; создание задачи и receipt атомарны. Исчезновение сигнала не устанавливает done.

**Почему.** CI или мониторинг дают полезную обратную связь, но могут повторять доставку, приходить не по порядку и сообщать симптом без причины. Draft сохраняет обычные шаги воспроизведения, планирования и проверки. Разделение наблюдения и evidence не позволяет внешнему сервису обойти условия приёмки.

**Цена и пересмотр.** Нужен адаптер, нормализующий разрешённое наблюдение; встроенного webhook/polling нет. Дедупликация локальна для controller, журнал не переносится через Git и пока не имеет retention. Один поток направляется одному controller. Распределённая доставка потребует отдельного протокола. [Сигналы](external-signals.md).

## Как добавлять решения

Новое решение должно отвечать на пять вопросов: какая конкретная проблема возникла, какие варианты рассматривались, почему выбран этот, какие ограничения принимаются и какое наблюдение заставит пересмотреть выбор. Укажите затронутые инварианты, миграцию и способ проверки. Связанные инструкции переписываются под новое поведение; старое обоснование сохраняется как история с явным статусом замены.

## D23. Измерение отделено от самоотчёта модели

**Решение.** Вызов регистрируется до запуска, нормализованные счётчики берутся из runtime envelope. Ошибка не удаляет расход, отсутствие счётчиков даёт unknown. Тарифная оценка содержит снимок цен и не называется счётом по подписке.

**Почему.** Для выбора модели нужна стоимость принятого результата вместе с ошибками, а не стоимость удачного ответа. Пропущенные вызовы создают ложную экономию. История до инструментирования не восстанавливается догадкой.

**Цена.** CLI могут менять формат telemetry. Нужны parser fixtures, маркировка покрытия и выбранный явно live-пилот после обновления. [Метрики](metrics.md).

## D24. Знания имеют владельца, источник и тип

**Решение.** UUID-записи в Git различают факты, опыт, решения, гипотезы и сводки. Подробности компонента остаются в нём. Изменение источника или неоднозначная замена исключает знание из обычной выдачи. Markdown остаётся читаемым первоисточником.

**Почему.** Повторённое предположение не становится правилом. Одновременные изменения команд не должны перезаписывать общий большой файл или выбирать победителя только по времени. Сводка не должна скрывать устаревшую основу.

**Цена.** Digest гарантирует версию, а не истинность интерпретации. Правила и обязательные требования сохраняются в отдельном полном контексте; поиск выдаёт вспомогательные сведения. Поиск пока лексический с точными entities и ограниченным каталогом. [Память](project-memory.md).

## D25. Бюджет дополнительного контекста проверяется в байтах

**Решение.** Подбор выдаёт целые релевантные записи в границах maxBytes, обязательная постановка не обрезается. Исполнитель и reviewers используют одинаковый снимок.

**Почему.** У runtime разные токенизаторы и скрытый добавочный контекст. Точная граница UTF-8 воспроизводима; фактические токены фиксируются отдельно. Обрезка требований ради экономии меняла бы смысл утверждённой задачи.

**Цена.** Это не полный token budget модели. Улучшение экономичности подтверждается сопоставимым экспериментом.

## D26. История решений не предсказывает неизвестные исходы

**Решение.** Dispatch сохраняет доступные варианты до результата. Offline аудит видит только эти входы; альтернативный выбор без наблюдения считается unsupported. Стратегии не меняют gates и не устанавливаются автоматически.

**Почему.** Изменение порядка разработки может изменить код и результат последующих попыток. Победа на повторном чтении старых удачных исходов не доказывает выигрыш на новых задачах.

**Цена.** Корпус инженерных задач и сравнение отчётов дают стартовую оценку, но для нового проекта нужна отдельная контрольная выборка. Текущий replay — аудит отдельных решений, не симулятор полной альтернативной разработки. [Эксперименты](experiments.md).

## D27. Полнота считается от намерения и инвентаря источников

**Решение.** INTENT.md хранит цель, пользователей, ограничения и истории по релизам; генератор связывает критерии с committed REQ. Истории становятся обычными REQ-intent секциями и используют существующие постановки, review, SHA evidence и Git sync. В workspace хранятся ссылки и digests карт компонентов.

**Причина.** Проверка только созданных задач не обнаруживает требование, забытое при декомпозиции. Поэтому intent_report обходит весь выбранный релиз и все REQ объявленных sources. Явные исключения имеют обоснование и закреплённый digest: изменение исключённого требования требует пересмотра.

**Цена.** Инвентарь источников и смысловую достаточность тестов проверяет ведущий агент/reviewer. Необъявленный файл автоматически не обнаруживается. Общий отчёт не является атомарным snapshot нескольких Git-репозиториев; полноценная приёмка сочетания SHA остаётся ChangeSet. Полнота покрытия не заменяет принятие или публикацию.

**Почему один файл.** Типизированный блок и Markdown-представление лежат рядом, а их совпадение проверяется. Отдельный реестр статусов и дополнительная база не появляются. Свободный Markdown агент нормализует в профиль с сохранением смысла; это осознанная граница поддержки формата.

## D28. Стек подключается из компонента и собирается из частей

**Решение.** Профиль выбирается по встроенному ID или локальному JSON; extends объединяет части стека, проверок и окружения. Источники принадлежат компоненту, lock фиксирует весь состав, роли и права инструментов задаются отдельно.

**Причина.** Закрытый перечень стеков заставлял менять инструмент ради Python, NestJS или нового способа сборки приложения. Композиция позволяет переиспользовать проверки, сохраняя собственные правила проекта и единые условия приёмки. Локальный источник и digest исключают скрытое сетевое обновление.

**Цена.** Ведущий агент обязан подготовить реальные команды и проверить среду. Конфликты не разрешаются автоматически; обновление требует сверки defaults с действующей политикой. Готовый manifest не доказывает работоспособность конкретного продукта. Старые builtin leaf locks остаются совместимыми.

## D29. Продуктовая карта связывает пользовательские возможности с реализацией

**Решение.** Приложения, технические компоненты и репозитории имеют отдельные ID. Общий INTENT хранит фичи, их scope по приложениям и ссылки на локальные истории. Статусы вычисляются по покрытию и совместным проверкам. Локальные задачи и подробные критерии не копируются в общую карту.

**Причина.** Разделение только на фронтенд/бэкенд скрывает сквозной результат: успешные независимые задачи ещё не гарантируют, что блокировка участника работает в каждом клиенте. Явные included/deferred/not-applicable выявляют пропуск уже при планировании. Отсутствие второго изменяемого списка статусов защищает память от расхождений.

**Цена.** Агент поддерживает карту и проверяет достаточность тестов. Каталог размещения компонентов не заменяет write scope, настройки сборки и repository DAG. Для монорепозитория сохраняется общая граница Git-интеграции.

## D30. Приёмка релиза закрепляет продуктовый смысл и совместную версию

**Решение.** ChangeSet с releaseId требует актуального полного покрытия, принятых локальных досок, всех задач релиза и полной совместной проверки. Verification закрепляет digest INTENT, gates и manifest SHA. Перед приёмкой runner повторно проверяет эту связь. Обычные технические ChangeSet продолжают обслуживать промежуточные этапы, но не объявляют продуктовый релиз принятым.

**Причина.** Проверка полноты только по инструкции ведущему агенту могла быть забыта. Привязка к существующему ChangeSet делает её обязательной и использует уже существующие leases, evidence, remote completion и согласования. Отдельный планировщик или новая таблица готовности релизов не нужны.

**Цена.** Полные gates дороже affected-проверок. Digest общей карты консервативно инвалидирует текущую готовность даже при изменении будущего объёма. То же относится к изменениям исходных файлов и плана участвующего репозитория: proof закрепляет эти входы целиком, чтобы не повторять дорогой семантический аудит внутри lease. Совместная приёмка не переносится через Git как локальный PASS и не подтверждает рыночную ценность продукта. Подробный договор — [карта продукта](product-map.md).

## D31. Одна система, три последовательных процесса

**Проблема.** Смешанная доска скрывала разницу между выбором нужного продукта, проектированием решения и выполнением задач. Запуск панели после setup делал самый важный этап непрозрачным, а автоматическое техническое согласование могло восприниматься как согласие пользователя с замыслом.

**Решение.** Панель стартует в пустом workspace. Продукт → архитектура и стек с C1/C2 → разработка представлены отдельными этапами одной системы. Первые два перехода требуют решения пользователя по конкретной версии. `approvalMode` управляет последующими техническими подтверждениями. Задачи закрепляют обе версии; изменение входа требует пересогласования и явной корректировки задач.

**Почему.** Общая система сохраняет связь решения и исполнения без переноса карточек между трекерами. Два решения ограничивают вмешательство пользователя моментами, когда определяется нужный результат и стоимость его устройства. Ранний сервер позволяет видеть черновики и вопросы до появления приложения. C1 показывает окружение системы, C2 — её части и связи; это помогает оценивать стек в контексте ответственности.

**Цена и границы.** Содержательную работу выполняет активный ведущий агент: сервер не превращается в автономного исследователя продукта. Подтверждение в локальной панели — разделение обязанностей, а не удостоверение личности человека. Согласования хранятся одним общим Git-record: конкурентные изменения вызывают явный конфликт. Существующие workspace включают новый процесс через `start`; история не получает фиктивных решений. Разделение сервисов или отдельных записей на изменение имеет смысл после появления измеренной потребности, а не ради дополнительной оркестрации.

**Проверка.** Изменения должны проверять блокировки, устаревшие решения, ранний запуск, совместимость хранилищ, Git-конфликты и UI. [Порядок работы](staged-workflow.md).

## D32. Пользователь выбирает размещение до начала работы

**Проблема.** Обязательный отдельный workspace создавал второй репозиторий и две базы даже для небольшого продукта. Молчаливый выбор по текущему каталогу мог записать память не туда. Простое снятие запрета совпадающих путей приводило к пересечению общих и локальных INTENT, identity, задач и знаний.

**Решение.** Перед первым `start` пользователь выбирает `embedded` или `separate` и абсолютный путь. Ведущий агент объясняет варианты и спрашивает только недостающие сведения. Переносимый маркер хранит режим без локальных путей; локальная копия закрепляет его за текущей базой. Панель и CLI показывают выбранное размещение с первого запуска. Embedded использует корень единственного репозитория, одну SQLite и пространства общей/локальной Git-памяти. Separate сохраняет размещение coordinator вне самостоятельных репозиториев. Продуктовые согласования и правила приёмки одинаковы.

**Почему.** Граница Git определяет интеграцию кода, а не количество приложений. Монорепозиторий с сайтом, API, мобильным клиентом и пакетами остаётся одним репозиторием; его компоненты описываются в продуктовой карте. Разные логические владельцы нужны и внутри одного Git, чтобы карта продукта не дублировала подробные задачи и чтобы переносимая память сохраняла однозначную принадлежность. Явное решение до открытия БД предотвращает необходимость исправлять случайно выбранное размещение после начала работ.

**Цена и границы.** Embedded допускает один репозиторий. Git worktree исполнителя не становится новым controller; независимый clone может иметь свою локальную базу. Изменить режим простым флагом или правкой маркера нельзя: миграция ещё не реализована. Автоматический журнал embedded хранится локально, а содержательные решения агент закрепляет в отслеживаемых документах. Существующие отдельные workspace сохраняют свой режим без повторного выбора. [Порядок работы](workspace-modes.md).
