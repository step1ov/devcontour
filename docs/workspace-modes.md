# Где хранить workspace

[Примеры запуска через CLI и skill](start-examples.md) показывают команды и поручения для каждого режима.

Перед первым запуском пользователь выбирает размещение оркестрации. Для одного репозитория, включая монорепозиторий, удобно хранить всё внутри проекта. Для нескольких самостоятельных репозиториев подходит отдельный workspace. Оба варианта используют тот же процесс: продукт → утверждение → архитектура и стек → утверждение → разработка.

## Выбор без неявного значения по умолчанию

Ведущий агент задаёт один вопрос, если выбор ещё не указан:

> Где хранить оркестрацию: внутри репозитория проекта или в отдельном workspace? Укажите режим и абсолютный путь: в первом случае корень проекта, во втором — отдельную папку.

Агент может рекомендовать вариант по структуре проекта, но не выбирает его за пользователя. Если режим уже указан в поручении или сохранён для этого workspace, повторного вопроса нет. Путь не угадывается по текущему каталогу. Выбор места хранения не зависит от автоматических технических согласований.

| Вариант                          | Когда подходит                                                                        | Путь `--workspace`                                       | Хранение                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------- |
| `embedded` — внутри репозитория  | Один проект или монорепозиторий                                                       | Корень Git-репозитория; Git можно инициализировать позже | Один Git, одна локальная SQLite                                      |
| `separate` — отдельный workspace | Несколько самостоятельных репозиториев; либо намеренное разделение координации и кода | Отдельная папка вне репозиториев компонентов             | Общая SQLite и локальная БД каждого компонента; отдельные Git-памяти |

Первый запуск требует явного `--workspace-mode`. Если режим отсутствует, CLI объясняет варианты и не создаёт базу. Интерактивный вопрос задаёт ведущий агент в чате; CLI не блокируется в ожидании терминального ввода.

До создания SQLite команда добавляет в `.gitignore` правило `/.devcontour-local/`, сохраняя существующие правила проекта. Локальное состояние исключено из Git уже на продуктовом этапе, даже если Git будет инициализирован позже.

## Внутри одного репозитория

```sh
devcontour start --workspace-mode embedded --workspace /absolute/shop --port 0
```

```text
shop/                              # workspace и единственный Git-репозиторий
  apps/
  services/
  packages/
  docs/
    spec.md
    implementation-intent.md       # подробные истории и критерии реализации
  INTENT.md                        # общая карта продукта и релизов
  devcontour.workspace.json        # выбранный режим, без абсолютных путей
  devcontour.component.json        # роли, gates и правила репозитория после setup
  .devcontour/                     # переносимая память в том же Git
    preparations/                  # продуктовые версии и решения
    components/main/               # задачи, локальные доски, контракты и receipts
  .devcontour-local/               # SQLite, конфигурация, worktree и артефакты; ignored
    state.sqlite
    journal/                       # автоматически пересобираемый дневник
```

`main` — ID репозитория при обычном setup; реестр может задать другой ID. Это логическое пространство записей, а не вложенный Git или вторая база. Общие и локальные сущности не дублируются. Папки приложений и внутренних пакетов описываются в карте продукта; отдельно регистрировать их как Git-репозитории не нужно.

После двух пользовательских согласований агент выполняет setup с одинаковыми `--repository` и `--workspace`. Сервер подключает конфигурацию на том же URL. Профиль монорепозитория содержит проверки нужных стеков и совместных сценариев.

Общий и локальный intent имеют разные роли. `INTENT.md` связывает фичи, приложения и релизы; `docs/implementation-intent.md` содержит подробные истории и критерии единственного репозитория. `intent_render` и `intent_snapshot` возвращают фактическое поле `source`: агент использует его при записи и привязке требований. Замена одного документа другим сломает проверку владельца.

## Отдельный workspace

```sh
devcontour start --workspace-mode separate --workspace /absolute/shop-workspace --port 0
```

Код остаётся в `/absolute/shop`, библиотеки — в своих репозиториях. Общие решения находятся в `shop-workspace`. Для Git-синхронизации workspace имеет собственный Git. Настройка нескольких репозиториев описана в [руководстве](workspaces.md).

В исходном checkout замените `devcontour` на `npm run devcontour --`. Установка самого инструмента остаётся отдельной при обоих вариантах.

## Что видно и что сохраняется

Вверху панели с первого запуска видны «Внутри репозитория» или «Отдельный workspace» и абсолютный путь текущего workspace. CLI печатает тот же выбор рядом с URL. Переносимый `devcontour.workspace.json` содержит только версию формата и режим. Локальная копия выбора в `.devcontour-local/workspace-selection.json` защищает текущую БД от незаметного изменения режима через правку файла или Git pull.

При повторном запуске достаточно `devcontour start --workspace /absolute/shop --port 0`. Другой `--workspace-mode` для существующего workspace отклоняется. Смена режима — отдельная миграция размещения памяти, которой пока нет; не переносите рабочую SQLite и не меняйте режим вручную. Существующие настроенные workspace без маркера сохраняют прежний отдельный режим; первый `start` записывает этот выбор.

## Команда, Git и исполнители

В embedded команда клонирует один репозиторий, включая маркер режима, правила, оба intent и `.devcontour/`. SQLite, артефакты, leases и локальная исполняемая конфигурация в Git не попадают. Агент восстанавливает подготовку через ранний sync, заново настраивает конфигурацию для путей текущего компьютера и выполняет полный sync. Готовность и приёмка проверяются по прежним правилам; чужие незавершённые процессы не возобновляются.

Общая и локальная память синхронизируются в одном Git, с отдельными логическими владельцами и baseline внутри единой SQLite. Конкурентные правки требуют того же явного разрешения конфликтов, что и в отдельном workspace. Перед sync сервер и другие записывающие клиенты должны быть остановлены. [Правила синхронизации](team-sync.md).

Controller запускается только в основном checkout. Git worktree исполнителя получает правила и переносимую память как файлы, но не локальную БД и не право запустить новую оркестрацию. Команды отклоняют такую попытку; обычная защита владельца Git дополнительно не допускает другого controller для того же репозитория. Независимый Git clone имеет собственное локальное исполнение и синхронизирует задачи по правилам команды.

Во встроенном режиме автоматический дневник пишется в `.devcontour-local/journal`, чтобы обновление статусов не создавало постоянных незакоммиченных правок исходного репозитория. Содержательные решения и публичный changelog агент сохраняет отдельно в отслеживаемых документах.
