# Правила приёмки и границы MVP

DevContour 0.1 — локальный controller для проверяемой разработки одного или нескольких Git-репозиториев. Этот документ фиксирует обязательные условия принятия и пределы текущей реализации. Концепции раскрыты в [словаре](concepts.md), причины — в [решениях](decisions.md).

## Условия done

Самоотчёт модели, успешный commit или зелёный hook недостаточны. Для принятия Task нужны:

1. Утверждённая неизменившаяся постановка и закреплённые контракты.
2. Завершённые зависимости, актуальное владение попыткой и совпадающая test/runtime policy.
3. Допустимый diff: защищённые пути, context sources и write scope не нарушены.
4. Candidate commit, прошедший все gates и независимое ревью.
5. Integration commit с текущей принятой веткой, снова прошедший gates и review.
6. Успешный cleanup и продвижение локального ref с проверкой ожидаемого старого SHA.
7. Запись результата доменным сервисом с сохранёнными evidence.

Test gate требует свежий непустой JUnit, успешный exit code, отсутствие failures/errors/skips и неизменность проверяемых tracked-исходников. Review с blocking findings не считается успешным независимо от флага approved. Evidence другой попытки/SHA/фазы не заменяет требуемое доказательство.

Это подтверждает объявленные проверки, а не отсутствие всех возможных дефектов. Достаточность сценариев и соответствие ТЗ остаются предметом постановки и независимого review.

## Доска и общий результат

Приёмка доски требует завершённых задач текущей ревизии и присутствия result SHA в соответствующих локальных ветках. Сохраняется неизменяемый snapshot. По умолчанию принимает ведущий агент; operator mode добавляет ручное подтверждение.

ChangeSet объединяет доски одного результата. `workspace-verify` фиксирует manifest всех компонентов, задачи, ревизии, policy и выполняет необходимые совместные gates. `changeset-accept` требует успешной актуальной Verification. Приёмка отдельных досок и общего ChangeSet — разные записи; одно действие не выполняет другое автоматически.

`completionMode: local` допускает приёмку общего результата без публикации. `remote` дополнительно требует Delivery с подтверждёнными merge/tree/CI. Локальные задачи при этом остаются `done` до публикации. Ни один режим не означает автоматического deployment или выпуска пакетов.

## Корректировка после приёмки

1. Укажите принятую доску, корневые задачи и причину изменения.
2. DevContour найдёт актуальные заменяемые задачи и транзитивных потребителей во всём графе, включая другие доски.
3. Создаст новую активную ревизию и draft-задачи с `supersedes`. Зависимости между заменами перенаправятся на новые IDs.
4. Ведущий агент обновит AC, контракты и область работы, проведёт новое review и запустит очередь.
5. После проверок будет принята следующая ревизия. Незатронутые результаты переиспользуются; предыдущая история сохраняется.

Пример: `API-1 → Backend-1 → Screen-1` после изменения API получает `API-2 → Backend-2 → Screen-2`. Screen-2 может потребовать только повторной проверки без изменения кода; это допустимый проверяемый результат.

Анализ консервативный: все зависимые результаты перепроверяются. Если затронутая цепочка ещё не завершена, корректировка отклоняется: сначала завершите или согласованно перепланируйте её, не меняя SQLite вручную. Последующая корректировка разрешает актуальные концы цепочек supersedes и не клонирует заново всю историю.

Междосочные замены входят в новую ревизию инициирующей доски; прежний снимок другой доски остаётся историей прошлого результата. Принятый ChangeSet не открывается заново: создаётся следующий с `supersedes`. У ещё непринятого ChangeSet следующая Verification берёт актуальные ревизии его досок; изменение набора досок оформляется новым ChangeSet.

## Реализовано

| Область             | Текущая возможность                                                                       |
| ------------------- | ----------------------------------------------------------------------------------------- |
| Оркестрация         | Один scheduler на workspace, 1–4 workers, DAG, leases, fencing, явные retries             |
| Роли и runtime      | Architect/backend/frontend/QA, Codex/Claude, независимый reviewer; demo отдельно          |
| Git                 | Worktree на попытку, candidate/integration checks, CAS и восстановление окна Git/SQLite   |
| История             | Неизменяемые ревизии, корректировки, events, evidence и Markdown-дневники                 |
| Workspace           | Несколько репозиториев, общие контракты, ChangeSet и совместные gates                     |
| Локальность данных  | Component SQLite, настройки/роли/журнал в компоненте, central → component migration       |
| Инженерный контекст | Закреплённые instructions, scope, discoveries, repository/gate DAG                        |
| Среда               | Explicit env/tool profiles, dependency snapshots, lifecycle/cleanup, host resource leases |
| Forge               | Read-only GitLab/GitHub/command, human handoff, remote completion                         |
| Интерфейс           | Локальные граф/список/история, контракты, ChangeSet и артефакты                           |

## Ограничения

- Один хост, до 10 подключённых компонентов, доверенный локальный пользователь. Нет SaaS, tenant isolation или защиты от враждебного процесса того же OS-пользователя. Worktree не является sandbox.
- Активный ведущий агент нужен для bootstrap, новых этапов и разбора сбоев. Нет watcher, запускающего полный продуктовый цикл по появлению ТЗ в docs, и встроенного чата-планировщика в консоли.
- Profiles настраивают процесс; универсальный генератор приложений всех стеков не реализован. Выбор модели и переносимость её сессии остаются ограничены CLI.
- Стандартные тесты используют fixtures, не live providers. Авторизация моделей, корпоративные MCP, устройства, Postgres и private registry проверяются отдельным проектным пилотом.
- Нет автоматических push/PR/MR/merge, package publication, forge webhooks, production deployment, атомарной Git-транзакции нескольких репозиториев и федерации controller.
- Ограничиваются параллелизм, сроки и число попыток. Общего денежного/token budget между провайдерами и workspace нет.
- Repository graph описывает целые Git-репозитории; анализа внутренних пакетов монорепозитория нет. Affected-режим зависит от полноты явно заданных связей.
- Host leases координируют заявленные ресурсы, но не создают устройства/контейнеры и не управляют сторонними процессами автоматически.
- Нет автоматического retention/GC, универсального backup/restore, remap путей или слияния независимых непустых компонентных баз.
- Во встроенных forge adapters ограничены страницы наблюдаемых checks/jobs; сложные инсталляции требуют адаптированного read-only command provider. Повторное использование delivery неизменённой библиотеки между разными ChangeSet не автоматизировано.

## Направление развития

Сначала провести небольшой реальный сквозной пилот: bootstrap → Codex/Claude → реальные gates → ChangeSet → human publication → remote-check. Измерить время задач, retries, интеграционные конфликты и ручные действия. Затем выбирать расширение по обнаруженному ограничению: изоляция среды, бюджеты, миграции/retention, новые runtime или распределённое исполнение.

Наличие пункта в этом направлении не является работающей функцией. Новое поведение должно сохранять описанные условия приёмки либо явно менять их с обоснованием, миграцией и проверками.
