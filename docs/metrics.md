# Метрики процесса

`devcontour metrics --workspace /absolute/workspace` показывает общий контур; `--repository-id main` выбирает компонент. MCP предоставляет `workflow_metrics` с тем же выбором владельца. Большой полный отчёт читайте через CLI.

Без `repositoryId` это **не сумма всех компонентов**: в ответ входят общие задачи/доски и ChangeSet. Чтобы оценить продукт с библиотеками, прочитайте каждый нужный компонент отдельно и общий контур. Не суммируйте длительности параллельных попыток как календарное время проекта. Метрики доступны через API/CLI; отдельной панели с этими измерениями в UI пока нет.

Каждая локальная попытка содержит общий elapsed time, статус, runtime/model, digest политики и измеренные интервалы: реализация, candidate/integration test gates, независимое review, ожидание интеграции, setup/ready/cleanup настроенного lifecycle. Интервалы имеют IDs и события начала/окончания. При аварии незакрытый интервал помечен `incomplete`; это не успешное измерение. Некоторые подготовительные действия не инструментированы, поэтому сумма этапов не обязана равняться общему времени.

Ожидание зависимостей считается от утверждения до готовности последней зависимости. Ожидание выдачи — от готовности до claim; оно объединяет паузу, доступность workers и назначение участнику. Оно не называется временем работы модели. Старые/импортированные записи без временных границ дают `null`, а не выдуманный ноль.

Отчёт сохраняет failed/cancelled/expired попытки. Доля приёмок с первой попытки считается среди локальных задач, завершённых успешно или неуспешно; активные задачи и импортированные receipts исключены. Корректировки видны отдельно. В общем контуре также есть время ChangeSet и, для remote completion, ожидание после успешной совместной проверки до приёмки. Это ожидание не является точным временем работы человека.

`firstAttemptAcceptanceRate` — число локальных done с одной попыткой, делённое на число локальных done/failed/cancelled с хотя бы одной попыткой; если знаменатель пуст, значение `null`. `counts.failed` считает Run в failed/cancelled/expired, а `counts.accepted` — задачи со статусом done, не число принятых досок. Исторические superseded-задачи остаются в статистике. Ожидание до первого claim ещё не появляется как завершённая попытка.

## Расходы вызовов

Планирование, contract/plan review, реализация и candidate/integration review регистрируют вызовы в owner-local SQLite (`local_workflow`, namespace `usage`). Запись создаётся до запуска runtime и сохраняет ошибку/отмену; сырые ответы и prompt не копируются в статистику. Сохраняются runtime/model/version, этап, IDs задачи/предмета, время, digest и размер prompt. `returned` означает возврат runtime, а не успешную приёмку задачи. Обрыв controller оставляет active-запись с неполным покрытием.

Claude telemetry читается из финального события `result.usage` и `total_cost_usd` в stream-json; Codex — из `turn.completed.usage`. Кеш нормализуется: inputTokens включает обычный ввод, чтение и запись кеша, поэтому повторно прибавлять cache tokens нельзя. Повреждённый/незнакомый формат не превращается в ноль. Повреждённая строка сохраняет доступные счётчики других событий, но делает поток неполным. Ненулевой exit, timeout и отмена оставляют `complete: false`, даже если часть расхода известна. Данные в structured output самой модели не считаются telemetry.

CLI пишет stdout/stderr в `runtime.log` по мере выполнения. Известные секреты маскируются с учётом границ чанков; лог ограничен по размеру. Для произвольного пользовательского redactor без метаданных секретов вывод удерживается до завершения, чтобы не раскрыть часть секрета. Стандартные redactors DevContour поддерживают потоковую запись. Финальный `runtime.json` и локальная запись usage, связанная с runId, сохраняют время последнего вывода, хвосты обоих потоков, exit code, сигнал, timeout/отмену. Перед остановкой процесс собирает дерево своих дочерних процессов без аргументов команд; если ОС запрещает `ps`, сохраняется явная причина отсутствия инвентаря. Это диагностика попытки, а не PASS evidence.

`costSource: provider-reported` обозначает стоимость, сообщённую runtime. Если её нет, явная таблица `prices` может дать `tariff-estimate`; нужны все токеновые счётчики, точные runtime/model и применимый effectiveAt. Тариф фиксируется в записи при начале вызова. По умолчанию таблица пуста. Обе величины могут отличаться от реального счёта по подписке. Пример настройки — [конфигурация](configuration.md).

`costUsd` равен полной известной сумме только при завершённых измерениях всех учтённых вызовов и наличии telemetry-записей для всех локальных попыток владельца. Active-попытка, старый Run без инструментирования или неизвестная стоимость дают null. `usage.knownCostUsd` показывает известную часть; ноль здесь не означает бесплатную работу. `unknownCalls` и `estimatedCalls` описывают покрытие. Исторические вызовы планирования до появления измерений восстановить нельзя; сведения о них отсутствуют.

`usage.costPerAcceptedTaskUsd` делит полный расход владельца, включая ошибки и его подготовительные review, на число локальных done без imported receipts. Нет принятой задачи или полного измерения — null. Это накопительная метрика владельца, не стоимость отдельного спринта. Планирование всего workspace учитывается в общем контуре; plan review локальной доски — в компоненте. Для суммы продукта с библиотеками читайте общий контур и все компоненты, сохраняя признак неизвестного покрытия.

Подробные вызовы читайте через `usage_report` с repositoryId, limit 1–50 и cursor. Cursor становится недействительным при изменении записей; начните с первой страницы. Полные результаты доступны через AgentService/CLI/HTTP/MCP. Usage, runtime logs, dispatch journal и цены не входят в Git-память задач. Размер исходного prompt — только переданная DevContour часть контекста: runtime может добавить системные инструкции и схемы инструментов.

Сравнение конфигураций и ограничения статистики описаны в [экспериментах](experiments.md). При смене версии CLI проверьте parser fixtures и небольшой явно разрешённый live-пилот; старые счётчики нельзя дополнять выдуманными значениями.
