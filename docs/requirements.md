# Требования и доказательства

[Карта INTENT](intent.md) добавляет проверку от полного заявленного объёма релиза. Её сгенерированные REQ-intent секции привязываются к Task.requirements вместе с подробными REQ. Поэтому смена цели/критерия использует те же digests, requirement-source и корректировки. requirements-report проверяет существующие связи задач; intent-report дополнительно обнаруживает истории без задач и нераспределённые REQ всех объявленных sources.

## Подготовка и привязка

Агент выделяет в `docs/spec.md` разделы второго уровня с устойчивыми IDs, например `## REQ-search: Поиск сообщений`. Раздел продолжается до следующего заголовка первого или второго уровня. Заголовки внутри fenced code не считаются требованиями. Оператору не нужно заполнять отдельный реестр.

После коммита ТЗ агент вызывает `devcontour requirements-snapshot --repository-id main --file docs/spec.md --workspace /absolute/workspace`. Команда читает обычный Git-файл из HEAD и возвращает `id`, `text`, `digest`. Незакоммиченные изменения не являются новой версией входа. Digest охватывает текст раздела, поэтому изменение соседнего требования не инвалидирует все задания.

`source` — относительный путь внутри **репозитория этой задачи**, включая для библиотеки. Привязка не может читать ТЗ из соседнего продукта или общего workspace. Требования библиотеки записываются в её документах с происхождением и связью с общим контрактом; координационная карта хранит ссылки. Это сохраняет локальность задач и позволяет повторить проверку на другой машине.

Например, для раздела `## REQ-search: Поиск сообщений`:

| Поле элемента `Task.requirements` | Откуда берётся                                                                                         |
| --------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `id`                              | `REQ-search` из snapshot                                                                               |
| `source`                          | `docs/spec.md` в том же компоненте                                                                     |
| `text`, `digest`                  | Дословные значения snapshot, включая заголовок                                                         |
| `gate`                            | ID реально настроенного gate с `kind: test`, например `chat-e2e`                                       |
| `scenario`                        | «Поиск по seed возвращает подходящие сообщения; пустой результат показывает empty-state»               |
| `testId`                          | ID testcase, доказывающего сценарий, как его пишет отчёт проверки: `chat.search.finds seeded messages` |

Список добавляется при импорте плана или редактировании черновика. Автоматического разбора произвольного ТЗ в полное покрытие нет: агент выделяет разделы и проверяет, что все порученные требования учтены. Файл ограничен 1 MB, один раздел — 12000 символами; IDs внутри файла уникальны. Разделы вне формата REQ не становятся машинными требованиями.

В `requirements` задания входят возвращённые поля, `source` с относительным путём, `gate` с ID существующей test-проверки и `scenario` с ожидаемым наблюдаемым поведением. Эти данные включены в digest постановки, план review, контекст исполнителя и командный Git sync. Память следует владельцу задания. Сценарий описывает обязательство теста.

## Чем подтверждён критерий

Зелёная проверка сама по себе значит «эта проверка прошла», а не «заявленное поведение кто-то проверял»: общий gate бывает зелёным и тогда, когда сценарий не проверяет ни один тест. Поэтому уровень доказательства называется прямо.

| Уровень    | Что известно                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------ |
| `testcase` | Критерий назвал `testId`, этот тест выполнился на принятом SHA и прошёл                          |
| `gate`     | Проверка была зелёной, но сценарий не связан с конкретным тестом — прежний, более слабый уровень |
| `none`     | Подтверждения нет; причина названа в отчёте                                                      |

Проверки нужен отчёт с перечнем testcases (`report: junit`): из него берётся манифест выполненного — id каждого теста и его исход. Подтверждения не дают посторонний зелёный тест, пропущенный или упавший, повторяющийся id (неясно, какой имелся в виду), обрезанный по размеру манифест, evidence фазы кандидата и evidence на другом SHA. Повреждённый отчёт не даёт манифеста вовсе и проваливает проверку.

Задача, назвавшая `testId`, обязана предъявить его при приёмке — иначе приёмка отказывает с указанием причины. Задачи без `testId` принимаются на прежнем уровне: история не переписывается и не выдаётся за более сильное доказательство.

Разметка сама по себе ничего не доказывает: тест может носить имя сценария и не проверять его. Поэтому независимое ревью получает указание открыть названный тест и отклонить его, если тест не исполняет сценарий или прошёл бы и при сломанном поведении.

## Три версии источника

Runner сопоставляет требования с HEAD основного checkout компонента, candidate и integration SHA. Отсутствующий или изменившийся раздел блокирует принятие Task. Специальное evidence `requirement-source` необходимо вместе с обычными gates и review; одно совпадение текста не доказывает реализацию поведения. Workflow дополнительно проверяет свежесть источника перед приёмкой. Ручная приёмка остаётся проверкой сохранённых evidence/SHAs, поэтому ведущему агенту также нужен актуальный `requirements-report`.

До первого старта сервера ТЗ включается в bootstrap commit. Если `devcontour/accepted` уже существует, новый commit ТЗ в основном checkout не обновляет её автоматически: новая задача должна перенести закреплённый текст в candidate вместе с реализацией. Утверждённый текст есть в её контексте. Убедитесь, что scope разрешает нужный документ; если он защищён, ведущий агент заранее подготавливает согласованное изменение процесса. Не редактируйте refs вручную ради обхода проверки.

`requirements-report --repository-id main` показывает цепочку постановка → требование → gate/scenario → result SHA и актуальность покрытия. Старый `done` сохраняется как исторический факт; он не доказывает соответствие новому ТЗ. Отчёт не объявляет полноту всего ТЗ, если часть разделов вообще не связана с задачами.

Отчёт показывает актуальные концы цепочек `supersedes`. `fresh` означает совпадение закреплённого раздела с committed HEAD; `verified` дополнительно требует `done` и PASS указанного test gate на integration/result SHA. Evidence может происходить из локальной попытки или доверенного Git receipt; импорт не становится повторным локальным тестированием. Историю прежних ревизий читайте на доске.

## Изменение ТЗ

`requirements-correct --board ID --reason "…"` на принятой доске обнаруживает изменившиеся разделы, создаёт новую ревизию с транзитивными потребителями и обновлёнными привязками. Новые задания остаются draft до review. Удалённый раздел требует явного перепланирования. Если затронутая цепочка ещё выполняется, действуют обычные ограничения корректировок.

Перед командой закоммитьте новую версию источника при остановленной работе. Команда обновляет привязки текста/digest, но не переписывает за агента AC, `scenario`, контракт, тест или реализацию. Пересмотрите их, проверьте влияние на потребителей, затем зарегистрируйте workflow новой ревизии. Несвязанный новый REQ потребует отдельной задачи: команда ищет изменения уже существующих связей. Если ничего не изменилось, ответ — `status: unchanged`.

MCP предоставляет `requirements_snapshot`, `requirements_report`, `requirements_correct`. Для больших ответов действует общий лимит 64 KiB с явной ошибкой; полный отчёт доступен через CLI. Новые привязки необязательны для старых заданий; без них прежние гарантии приёмки сохраняются, а прослеживаемость требований не заявляется.
