# Требования и доказательства

Агент выделяет в `docs/spec.md` разделы второго уровня с устойчивыми IDs, например `## REQ-search: Поиск сообщений`. Раздел продолжается до следующего заголовка первого или второго уровня. Заголовки внутри fenced code не считаются требованиями. Оператору не нужно заполнять отдельный реестр.

После коммита ТЗ агент вызывает `devcontour requirements-snapshot --repository-id main --file docs/spec.md --workspace /absolute/workspace`. Команда читает обычный Git-файл из HEAD и возвращает `id`, `text`, `digest`. Незакоммиченные изменения не являются новой версией входа. Digest охватывает текст раздела, поэтому изменение соседнего требования не инвалидирует все задания.

В `requirements` задания входят возвращённые поля, `source` с относительным путём, `gate` с ID существующей test-проверки и `scenario` с ожидаемым наблюдаемым поведением. Эти данные включены в digest постановки, план review, контекст исполнителя и командный Git sync. Память следует владельцу задания. Сценарий описывает обязательство теста; совпадение его текста с именем testcase автоматически не проверяется — достаточность покрытия оценивает независимое ревью.

Runner сопоставляет требования с исходным HEAD, candidate и integration SHA. Отсутствующий или изменившийся раздел блокирует приёмку. Специальное evidence `requirement-source` необходимо вместе с обычными gates и review. Изменения ТЗ, нужные в принятой ветке, должны войти в проверяемый результат задачи; утверждённый текст присутствует в её контексте. Не редактируйте рабочие refs для обхода проверки.

`requirements-report --repository-id main` показывает цепочку постановка → требование → gate/scenario → result SHA и актуальность покрытия. Старый `done` сохраняется как исторический факт; он не доказывает соответствие новому ТЗ. Отчёт не объявляет полноту всего ТЗ, если часть разделов вообще не связана с задачами.

`requirements-correct --board ID --reason "…"` на принятой доске обнаруживает изменившиеся разделы, создаёт новую ревизию с транзитивными потребителями и обновлёнными привязками. Новые задания остаются draft до review. Удалённый раздел требует явного перепланирования. Если затронутая цепочка ещё выполняется, действуют обычные ограничения корректировок.

MCP предоставляет `requirements_snapshot`, `requirements_report`, `requirements_correct`. Для больших ответов действует общий лимит 64 KiB с явной ошибкой; полный отчёт доступен через CLI. Новые привязки необязательны для старых заданий; без них прежние гарантии приёмки сохраняются, а прослеживаемость требований не заявляется.
