# Руководство разработчика DevContour

Здесь описана работа над самим инструментом. Создание продукта с его помощью начинается с [workflow](workflow.md) и [START.md](../START.md). Для исправления исходников DevContour отдельный продуктовый workspace спрашивать не нужно.

## Подготовить среду

Нужны Node.js 24.3+, npm, Git. Сверьте `package.json` и lockfile; не обновляйте зависимости просто для первого запуска. Реальные модели для стандартных тестов не требуются.

```sh
cd /Users/antonstepanov/PhpstormProjects/devcontour
npm ci
npm run dev
```

`dev` поднимает demo и Vite middleware. Для серверных изменений перезапускайте процесс. Для изолированного учебного экземпляра используйте `npm run devcontour -- demo --data /tmp/devcontour-dev --port 4318 --dev`.

Для браузерных проверок:

```sh
npx playwright install chromium
npm run check
npm run format:check
```

На CI Linux устанавливаются и зависимости браузера через `playwright install --with-deps chromium`. Если среда запрещает запуск браузера, сохраните точную причину: это невыполненная проверка, а не повод заменить её пустым тестом.

Проверьте `git status`, если это Git checkout. Распакованный дистрибутив может не содержать `.git`; hooks в нём не устанавливаются. Для командной разработки используйте полноценный Git checkout и обычный процесс веток/review команды.

## Что запускать ежедневно

| Команда                 | Назначение                                                              |
| ----------------------- | ----------------------------------------------------------------------- |
| `npm run dev`           | Demo + Vite для локальной разработки UI                                 |
| `npm run typecheck`     | Проверка TypeScript без сборки                                          |
| `npm run lint`          | Проверка использования цветовых токенов; это не общий ESLint            |
| `npm run build`         | Typecheck и Vite-сборка UI                                              |
| `npm test`              | Node unit/integration tests, включая реальные временные Git-репозитории |
| `npm run test:e2e`      | Playwright и accessibility-сценарии                                     |
| `npm run check`         | lint → build → test → test:e2e                                          |
| `npm run format:check`  | Prettier; выполняется отдельно от check                                 |
| `npm run hooks:install` | Установка hooks в Git-копии                                             |

Pre-commit запускает token lint и typecheck; pre-push и текущий GitHub Actions workflow — `check`. Наличие CI-конфига для GitHub не ограничивает forge продуктов: это разные интеграции. Для другого CI воспроизведите те же проверки и сохранение отчётов.

## Первое знакомство с кодом

Читайте в таком порядке:

1. `src/core/model.ts` — сущности, точные статусы и Config.
2. `src/core/graph.ts` и `plan.ts` — зависимости и импорт.
3. `src/core/service.ts` — утверждение, claim, evidence, finish, retry и correct.
4. `src/core/store.ts` — транзакционная оболочка изменений; затем `component-storage.ts` — физическая локальность данных.
5. `src/runner/scheduler.ts` — исполнение одной попытки и интеграция.
6. `src/runner/adapters.ts`, `gates.ts`, `process.ts` — границы с CLI, отчётами и subprocess.
7. `src/core/workspace.ts` / `src/runner/workspace.ts` — общий результат.
8. `src/cli.ts`, `src/server/http.ts`, `src/web/App.tsx` — пользовательские входы и отображение.

Отследите один demo Run: ID задачи → claim → артефакты → candidate SHA → integration SHA → resultSha. Затем разберите failed Run и убедитесь, почему его нельзя принять. Такой маршрут быстрее объясняет систему, чем чтение UI от начала до конца.

## Инварианты при изменениях

- Редактируется только допустимая текущим состоянием постановка. Утверждённый spec digest и принятые snapshots не меняются задним числом.
- Циклы и неизвестные ссылки запрещены во всех DAG.
- Все записи активной попытки проверяют актуальное владение/token. Старый ответ не завершает новый Run.
- `done` связан с candidate/integration evidence, текущей политикой и Git-интеграцией. Новое API не может обойти это правило.
- Локальные тела задач/попыток и snapshots не начинают храниться в coordinator ради удобства нового экрана.
- Отмена, timeout и cleanup failure сохраняют корректность состояния и ресурсов.
- Несовместимость профиля/контекста — явная ошибка; молчаливый fallback меняет условия проверенной работы.
- Demo/fixture не превращается в production runtime при отсутствии credentials.

Причины этих ограничений — в [решениях](decisions.md). Если новое требование конфликтует с ними, сначала оформите изменение модели и миграцию, затем реализацию.

## Обычный цикл изменения

1. Опишите наблюдаемую проблему и ожидаемое поведение: кто вызывает действие, в каком состоянии, какой результат должен увидеть.
2. Найдите доменный слой и тест, который уже проверяет ближайший инвариант. Согласуйте формат на границе core/runner/API до параллельного изменения этих частей.
3. Для дефекта воспроизведите его существующим сценарием или небольшим regression test. Для новой возможности проверьте позитивный результат и существенный отказ: stale token, другой SHA, отмена или повреждённый отчёт — в зависимости от риска.
4. Реализуйте изменение в одном источнике правил. CLI и HTTP должны вызывать его, а не копировать проверки.
5. Выполните подходящие тесты, затем требуемый общий check. Запишите реальные результаты и ограничения среды.
6. Обновите руководство, примеры, переносимые правила и обоснование, если изменился договор системы.
7. В review передайте проблему, новое поведение, совместимость и проверку. Число изменённых файлов само по себе ничего не объясняет.

Не нужны тесты, буквально повторяющие строку документации или внутреннюю реализацию. Нужны тесты, способные поймать потерю важной гарантии. Документационное изменение проверяйте ссылками, форматами и исполнимостью примеров; полный модельный пилот для новой формулировки не требуется.

## Карта тестов

| Область                 | Где искать                                               | Что проверять при расширении                                                                |
| ----------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Задачи, DAG, ревизии    | `tests/core.test.ts`                                     | Цикл, неизвестная зависимость, stale spec, immutable acceptance, transitive correction      |
| Runtime и Git           | `tests/runner.test.ts`                                   | Candidate/integration failure, конфликт merge, поздний ответ, неизменность проверенного SHA |
| Общий результат         | `tests/workspace.test.ts`                                | Комбинация версий, провал consumer gate, изменившаяся policy, snapshot приёмки              |
| Context/scope/resources | `tests/engineering.test.ts`                              | Digest, protected paths, findings, ресурсное владение                                       |
| Хранилища/интеграции    | `tests/enterprise.test.ts`                               | Локальность записей, миграция, cleanup, dependencies, forge observations                    |
| Начало работы           | `tests/setup.test.ts`, `scope.test.ts`, `config.test.ts` | Существующие файлы, явный workspace, profile locks, совместимость                           |
| AI-согласования         | `tests/agent-control.test.ts`                            | Независимость, blocking review, изменённая после review постановка, operator mode           |
| HTTP/UI                 | `tests/http.test.ts`, `e2e/harness.spec.ts`              | Origin/Host, заголовки, публичный сценарий, доступность и состояния интерфейса              |

Fixtures используют временные репозитории, bare remotes, локальные HTTP-ответы и управляемые процессы. Они проверяют поведение без платного API и credentials. Не заменяйте реальную Git-проверку mock-ответом там, где риск заключается именно в Git ancestry/ref/worktree.

При изменении workflow обязательны core tests и Git fixture; при изменении UI — браузер. Доступность live Codex/Claude, устройства и корпоративного MCP проверяется отдельным выбранным пилотом. Полный отчёт должен различать PASS, FAIL, not run и ограничение среды.

## Добавить runtime

Текущий набор `codex | claude | demo` явно перечислен в схемах. «Плагин runtime» ещё не загружается динамически.

Проверьте `AgentAdapter` и формат реализации/review в `adapters.ts`. Новый адаптер должен принимать cwd, prompt, schema, model, timeout/signal, tool profile и возвращать нормализованные данные/лог. Изменения затронут runtime enums, конфигурацию ролей, инструменты, doctor, политику независимого review, planner/agent-control, UI и fixtures.

Обязательные случаи: невалидный JSON, ненулевой exit, зависший процесс, отмена, отсутствие credentials, blocking finding при положительном approved, маскирование известного секрета. Нельзя считать произвольный stdout корректным ответом только по совпадению слова PASS.

## Добавить стек или gate

Профиль находится в `packs/profiles/`, но список разрешённых профилей также закреплён в loader/config. Добавьте manifest, поддержку загрузки, lock/digest и пример реального reporter. Проверьте повторный setup и поведение при изменённом профиле. Не меняйте существующую версию профиля без осознанного обновления lock у потребителя.

Новый gate обычно является конфигурацией и проектным скриптом, а не изменением ядра. `command` — массив argv без неявного shell. Test gate пишет свежий JUnit в `HARNESS_REPORT_PATH`, возвращает корректный код выхода, не меняет tracked-код и очищает внешние ресурсы. Новый формат доказательств потребует изменения схем и правил acceptance.

## Добавить forge

Читайте нормализованный интерфейс в `src/runner/forge.ts` и условия в `src/core/delivery.ts`. Провайдер возвращает source/merge SHA, дерево и checks; общий домен решает, достаточно ли наблюдения. Для частной установки можно сначала использовать `command` adapter, соблюдая его вход/выход и read-only права.

Проверьте pending, failure, skipped, отсутствие CI, CI на другом SHA, изменённое дерево, merge/squash, target ancestry, timeout, stale token и повтор одного handoff. Не помещайте вызов push/MR/merge в существующий read-only контракт.

## Изменить storage или общую схему

Загрузчик принимает `version: 1`; общей инфраструктуры автоматических миграций всех будущих схем нет. Для нового поля определите default для старых данных, физического владельца, поведение исторического snapshot и участие в digest. Для несовместимого формата нужна явная миграция с проверкой восстановления и резервной копией.

Проверьте central и component mode, rollback при отказе, чтение из нескольких клиентов и отсутствие тел локальных объектов в coordinator. Простой `ALTER` или новое поле JSON без проверки accepted history может сделать старое доказательство двусмысленным.

## Изменить UI и документы

UI отображает серверное состояние и объясняет блокировку. Новый цвет вводится через `src/web/tokens.css`; в компонентах используются семантические переменные. Проверяйте клавиатуру, focus, мобильную ширину, loading/empty/error, длинные тексты и переход к evidence.

При изменении `START.md`, `workspaces.md`, `engineering-context.md` или `project-integration.md` проверяйте также перенос `setup`: в продукте эти документы имеют другие имена. Существующие продуктовые копии сохраняются, поэтому обновление шаблона не является их автоматической миграцией.

## Что не стоит делать первым расширением

Не увеличивайте количество контроллеров до измерения bottleneck. Не добавляйте SaaS-доступ поверх локального HTTP без модели доверия. Не заменяйте Git/SQLite-инварианты «договорённостью в промпте». Практичный следующий этап — один реальный продуктовый пилот с измерением времени ожидания, стоимости двойных проверок, причин retries и ручных действий; по этим данным выбирается следующий вертикальный срез системы.

## Развивать Git sync

Формат задаёт `src/core/sync-model.ts`, преобразование и инварианты — `sync-state.ts`, операции с рабочим деревом — `src/runner/git-sync.ts`. Baseline пишется через Store в физическую БД владельца. `tests/git-sync.test.ts` использует независимые clones и настоящие commit/pull: это обязательная проверка для изменения формата и reconciliation.

Проверяйте идемпотентность, разные локальные пути, UUID, одновременное добавление задач в доску, независимые/конфликтующие поля, неверный DAG, неизменность accepted history, отсутствие result SHA и отказ без частичного изменения БД. Не добавляйте секреты, логи, токены или executable config в переносимую запись. Peer receipt — отдельное происхождение результата, UI и документация должны сохранять это различие.
