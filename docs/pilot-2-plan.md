# Пилот 2: от ТЗ до принятой фичи

Статус: **подготовлен, не выполнялся**. Пилот проверяет самостоятельное планирование ведущим агентом, карту продукта и совместный результат. Fixture-тесты инструмента этого не доказывают.

## Подготовка и разрешение

1. Выполнить `node scripts/reviewer-sandbox-probe.mjs` на хосте, где будет работать reviewer. Чтение и тест должны пройти, запись в файл и Git ref должна быть запрещена. Ошибка запуска sandbox — блокер пилота, а не успешный запрет записи.
2. Подготовить документы без моделей: `node scripts/prepare-pilot-2.mjs`. Скрипт напечатает путь отдельного временного каталога с [ТЗ](pilot-2-spec.md), пустым журналом вмешательств и планом лимитов.
3. Человек выбирает точные модели ведущего агента, автора и reviewer, задаёт денежный бюджет и явно разрешает запуск. Значения не выбираются автоматически из подписки. Автор и reviewer используют разные runtime. Материалы не передаются моделям до этого разрешения.
4. Ведущий агент получает ТЗ и явный workspace; сам выполняет setup, локальные INTENT, карту, контракты, задачи и workflow. Максимум пять задач, один исполнитель одновременно и одна попытка на задачу. Декомпозиция и approvals заранее не заполнены.

Для отдельной проверки команд reviewer на уже существующем маленьком сценарии подготовлен запуск (тоже только после разрешения):

```sh
npm run test:live -- --live --author-model AUTHOR_MODEL --reviewer-model REVIEWER_MODEL --require-review-commands
```

Он требует реального события выполнения `node verify.mjs --read-only` с exit 0 и маркером вывода. Прежний diff-only ответ теперь завершит этот строгий пилот ошибкой. Это проверка одного сценария reviewer, не замена пилоту самостоятельной декомпозиции.

## Лимиты и остановка

Предложенный максимум: 20 вызовов, включая ведущего агента, контрактное/плановое ревью, реализацию и оба code review; 240 секунд на попытку; 60 минут всего; 3–5 задач. Человек может уменьшить лимиты перед разрешением. Повторы после сбоя требуют решения наблюдателя и расходуют тот же бюджет, а не получают новый.

`pilot-limits.json` — план наблюдения, а не новый формат конфигурации controller. Агент переносит concurrency, maxAttempts и runTimeoutMs в действующие поля конфигурации. Единого денежного или межсессионного лимита вызовов ведущего агента и двух CLI пока нет. Поэтому запуск проходит под наблюдением: после каждого вызова фиксируются токены и известная/оценочная стоимость; до следующего вызова наблюдатель сверяет остаток. При неизвестной цене автоматическое продолжение приостанавливается до решения человека. При достижении лимита останавливаются ведущая сессия и сервер, отменяется активная попытка; одной паузы выдачи задач недостаточно для остановки уже работающего CLI. Текущий вызов может превысить денежный порог до получения telemetry — жёсткий долларовый стоп не заявляется.

Тарифы, если нужны оценки, задаются явно с источником, точной моделью и effectiveAt. API-оценка не выдаётся за фактический счёт подписки.

## Наблюдение

Наблюдатель ведёт interventions.jsonl: время, этап, действие, причина и инициатор. Автоматические usage записи собираются по владельцам; ведущие вызовы вне controller записываются отдельно с указанием, что источник — наблюдение, а не runtime telemetry. Нужно измерить:

- Вызовы, токены, известную/оценочную стоимость по runtime и ролям; candidate и integration review отдельно; unknown сохраняется как unknown.
- Ретраи, неудачные попытки и причины; число ручных исправлений конфигурации, кода и постановок.
- Время подготовки карты ведущим агентом, число ошибок, найденных валидатором, intent-report и reviewer, число циклов исправления.
- Изменения карты после совместной проверки: что изменилось, обосновано ли устаревание, длительность и стоимость повторного полного прогона.
- Число review с подтверждёнными командами, число diff-only и конкретные причины.
- Прочитанные разделы START и skill, объём контекста; если CLI не даёт такой трассы, значение неизвестно, а не восстановлено по успешному результату.

После первой успешной Verification наблюдатель один раз меняет описание отложенной CSV-фичи. Агент должен заметить устаревание, сохранить историю и повторить приёмку. Это отдельная контролируемая проверка консервативного digest; её время и расход записываются отдельно от разработки сценария.

## Критерии

**Успех:** агент сам создал валидную карту и 3–5 задач с зависимостью; реализованы создание и сохранение списка; негативные, совместные и браузерные проверки проходят; у code reviewer есть подтверждённая команда теста; releaseId принят на актуальных SHA; изменение карты инвалидирует прежнюю готовность; повторная приёмка сохраняет историю; лимиты соблюдены и вмешательства раскрыты.

**Провал:** фиктивные/ослабленные тесты, необнаруженная неполнота scope, ложная приёмка, изменение reviewer защищённых файлов/refs, недоказанный запуск команды в строгой части, исчерпание лимитов или ручное написание существенной части реализации вместо агента. Ошибка доступа/среды фиксируется отдельно как blocked, без оценки качества модели по незапущенному сценарию.

До реального запуска такой отчёт не заполняется вымышленными значениями.

Сырые логи остаются локально. В evidence публикуются только очищенные от секретов, личных путей и продуктовых данных результаты. Push и публикация остаются отдельным действием человека.
