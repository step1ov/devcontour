# Карта документации

Контекст для ведущего агента и переносимые точки продолжения — [интерфейс агента](agent-interface.md).

Установка без исходников и проверка npm-архива — [поставка DevContour](distribution.md).

Подключение из AI-клиента — [MCP и переносимый skill](mcp-server.md).

Документация описывает текущий MVP DevContour. «Реализовано» означает наличие механизма в коде; это не обещание успешного подключения любого внешнего сервиса без настройки. Возможности будущих версий отмечены отдельно. Команды выполняются из каталога установленного DevContour, если явно не указано другое.

## Первые полчаса

1. Пройдите [быстрый старт](quickstart.md): запустите demo, откройте задачу, найдите её попытку, тесты и итоговый SHA.
2. Прочитайте [концепции](concepts.md): разницу между установкой, workspace и компонентом; между задачей, доской и ChangeSet.
3. Выберите маршрут ниже. Все детали конфигурации заранее запоминать не нужно.

## Источники истины

У документации и артефактов разные роли:

- ТЗ и утверждённые контракты задают ожидаемое поведение продукта.
- Git хранит исходники, тесты, правила компонента и принятые изменения кода.
- SQLite хранит задачи, попытки, события и записи приёмки. Markdown-дневник — восстанавливаемое представление этих записей.
- В командном режиме `.devcontour/` хранит переносимое состояние задач. `sync` согласует его с SQLite по последней baseline; активные процессы и локальные артефакты в Git не переносятся.
- Версионируемые `memory/` и ADR хранят проверенные знания и объяснения решений; они не дублируют оперативные статусы задач.
- Схемы и доменные проверки в `src/core` задают реально поддерживаемый формат и переходы. Если руководство расходится с кодом, это дефект документации или реализации, который нужно проверить и исправить, а не повод обходить проверку.

Примеры с `/absolute/...`, `example.internal`, условными IDs и именами скриптов требуют подстановки. Они показывают формат; соответствующий скрипт и доступ должны существовать в конкретном проекте. Полные JSON-примеры импорта находятся в `packs/`; большинство JSON-блоков справочников — фрагменты конфигурации.

## Как поддерживать документы

Изменение поведения сопровождается правкой соответствующего руководства, примера и, при изменении принципа, записи в [решениях](decisions.md). Не добавляйте очередную заметку «теперь поддерживается» поверх устаревшего раздела: перепишите его под текущее состояние. Общие правила держите в одном нормативном месте, из остальных документов ссылайтесь на него.

`START.md`, `workspaces.md`, `engineering-context.md` и `project-integration.md` переносятся `setup` в продукт под именами `harness-*.md`. Существующие копии не перезаписываются. При обновлении проверьте ссылки и осознанно перенесите полезные изменения в правила продукта.
