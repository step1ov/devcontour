# Проектные знания и контекст

Память помогает агенту восстановить решения и опыт своего компонента. Она не ведёт второй список статусов задач, не подтверждает тесты и не меняет права исполнителя. Оперативные статусы остаются в SQLite, переносимые задачи — в формате [Git-синхронизации](team-sync.md), человеческие обоснования — в Markdown.

## Что сохранять

`memory_retain` создаёт отдельный неизменяемый JSON в `<owner>/.devcontour/knowledge/<uuid>.json`. Владелец выбирается явно: `repositoryId` означает репозиторий компонента, отсутствие поля — общий workspace. Подробности библиотеки не копируются в общую память. Ссылки `supports` и `supersedes` разрешены только внутри этого владельца.

В режиме `embedded` оба владельца находятся в одном Git. Общая память сохраняет путь `.devcontour/knowledge/`, локальная использует `.devcontour/components/<repositoryId>/knowledge/`; её `context-identity.json` находится под тем же префиксом. Это исключает смешивание записей и не создаёт второй БД. Используйте путь из ответа API. [Режимы размещения](workspace-modes.md).

| kind       | Содержание                                        | Ограничение                                                                                 |
| ---------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| fact       | Утверждение с источником                          | Наличие источника не доказывает верность интерпретации агента                               |
| experience | Наблюдение из выполнения и проверенное объяснение | Сначала сохраните подходящий отчёт в Git                                                    |
| decision   | Документированное решение проекта                 | Запись не создаёт контракт или approval; источник должен описывать реально принятое решение |
| hypothesis | Предположение для будущей проверки                | По умолчанию исключено из рабочего контекста                                                |
| summary    | Производная сводка                                | Обязательны `supports`; устаревшая или спорная основа делает сводку устаревшей              |

Сохранение не вызывает LLM. Ведущий агент формулирует текст, выбирает тип и источники. API проверяет структуру и происхождение, а смысловое соответствие источнику остаётся ответственностью автора и review проекта. Не сохраняйте полный диалог, credentials и самооценку модели как подтверждённый факт.

Пример `request.json` после коммита исходного ADR:

```json
{
  "operation": "memory_retain",
  "input": {
    "repositoryId": "chat",
    "kind": "decision",
    "subject": "chat.pagination",
    "text": "Список сообщений использует cursor pagination; offset не является частью публичного контракта.",
    "entities": ["chat", "pagination"],
    "sources": ["docs/decisions/pagination.md"]
  }
}
```

Передайте файл через `devcontour agent --workspace /absolute/workspace --file /absolute/request.json` либо отправьте тот же envelope в HTTP/MCP. ID `chat` должен существовать в конфигурации. API читает обычные committed-файлы из HEAD, закрепляет SHA и digest текстового содержимого. Незакоммиченные изменения источника не входят в запись. Для общей памяти источники находятся в Git самого workspace.

`observedAt` необязателен: время описываемого события может отличаться от `createdAt`. Будущие даты отклоняются. Для замены передайте UUID прежних записей в `supersedes`; они должны иметь тот же `subject` и `kind`. История сохраняется. Параллельные несовместимые `fact`/`decision` с одним subject получают `conflicting`; выбор «последняя запись победила» не применяется. Разрешение конфликта — новая запись с обоими UUID в `supersedes`.

## Извлечение и актуальность

```json
{
  "operation": "memory_recall",
  "input": {
    "repositoryId": "chat",
    "query": "пагинация сообщений",
    "entities": ["pagination"],
    "maxBytes": 8000
  }
}
```

Поиск сопоставляет слова запроса и точные entity IDs, ранжирует совпадения и использует время/UUID для устойчивого порядка. `after`/`before` ограничивают время наблюдения, либо создания, если `observedAt` отсутствует. Пустой запрос возвращает подходящие записи по времени. Векторного поиска, нечёткого разрешения сущностей и дополнительной модели ранжирования пока нет.

По умолчанию возвращаются только current-записи, кроме hypothesis. Изменённый или удалённый файл источника, неизвестный/заменённый support, спорная основа и цикл supports исключают знание из обычной выдачи. Статусы `stale`, `superseded`, `conflicting`, `ungrounded` можно исследовать через `includeUncertain: true`; этот флаг не делает их достоверными. Совпадение digest проверяет актуальность текста, а не истинность его интерпретации. Граф знаний допускает связи, не связанные с порядком работы; он не заменяет DAG задач.

`maxBytes` ограничивает сериализованный непустой массив записей в UTF-8, а не обещает точное число токенов любого провайдера. Диапазон 0–24000, по умолчанию 8000. Целые записи выбираются без обрезки текста, не поместившиеся учитываются в `omitted`. Метаданные envelope не входят в бюджет. Пустая выдача имеет `usedBytes: 0`; служебные символы `[]` не считаются полезным контекстом. При нулевом бюджете записи не выдаются. Фактические токены измеряет [runtime telemetry](metrics.md).

Текущая реализация читает локальные JSON непосредственно: до 2000 записей, до 32 KiB на запись. Нет внешнего сервиса или отдельного поискового индекса для синхронизации. После clone каталог читается сразу; превышение лимита — явная ошибка. Для существенно больших банков нужен отдельный индекс/адаптер с теми же правилами владения и происхождения.

## Как память попадает в выполнение

Перед реализацией scheduler подбирает знания по названию, описанию и contract IDs задачи. `memoryPolicy.maxBytes` задаёт бюджет, 0 отключает вспомогательную выдачу. Для локальной задачи источники проверяются относительно начального принятого SHA; для общей задачи используются источники HEAD workspace. Снимок передаётся исполнителю и обоим reviewers без повторного поиска. Run хранит IDs, revision, digest и размер, артефакт `context.json` — выданный текст. Позднее изменение каталога не подменяет контекст уже начавшейся попытки.

Полные требования, критерии приёмки, контракты и закреплённые context packs передаются отдельно и не сокращаются этим бюджетом. Память помечена как вспомогательные данные, не как исполняемые инструкции. Значимые проектные ограничения по-прежнему оформляются контрактом или обязательными правилами; их нельзя полагать доступными только через поиск.

Изменение каталога или актуальности его источников отражается в overview revision и `checkpoint_changes` как изменение записи `knowledge`. Это подсказка перечитать контекст, а не разрешение возобновить старый процесс.

## Совместная работа

`.devcontour/context-identity.json` использует уже существующий Git identity владельца, как checkpoints. Инициализируйте и закоммитьте identity до раздачи независимых clones. Новые UUID-файлы объединяются обычным Git; одинаковые записи не редактируются на месте. После получения чужих изменений поиск заново вычисляет актуальность и противоречия. `sync` задач не импортирует знания в SQLite и не переименовывает их владельца.

Ведущий агент сохраняет знания после содержательного этапа: сначала документирует и коммитит источник, затем создаёт типизированную запись, проверяет выдачу и коммитит переносимую память в соответствующем репозитории. Внешнюю публикацию выполняют по принятой в проекте политике. Symlinks, неправильные имена файлов и несовпадение identity/владельца отклоняются.
