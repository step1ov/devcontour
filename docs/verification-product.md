# Проверка карты продукта и приёмки релиза

Дата: 18 сентября 2026 года. Среда: macOS, Node.js 24.3.0. Проверки используют временные Git-репозитории, worktrees и независимые clones. Новых вызовов моделей, push или публикации в этом изменении не было.

## Что изменилось

Продуктовая карта разделяет пользовательские приложения, технические компоненты и Git-репозитории. Матрица фич задаёт явный объём каждого релиза: включено, отложено или неприменимо. Общая карта хранит ссылки на локальные истории; задачи и подробные требования остаются у своих репозиториев.

Продуктовый ChangeSet связан с `releaseId`. Для его приёмки обязательны актуальное покрытие, принятые доски и полный набор совместных проверок. Готовность в UI, CLI и agent API вычисляется из этих данных. Отдельного изменяемого флага «фича готова» нет.

## Проверенные сценарии

`tests/product.test.ts` использует два настоящих Git-репозитория: приложение и библиотеку. В репозитории приложения описаны два интерфейса, чтобы проверить монорепозиторий без искусственного разделения хранилищ. Fixture проверяет:

- Полноту матрицы, устойчивые ссылки, отсутствие циклов компонентов, корректность путей, реальное существование тестовых gates и локальных историй.
- Отсутствие копий подробных задач в общем представлении и отказ CLI `--require-accepted` до приёмки.
- Отказ при неполном ChangeSet, непринятых досках, отсутствии guard и проваленной совместной проверке; полный набор gates даже при настройке affected.
- Успешный путь от локальных задач до продуктовой приёмки, требования режима operator и неизменность исторической записи.
- Устаревание результата после изменения карты, источника требований, доказательств задачи или принятого SHA, даже если Git tree не изменился.
- Повторную проверку изменённой карты через сохраняемый workflow ведущего агента.
- Перенос `releaseId` через независимые Git clones без переноса локального Verification или права объявить релиз принятым. Привязку уже принятого ChangeSet нельзя изменить через sync.

Для совместного gate используется настоящий исполняемый тест данных двух репозиториев с JUnit. Исполнители задач — fixture-адаптеры: проверяются оркестрация, Git и правила приёмки, а не качество генерации реальной модели или полнота тестов готового чата.

`e2e/product.spec.ts` добавляет проверку матрицы, выбора релиза, перехода к репозиторию, ошибки чтения без старого зелёного статуса и доступности на desktop/mobile. Основной сценарий подменяет только ответ продуктового API согласованным fixture; отдельный сценарий проверяет отсутствие карты на настоящем demo API. В текущей среде оба сценария заблокированы запуском браузера.

Ручная браузерная проверка выполнена на отдельном временном workspace с committed-картами и настоящим API. На ширине 390 px ширина документа также 390 px: широкая матрица прокручивается внутри своей области. Область доступна с клавиатуры; ArrowRight меняет позицию прокрутки. Непринятый релиз не показан готовым. После проверки временный сервер больше не принимает соединения; вкладка закрыта, размер окна браузера восстановлен.

## Исправление, найденное полным прогоном

Первый общий прогон дал 125/126 PASS: повторный синхронный Git-аудит каждой записи evidence под нагрузкой задерживал heartbeat Verification. Исправление не увеличивает время lease: полный аудит выполняется до его начала, а при закреплении manifest, завершении и приёмке сравниваются закреплённые SHA, файлы источников и состояние задач/доказательств. Повторные чтения кешируются только внутри одного вызова. Проверка Git ancestry группируется с возвратом к индивидуальным проверкам при расхождении.

Повторный полный прогон прошёл все 126 Node tests при прежних ограничениях lease.

## Границы доказательства

Карта не доказывает, что требования верно поняты, а тесты достаточны для пользователя: это проверяют ведущий агент и независимый reviewer. Технический `path` не меняет границы записи или планирование исполнителей. Продуктовый граф не заменяет граф зависимостей задач и репозиториев.

Актуальность проверяется консервативно: изменения всей общей карты, целого файла требований или задач в участвующем репозитории могут потребовать повторной проверки, даже если относятся к будущему релизу. Распределённой транзакции между Git-репозиториями нет; внешние писатели должны быть исключены во время приёмки.
