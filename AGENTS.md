# Разработка DevContour

Если поручено создать или развивать продукт по ТЗ, сначала определите workspace текущей сессии. Если пользователь ещё не указал его путь, задайте обязательный вопрос: «В какой папке вести workspace этого проекта? Укажите абсолютный путь». Дождитесь ответа до setup, создания задач и запуска сервера, даже при approvalMode=agent. Не выбирайте workspace по cwd, чужому диалогу или последнему запуску. Если путь уже указан в текущем поручении/контексте продолжаемой работы, используйте его без повторного вопроса. Это правило относится к разработке продукта; при изменении исходников самого DevContour спрашивать продуктовый workspace не нужно.

Далее действуйте как ведущий агент по [START.md](START.md). Сразу после выбора workspace запустите `start --workspace ...`: панель нужна до setup. Продуктовую часть, затем архитектуру и стек с C1/C2 обязательно утверждает пользователь в панели. Только после обоих решений начинайте setup и разработку. Технические планы и контракты далее согласует агент через независимое ревью; `approvalMode: "operator"` добавляет ручные технические согласования. Не перекладывайте настройку профилей, правил и проверок на оператора. Для каждой команды явно передавайте --workspace выбранного проекта (либо --data существующей конфигурации). Не записывайте продуктовый прогресс или настройку «текущий workspace» в общий каталог devcontour. Это отличается от задачи изменения исходников самого инструмента; для неё действуют правила ниже.

Сначала прочитайте README.md, docs/mvp.md и docs/architecture.md. Маршрут нового разработчика — docs/development.md, карта документации — docs/index.md; обоснования инвариантов — docs/decisions.md. Сохраняйте историю принятых ревизий, DAG-инварианты, fencing и привязку evidence к SHA.

Изменения workflow проверяйте тестами ядра и реальным Git fixture. UI — через браузер. `npm run check` включает build, unit/integration и Playwright. Не заменяйте недоступный обязательный инструмент молчаливым skip; фиксируйте ограничение и используйте доступный способ проверки поведения.

Тесты по умолчанию не вызывают модели и не читают provider credentials. Live-вызовы — отдельный явно выбранный запуск. Не выдавайте demo adapter за AI-реализацию.

Командная память и обмен задачами описаны в docs/team-sync.md. Изменение sync проверяйте на независимых Git clones: UUID, three-way merge, rollback при конфликте/невалидном DAG, локальность baseline, receipt и доступность result SHA. Не переносите leases и исполняемую конфигурацию в Git. Peer receipt обозначает принятую историю доверенного Git-репозитория, а не локальный запуск проверок.

Канонические визуальные токены — src/web/tokens.css. Переиспользуемые правила целевого проекта — templates/project; не навязывайте их существующему репозиторию без проверки его соглашений.
