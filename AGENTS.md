# Разработка DevContour

Если поручено создать или развивать продукт по ТЗ, сначала определите режим размещения и абсолютный путь workspace. Если выбор ещё не передан пользователем и не сохранён в `devcontour.workspace.json`/существующей конфигурации, спросите: «Где хранить оркестрацию: внутри репозитория проекта или в отдельном workspace? Укажите режим и абсолютный путь». Объясните варианты: `embedded` — корень единственного Git-репозитория или монорепозитория; `separate` — отдельная папка для координации самостоятельных репозиториев. Не выбирайте режим за пользователя. Уже известные сведения повторно не спрашивайте. Дождитесь недостающего выбора до setup, задач и запуска сервера, даже при `approvalMode: agent`. Не выводите путь из cwd или чужой сессии. При изменении исходников самого DevContour продуктовый workspace и режим спрашивать не нужно.

Далее действуйте как ведущий агент по [START.md](START.md). Сразу после выбора workspace запустите `start --workspace-mode embedded|separate --workspace ...` с выбранным значением; для сохранённого режима флаг необязателен: панель нужна до setup. Продуктовую часть, затем архитектуру и стек с C1/C2, затем референсы и — при применимом интерфейсе — концепт и дизайн-систему обязательно утверждает пользователь в панели. Только после всей цепочки начинайте setup и разработку: `setup` проверяет её сам и откажет раньше. Технические планы и контракты далее согласует агент через независимое ревью; `approvalMode: "operator"` добавляет ручные технические согласования. Не перекладывайте настройку профилей, правил и проверок на оператора. Для каждой команды явно передавайте --workspace выбранного проекта (либо --data существующей конфигурации). Не записывайте продуктовый прогресс или настройку «текущий workspace» в общий каталог devcontour. Это отличается от задачи изменения исходников самого инструмента; для неё действуют правила ниже.

Сначала прочитайте README.md, docs/mvp.md и docs/architecture.md. Маршрут нового разработчика — docs/development.md, карта документации — docs/index.md; обоснования инвариантов — docs/decisions.md. Сохраняйте историю принятых ревизий, DAG-инварианты, fencing и привязку evidence к SHA.

Изменения workflow проверяйте тестами ядра и реальным Git fixture. UI — через браузер. `npm run check` включает build, unit/integration и Playwright. Не заменяйте недоступный обязательный инструмент молчаливым skip; фиксируйте ограничение и используйте доступный способ проверки поведения.

Тесты по умолчанию не вызывают модели и не читают provider credentials. Live-вызовы — отдельный явно выбранный запуск. Не выдавайте demo adapter за AI-реализацию.

Командная память и обмен задачами описаны в docs/team-sync.md. Изменение sync проверяйте на независимых Git clones: UUID, three-way merge, rollback при конфликте/невалидном DAG, локальность baseline, receipt и доступность result SHA. Не переносите leases и исполняемую конфигурацию в Git. Peer receipt обозначает принятую историю доверенного Git-репозитория, а не локальный запуск проверок.

Канонические визуальные токены — src/web/tokens.css. Переиспользуемые правила целевого проекта — templates/project; не навязывайте их существующему репозиторию без проверки его соглашений.

## Приватные оценки и анализы — правило для всех агентов

Правило применяется к ведущему агенту, исполнителям, исследователям и ревьюерам независимо от используемого AI-клиента.

- Любые оценки, assessments, сравнения и анализы, содержащие ссылки на аналогичные или сторонние проекты либо сведения о них, сохраняйте только в игнорируемом `.private/`. Публичность исходного репозитория или статьи не делает такой анализ публичным материалом DevContour.
- В том же каталоге храните результаты аудитов и ревью, логи, артефакты проверок, скриншоты и сведения о реальных пилотных проектах. Это относится и к тексту документов, и к именам файлов, изображениям, путям, URL и идентификаторам.
- В публичном Git остаются исходники, руководства, roadmap и todo. Из локального анализа переносите туда только обезличенные задачи, обоснования и критерии приёмки, без сравнений с конкретными проектами и без ссылок на приватные материалы.
- Не добавляйте `.private/` и другие игнорируемые материалы через `git add -f`, не включайте их в коммиты, PR, npm-архивы или иные распространяемые артефакты. Сообщения коммитов и описания PR также публичны: описывайте в них изменения поведения, без данных пилотов и результатов приватных исследований. Перед подготовкой коммита проверяйте staged diff и сообщение, перед передачей пакета — его состав.
- Если материал уже отслеживается, сначала сохраните его локально в `.private/`, уберите из индекса Git и удалите публичные ссылки. Один `.gitignore` не исключает отслеживаемый файл и не очищает прежние коммиты. Для публичных примеров используйте вымышленные названия и пути.
